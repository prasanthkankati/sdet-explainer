11.2 Guidelines, Worst Practices & Exceptions

Official Selenium test practices: atomic tests, test data seeding via API, anti-patterns to avoid (CAPTCHAs, file download UI clicks, link spidering), and the WebDriverException hierarchy.

The final chapter of the official Selenium documentation codifies engineering best practices, anti-patterns ('Worst Practices') that cause flaky test suites, and the complete org.openqa.selenium.WebDriverException hierarchy. Writing deterministic, fast UI automation requires keeping tests small and atomic, seeding state via APIs or cookies instead of repeating UI steps, and knowing which tasks should never be automated through a browser.

Before you start

Prerequisite: 11.1 Page Object Models & Domain-Specific Language

Where it fits

These architectural guidelines and exception handling rules govern how your entire test suite is designed, reviewed, and maintained in production CI/CD.

Key points

  1. Keep Tests Atomic & Independent: Each @Test method should verify one cohesive behavior and never depend on the execution order of another test (avoid dependsOnMethods).
  2. Seed State via API / Cookies: Do not navigate through 5 UI screens just to set up test data; create the user/cart via a fast REST API call, inject the auth cookie, and open the target page directly.
  3. Official Selenium Worst Practices (What NOT to automate in Selenium): Never automate CAPTCHAs (disable them in test environments), never spider all links via UI clicks, never run performance/load tests via WebDriver, and avoid testing Gmail/third-party email UIs.
  4. All Selenium exceptions inherit from the unchecked runtime exception org.openqa.selenium.WebDriverException.
  5. Understanding the exact root cause and fix for the top 8 exceptions (NoSuchElementException, StaleElementReferenceException, TimeoutException, ElementClickInterceptedException, ElementNotInteractableException, NoAlertPresentException, NoSuchWindowException, SessionNotCreatedException) is essential for every SDET interview.

How it works

  1. Design each test around the Arrange-Act-Assert pattern: Arrange state via API/cookies, Act on the specific UI page under test via a Page Object, and Assert the outcome.
  2. In test environments, work with developers to disable CAPTCHAs or configure a test bypass token rather than trying to break security gates.
  3. When a test fails in CI, inspect the thrown WebDriverException subclass, captured screenshot, and BiDi console/network logs to pinpoint whether the failure is an application defect or a synchronization gap.

Handling StaleElementReferenceException cleanly with ExpectedConditions.refreshed():

package dev.selenium.practices; // Declares package

import org.openqa.selenium.By; // Imports By locator class
import org.openqa.selenium.StaleElementReferenceException; // Imports StaleElementReferenceException
import org.openqa.selenium.WebDriver; // Imports WebDriver interface
import org.openqa.selenium.WebElement; // Imports WebElement interface
import org.openqa.selenium.chrome.ChromeDriver; // Imports ChromeDriver
import org.openqa.selenium.support.ui.ExpectedConditions; // Imports ExpectedConditions
import org.openqa.selenium.support.ui.WebDriverWait; // Imports WebDriverWait
import java.time.Duration; // Imports Duration class

public class ExceptionResilienceExample { // Declares class
    public static void main(String[] args) { // Main method
        WebDriver driver = new ChromeDriver(); // Starts Chrome session
        try { // Guarded block
            driver.get("https://www.selenium.dev/selenium/web/dynamic.html"); // Loads dynamic test page
            WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(10)); // Creates 10s wait
            By revealButton = By.id("reveal"); // Stores locator as By (not stale-prone WebElement)

            // ExpectedConditions.refreshed() catches StaleElementReferenceException and re-locates element
            WebElement btn = wait.until( // Polls until element is fresh and clickable
                ExpectedConditions.refreshed(ExpectedConditions.elementToBeClickable(revealButton)) // Wraps condition
            ); // Returns fresh WebElement
            btn.click(); // Clicks safely
        } catch (StaleElementReferenceException e) { // Explicit recovery example if needed
            driver.findElement(By.id("reveal")).click(); // Re-locates fresh DOM reference and clicks
        } finally { // Teardown block
            driver.quit(); // Closes browser cleanly
        } // Ends finally
    } // Ends main
} // Ends class

Common mistakes

  1. Chaining 10 @Test methods together with TestNG dependsOnMethods so Test 2 relies on the browser state left behind by Test 1; if Test 1 fails, all 9 remaining tests are skipped and cannot run in parallel.
  2. Automating third-party email providers (like Gmail or Outlook web UI) in Selenium to read a 2FA OTP code; fix by querying a test mail API (such as Mailosaur, MailHog, or internal DB/API).
  3. Catching Exception in @Test methods and printing e.printStackTrace() without re-throwing, which marks broken tests as PASSED (false greens) in CI/CD!

Interview questions

Basics

Are Selenium exceptions (like NoSuchElementException and TimeoutException) checked or unchecked exceptions in Java?
All Selenium exceptions inherit from org.openqa.selenium.WebDriverException, which extends java.lang.RuntimeException. Therefore, all Selenium exceptions are unchecked runtime exceptions.

What is StaleElementReferenceException and why does it happen?
StaleElementReferenceException occurs when you locate a WebElement, the web page subsequently refreshes or re-renders that part of the DOM (destroying the original HTML node), and you then try to call a method like click() or getText() on the old WebElement reference.

Name four things the official Selenium documentation lists under 'Worst Practices' (things you should NOT automate with Selenium).
The official Worst Practices are: (1) Automating CAPTCHAs, (2) Automating file downloads by clicking through OS native save dialogs instead of verifying via HTTP client, (3) Spidering/crawling every link on a site for 404s via browser clicks, and (4) Running performance/load tests via WebDriver.

How it works

What is the class hierarchy of NoSuchElementException in Selenium?
java.lang.Object -> Throwable -> Exception -> RuntimeException -> WebDriverException -> NotFoundException -> NoSuchElementException.

How does ExpectedConditions.refreshed() prevent StaleElementReferenceException?
ExpectedConditions.refreshed(condition) wraps an inner condition (such as elementToBeClickable(By)). If the DOM re-renders mid-check and throws StaleElementReferenceException, refreshed() catches it and forces the inner condition to re-find the element on the next poll.

Why should you avoid checking for broken links across a 500-page website by clicking every <a> tag in Selenium?
Clicking every link in a real browser requires full page rendering, CSS layout, and JS execution, taking hours. Instead, use Selenium findElements(By.tagName("a")) to collect the href URLs and send fast parallel HTTP HEAD/GET requests using Java's HttpClient.

Real situations

How should an automation team handle CAPTCHAs or 2FA in staging environments?
CAPTCHAs exist specifically to block automation. In test/staging environments, developers should either disable CAPTCHA via a feature flag, whitelist the CI runner IP, or provide a deterministic test-environment bypass token/API.

You are testing the Checkout page. Why shouldn't your Checkout test log in via the UI, search for a product via the UI, and click Add to Cart via the UI every time?
Repeating Login, Search, and Add-to-Cart UI flows inside 30 different Checkout tests makes the suite slow and causes all 30 Checkout tests to fail if the Search bar breaks. Instead, seed the user session and shopping cart via a 50ms backend API call, inject the session cookie, and navigate directly to /checkout.

Why is catching Exception inside a @Test method and logging it without throwing an AssertionError one of the worst bugs in QA?
TestNG and JUnit only mark a @Test as FAILED if an unhandled AssertionError or Exception escapes the @Test method. Catching and swallowing an exception causes the test runner to report a 100% green PASS while the application is broken.

Troubleshooting

How do you systematically eliminate StaleElementReferenceException in a React or Angular test suite?
First, store private final By locators in Page Objects rather than caching WebElement references. Second, use ExpectedConditions.refreshed(ExpectedConditions.elementToBeClickable(by)) in your BasePage click/type helpers.

What is the difference between ElementNotInteractableException and ElementClickInterceptedException?
ElementNotInteractableException means the target element itself is hidden (display:none, visibility:hidden, or off-screen). ElementClickInterceptedException means the target element IS visible, but another element (such as a modal backdrop or spinner) is sitting on top of its click coordinates.

Why do tests that use TestNG dependsOnMethods fail to scale in parallel CI execution?
dependsOnMethods forces sequential ordering between test methods, preventing TestNG from scheduling them across parallel worker threads and causing cascading skips whenever an upstream test fails.

Design choices

Why did Selenium design WebDriverException as an unchecked RuntimeException instead of a checked Exception?
If WebDriverException were checked, every single Page Object method and @Test method would be cluttered with throws WebDriverException declarations or boilerplate try-catch blocks.

What is the Test Pyramid and where do Selenium WebDriver tests sit within it?
The Test Pyramid places fast unit tests at the wide base, API/integration tests in the middle, and end-to-end UI tests (Selenium) at the top. Keeping Selenium focused on critical user journeys while pushing combinatorial logic down to API/unit tests keeps CI fast and reliable.

What are the characteristics of a 'Gold Standard' Selenium test?
It is atomic (tests one thing), autonomous (creates its own isolated data via API/cookies), deterministic (uses explicit waits with zero Thread.sleep), encapsulated (uses POM with private By locators), and cleans up its session in @AfterMethod.

Quick answers

  1. What is the base class of all Selenium exceptions? org.openqa.selenium.WebDriverException (an unchecked RuntimeException).
  2. How do you fix StaleElementReferenceException? Re-locate the element via its By locator or use ExpectedConditions.refreshed().
  3. Should you automate CAPTCHAs with Selenium? No, disable CAPTCHAs or use a test bypass token in test/staging environments.
  4. How should you set up precondition state (login/cart) for a Checkout test? Seed state via fast backend API calls and inject session cookies.
  5. What happens if a @Test catches an exception and does not re-throw it? The test falsely reports as PASSED (a false green).
