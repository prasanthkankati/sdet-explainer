10.1 Grid Execution Modes & Architecture

Scaling parallel cross-browser execution across Standalone, Hub & Node, and Fully Distributed Selenium Grid 4 architectures.

Selenium Grid 4 allows you to execute WebDriver tests in parallel across multiple machines, operating systems, and browser versions from a single central entry point. Re-architected from scratch in Selenium 4 around six decoupled components (Router, Distributor, Session Map, New Session Queue, Event Bus, and Node), Grid can run in Standalone mode, classic Hub & Node mode, or a cloud-native Fully Distributed mode.

Before you start

Prerequisite: 9.1 Automated Driver & Browser Management

Where it fits

Selenium Grid is the execution infrastructure layer in CI/CD pipelines (typically deployed via Docker Compose or Kubernetes) that receives RemoteWebDriver requests.

Key points

  1. Grid 4 consists of six internal components: Router,Session Queue, Distributor, Session Map, Event Bus, and Nodes.
  2. Mode 1 (Standalone): Runs all six components and browser drivers inside a single JVM process via java -jar selenium-server.jar standalone.
  3. Mode 2 (Hub & Node): Combines Router, Distributor, Session Map, Queue, and Event Bus into one Hub machine, while multiple Node machines register over TCP/Event Bus.
  4. Mode 3 (Distributed): Runs each of the six components as an independent microservice (ideal for large Kubernetes clusters).
  5. Grid 4 exposes a built-in React UI dashboard at http://localhost:4444/ui and a GraphQL endpoint at http://localhost:4444/graphql for live observability.

How it works

  1. The Java test calls new RemoteWebDriver(new URL("http://grid:4444"), chromeOptions), sending a POST /session request to the Grid Router.
  2. Because the request has no SessionId yet, the Router places it into the New Session Queue.
  3. The Distributor pulls the request from the Queue, finds a registered Node with an available Chrome slot, starts the session on that Node, and writes the SessionId -> Node URI mapping into the Session Map.
  4. For all subsequent commands (get, findElement, click), the Router looks up the SessionId in the Session Map and forwards the request directly to that Node.

CLI commands to launch Selenium Grid 4 and Java RemoteWebDriver connection:

package dev.selenium.grid; // Declares package

// CLI 1 (Standalone): java -jar selenium-server-4.26.0.jar standalone
// CLI 2 (Hub & Node): java -jar selenium-server-4.26.0.jar hub
//                     java -jar selenium-server-4.26.0.jar node --hub http://hub-ip:4444

import org.openqa.selenium.Platform; // Imports Platform enum
import org.openqa.selenium.WebDriver; // Imports WebDriver interface
import org.openqa.selenium.chrome.ChromeOptions; // Imports ChromeOptions
import org.openqa.selenium.remote.RemoteWebDriver; // Imports RemoteWebDriver
import java.net.URI; // Imports URI class

public class GridExecutionExample { // Declares class
    public static void main(String[] args) throws Exception { // Main method
        ChromeOptions options = new ChromeOptions(); // Creates ChromeOptions for Grid negotiation
        options.setPlatformName(Platform.LINUX.name()); // Requests a Linux container Node
        options.setBrowserVersion("stable"); // Requests stable Chrome version

        WebDriver driver = new RemoteWebDriver( // Connects to Selenium Grid Router
            URI.create("http://localhost:4444").toURL(), options // Passes Router URL and capabilities
        ); // Session assigned by Distributor and recorded in Session Map
        try { // Guarded block
            driver.get("https://www.selenium.dev/documentation/grid/"); // Executes on remote Node
            System.out.println("Grid Page Title: " + driver.getTitle()); // Prints page title
        } finally { // Teardown block
            driver.quit(); // Frees slot on Node and removes SessionId from Session Map
        } // Ends finally
    } // Ends main
} // Ends class

Common mistakes

  1. Running parallel TestNG tests against Selenium Grid while sharing a single non-thread-safe WebDriver variable across threads; fix by isolating each thread's RemoteWebDriver in ThreadLocal<WebDriver>.
  2. Omitting driver.quit() when a test fails, which leaves the Grid Node slot occupied until the 300-second session timeout expires, starving queued tests.
  3. Setting TestNG thread-count=50 when the Selenium Grid only has 5 total browser slots, causing tests at the back of the New Session Queue to time out if execution takes longer than --session-request-timeout.

Terms to know

Interview questions

Basics

What are the three deployment modes of Selenium Grid 4?
The three modes are: (1) Standalone (all components and browsers run in a single process on one machine), (2) Hub and Node (one central Hub coordinates multiple remote Node machines), and (3) Distributed (Router, Queue, Distributor, Session Map, Event Bus, and Nodes run as separate microservices).

What are the six internal components of Selenium Grid 4?
The six components are Router, New Session Queue, Distributor, Session Map, Event Bus, and Node.

What URL do you open in a browser to view the Selenium Grid 4 live console dashboard?
Open http://localhost:4444/ui (or http://grid-host:4444/ui), which displays registered nodes, available browser stereoypes, active sessions, and live VNC previews.

How it works

How does the Grid 4 Router handle a new session request differently from an existing session command?
When a request arrives without a SessionId (POST /session), the Router sends it to the New Session Queue so the Distributor can allocate a Node. When a request arrives with an existing SessionId (like POST /session/{id}/element), the Router queries the Session Map and forwards the command straight to the hosting Node, bypassing the Distributor.

How do Hub and Nodes communicate in Grid 4 compared to Grid 3?
Grid 3 relied on chatty HTTP polling between Hub and Nodes. Grid 4 uses an Event Bus (powered by ZeroMQ on ports 4442 and 4443) for asynchronous, event-driven Node registration and health heartbeats.

What is Dynamic Grid mode in Docker?
In Dynamic Grid mode, instead of keeping idle browser containers running 24/7, the Grid spawns a brand-new, clean browser Docker container on the fly when a session request arrives, records video if configured, and destroys the container the instant driver.quit() is called.

Real situations

How do you watch a live browser screen while a test is running inside a Selenium Grid Docker container?
Official Selenium Docker images (selenium/node-chrome) include a built-in VNC and noVNC server. Open http://localhost:4444/ui, click the Sessions tab, and click the camera icon (default password: secret) to watch the live browser inside your web browser.

How do you query Selenium Grid 4 metrics (like queued session count or active slots) programmatically for CI auto-scaling?
Send a POST query to the Grid 4 GraphQL endpoint at http://localhost:4444/graphql or check the /status readiness endpoint.

When should a team use Standalone mode vs Hub & Node mode?
Use Standalone mode on a single developer workstation or a single beefy CI agent using docker run -d -p 4444:4444 --shm-size="2g" selenium/standalone-chrome. Use Hub & Node or Kubernetes KEDA scaling when running 10+ concurrent browsers across multiple machines.

Troubleshooting

Why did a remote Node fail to register with the Grid Hub even though port 4444 is open?
In Grid 4 Hub & Node mode, Nodes communicate with the Hub's Event Bus over TCP ports 4442 (publish) and 4443 (subscribe) in addition to HTTP port 4444. Ensure firewall and Docker security groups open ports 4442, 4443, and 4444.

Why do Chrome sessions crash inside Docker Grid containers when --shm-size="2g" is omitted?
Docker defaults /dev/shm to 64MB, which is too small for modern Chrome rendering. Either start the Docker container with --shm-size="2g" or pass --disable-dev-shm-usage in ChromeOptions.

What causes SessionNotCreatedException: Could not start a new session. New session request timed out?
All Grid Nodes were busy running other tests (or no Node matched your requested browser/platform capabilities), so the request sat in the New Session Queue until --session-request-timeout (default 300s) expired.

Design choices

Why did Selenium Grid 4 split the monolithic Hub into Router, Queue, Distributor, and Session Map?
In Grid 3, a single Hub lock handled both new session matching and active command routing, creating a bottleneck under heavy parallel load. Splitting them allows the Router and Session Map to route active commands with zero contention while the Distributor assigns new sessions.

Why is OpenTelemetry integrated into Selenium Grid 4?
Grid 4 instruments every component with OpenTelemetry spans, allowing DevOps teams to export distributed traces to Jaeger or Zipkin and pinpoint whether latency occurred in the Queue, Distributor, or Node.

How many concurrent sessions does a Grid Node allow by default?
By default, a Node limits max-sessions to the number of available CPU processors on the host (with 1 session per Chrome/Firefox driver slot unless overridden via --max-sessions).

Quick answers

  1. What are the 3 Grid 4 execution modes? Standalone, Hub & Node, and Distributed.
  2. Which Grid 4 component maps SessionId to Node URI? The Session Map.
  3. Which ports does the Grid 4 Event Bus use? Ports 4442 and 4443 (plus 4444 for the HTTP Router).
  4. What is the URL for the Grid 4 web dashboard? http://localhost:4444/ui.
  5. Why pass --shm-size="2g" to Selenium Docker containers? Prevents Chrome crashes caused by Docker's default 64MB /dev/shm limit.
