4.5 Inheritance (IS-A) vs Composition (HAS-A)

Single and multilevel inheritance with extends, why Java forbids multiple class inheritance (Diamond Problem), and why frameworks favor HAS-A Composition over bloated BaseTest hierarchies.

Inheritance (extends) establishes an IS-A hierarchy where a subclass inherits fields and methods from one parent superclass to reuse common code and support polymorphism. Composition (HAS-A) embeds helper objects as fields inside a class instead of inheriting, keeping automation frameworks modular and avoiding fragile deep inheritance trees.

Before you start

Prerequisite: 4.4 Core Keywords: static, final, this, super & instanceof

Where it fits

Selenium tests commonly extend a lightweight BaseTest for lifecycle hooks (IS-A), while Page Objects compose WebDriver, WebDriverWait, and shared HeaderComponent widgets as private fields (HAS-A).

Key points

  1. Every Java class implicitly extends java.lang.Object if no explicit extends clause is declared, giving every object equals(), hashCode(), toString(), and getClass().
  2. Java supports Single (B extends A), Multilevel (C extends B extends A), and Hierarchical (B extends A and C extends A) class inheritance.
  3. Java explicitly forbids multiple class inheritance (class C extends A, B) to prevent the Diamond Problem—ambiguity over which parent's conflicting implementation or state field to inherit.
  4. A class CAN implement multiple interfaces (implements WebDriver, TakesScreenshot, JavascriptExecutor); if two interfaces provide conflicting Java 8 default methods, the implementing class must explicitly override the method to resolve ambiguity.
  5. IS-A (Inheritance) couples child classes tightly to parent changes at compile time, whereas HAS-A (Composition) connects independent components via fields and interfaces.
  6. Favoring Composition over Inheritance avoids creating massive 1,500-line BaseTest or BasePage god-classes carrying unrelated dependencies into simple tests.

How it works

  1. Model true specialization hierarchies with shallow inheritance—for instance, Selenium's ChromeDriver extends ChromiumDriver extends RemoteWebDriver.
  2. Create small focused component classes like HeaderComponent that encapsulate shared navigation bar locators and accept WebDriver in their constructor.
  3. Embed private final HeaderComponent header; inside HomePage and CartPage instead of forcing every page to inherit header methods via a giant BasePage.
  4. Keep BaseTest strictly scoped to driver setup and teardown so tests stay independent and composable.

Combining shallow BasePage inheritance with HAS-A Page Component composition:

package dev.java.oop; // Declares package

import org.openqa.selenium.By; // Imports By locator
import org.openqa.selenium.WebDriver; // Imports WebDriver interface

class HeaderComponent { // Reusable UI widget modeled via Composition
    private final WebDriver driver; // HAS-A WebDriver reference
    private final By cartBadge = By.className("cart-count"); // Encapsulated navbar locator

    HeaderComponent(WebDriver driver) { // Receives active driver via constructor
        this.driver = driver; // Stores driver privately
    } // Ends constructor

    public int getCartCount() { // Exposes widget action to any page composing it
        return Integer.parseInt(driver.findElement(cartBadge).getText().trim()); // Parses cart count
    } // Ends getCartCount
} // Ends HeaderComponent

class StoreBasePage { // Shallow base class holding common page driver
    protected final WebDriver driver; // Protected driver shared by page subclasses

    StoreBasePage(WebDriver driver) { // Base constructor
        this.driver = driver; // Assigns driver reference
    } // Ends constructor
} // Ends StoreBasePage

public class ProductCatalogPage extends StoreBasePage { // IS-A StoreBasePage
    private final HeaderComponent header; // HAS-A HeaderComponent via composition

    public ProductCatalogPage(WebDriver driver) { // Child constructor
        super(driver); // Initializes StoreBasePage parent first
        this.header = new HeaderComponent(driver); // Composes reusable header widget
    } // Ends constructor

    public HeaderComponent header() { // Exposes composed widget cleanly
        return header; // Returns HeaderComponent instance
    } // Ends header accessor
} // Ends ProductCatalogPage

Common mistakes

  1. Putting database utilities, Excel readers, Slack notifiers, and login steps all inside one bloated BaseTest parent class so every simple UI smoke test inherits 40 unrelated methods.
  2. Misusing inheritance just to reuse two utility methods (class LoginPage extends ExcelUtils); a LoginPage is NOT an Excel utility—inject or call a helper via composition or static utility instead.
  3. Forgetting that private fields and methods on a parent class are NOT directly visible inside a child subclass (though they still exist inside the child's Heap object and are accessed via parent getters/methods).
  4. Building deep 5-level inheritance chains (A -> B -> C -> D -> E) where debugging a single broken test requires tracing hooks across five files.

Interview questions

Basics

What are the types of inheritance supported for classes in Java?
Java supports Single inheritance (B extends A), Multilevel inheritance (C extends B where B extends A), and Hierarchical inheritance (both B and C extend A). Multiple inheritance of classes (C extends A, B) and hybrid combinations involving multiple parent classes are forbidden at compile time.

What is the difference between IS-A (Inheritance) and HAS-A (Composition)?
IS-A expresses specialization using extends—for example, ChromeDriver IS-A RemoteWebDriver. HAS-A expresses ownership or delegation through instance fields—for example, LoginPage HAS-A WebDriver and HeaderComponent. Inheritance links classes statically at compile time, whereas Composition lets classes assemble modular pieces flexibly.

What is the implicit root parent class of every Java class?
Every class that does not explicitly write extends SomeParent implicitly extends java.lang.Object. Because of this single root hierarchy, every Java object supports toString(), equals(), hashCode(), and getClass().

How it works

Explain the Diamond Problem and why Java forbids multiple class inheritance.
Suppose classes B and C both extend A and override A.connect() differently, and class D tried to extend both B and C. When D invokes connect() without overriding it, the compiler cannot decide whether to run B.connect() or C.connect(), and duplicate state fields from A create memory ambiguity. Forbidding multiple class inheritance eliminates this ambiguity at the language level.

How does Java resolve the Diamond Problem when a class implements two interfaces that share the same Java 8 default method signature?
Because interfaces carry no mutable instance state fields, Java allows implementing multiple interfaces (implements InterfaceA, InterfaceB). If both interfaces supply a default method with the identical signature, compilation fails unless the implementing class overrides that method explicitly—choosing one parent default via InterfaceA.super.methodName() or writing a fresh implementation.

Does a child object inherit the parent's private fields in memory?
When a child object is created on the Heap, space is allocated for ALL instance fields declared in both the parent and child classes, including the parent's private fields. However, Java access rules forbid the child class from referencing those private fields by name directly—the child interacts with them strictly through the parent's protected or public constructors and methods.

Real situations

In a Selenium framework for https://qkart-qa-web.labs.crio.do/, how should you share the top search/cart header across HomePage, CheckoutPage, and ProfilePage?
Use Composition (the Page Component pattern): build a dedicated HeaderComponent class encapsulating the search bar, login button, and cart badge, and store a private final HeaderComponent header inside each Page Object that renders that header. Avoid putting header locators on BasePage, because pages like a standalone CheckoutFrame or ErrorPage might not render a header at all.

Why is class CheckoutTest extends LoginTest an anti-pattern in TestNG frameworks?
Extending one concrete test class from another couples test setup, annotations, and state across unrelated suites, breaking atomic test independence and preventing safe parallel test execution. Both CheckoutTest and LoginTest should extend a minimal BaseTest (or use TestNG listeners/composition) and seed login state via cookies or APIs.

How does Selenium itself combine Inheritance and Interfaces in ChromeDriver?
ChromeDriver extends ChromiumDriver which extends RemoteWebDriver (IS-A class inheritance sharing W3C command execution code), while RemoteWebDriver implements multiple capability interfaces (WebDriver, TakesScreenshot, JavascriptExecutor) and composes a CommandExecutor (HAS-A).

Troubleshooting

Why does a massive BaseTest god-class slow down and break CI maintenance?
When BaseTest contains Excel helpers, API clients, UI login steps, DB clients, and 15 @BeforeMethod checks, every test suite loads unnecessary state and a minor refactor to one helper triggers recompilation and regression risks across hundreds of unrelated tests. Decompose utilities into small composable classes injected only where needed.

Why does class PageA extends BasePage, RetryHelper fail to compile?
Java permits at most one class after extends. Convert shared helper contracts into interfaces or compose a private final RetryHelper retryHelper; instance field inside PageA.

Why did a parent class variable inside a child test return null when both classes declared WebDriver driver;?
Declaring a field with the same name in a subclass does NOT override the parent's field; it hides (shadows) it as a second distinct Heap slot. Methods defined in the parent still read the parent slot while child methods read the uninitialized child slot. Remove the duplicate field declaration in the subclass.

Design choices

Why does Effective Java advise 'Favor composition over inheritance'?
Inheritance exposes parent implementation details to subclasses and locks the design permanently at compile time; changing a non-private parent method can break child overrides unexpectedly. Composition interacts strictly through stable public contracts and lets you swap implementations (for example, swapping a mock config reader or headless vs grid driver strategy) cleanly.

When IS inheritance genuinely the right choice in a test automation framework?
Use inheritance strictly when a genuine IS-A relationship holds and the base class is explicitly designed for extension—for example, BasePage holding shared WebDriverWait click/type wrappers for Page Objects, or BaseTest holding standardized TestNG @BeforeMethod/@AfterMethod driver lifecycle setup.

Why should classes not designed for subclassing be marked final or avoid protected hooks?
Keeping classes non-inheritable by default prevents external tests from extending utility or concrete Page Object classes in unintended ways that violate internal invariants.

Quick answers

  1. How many classes can one Java class extend directly? At most 1 class.
  2. How many interfaces can one Java class implement? Unlimited (separated by commas).
  3. What is the root superclass of every Java class? java.lang.Object.
  4. Why does Java forbid multiple class inheritance? To eliminate the Diamond Problem ambiguity over inherited implementations and state.
  5. Which design relationship does Composition represent? HAS-A (holding helper objects as fields).
  6. How should shared UI widgets like Headers and Footers be modeled in Selenium? Via Composition using Page Component classes rather than bloating BasePage.
