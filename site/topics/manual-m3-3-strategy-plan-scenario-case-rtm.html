3.3 Test Strategy vs Test Plan, Test Scenario vs Test Case & RTM

1. The Base: What Are Test Artifacts and How Do They Connect from Top to Bottom?

Test Artifacts are the formal engineering documents and work products created across the STLC—flowing top-down from an organization-wide Test Strategy, to a project-specific Test Plan, down to high-level Test Scenarios, granular step-by-step Test Cases, and connected via the Requirement Traceability Matrix (RTM).

The Problem They Solve: Without a clear hierarchy of test documents, every project team reinvents quality standards from scratch, new QA engineers don't know which browsers or environments are in scope, and test execution relies on memory instead of reproducible steps. Organizing artifacts into a 4-level top-down hierarchy ensures consistency from the VP of Engineering down to individual `@Test` methods.

3. Pair 1 Explained: Test Strategy vs Test Plan (IEEE 829 Standard)

  • 1. Test Strategy: A high-level, static organizational document (owned by the QA Director / Principal SDET) that defines the company's overarching testing philosophy: which test levels exist, standard automation stack (`Java 21 + Selenium 4 + TestNG + RestAssured`), coding standards, defect severity definitions, and CI/CD merge gates.
  • 2. Test Plan: A dynamic, project-specific execution blueprint (owned by the QA Lead / SDET Lead) created during STLC Phase 2 that specifies how a particular release or sprint will be tested.
    • Exact Sections (Properties) of an IEEE 829 Test Plan:
      1. Test Plan Identifier & Objective
      2. Scope: Features to be Tested (In-Scope) vs Not to be Tested (Out-of-Scope)
      3. Test Approach / Types (Smoke, Sanity, Regression, API, Performance)
      4. Entry Criteria, Suspension Criteria & Exit Criteria
      5. Test Deliverables (RTM, Test Cases, ExtentReports, Summary Report)
      6. Test Environment & Tool Requirements (URLs, Browsers, Test Data)
      7. Schedule, Effort Estimation & Staffing Responsibilities
      8. Risks, Assumptions & Contingency/Mitigation Plan

4. Pair 2 Explained: Test Scenario vs Test Case (And Exact Test Case Fields)

  • 1. Test Scenario ("WHAT to test"): A high-level, single-sentence description of an end-to-end user functionality or business flow to be validated (e.g., TS_Checkout_01: Verify user can complete purchase using a Credit Card).
  • 2. Test Case ("HOW to test"): A detailed, atomic set of preconditions, exact inputs, step-by-step actions, and expected outcomes written to verify one specific positive or negative path of a Test Scenario.
  • The 10 Mandatory Fields (Properties) of a Standard Test Case:
    1. Test Case ID: `TC_LOGIN_001`
    2. Requirement / RTM ID & Scenario ID: `REQ_101 / TS_LOGIN_01`
    3. Test Case Title / Description: Verify login with valid email and valid password
    4. Priority / Type: `P0 (Smoke / Positive)`
    5. Preconditions: User account `qa@shop.com` is registered and active; user is on `/login` page
    6. Test Steps: 1. Enter email, 2. Enter password, 3. Click Login button
    7. Test Data: `Email = qa@shop.com`, `Password = Pass#123`
    8. Expected Result: User is redirected to `/dashboard` and greeting `"Welcome, QA"` is displayed
    9. Actual Result & Status: Filled during Phase 5 Execution (`PASS` / `FAIL` / `BLOCKED`)
    10. Automation Status & Defect ID: `Automated (LoginTest#verifyValidLogin)` / `Defect ID` if failed

5. Real SDET Code Trace: Mapping Test Scenario, Test Case ID & RTM ID in TestNG

import org.testng.Assert;
import org.testng.annotations.Test;

// TEST SCENARIO (TS_LOGIN_01): Verify User Login Functionality
public class LoginScenarioTest extends BaseTest {

    // TEST CASE 1 (TC_LOGIN_001 - Positive) -> Mapped to RTM REQ_101
    @Test(priority = 1, groups = {"smoke", "regression"},
          description = "RTM:REQ_101 | TC_LOGIN_001: Verify login with valid credentials")
    public void verifyValidLogin() {
        LoginPage loginPage = new LoginPage(getDriver());
        DashboardPage dash = loginPage.loginAs("qa@shop.com", "Pass#123");
        Assert.assertEquals(dash.getHeadingText(), "Welcome, QA");
    }

    // TEST CASE 2 (TC_LOGIN_002 - Negative) -> Mapped to RTM REQ_101
    @Test(priority = 2, groups = {"regression"},
          description = "RTM:REQ_101 | TC_LOGIN_002: Verify error banner on invalid password")
    public void verifyInvalidPasswordError() {
        LoginPage loginPage = new LoginPage(getDriver());
        loginPage.loginAs("qa@shop.com", "WrongPass!");
        Assert.assertEquals(loginPage.getErrorBanner(), "ERR_INVALID_CREDENTIALS");
    }
}

Interview Answer: "Test Strategy vs Test Plan: Test Strategy is a static, organization-level document defining overall quality standards and tools, whereas a Test Plan is a dynamic, project-specific document defining scope, schedule, resources, risks, and entry/exit criteria for a release. Test Scenario vs Test Case: A Test Scenario is a high-level one-liner stating WHAT to test, whereas a Test Case details HOW to test with exact preconditions, steps, test data, and expected results."

6. Self-Check

  1. Which document is static at the organization level, and which is dynamic at the project/release level? (Test Strategy is static/organization-level; Test Plan is dynamic/project-level.)
  2. What is Suspension Criteria inside a Test Plan? (The threshold condition under which QA temporarily halts all test execution—for example, if the staging environment goes down or >40% of core test cases are blocked by a critical defect.)
  3. How does Forward Traceability differ from Backward Traceability in an RTM? (Forward maps `Requirement -> Test Case` to ensure 100% of requirements are tested; Backward maps `Test Case -> Requirement` to ensure no extra unrequested features/tests are being built.)
