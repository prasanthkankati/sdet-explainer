M1.3 Question Bank: STLC Phases, Entry/Exit Criteria, RTM & Closure (35 Questions)

Tier 1: Core Definitions, Phases & Deliverables (Q1–Q10)

  1. What is STLC, and what are all 6 phases in exact sequence?
    STLC (Software Testing Life Cycle) is the step-by-step testing process executed by QA. The 6 phases are: 1. Requirement Analysis → 2. Test Planning → 3. Test Case Design & Development → 4. Test Environment Setup → 5. Test Execution → 6. Test Cycle Closure.
  2. What is the difference between SDLC and STLC?
    SDLC covers the entire software creation process (Requirements, Design, Coding, Testing, Deployment, Maintenance) across all teams. STLC covers specifically the testing phases owned by QA/SDET, running in parallel with SDLC phases to verify and validate the product.
  3. What are Entry Criteria and Exit Criteria in STLC?
    Entry Criteria are the mandatory prerequisite conditions and inputs required *before* a testing phase can start. Exit Criteria are the quality conditions, metrics, and deliverables that must be completed *before* a phase can be formally closed.
  4. Can the Exit Criteria of one STLC phase act as the Entry Criteria of the next phase? Give an example.
    Yes. The Exit Criteria of Phase 3 (Peer-reviewed and signed-off Test Cases, Test Data, and RTM) directly form the Entry Criteria required to start Phase 5 (Test Execution). Similarly, Phase 4's Exit Criterion (Passing Smoke Test) is the Entry Criterion for Phase 5.
  5. What is an RTM (Requirement Traceability Matrix), and in which STLC phase is it created vs updated?
    An RTM is a document that maps every Requirement ID to its corresponding Test Case IDs, Automation Script IDs, Execution Status, and Defect IDs to guarantee 100% test coverage. It is initialized in Phase 1 (Requirement Analysis), mapped to test cases in Phase 3, updated with Pass/Fail/Defect IDs in Phase 5, and audited for 100% coverage in Phase 6.
  6. What are the 3 types of Traceability Matrix (Forward, Backward, Bidirectional)?
    1. Forward Traceability (Requirement → Test Case): Ensures every business requirement has at least one test case.
    2. Backward / Reverse Traceability (Test Case → Requirement): Ensures we are not writing bloated test cases for features that were never requested ("gold-plating").
    3. Bidirectional Traceability (Forward + Backward): Combines both to prove 100% coverage with zero orphan requirements and zero unmapped tests.
  7. What is Automation Feasibility Analysis, and why is it done in Phase 1 instead of Phase 5?
    It evaluates whether a feature is suitable and cost-effective to automate (checking tech stack support, DOM stability, frequency of execution, and ROI). It must happen in Phase 1 so Phase 2 (Test Planning) can allocate SDET resources and Phase 3 can develop the scripts before execution starts.
  8. What is the difference between a Test Plan and a Test Summary (Closure) Report?
    A Test Plan is written in Phase 2 (before testing) defining what we *plan* to test, scope, schedule, tools, and risks. A Test Summary Report is written in Phase 6 (after testing) summarizing what was *actually* executed, pass/fail counts, open defects, waivers, and the final Go/No-Go release recommendation.
  9. Why is Smoke Testing performed in Phase 4 (Test Environment Setup) before Phase 5 (Test Execution)?
    Smoke Testing acts as the Build Verification Gate. If the QA database connection is broken or the login page returns HTTP 500, running a 500-case regression suite in Phase 5 wastes QA time and floods Jira with duplicate environment bugs.
  10. What is the difference between a Blocked test case and a Failed test case during Phase 5 (Test Execution)?
    A Failed test case was executed completely, and the actual result did not match the expected result. A Blocked test case *could not be executed at all* because a precondition failed (e.g., "Verify Order History" is Blocked because the "Place Order" button is throwing a 500 error, or the third-party payment sandbox is down).

Tier 2: Why / Why Not & Deep Comparisons (Q11–Q18)

  1. Why not write Test Cases during Phase 5 (Test Execution) while clicking through the live application?
    If you write test cases by looking at the already-built UI instead of the SRS/User Story in Phase 3, you will document the developer's bugs as expected behavior! Designing test cases in Phase 3 from requirements ensures independent validation against what the system *should* do, not just what the developer happened to build.
  2. Who owns Phase 4 (Test Environment Setup)—Developers, DevOps, or QA?
    While DevOps/Infra provisions the servers/containers and Developers deploy the build, QA owns verifying environment readiness: configuring test properties, seeding baseline test data, verifying mock endpoints, and executing the Smoke Test Gate to accept or reject the build.
  3. What is "Suspension Criteria" vs "Exit Criteria" in a Test Plan?
    Suspension Criteria define when testing must be paused mid-cycle (e.g., if >30% of test cases are blocked by a core API crash or environment outage). Exit Criteria define when testing is successfully finished and ready for sign-off.
  4. Why do we map Defect IDs inside the RTM during Phase 5?
    So during impact analysis or regression, if Requirement `REQ-204` changes or fails, we can immediately see every historical defect (`BUG-88`, `BUG-102`) and every test case tied to that requirement.
  5. What happens in STLC if a feature is marked "Out of Scope" in the Phase 2 Test Plan, and a bug escapes to production in that feature?
    Because the Phase 2 Test Plan explicitly listed that feature under Out-of-Scope (and explained the risk) and stakeholders formally signed off on the Test Plan, accountability is transparent. This is why getting formal stakeholder sign-off on Phase 2 Out-of-Scope items is critical for a QA Lead.
  6. In Agile (2-week sprints), do we still follow all 6 STLC phases, or is STLC only for Waterfall?
    We still follow all 6 STLC phases inside every 2-week sprint, compressed and continuous:
    • Phase 1 & 2 happen in Backlog Refinement & Sprint Planning (Day 1).
    • Phase 3 & 4 happen on Days 2–5 while devs code.
    • Phase 5 happens continuously as stories move to `Ready for QA` (Days 4–9).
    • Phase 6 happens at Sprint Review / Release Sign-off (Day 10).
  7. Why should Test Data preparation happen in Phase 3 instead of Phase 5?
    Preparing complex test data (e.g., 50 user accounts with specific credit scores, expired subscriptions, or multi-row Excel `.xlsx` sheets) takes significant time. Doing it in Phase 3 ensures zero idle time once the build lands in Phase 5.
  8. What metrics are included in the Phase 6 Test Closure Report?
    1. Total Requirements vs Covered Requirements (`RTM Coverage %`).
    2. Total Test Cases Planned vs Executed vs Passed / Failed / Blocked.
    3. Defect Summary broken down by Severity (`S1/S2/S3/S4`) and Status (`Closed`, `Deferred`).
    4. Automation Execution Pass % and execution duration.

Tier 3: Real-World Tricky & Edge-Case Scenarios (Q19–Q26)

  1. [Scenario — PM Pressures QA to Skip Entry Criteria] A build is deployed late. Entry Criteria require a unit test report and a passing Smoke Test, but the PM tells you to skip the Smoke Test and start full functional execution immediately with 6 QA engineers. What do you do?
    I do not blindly throw 6 engineers at an unverified build, nor do I simply refuse to work. I explain that if the build is broken, 6 engineers will waste hours logging duplicate crash bugs. I propose running the automated Smoke Suite first (which takes 5–10 minutes) while the team prepares execution runs; if Smoke passes, all 6 engineers start immediately, and if it fails, we save 6x wasted effort and return the build to Dev.
  2. [Scenario — Undocumented Slack Feature Discovered in Phase 5] During Phase 5 Test Execution, you find a new "Export to CSV" button that is not in the SRS or your RTM. Developers say the client asked for it on Slack. How do you handle this?
    1. Confirm with the Product Owner/BA that the Slack request is an approved requirement.
    2. Have the PO add a formal Requirement/Story ID so it is no longer "shadow scope".
    3. Add the Requirement ID to the RTM, design positive/negative test cases for CSV export, execute them, and run a mini-regression on the surrounding table module.
  3. [Scenario — Premature Test Closure on 95% Execution] Release day arrives. 95% of test cases passed, 0 high-severity bugs are open, and the manager asks you to sign off Phase 6 Test Closure. However, the unexecuted 5% are Payment Gateway tests that were Blocked by sandbox downtime. Do you sign off?
    No unconditional sign-off. Execution percentage (`95%`) without risk context is misleading—shipping an untested Payment Gateway is a critical business risk. I escalate the blocker, get the sandbox restored to run those 5% payment tests, or—if business insists on releasing with payment feature-flagged off—issue a Conditional Sign-Off with Explicit Risk Waiver documented in the Test Summary Report.
  4. [Scenario — 100% Tests Executed and Passed, Still Can't Close Phase 5] Can a test cycle have 100% of test cases executed and 100% passed, yet still fail Exit Criteria? How?
    Yes! If the RTM audit reveals that 3 critical requirements from the SRS were accidentally never mapped to any test cases (`Requirement Coverage = 75%`), or if non-functional Exit Criteria (like security/performance SLAs) were not executed.
  5. [Scenario — Developer Rejects Bug Saying "Not in SRS"] In Phase 5, you log a bug because typing 500 characters into the "First Name" field crashes the layout. The developer marks it `Invalid` saying the SRS didn't specify a max length. How could STLC Phase 1 have prevented this, and how do you resolve it now?
    In Phase 1 (Requirement Analysis), QA should check for missing field-length boundaries and get them added to the SRS before coding. Right now in Phase 5, a UI layout crash is still a valid usability/validation bug—I attach the screenshot, bring in the PO during bug triage to define the standard limit (e.g., 50 chars), and get it fixed.
  6. [Scenario — High Defect Reopen Rate in Phase 5] During Phase 5, 40% of bugs marked "Fixed" by developers fail Retesting and have to be Reopened, delaying STLC closure. How do you fix this using STLC guardrails?
    Tighten the Entry Criteria for Bug Retesting: require developers to (1) verify their fix locally in the dev environment with unit tests, (2) specify the exact build version number containing the fix in the Jira ticket, and (3) run the automated PR smoke/regression check before moving a ticket to `Ready for QA Retest`.
  7. [Scenario — Zero Time Left for Full Regression] An emergency hotfix lands 2 hours before production deployment. Full manual + UI regression takes 6 hours. How do you execute Phase 5 & 6 safely?
    1. Perform Impact Analysis using the RTM to identify the exact modules touched by the hotfix.
    2. Execute Retesting on the hotfix defect + Sanity & Risk-Based Regression on the impacted modules.
    3. Run the Parallel Selenium/API Smoke & Critical-Path Suite (`ThreadLocal` across multiple threads) to validate core flows within 20 minutes before signing off.
  8. [Scenario — Orphan Test Cases Found in Phase 6] While auditing the RTM in Phase 6, you find 40 old Selenium tests that don't map to any current requirement because that feature was removed 3 sprints ago. What do you do?
    Use Backward Traceability to confirm the feature is retired, remove those 40 obsolete tests from the active regression suite to eliminate code bloat and CI execution waste, and log the cleanup in the Test Closure Report.

Tier 4: SDET, Automation & CI/CD in STLC (Q27–Q31)

  1. How do you automate the Requirement Traceability Matrix (RTM) in a Selenium + TestNG framework?
    Use custom annotations or TestNG `@Test(description = "REQ-105")` / Allure `@Issue("JIRA-105")` `@TmsLink("TC-201")` annotations on every test method. When `mvn test` finishes, the Allure or ExtentReport listener parses those annotations and auto-generates a live RTM mapping Requirements → Test Cases → Pass/Fail results.
  2. In Phase 1 (Automation Feasibility), what top 5 criteria make a test case a BAD candidate for Selenium UI automation?
    1. One-time ad-hoc tests that will never be re-run.
    2. Features whose UI design is changing every day (wait until UI stabilizes or test at the API layer instead).
    3. Pure visual/UX subjective checks ("Does this font look appealing?").
    4. Flows blocked by un-bypassable third-party CAPTCHA / physical hardware tokens in QA (unless mocked/whitelisted).
    5. Scenarios that can be validated 50x faster at the Unit or REST API layer.
  3. How does Docker / Selenium Grid speed up STLC Phase 4 (Environment Setup) and Phase 5 (Test Execution)?
    In Phase 4, instead of manually installing Chrome, Firefox, and Edge drivers on physical VMs, a `docker-compose.yml` spins up a clean Selenium Grid in 10 seconds. In Phase 5, running tests with `ThreadLocal<WebDriver>` across 10 Docker browser nodes cuts a 2-hour sequential regression run down to 12 minutes.
  4. What is the difference between a Test Plan (STLC Phase 2) and a Test Strategy?
    A Test Strategy is a high-level, organization-wide or long-term document (rarely changes) defining general testing standards, tools, test pyramid ratios, and CI/CD gates across projects. A Test Plan is a project- or release-specific document written in STLC Phase 2 detailing the exact scope, schedule, environment, and resources for *this specific release*.
  5. How does Shift-Left change the relationship between STLC Phase 3 (Test Development) and SDLC Phase 3 (Coding)?
    Instead of waiting for SDLC Coding to finish before starting STLC Test Development, both run simultaneously: SDETs write API tests from Swagger contracts and Selenium Page Objects from agreed DOM IDs while developers write the application code.

Tier 5: Rapid-Fire Curveballs & True/False Traps (Q32–Q35)

  1. True or False: "Test Execution is the first phase of STLC."
    False. Requirement Analysis is Phase 1; Test Execution is Phase 5 (4 phases of preparation happen before execution!).
  2. True or False: "If all test cases are executed, STLC Phase 5 Exit Criteria are automatically met even if 3 Critical bugs are still Open."
    False. Execution Exit Criteria require both execution completion and resolution/closure of all Blocker/Critical/High severity defects.
  3. Which STLC phase produces the "Ambiguity Review Report"?
    Phase 1: Requirement Analysis.
  4. Give a 20-second interview summary of STLC and how you execute it as an SDET.
    "STLC is the 6-phase testing lifecycle inside SDLC: Requirement Analysis, Test Planning, Test Case & Script Development, Environment Setup, Test Execution, and Test Closure. Each phase has strict Entry and Exit criteria. As an SDET, I initialize the RTM and assess automation feasibility in Phase 1, build Page Objects and TestData in Phase 3, enforce an automated Selenium Smoke Gate in Phase 4, run parallel regression in Phase 5, and deliver metric-driven Test Summary sign-offs in Phase 6."
