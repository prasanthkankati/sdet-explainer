4.3 Access Modifiers & Encapsulation

The 4 visibility levels (private, default, protected, public), complete scope matrix, and why Page Objects encapsulate private By locators.

Java controls which classes and packages can read or invoke fields, constructors, and methods through four explicit visibility levels. Combining restrictive access modifiers with controlled public methods enforces Encapsulation, keeping internal implementation details hidden while exposing clean contracts.

Before you start

Prerequisite: 4.2 Constructors: Default, Parameterized, Chaining & Singleton

Where it fits

Encapsulation is the structural backbone of the Selenium Page Object Model (private final By locators paired with public business methods) and API data POJOs.

Key points

  1. Java's four access modifiers ordered from narrowest to widest scope are: private < default (package-private, no keyword) < protected < public.
  2. private members are accessible strictly inside the declaring class itself (never in subclasses or external classes).
  3. Default (package-private) members (omitting any modifier keyword) are accessible inside the declaring class and any class inside the exact same package.
  4. protected members are accessible inside the same package AND inside subclasses residing in different packages (via inheritance).
  5. public members are accessible from any class across every package.
  6. Top-level classes and interfaces may only be declared public or package-private (never private or protected), whereas nested classes support all four modifiers.
  7. Encapsulation bundles data and methods while hiding internal fields with private and exposing validated public accessors or business actions.

How it works

  1. Declare DOM selectors as private final By inside a Page Object class (for instance, inside package pages).
  2. Declare shared framework helpers on BasePage as protected so Page Objects in sub-packages inherit them while test classes in package tests cannot invoke raw driver primitives directly.
  3. Expose domain actions like loginAs(user, pass) as public so TestNG classes call clean business workflows without coupling to DOM locators.
  4. For API request/response POJOs, keep fields private and enforce data constraints inside setters or constructors.

Applying Encapsulation and visibility scopes across BasePage and LoginPage:

package dev.java.oop; // Declares package

import org.openqa.selenium.By; // Imports By locator
import org.openqa.selenium.WebDriver; // Imports WebDriver

class EncapsulatedLoginPage { // Package-private top-level class
    private final WebDriver driver; // Encapsulated driver cannot be reassigned externally
    private final By emailField = By.id("username"); // Private locator hidden from @Test classes
    private final By loginBtn = By.cssSelector("button[type='submit']"); // Single source of truth

    public EncapsulatedLoginPage(WebDriver driver) { // Public constructor for test packages
        this.driver = driver; // Stores driver reference privately
    } // Ends constructor

    protected void clickLocator(By locator) { // Protected helper accessible to package and subclasses
        driver.findElement(locator).click(); // Executes Selenium click safely
    } // Ends protected helper

    public void submitLogin(String email) { // Public business method exposed to tests
        if (email == null || email.isBlank()) { // Enforces validation invariant at boundary
            throw new IllegalArgumentException("Email must not be blank"); // Fails fast on bad test input
        } // Ends validation check
        driver.findElement(emailField).sendKeys(email); // Interacts with private locator
        clickLocator(loginBtn); // Reuses protected helper internally
    } // Ends submitLogin
} // Ends class

Common mistakes

  1. Declaring Page Object locators as public static By usernameInput = ...;; exposing public locators lets @Test classes leak DOM details and duplicate click/wait logic outside the Page Object.
  2. Writing the literal word default before a field (default int count;); package-private access uses NO modifier keyword—default is valid only in switch blocks and interface default methods.
  3. Making helper fields on BaseTest package-private when tests live in sub-packages (tests.auth vs base); sub-packages are completely separate packages in Java, so subclasses need protected access.
  4. Attempting to narrow visibility when overriding a method (for example, overriding a public parent method as protected or private); Java forbids making an overridden method less visible.

Interview questions

Basics

List Java's four access modifiers in order from most restrictive to least restrictive.
From tightest to widest visibility: private (same class only), package-private / default (same class and same package), protected (same package plus subclasses in external packages), and public (accessible everywhere). Choosing the narrowest visibility that compiles keeps coupling minimal.

What is Encapsulation in Java and why does it matter in test automation?
Encapsulation wraps state (fields) and behavior (methods) inside a single class while restricting direct external access to internal representation via private fields. In Selenium Page Objects, hiding private final By locators ensures test classes call public business methods like addProductToCart() rather than directly referencing fragile CSS/XPath selectors. When UI markup changes, only the Page Object changes.

Can a top-level Java class be marked private or protected?
No. Top-level classes and interfaces can only be public or package-private (no modifier). Only nested member classes, fields, constructors, and methods support private and protected.

How it works

How does protected behave across packages when a subclass holds a reference to a parent object?
Inside a subclass in package B extending parent class BasePage in package A, the subclass can access protected members inherited on this or on another instance of the subclass itself. However, the subclass in package B cannot create a raw new BasePage() parent reference and access its protected members directly—cross-package protected access works strictly through inheritance.

Are sub-packages like com.qkart.tests.login considered part of com.qkart.tests for default/package-private access?
No. In Java, packages have a flat visibility boundary regardless of folder nesting. com.qkart.tests and com.qkart.tests.login are treated as completely separate packages with zero package-private sharing between them.

Does encapsulation still allow mutating an object's internal state if a getter returns a mutable List?
Returning a raw reference to a mutable private List or array breaks encapsulation because external callers can invoke page.getItems().clear() and mutate internal state silently. Return an unmodifiable copy using List.copyOf(items) or Collections.unmodifiableList(items) to protect internal state.

Real situations

In an enterprise Selenium framework, which modifier should be used for BasePage.driver, By locators, and PageObject action methods?
Declare By locators as private final inside each specific Page Object so neither tests nor other pages depend on them. Declare shared wait/click helpers and driver on BasePage as protected so child Page Objects across packages reuse them while @Test classes cannot call raw Selenium primitives. Mark business workflow methods like checkout() as public.

How does Encapsulation protect test data POJOs used in API testing?
Marking fields private inside an API request POJO lets setter or builder methods validate constraints—including rejecting negative quantities or malformed emails—before serializing JSON to the API endpoint.

Why does TestNG require @Test methods and constructors to be public (or package-visible in matching packages) in typical CI suites?
TestNG scans classes from outside your test package using reflection, and @Test methods represent entry points invoked by the external runner. Keeping @Test methods public guarantees TestNG discovers and runs them reliably.

Troubleshooting

Why did moving WaitHelper from package pages into utils break compilation on package-private helper methods?
Methods written without an access modifier default to package-private visibility, so relocating callers into a separate package immediately cuts off visibility with 'method is not public in WaitHelper; cannot be accessed from outside package'. Explicitly add public for cross-package utilities.

Why does overriding a parent method with narrower visibility like changing public void click() to protected void click() fail compilation?
Java enforces Liskov Substitution rules on overridden methods: any caller holding a parent reference expects public access, so narrowing visibility on a child override breaks polymorphic calls and triggers 'attempting to assign weaker access privileges'. You may widen visibility (for example, protected to public), never narrow it.

Why can two instances of the exact same class read each other's private fields?
In Java, private restricts visibility at the class boundary, not the individual object boundary. Inside equals(Object o) on User, casting to User other allows reading other.id directly even though id is private.

Design choices

Why should automated framework engineers start every new field or helper as private and widen only when needed?
Minimizing surface area prevents external classes from accidentally coupling to internal fields or helper details. Once a member is made public, refactoring or removing it requires auditing the entire codebase; keeping helpers private or package-private preserves refactoring freedom.

When building a fluent Page Object API, why should low-level methods like waitForElement(By) be protected rather than public?
Exposing low-level wait or click primitives publicly invites test authors to pass raw By locators inside @Test classes, eroding Page Object Model boundaries. Making those primitives protected in BasePage keeps them strictly inside the Page Object hierarchy.

Why do modern Java 16+ record classes make fields private final automatically?
Records model immutable data carriers (like API response DTOs or test configuration pairs) where encapsulation forbids post-construction field tampering. Generating private final fields alongside read-only accessors enforces immutability with zero boilerplate.

Quick answers

  1. What are Java's 4 access levels? private, default (package-private), protected, and public.
  2. Which keyword applies package-private visibility? No keyword at all (omitting any access modifier).
  3. Can an overridden method have narrower visibility than the parent method? No; it can only keep the same visibility or widen it.
  4. What visibility modifier should Page Object By locators use? private final.
  5. What access modifiers are legal on a top-level class? public or package-private only.
  6. What is the difference between package-private and protected? protected additionally grants access to subclasses residing in different packages.
