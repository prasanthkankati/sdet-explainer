1.1 Verification vs Validation (Static vs Dynamic Testing)

1. The Base: What is Software Testing and Why Do We Need It?

Software Testing is the complete process of evaluating project artifacts (requirements, design, source code) and the running application to prevent defects early, detect runtime bugs before release, and prove the software meets both the technical specification and the user's business need.

The Problem It Solves: When a business wants a feature (e.g., "Users can transfer up to $1,000 per day"), humans write that requirement in English, architects design it, and developers write code in Java or TypeScript. Mistakes happen at every stage: an unclear specification, a developer coding < 1000 instead of <= 1000, or a server crash when clicking "Transfer". Software Testing catches these flaws at every stage.

Core Terminology Defined First (Error vs Defect vs Failure & Project Artifacts):

  • 1. Error (Mistake): A human mistake made by a Business Analyst, Architect, or Developer (e.g., a developer misreads the discount formula and thinks a discount should be added instead of subtracted).
  • 2. Defect (Bug / Fault): The actual flaw written inside a document or source code file as a result of that human error (e.g., line 4 of CartCalculator.java contains price + discount instead of price - discount).
  • 3. Failure: The observable incorrect behavior when the compiled application actually runs (e.g., a user applies a 20% coupon on a $100 item and the checkout screen charges $120 instead of $80).
  • 4. Project Artifacts: All tangible files created during a software project before or during coding—including requirement docs (BRS/SRS), Jira User Stories, API contracts (Swagger), Test Cases, and source code files (.java, .ts).

2. Where Do Static and Dynamic Testing Fall? (The Classification Tree)

Based on whether we execute (run) the code or not, all of Software Testing is divided into 2 fundamental branches:

  1. Static Testing (performed via Verification) — Testing without executing the code.
  2. Dynamic Testing (performed via Validation) — Testing by executing the running code.
SOFTWARE TESTING Root Classification by Code Execution
Splits on one question: "Do we compile and run the application code?"
1. STATIC TESTING (Verification) • Code is NOT executed
• Checks: Requirements, Design, Test Cases, Source Code text
• Goal: Prevent defects early (1x cost)
• Sub-types: Manual Reviews (Informal, Walkthrough, Technical, Inspection) & Static Analysis (SonarQube)
2. DYNAMIC TESTING (Validation) • Code IS compiled & executed
• Checks: Running App, Live APIs, Browser DOM, DB
• Goal: Detect runtime defects (10x cost)
• Sub-types: Functional (Unit, Integration, System, UAT) & Non-Functional (Performance, Security)

Interview Answer: "Based on code execution, Software Testing is classified into Static Testing and Dynamic Testing. Static Testing evaluates documents and source code without executing the program (Verification), whereas Dynamic Testing evaluates the behavior of the software by actually executing it with test inputs (Validation)."

3. Branch 1: Static Testing (Verification)

Definition: Static Testing is the evaluation of project documents (BRS, SRS, Jira User Stories, API specs, Test Cases) and source code (.java, .ts) without executing the program. It performs Verification: "Are we building the product right according to the specification?"

Why we need it (Cost of Defect Multiplier — IBM/NIST Standard):

  • Fixing a defect during Requirement/Code Review (Static Verification): 1x cost (minutes).
  • Fixing it during QA Test Execution (Dynamic Validation): 10x cost (requires bug logging, dev debugging, code fix, new build, retest).
  • Fixing it in Production: 100x cost (customer impact, hotfix, rollback).

Sub-Types of Static Testing (Listed First, Explained in Order):

  1. Manual Static Reviews (4 levels from least to most formal: Informal Review, Walkthrough, Technical Review, Inspection)
  2. Automated Static Code Analysis (SonarQube, Checkstyle, PMD, SpotBugs, ESLint)

Explained in order:

  1. Informal Review: Peer check without a formal meeting or checklist (e.g., a teammate reads your test cases or PR and leaves comments).
  2. Walkthrough: Led by the author of the document/code, who walks the team through the logic to explain it and gather open feedback.
  3. Technical Review: Led by technical experts / senior SDETs to verify architecture, Swagger API contracts, or automation framework standards.
  4. Inspection (Most Formal): Led by a trained Moderator (never the author) with defined roles (Author, Reader, Recorder/Scribe, Inspector), formal entry/exit criteria, checklists, and logged defect metrics.
  5. Automated Static Code Analysis: Tools that parse source code AST (Abstract Syntax Tree) without running the app to catch null-pointer risks, dead code, hardcoded waits, security vulnerabilities (SAST), and cyclomatic complexity.

In What Exact Cases Do We Perform Static Testing?

  • Case 1 (Sprint Refinement): Reviewing new Jira stories and Acceptance Criteria for ambiguity or missing negative scenarios before coding begins.
  • Case 2 (Design Sign-Off): Reviewing Swagger/OpenAPI schemas, wireframes, and DB tables before backend implementation.
  • Case 3 (Test Readiness): Peer-reviewing manual test cases and RTM coverage before build deployment.
  • Case 4 (Pull Request Gate): Reviewing developer .java code or SDET Selenium Page Object PRs + running SonarQube before merging to main.

4. Branch 2: Dynamic Testing (Validation)

Definition: Dynamic Testing is the evaluation of the software by compiling and executing the program with test inputs and comparing actual runtime outputs against expected business outcomes. It performs Validation: "Did we build the right product that actually works for the user?"

Why we need it even after Static Testing: Static Testing cannot observe runtime memory, network timeouts, database locks, browser DOM rendering differences, CORS failures, or whether the finished workflow actually satisfies the real end-user.

Sub-Types of Dynamic Testing (Listed First, Explained in Order):

  1. Functional Dynamic Testing (Unit, Integration, System, User Acceptance Testing [UAT])
  2. Non-Functional Dynamic Testing (Performance/Load, Security/Penetration, Usability, Compatibility)

Explained in order:

  1. Unit Testing: Executing individual methods/classes in isolation (JUnit / TestNG).
  2. Integration Testing: Executing combined services, DB queries, and live REST APIs (RestAssured / Postman).
  3. System Testing: Executing the complete end-to-end application in a QA environment (Manual UI + Selenium / Playwright automation).
  4. User Acceptance Testing (UAT): Business stakeholders/end-users validating real-world workflows before go-live.
  5. Non-Functional Testing: Executing the system under load (JMeter/k6) or security attacks (OWASP ZAP) to measure speed, stability, and resilience.

In What Exact Cases Do We Perform Dynamic Testing?

  • Case 1 (Local Dev Build): Running unit tests after compiling a class.
  • Case 2 (QA Build Deployment): Running automated Selenium Smoke Tests to verify the deployed build is stable enough for testing.
  • Case 3 (In-Sprint Story Validation): Executing positive, negative, and boundary test cases against live UI and APIs.
  • Case 4 (Pre-Release Regression): Executing parallel Selenium/Playwright regression suites in CI/CD before production release.

6. Real Code Trace: Static vs Dynamic Testing on the Same Feature

public class CartCalculator {
    public static double calculateFinalPrice(double price, double discountPercent) {
        // BUG: Developer wrote '+' instead of '-'
        return price + (price * discountPercent / 100);
    }
}

public class CartTest {
    public static void main(String[] args) {
        double actual = CartCalculator.calculateFinalPrice(100.0, 20.0);
        double expected = 80.0;
        System.out.println("Actual output at runtime : " + actual);
        System.out.println("Expected output          : " + expected);
        System.out.println("Validation Passed?       : " + (actual == expected));
    }
}
Actual output at runtime : 120.0
Expected output          : 80.0
Validation Passed?       : false
  • Static Testing catch: In the GitHub Pull Request review (before running java CartTest), the reviewer sees price + ... on line 4 and flags it immediately.
  • Dynamic Testing catch: When java CartTest (or a Selenium test reading the cart total from the browser DOM) runs with inputs (100.0, 20.0), it produces 120.0 instead of 80.0 and fails the assertion.
