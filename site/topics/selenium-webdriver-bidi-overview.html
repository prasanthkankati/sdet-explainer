8.1 WebDriver BiDi Architecture & Setup

Next-generation W3C Bidirectional (BiDi) WebSocket communication vs classic HTTP request-response and vendor-locked CDP.

Classic W3C WebDriver uses a synchronous HTTP request-response model where the browser cannot push asynchronous events back to the Java test script. WebDriver BiDi is the official cross-browser W3C bidirectional specification that establishes a persistent WebSocket channel (enabled via options.enableBiDi() or webSocketUrl: true), combining the best of classic WebDriver and Chrome DevTools Protocol (CDP) across Chrome, Firefox, and Edge.

Before you start

Prerequisite: 7.2 Keyboard & Wheel Actions

Where it fits

WebDriver BiDi is enabled in your browser Options when tests need real-time event listeners (console errors, network interception, DOM mutations, or isolated user contexts).

Key points

  1. Classic WebDriver uses unidirectional HTTP (Client -> Driver -> Browser), requiring polling to detect browser changes.
  2. WebDriver BiDi uses a full-duplex WebSocket connection, allowing the browser to push real-time events (logs, network traffic, crashes) to Java immediately.
  3. To enable WebDriver BiDi in Selenium 4, call options.enableBiDi() (or options.setCapability("webSocketUrl", true)) before creating the driver.
  4. Unlike Chrome DevTools Protocol (CDP), which is proprietary to Chromium and changes with every Chrome version, WebDriver BiDi is a stable, vendor-neutral W3C standard supported by Firefox, Chrome, and Edge.
  5. BrowsingContext in WebDriver BiDi can create isolated incognito-like user contexts within a single browser instance to test multiple concurrent logged-in users.

How it works

  1. Create a ChromeOptions or FirefoxOptions instance and call options.enableBiDi() (which sets the W3C capability webSocketUrl to true).
  2. Instantiate the driver; during the session handshake, the browser driver starts a WebSocket server and returns its ws:// URL in the capabilities response.
  3. Selenium's Java client automatically connects its internal Java 11+ WebSocket client to that ws:// endpoint.
  4. The test registers event consumers (such as LogInspector or Network) that receive live event callbacks whenever the browser emits matching events.

Enabling W3C WebDriver BiDi and using BrowsingContext in Java:

package dev.selenium.bidi; // Declares package

import org.openqa.selenium.WebDriver; // Imports WebDriver interface
import org.openqa.selenium.bidi.browsingcontext.BrowsingContext; // Imports BiDi BrowsingContext
import org.openqa.selenium.bidi.browsingcontext.ReadinessState; // Imports BiDi ReadinessState
import org.openqa.selenium.chrome.ChromeDriver; // Imports ChromeDriver
import org.openqa.selenium.chrome.ChromeOptions; // Imports ChromeOptions

public class BiDiOverviewExample { // Declares class
    public static void main(String[] args) { // Main method
        ChromeOptions options = new ChromeOptions(); // Creates ChromeOptions
        options.enableBiDi(); // Sets W3C webSocketUrl: true capability for BiDi

        WebDriver driver = new ChromeDriver(options); // Starts session with WebSocket channel active
        try { // Guarded block
            BrowsingContext context = new BrowsingContext(driver, driver.getWindowHandle()); // Binds BiDi context to tab
            context.navigate("https://www.selenium.dev/", ReadinessState.COMPLETE); // Navigates via BiDi protocol
            System.out.println("BiDi Context ID: " + context.getId()); // Prints active browsing context ID
        } finally { // Teardown block
            driver.quit(); // Closes WebSocket and terminates browser
        } // Ends finally
    } // Ends main
} // Ends class

Common mistakes

  1. Attempting to instantiate LogInspector, Network, or BrowsingContext without calling options.enableBiDi() first, which throws BiDiException: BiDi is not enabled.
  2. Writing new framework utilities against raw version-specific DevTools (v128, v129) CDP packages when a standardized W3C WebDriver BiDi API already exists.
  3. Forgetting to close or clean up event listeners when reusing a long-lived session across multiple tests.

Interview questions

Basics

What is WebDriver BiDi and what problem does it solve?
WebDriver BiDi is the W3C Bidirectional WebDriver standard. Classic WebDriver only supports HTTP request-response commands initiated by the test script; BiDi adds a persistent two-way WebSocket connection so the browser can stream real-time events (console logs, JS exceptions, network traffic) back to the test.

How do you enable WebDriver BiDi in a Selenium 4 Java test?
Call options.enableBiDi() (or options.setCapability("webSocketUrl", true)) on your ChromeOptions, FirefoxOptions, or EdgeOptions object before creating the driver.

Why is WebDriver BiDi preferred over the Chrome DevTools Protocol (CDP)?
CDP is a proprietary Chromium debugging protocol that does not work in Firefox or Safari and frequently breaks when Chrome updates. WebDriver BiDi is an official, cross-browser W3C standard designed specifically for stable test automation.

How it works

What happens during session creation when webSocketUrl: true is passed in capabilities?
The browser driver launches the browser with a WebSocket listener and returns a ws://localhost:port/session/... URL in the session handshake response. Selenium's Java client connects to that WebSocket for full-duplex messaging.

Can a single test mix classic WebDriver commands (like driver.findElement) and WebDriver BiDi APIs?
Yes. Selenium 4 is designed so classic HTTP commands and BiDi WebSocket event streams coexist seamlessly within the exact same WebDriver session.

What are ReadinessState options in BiDi BrowsingContext.navigate()?
BrowsingContext.navigate(url, ReadinessState) supports ReadinessState.NONE, ReadinessState.INTERACTIVE (DOMContentLoaded), and ReadinessState.COMPLETE (load event) on a per-navigation basis.

Real situations

Why did upgrading Chrome often break Selenium tests that imported org.openqa.selenium.devtools.v12X packages?
Raw CDP domains are tied to specific Chromium versions (such as v127, v128). Using Selenium's portable W3C BiDi APIs (LogInspector, Network, BrowsingContext) decouples your code from specific Chrome release numbers.

Does WebDriver BiDi work when running tests remotely through Selenium Grid 4?
Yes. Selenium Grid 4's Router and Node components natively proxy WebSocket connections, forwarding BiDi event streams between your Java test runner and the remote browser container.

How does BiDi allow testing two logged-in users in the same browser process?
BiDi's Browser module supports creating isolated User Contexts (similar to independent incognito profiles with separate cookies and storage) inside one running browser process, avoiding the memory overhead of launching a second browser.

Troubleshooting

What causes org.openqa.selenium.bidi.BiDiException: Cannot create instance of BiDi, webSocketUrl capability is not enabled?
You instantiated a BiDi class (like LogInspector or BrowsingContext) on a driver session that was started without calling options.enableBiDi(). Add options.enableBiDi() before new ChromeDriver(options).

Why did a BiDi WebSocket connection fail through a corporate reverse proxy on Selenium Grid?
Some older HTTP reverse proxies or load balancers drop WebSocket Upgrade headers (Connection: Upgrade, Upgrade: websocket). Configure the proxy/ingress controller to allow WebSocket pass-through.

How do you check programmatically if a WebDriver instance supports BiDi?
Check if the driver implements HasBiDi and call ((HasBiDi) driver).getBiDi() after enabling the capability.

Design choices

Why did the W3C Browser Testing and Tools Working Group create BiDi instead of standardizing CDP?
CDP exposes internal Blink/V8 engine structures that do not exist in Mozilla's Gecko (Firefox) or Apple's WebKit (Safari). W3C BiDi defines a clean, engine-agnostic contract that all browser vendors implement.

When should you still use classic WebDriver commands vs BiDi commands?
Continue using standard driver.findElement(), click(), and sendKeys() for everyday DOM interactions, and attach BiDi modules (LogInspector, Network) for event streaming, network mocking, and console monitoring.

Why is event-driven testing faster than polling for console or network state?
Instead of repeatedly querying the browser in a loop, the browser pushes the exact event over the WebSocket the millisecond it occurs, eliminating polling delay.

Quick answers

  1. Which capability enables WebDriver BiDi? options.enableBiDi() (which sets webSocketUrl: true).
  2. What transport protocol does WebDriver BiDi use? Full-duplex WebSocket (ws://).
  3. Is WebDriver BiDi cross-browser or Chrome-only? It is an official cross-browser W3C standard (Chrome, Firefox, Edge).
  4. What exception is thrown if BiDi is used without enableBiDi()? org.openqa.selenium.bidi.BiDiException.
  5. Does Selenium Grid 4 support BiDi WebSocket proxying? Yes, Grid 4 natively proxies BiDi WebSocket connections.
