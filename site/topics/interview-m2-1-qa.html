M2.1 Question Bank: Levels of Testing — Unit, Integration, System & UAT (35 Questions)

Tier 1: Core Definitions, Sequence & Classification (Q1–Q10)

  1. Q1: What are the 4 levels of software testing in exact sequential order?
    A: (1) Unit Testing (Component Testing), (2) Integration Testing, (3) System Testing, and (4) User Acceptance Testing (UAT).
  2. Q2: Why are they called "Levels" of testing instead of "Types" of testing?
    A: Levels define where in the architecture hierarchy and SDLC we test (Method → Service Interface → Full App → Business User), whereas Types (Smoke, Regression, Performance, Security) define what quality attribute or objective we are testing. In fact, Regression or Smoke testing can be executed at any level (Unit, API Integration, or UI System level).
  3. Q3: What is Unit Testing and who performs it?
    A: Unit Testing is white-box testing of the smallest isolated piece of code (a single Java method or class) performed by Developers using JUnit or TestNG, with external dependencies (DB, network) mocked out via tools like Mockito.
  4. Q4: What is Integration Testing and what specific defects does it target?
    A: Integration Testing verifies the interaction, data flow, and contract between two or more connected modules or microservices. It targets interface defects: mismatched JSON field names, wrong HTTP status codes, SQL schema mismatches, serialization failures, and timeout propagation.
  5. Q5: What are the 2 main categories and 4 sub-types of Integration Testing?
    A: (1) Incremental Integration (where modules are added and tested one by one: Top-Down, Bottom-Up, and Sandwich/Hybrid), and (2) Non-Incremental Integration (Big Bang Integration, where all modules are coupled at once).
  6. Q6: What is a Stub vs what is a Driver in Integration Testing?
    A: A Stub is a passive dummy component used in Top-Down Integration to replace a missing lower-level called child module (returning hardcoded responses). A Driver is an active test harness used in Bottom-Up Integration to replace a missing higher-level calling parent module (invoking the child module under test).
  7. Q7: What is System Testing and what specification document does it validate against?
    A: System Testing is black-box end-to-end testing of the completely integrated software application in a production-like QA environment. It validates both functional and non-functional behavior against the SRS (System Requirement Specification).
  8. Q8: What is User Acceptance Testing (UAT) and who owns it?
    A: UAT is the final testing level performed by Business Stakeholders, Product Owners, Clients, or real End-Users to verify that the system satisfies business needs (BRS) and is ready for production go-live.
  9. Q9: What are the 2 types of UAT and how do they differ?
    A: Alpha Testing is performed in-house at the developer's site (controlled UAT staging environment) by internal staff/client reps before public release. Beta Testing is performed by real external end-users in their own real-world environments using a pre-release build.
  10. Q10: How do the 4 Test Levels map to the left side of the V-Model?
    A: Unit Testing ↔ LLD (Low-Level Design); Integration Testing ↔ HLD (High-Level Design); System Testing ↔ SRS (System Requirement Spec); UAT ↔ BRS (Business Requirement Spec).

Tier 2: Why / Why Not & Deep Comparisons (Q11–Q18)

  1. Q11: Why can't we skip Unit and Integration testing and just test everything at the System (UI) level with Selenium?
    A: This is the "Ice-Cream Cone Anti-Pattern": (1) UI tests are 50x–100x slower than unit/API tests, (2) a failing UI test doesn't tell you which backend class or microservice failed, (3) combinatorially testing every `if/else` branch through a browser UI is impossible, and (4) bugs caught at the System level cost 10x more to debug and fix than at the Unit level.
  2. Q12: Why is Incremental Integration always preferred over Big Bang Integration?
    A: In Incremental Integration, you connect one module at a time—if a test fails after connecting Module C to Module B, you know immediately that the bug is in the B↔C interface. In Big Bang, you connect 30 modules at once; when it crashes, isolating the faulty interface requires debugging the entire system.
  3. Q13: Why can all Unit tests pass 100% while the application still crashes during Integration Testing?
    A: Because Unit tests use mocks based on a developer's *assumptions* of how other services behave. For example, `OrderService` unit tests might mock `PaymentService` returning `"amount": 100.00` (number), whereas the real `PaymentService` returns `"amount": "$100.00"` (String), causing a `JsonParseException` when integrated!
  4. Q14: Why is System Testing considered Black-Box while Unit Testing is White-Box and Integration is Grey-Box?
    A: Unit Testing inspects internal code lines and `if/else` branches (White-Box). Integration Testing uses knowledge of API schemas, HTTP headers, and DB tables without reading internal method loops (Grey-Box). System Testing interacts strictly with the external UI/public endpoints as an end user without touching internal code (Black-Box).
  5. Q15: Why do we need UAT if the QA team already executed 100% of System Testing with zero open bugs?
    A: Because QA tests against the SRS (how the system was specified to work), whereas business users in UAT validate against real-world business workflows (BRS). A feature can match the SRS 100% and still be awkward or unusable for an actual bank teller or warehouse operator (Principle #7: Absence-of-errors fallacy).
  6. Q16: What is the difference between Component Integration Testing and System Integration Testing (SIT)?
    A: Component Integration Testing tests interactions between classes/packages inside the *same* application binary (after Unit Testing). System Integration Testing (SIT) tests end-to-end interactions across *separate* enterprise systems, microservices, and third-party gateways (e.g., E-Commerce App ↔ SAP ERP ↔ Stripe Gateway).
  7. Q17: When should you choose Top-Down Integration vs Bottom-Up Integration?
    A: Choose Top-Down when user interface and top-level business orchestration logic are high-risk and need early validation (using Stubs for DB/utilities). Choose Bottom-Up when low-level database engines, hardware drivers, or financial math libraries are already built and must be verified first (using Drivers).
  8. Q18: What is Operational Acceptance Testing (OAT) vs Contract/Regulatory Acceptance Testing inside UAT?
    A: OAT validates operational readiness for DevOps/SRE (backup/restore, disaster recovery failover, log monitoring, alerting). Regulatory Acceptance Testing validates legal/government compliance (PCI-DSS for payments, HIPAA for healthcare, GDPR for data privacy).

Tier 3: Real-World Tricky & Edge-Case Scenarios (Q19–Q25)

  1. Q19: Scenario: You are testing an `OrderController` module that calls `InventoryService` and `EmailNotificationService`. `InventoryService` is ready, but `EmailNotificationService` is still being built by another team. Which test double do you create: a Stub or a Driver?
    A: A Stub for `EmailNotificationService`, because `OrderController` (parent) calls `EmailNotificationService` (child). The stub simulates the missing child module and returns a dummy `200 OK / true` so `OrderController` + `InventoryService` integration can be tested immediately.
  2. Q20: Scenario: The backend team finished building the `InterestRateCalculator` utility class, but the Loan Application Web UI won't be ready for 2 sprints. How do you test `InterestRateCalculator` now?
    A: Write a Driver (a TestNG/JUnit test class or RestAssured test harness) that acts as the calling parent module, passes boundary loan amounts/tenures into `InterestRateCalculator`, and asserts the returned interest figures (Bottom-Up approach).
  3. Q21: Scenario: During System Testing in QA, a third-party Credit Bureau API charges $2 per API call and rate-limits after 50 calls. How do you run 1,000 automated System & Integration tests without paying $2,000 or getting blocked?
    A: Replace the live third-party endpoint in the QA environment with a Service Virtualization / API Stub server (using WireMock or MockServer) configured with realistic response payloads and latency, and run only 2–3 final smoke tests against the third-party sandbox.
  4. Q22: Scenario: During UAT, the Client raises a defect saying "We need a 'Bulk Export to PDF' button on the dashboard", which was never in the SRS or Sprint backlog. Is this a System Testing bug leak or a Change Request (CR)?
    A: It is a Change Request (CR) / New Enhancement, NOT a QA Defect Leakage—because the feature was never specified in the SRS. QA triages it with the Product Owner to schedule it into a future sprint rather than blocking the current release as a QA bug.
  5. Q23: Scenario: A bug is found in Production where mobile Safari users on iOS 17 cannot tap the "Confirm" button because a cookie banner overlaps it. Which Test Level missed this bug?
    A: Level 3: System Testing (specifically Cross-Browser / Mobile Compatibility Testing inside System Testing), because Unit and API Integration tests do not render CSS layouts or viewports.
  6. Q24: Scenario: Microservice A sends a `"userId": 10452` (Long) to Microservice B, which recently changed its DTO to expect `"user_id": "USR-10452"` (String). Which Test Level should catch this fastest in CI/CD before deploying to QA?
    A: Level 2: Integration Testing—specifically Consumer-Driven Contract Testing (using tools like Pact or Spring Cloud Contract) or automated API schema tests in the PR pipeline.
  7. Q25: Scenario: Can QA engineers participate in Unit and Integration testing, or is QA strictly restricted to System Testing?
    A: In modern SDET teams, SDETs actively participate in Level 1 & 2: reviewing developer unit test coverage in PRs, writing boundary cases developers missed, and owning Level 2 Automated API Integration & Contract test suites (`RestAssured` / `Testcontainers`) alongside Level 3 Selenium/Playwright System suites.

Tier 4: SDET, Automation (Selenium / API) & CI/CD Application (Q26–Q30)

  1. Q26: What is Mike Cohn's Test Automation Pyramid and what are its exact percentages?
    A: The Test Automation Pyramid structures automated tests into 3 layers by speed and maintenance cost: 70% Unit Tests at the base (fastest, cheapest, isolated), 20% Service / API Integration Tests in the middle (RestAssured/Postman), and 10% UI End-to-End System Tests at the top (Selenium/Playwright).
  2. Q27: How do you separate Unit, Integration, and System tests in a Maven + TestNG project so CI/CD runs them in stages?
    A: Use TestNG groups (`@Test(groups = "unit")`, `@Test(groups = "integration")`, `@Test(groups = "system")`) or Maven plugins (`maven-surefire-plugin` for `*Test.java` unit tests during `mvn test`, and `maven-failsafe-plugin` for `*IT.java` integration/system tests during `mvn verify`).
  3. Q28: In a Jenkins CI/CD pipeline, in what order do the Test Levels execute and why?
    A: Stage 1: Static Analysis + Unit Tests (`< 2 mins`) → Stage 2: API Integration & Contract Tests (`< 5 mins`) → Stage 3: Deploy to QA & run Selenium Smoke + System E2E Tests (`10–20 mins`). This enforces Fail-Fast: if a 10ms Unit test fails, Jenkins aborts immediately without wasting 20 minutes spinning up Selenium Grid browsers.
  4. Q29: How do you perform true database Integration Testing in Java without polluting a shared QA database?
    A: Use Testcontainers (which spins up a disposable Docker PostgreSQL/MySQL container during `mvn verify`) or an in-memory database / transactional rollback (`@Transactional`) so every integration test starts with a clean schema and leaves zero dirty data behind.
  5. Q30: In Playwright or Selenium 4, how can you combine Integration stubbing with UI System testing for faster execution?
    A: Use network interception (`page.route()` in Playwright or Chrome DevTools Protocol `Network.interceptRequest` in Selenium 4) to stub slow/third-party backend API responses while testing the frontend UI state transitions in a real browser.

Tier 5: Rapid-Fire Yes/No & 1-Liner Traps (Q31–Q35)

  1. Q31: Is a Stub used in Bottom-Up or Top-Down Integration?
    A: Top-Down Integration (it replaces a called lower-level child module).
  2. Q32: Is a Driver passive or active?
    A: Active—it calls the module under test (used in Bottom-Up Integration).
  3. Q33: Is Beta Testing performed at the developer's premise or the end-user's premise?
    A: At the end-user's own premise/environment (Alpha is at the developer's premise).
  4. Q34: Which testing level performs both Functional and Non-Functional testing of the whole application?
    A: Level 3: System Testing.
  5. Q35: What is Sandwich Integration Testing?
    A: A hybrid integration approach combining Top-Down (using Stubs) and Bottom-Up (using Drivers) simultaneously to converge on a middle target layer.
