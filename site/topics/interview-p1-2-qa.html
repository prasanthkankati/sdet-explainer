P1.2 Question Bank: Scripting Basics, Line-by-Line Anatomy, Async/Await & Fixtures (30 Questions)

Tier 1: Core Definitions & Syntax Mechanics (Q1–Q7)

  1. What is the difference between require() and import in a Playwright test file? (common)
    require() is the older CommonJS module loading syntax native to Node.js, whereas import is the modern ECMAScript Module (ESM) standard. Both load the identical testing primitives from @playwright/test. In modern TypeScript projects, import is standard and preferred for static analysis.
  2. Why do we use object destructuring const { test, expect } when importing from @playwright/test? (common)
    The @playwright/test package exports an entire suite of utilities, fixtures, and runner hooks. Object destructuring extracts only the specific test runner and expect assertion library into local scope, keeping code concise and avoiding repetitive namespace prefixes like playwright.test().
  3. What are the two parameters accepted by the test() function? (common)
    The first parameter is a test title string (e.g., 'HomepageTitle') used to identify the test in CLI outputs, test explorers, and HTML reports. The second parameter is an asynchronous callback function (e.g., async ({ page }) => { ... }) that receives injected fixtures and executes the test steps.
  4. What is a Playwright fixture in simple terms? (common)
    A fixture is an environment helper object whose setup, lifecycle, and teardown are managed automatically by the Playwright test runner. Fixtures provide tests with isolated resources—such as a clean browser tab ({ page }) or an HTTP client ({ request })—without manual instantiation or cleanup.
  5. Why must the test callback function always be prefixed with the async keyword? (common)
    Because JavaScript runs on a non-blocking asynchronous event loop, browser operations return Promises. Marking the callback function async allows the use of the await keyword inside its body, ensuring each asynchronous action pauses until the browser completes the operation before moving to the next line.
  6. What does the page.goto() method do, and when does it finish waiting? (common)
    page.goto(url) dispatches a navigation command to the browser and returns a Promise. By default, it resolves when the page fires the load event, guaranteeing that the HTML document and its initial stylesheets and scripts have finished loading before executing subsequent commands.
  7. What is the difference between page.title() and expect(page).toHaveTitle()? (common)
    page.title() is an asynchronous query that takes a single instantaneous snapshot of the document title string at that exact millisecond. expect(page).toHaveTitle() is a web-first assertion that automatically polls and auto-retries until the title matches the expected text or the assertion timeout expires, eliminating timing race conditions.

Tier 2: Async/Await & Language Mechanics (Q8–Q14)

  1. How does the JavaScript execution model differ from Java when automating browsers? (common)
    Java executes code in a synchronous, blocking series order on operating system threads; when driver.get() is called, the thread waits. JavaScript is single-threaded and non-blocking; calls to browser APIs initiate a background task and immediately return a Promise. Without await, JavaScript does not wait and executes the next line immediately.
  2. What is a Promise in JavaScript? (common)
    A Promise is an object representing the eventual completion (or failure) of an asynchronous operation and its resulting value. A Promise exists in one of three states: pending (in progress), fulfilled (completed successfully), or rejected (failed with an error).
  3. What exact technical role does the await keyword perform? (common)
    await suspends the execution of the enclosing async function until the Promise settles. If the Promise fulfills, await unwraps and returns its resolved value; if the Promise rejects, it throws an error that can be caught by a try/catch block or reported as a test failure.
  4. Why is const used instead of let or var when declaring imported packages and extracted variables? (common)
    const creates an immutable reference, preventing accidental variable reassignment elsewhere in the test script. Using const ensures that references to test, expect, and captured snapshots (like pageTitle) cannot be overwritten or mutated accidentally.
  5. Is page.url() an asynchronous Promise in Playwright? (advanced)
    No, page.url() is a synchronous getter function that returns the current main frame's URL string immediately from the local client state without an asynchronous WebSocket roundtrip. However, asserting on the URL using await expect(page).toHaveURL() is asynchronous because it auto-retries until redirects settle.
  6. Is calling await page.close() mandatory at the end of every Playwright test? (common)
    No, it is completely optional. Playwright's test runner implements automatic fixture lifecycle management; when the test() block exits (whether passing or failing), the runner automatically disposes of the page and destroys its parent BrowserContext to prevent memory leaks.
  7. What does console.log() do in a Playwright test executed in headless mode? (common)
    It prints the specified string or object directly to the terminal's standard output (stdout) stream where the test runner was executed. It does not print to the browser DevTools console unless injected into the page context via page.evaluate().

Tier 3: Real Situations & Scenarios (Q15–Q20)

  1. You run a test where page.click('#submit') has no await keyword. What happens? (common)
    The click action returns a pending Promise, but JavaScript does not wait for the browser to click the element and immediately advances to the next line or exits the test. The test often reports as PASSED because no error was thrown, even though the click never actually happened.
  2. Why should an automated test assert on both the page title and the page URL after a login flow? (common)
    Validating both the URL and title confirms that single-page application routing (URL pushState) completed and that the correct view component successfully rendered with expected title metadata. It prevents false passes where a URL redirect succeeded but the page body failed to render.
  3. How do you run a specific test file tests/homepage.spec.ts with a visible browser window? (common)
    Execute npx playwright test tests/homepage.spec.ts --headed in your terminal. Playwright overrides the default headless configuration and opens a visible Chromium, Firefox, or WebKit browser window so you can watch execution.
  4. A page takes 3 seconds to redirect from /login to /dashboard. How do you prevent a race condition? (common)
    Use the web-first URL assertion: await expect(page).toHaveURL(/.*dashboard/);. Playwright automatically polls the browser URL every 100 milliseconds until it matches the expected regex pattern or reaches the timeout, eliminating the need for hardcoded sleeps.
  5. How can you pass custom navigation options to page.goto() for a slow legacy web application? (advanced)
    You can pass an options object as the second argument: await page.goto('https://example.com', { waitUntil: 'networkidle', timeout: 60000 });. This instructs Playwright to wait until there are no network connections for at least 500ms and extends the navigation timeout to 60 seconds.
  6. How do you capture console output from the browser's developer console during a test? (advanced)
    Attach an event listener to the page fixture before navigating: page.on('console', msg => console.log('BROWSER LOG:', msg.text()));. Playwright streams all browser console.log, console.error, and warning messages directly over the WebSocket to your terminal.

Tier 4: Troubleshooting & Debugging (Q21–Q25)

  1. You encounter ReferenceError: require is not defined when running a test. What is the cause and fix? (advanced)
    Your project is configured as an ES Module (having "type": "module" in package.json or running in an ESM environment), which disables CommonJS require(). To fix it, switch the import statement to ES Module syntax: import { test, expect } from '@playwright/test';.
  2. An assertion fails with Timed out 5000ms waiting for expect(locator).toHaveTitle('STORE'). What should you check? (common)
    Check the terminal failure diff, which displays the exact actual title received versus the expected string (e.g., casing differences, leading spaces, or dynamic suffixes). Alternatively, the page may have encountered an error or redirect loop that prevented the title from updating.
  3. Why does expect(await page.title()).toBe('STORE') sometimes fail intermittently while await expect(page).toHaveTitle('STORE') passes reliably? (advanced)
    Because await page.title() evaluates the title at a single point in time; if a client-side JavaScript router updates the title 50ms later, the static check fails immediately. await expect(page).toHaveTitle() auto-retries continuously until the title matches, handling asynchronous DOM updates seamlessly.
  4. How do you debug a single test step-by-step to inspect what the { page } fixture sees? (common)
    Execute the test with the debug flag: npx playwright test tests/homepage.spec.ts --debug. This launches the Playwright Inspector, pauses execution at the first line, highlights targeted DOM elements, and lets you step through actions one by one.
  5. You see an error: TypeError: page.goto is not a function. What did you write incorrectly? (common)
    You forgot the curly braces when destructuring the fixture in the test signature, writing async (page) => instead of async ({ page }) =>. In Playwright, the test function receives a single context object containing fixtures; without braces, page refers to the entire test context object rather than the Page instance.

Tier 5: Design Choices & Best Practices (Q26–Q30)

  1. Why should production test suites avoid printing page titles and URLs with console.log()? (common)
    Manual console.log() statements create noisy, unparseable terminal output and do not validate test correctness. Web-first assertions (await expect(page).toHaveTitle()) validate state automatically and log rich, formatted diffs directly into HTML test reports only when failures occur.
  2. Why does Playwright prefer passing { page } as a fixture rather than instantiating a global page variable? (advanced)
    Global page variables share state across tests, causing concurrency collisions when running parallel worker processes. Dependency injection via { page } ensures that every test receives a dedicated, thread-safe, isolated page instance that cannot be corrupted by other tests running concurrently.
  3. When should you use regular expressions in toHaveTitle() and toHaveURL() assertions? (common)
    Use regex (e.g., await expect(page).toHaveURL(/.*index\.html/);) when URLs contain dynamic query parameters, session IDs, or varying domain environments (like staging vs production). This makes assertions robust against environmental variations without hardcoding absolute URLs.
  4. Why is await page.close() occasionally placed inside a test.afterEach() hook if it is optional? (advanced)
    In custom enterprise frameworks, engineers sometimes close pages explicitly to trigger custom cleanup telemetry, clear temporary indexedDB data, or disconnect specific network listeners before the runner tears down the entire BrowserContext.
  5. How does the Playwright test runner guarantee test independence? (advanced)
    By strictly executing each test inside a fresh BrowserContext created from scratch. Even if an earlier test modified cookies, stored credentials in localStorage, or changed session state, subsequent tests start with a completely empty, unpolluted browser context.
