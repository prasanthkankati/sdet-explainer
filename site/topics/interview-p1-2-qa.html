P1.2 Question Bank: Test Runner Engine, Fixtures Architecture, Page Anatomy & Async/Await (30 Questions)

Tier 1: Core Definitions & Syntax Mechanics (Q1–Q7)

  1. Why do we import test from @playwright/test and what does it actually represent? (common)
    test is the central Test Runner Engine, Suite Orchestrator, and Dependency Injection container in Playwright. We import it to register test cases with Playwright's worker scheduling engine. It manages the entire test lifecycle—including worker process allocation, declarative fixture injection, lifecycle hooks (beforeEach/afterEach), granular step reporting (test.step), retries, failure artifact capture, and test timeouts.
  2. What is the difference between require() and import in a Playwright test file? (common)
    require() is the CommonJS module loading syntax native to Node.js, whereas import is the modern ECMAScript Module (ESM) standard. Both load the identical testing primitives from @playwright/test. In modern TypeScript projects, import is standard and preferred for static type checking.
  3. Why do we use object destructuring const { test, expect } when importing from @playwright/test? (common)
    The @playwright/test package exports an entire suite of utilities, fixtures, and runner hooks. Object destructuring extracts only the specific test runner and expect assertion library into local scope, keeping code concise and avoiding repetitive namespace prefixes like playwright.test().
  4. What is a Playwright fixture in simple SDET terms? (common)
    A fixture is an isolated, reusable piece of environment setup and teardown that a test needs to run reliably. Fixtures provide tests with isolated resources—such as a clean browser tab ({ page }), an incognito session ({ context }), or an HTTP client ({ request })—without requiring manual instantiation, thread-local wrappers, or explicit teardown code.
  5. What is page in Playwright and what does it represent? (common)
    page is a built-in test-scoped fixture representing a single active browser tab or window running inside a completely fresh, isolated BrowserContext. It provides the primary API for DOM interaction, navigation (page.goto), locator querying, dialog handling, and event listening.
  6. Why must the test callback function always be prefixed with the async keyword? (common)
    Because JavaScript runs on a non-blocking asynchronous event loop, browser operations return Promises. Marking the callback function async allows the use of the await keyword inside its body, ensuring each asynchronous action pauses until the browser completes the operation before moving to the next line.
  7. What is the difference between page.title() and expect(page).toHaveTitle()? (common)
    page.title() is an asynchronous query that takes a single instantaneous snapshot of the document title string at that exact millisecond. expect(page).toHaveTitle() is a web-first assertion that automatically polls and auto-retries until the title matches the expected text or the assertion timeout expires, eliminating timing race conditions.

Tier 2: Architectural Mechanics & Fixtures Deep Dive (Q8–Q14)

  1. Explain Playwright's Tri-Layer Architecture: Browser vs BrowserContext vs Page. (advanced)
    A Browser is a heavyweight OS executable process (Chromium/Firefox/WebKit) launched once per worker thread. A BrowserContext is an isolated in-memory incognito session created in ~1ms with its own private cookies, storage, and cache. A Page is a single tab running inside that context. This separation allows hundreds of tests to run in isolated contexts without the overhead of launching separate browser processes.
  2. How does Playwright's fixture system differ from TestNG's BaseTest inheritance model? (advanced)
    TestNG relies on monolithic class inheritance (extends BaseTest) and rigid @BeforeMethod hooks that force every test to instantiate a browser regardless of need, relying on fragile ThreadLocal<WebDriver> to prevent concurrency bugs. Playwright uses Declarative Dependency Injection: tests request only the fixtures they need as arguments, setup and teardown are co-located via the use() callback, and resources are created on demand with zero state leakage.
  3. What is the role of the use() function inside a Playwright fixture? (advanced)
    The use() callback represents the boundary between fixture setup and teardown. Everything written before await use(resource) executes during the setup phase before the test runs. The use() call transfers the resource to the test body and suspends fixture execution until the test completes. Everything written after await use(resource) executes during the teardown phase (guaranteed to run even on test failure).
  4. What are all the built-in test-scoped fixtures provided by Playwright? (common)
    Playwright provides three primary test-scoped fixtures (created fresh per test): (1) page (single browser tab), (2) context (isolated browser context for multi-tab, permissions, cookies, network routing), and (3) request (isolated APIRequestContext for headless REST/GraphQL API automation).
  5. What are Playwright's built-in worker-scoped fixtures? (advanced)
    Worker-scoped fixtures are instantiated once per worker process and shared across all tests executed by that worker: (1) browser (the launched browser executable), (2) browserName (string: 'chromium', 'firefox', or 'webkit'), (3) browserType (the programmatic launcher), and (4) playwright (root library namespace).
  6. What is the { request } fixture and when should an SDET use it? (common)
    request is a built-in API client fixture that sends HTTP requests directly without launching a browser UI. SDETs use it for fast REST/GraphQL API testing, pre-test database seeding, bypassing UI login forms by calling authentication endpoints directly, or validating backend microservice state.
  7. How does the JavaScript execution model differ from Java when automating browsers? (common)
    Java executes code in a synchronous, blocking series order on operating system threads; when driver.get() is called, the thread blocks and waits. JavaScript runs on a single-threaded non-blocking event loop; browser calls return Promises immediately. Without await, JavaScript fires subsequent commands before previous browser operations finish.

Tier 3: Real Situations & Custom SDET Fixtures (Q15–Q20)

  1. How do SDETs implement Page Object Model (POM) using Playwright fixtures instead of new PageObject(page)? (advanced)
    By using test.extend<Fixtures>(). We extend the base test runner with custom fixtures for each page (e.g., loginPage: async ({ page }, use) => { await use(new LoginPage(page)); }). Test specs simply declare async ({ loginPage, cartPage }) => {} in their parameters, eliminating manual object instantiations across the entire framework.
  2. You run a test where page.click('#submit') has no await keyword. What happens? (common)
    The click action returns a pending Promise, but JavaScript does not wait for the browser to click the element and immediately advances to the next line or exits the test. The test often reports as PASSED because no error was thrown, even though the click never actually happened.
  3. Why should an automated test assert on both the page title and the page URL after a login flow? (common)
    Validating both the URL and title confirms that single-page application routing (URL pushState) completed and that the correct view component successfully rendered with expected title metadata. It prevents false passes where a URL redirect succeeded but the page body failed to render.
  4. How do you test a multi-tab or popup workflow where clicking a button opens a second tab? (advanced)
    Use the { context } fixture instead of relying purely on page. Await the popup event concurrently with the trigger: const [newPage] = await Promise.all([context.waitForEvent('page'), page.click('#open-tab')]);. This binds the new tab to an explicit newPage handle without flaky window switching index handles.
  5. How can you pass custom navigation options to page.goto() for a slow legacy web application? (advanced)
    Pass an options object as the second argument: await page.goto('https://example.com', { waitUntil: 'networkidle', timeout: 60000 });. This instructs Playwright to wait until there are no network connections for at least 500ms and extends the navigation timeout to 60 seconds.
  6. How do you capture console output from the browser's developer console during a test? (advanced)
    Attach an event listener to the page fixture before navigating: page.on('console', msg => console.log('BROWSER LOG:', msg.text()));. Playwright streams all browser console.log, console.error, and warning messages directly over the WebSocket to your terminal.

Tier 4: Troubleshooting & Debugging (Q21–Q25)

  1. You encounter ReferenceError: require is not defined when running a test. What is the cause and fix? (advanced)
    Your project is configured as an ES Module (having "type": "module" in package.json or running in an ESM environment), which disables CommonJS require(). To fix it, switch the import statement to ES Module syntax: import { test, expect } from '@playwright/test';.
  2. You see an error: TypeError: page.goto is not a function. What did you write incorrectly? (common)
    You forgot the curly braces when destructuring the fixture in the test signature, writing async (page) => instead of async ({ page }) =>. In Playwright, the test function receives a single context object containing fixtures; without braces, page refers to the entire test context object rather than the Page instance.
  3. An assertion fails with Timed out 5000ms waiting for expect(locator).toHaveTitle('STORE'). What should you check? (common)
    Check the terminal failure diff, which displays the exact actual title received versus the expected string (e.g., casing differences, leading spaces, or dynamic suffixes). Alternatively, the page may have encountered an error or redirect loop that prevented the title from updating.
  4. Why does expect(await page.title()).toBe('STORE') sometimes fail intermittently while await expect(page).toHaveTitle('STORE') passes reliably? (advanced)
    Because await page.title() evaluates the title at a single point in time; if a client-side JavaScript router updates the title 50ms later, the static check fails immediately. await expect(page).toHaveTitle() auto-retries continuously until the title matches, handling asynchronous DOM updates seamlessly.
  5. How do you debug a single test step-by-step to inspect what the { page } fixture sees? (common)
    Execute the test with the debug flag: npx playwright test tests/homepage.spec.ts --debug. This launches the Playwright Inspector, pauses execution at the first line, highlights targeted DOM elements, and lets you step through actions one by one.

Tier 5: Design Choices & Best Practices (Q26–Q30)

  1. How do authentication fixtures dramatically speed up large test suites compared to UI login per test? (advanced)
    Traditional UI tests log in through input fields on every test (taking 3-5 seconds per test). With Playwright authentication fixtures, we log in once via API or UI during global setup, save the session state to a JSON file (storageState.json), and inject that state into every test's BrowserContext in 1 millisecond.
  2. Why does Playwright prefer passing { page } as a fixture rather than instantiating a global page variable? (advanced)
    Global page variables share state across tests, causing concurrency collisions when running parallel worker processes. Dependency injection via { page } ensures that every test receives a dedicated, thread-safe, isolated page instance that cannot be corrupted by other tests running concurrently.
  3. When should an SDET write a custom fixture with worker scope instead of test scope? (advanced)
    Use worker scope when an expensive resource can be safely shared across multiple tests on the same thread without state pollution—such as an SSH tunnel, a Docker container connection, an administrative OAuth token generator, or a read-only database connection pool.
  4. Is calling await page.close() mandatory at the end of every Playwright test? (common)
    No, it is completely optional. Playwright's test runner implements automatic fixture lifecycle management; when the test() block exits (whether passing or failing), the runner automatically disposes of the page and destroys its parent BrowserContext to prevent memory leaks.
  5. How does the Playwright test runner guarantee 100% test independence and zero state bleeding? (advanced)
    By strictly executing each test inside a fresh BrowserContext created from scratch. Even if an earlier test modified cookies, stored credentials in localStorage, or changed session state, subsequent tests start with a completely empty, unpolluted browser context.
