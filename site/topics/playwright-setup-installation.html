Playwright

1.1 Setup for Playwright Testing (Node.js, npm init, Config & First Test)

Complete end-to-end installation walkthrough: Node.js engine verification, scaffolding via npm init playwright@latest, complete playwright.config.ts architecture, dedicated browser engine binaries, your first TypeScript test spec, CLI execution, interactive UI Mode, and CI/CD configuration.

Playwright by Microsoft is an enterprise-grade test automation library designed for modern web applications. Unlike traditional HTTP-polling WebDriver implementations, Playwright operates over a persistent, bi-directional WebSocket connection using the Chrome DevTools Protocol (CDP) for Chromium and equivalent internal debugging protocols for Firefox and WebKit. It ships with out-of-the-box auto-waiting, parallel isolated browser contexts, built-in network interception, web-first auto-retrying assertions, and a dedicated test runner (@playwright/test).

1. Real-Time Playwright Enterprise Framework Architecture

In modern enterprise test automation, Playwright with TypeScript is structured to cleanly separate test configuration, page models, test specs, custom fixtures, test data, and CI/CD pipelines:

playwright-e2e-framework/
├── package.json                         # Project dependencies, scripts (test, test:ui, report)
├── tsconfig.json                        # TypeScript compiler options (target, module, paths)
├── playwright.config.ts                 # 📍 Core runner control plane (workers, projects, retries, reporter)
├── .github/
│   └── workflows/
│       └── playwright.yml               # Automated CI workflow on push / PR
├── tests/
│   ├── auth/
│   │   └── login.spec.ts                # 📍 Chapter 1.1: Functional login spec with assertions
│   ├── checkout/
│   │   └── order-placement.spec.ts      # Multi-step checkout flow
│   └── api/
│       └── user-service.spec.ts         # Direct APIRequestContext integration tests
├── pages/
│   ├── base.page.ts                     # Common page actions, URL verification
│   └── login.page.ts                    # Page Object Model with Locator members
├── fixtures/
│   └── test-fixtures.ts                 # Custom test.extend() for dependency injection
├── test-data/
│   └── staging-users.json               # Environment-specific test payloads
└── playwright-report/                   # Auto-generated interactive HTML report with traces

How execution flows through this structure:

  1. CLI / CI Invocation: Developer or CI executes npx playwright test.
  2. Control Plane (playwright.config.ts): Playwright loads projects (Chromium, Firefox, WebKit), spins up worker processes based on CPU cores, and applies global timeout and reporter settings.
  3. Browser & Context Allocation: Each worker launches a single browser process and creates an isolated, zero-overhead BrowserContext (incognito session) per test method.
  4. Test Payload Execution (tests/): Tests execute asynchronously using TypeScript async/await, interacting with web elements via auto-waiting Locator objects.
  5. Failure Interception & Trace Capture: If an assertion fails, Playwright's trace recorder captures DOM snapshots, action logs, network waterfalls, and console outputs for time-travel debugging.
  6. Report Generation: The runner writes results to playwright-report/index.html and exits with code 0 (success) or 1 (failure).

2. System Prerequisites & Node.js Verification

Playwright requires Node.js LTS (Long Term Support) version 18.x or 20.x or higher. Verify your local environment before scaffolding:

# Check Node.js runtime version (must be >= 18.0.0)
node -v
# Example output: v20.18.0

# Check npm package manager version
npm -v
# Example output: 10.8.2

If Node.js is not installed, install it via the official installer (nodejs.org), nvm (macOS/Linux), or nvm-windows / winget install OpenJS.NodeJS.LTS (Windows).

4. Deep Anatomy of playwright.config.ts

The playwright.config.ts file is the master configuration file governing concurrency, timeouts, reporters, cross-browser projects, and artifact recording. Below is a production-grade enterprise configuration with explanatory comments:

import { defineConfig, devices } from "@playwright/test";

export default defineConfig({
  // Directory where test spec files are discovered
  testDir: "./tests",

  // Global test timeout per single test (30 seconds)
  timeout: 30 * 1000,

  // Assertion expect() auto-retry timeout (5 seconds)
  expect: {
    timeout: 5000,
  },

  // Run all tests in all spec files in parallel
  fullyParallel: true,

  // Fail the build on CI if test.only is accidentally committed
  forbidOnly: !!process.env.CI,

  // Retry failed tests on CI to handle environmental network flakiness
  retries: process.env.CI ? 2 : 0,

  // Parallel worker processes: 1 on CI (predictable resources), undefined locally (auto-scales to CPU cores)
  workers: process.env.CI ? 1 : undefined,

  // Test reporters: Terminal list output + Full HTML artifact report
  reporter: [
    ["list"],
    ["html", { open: "never", outputFolder: "playwright-report" }]
  ],

  // Shared configuration options across all browser projects
  use: {
    // Base application URL used for relative navigations like page.goto('/login')
    baseURL: process.env.BASE_URL || "https://practicetestautomation.com",

    // Record trace on first retry for time-travel debugging
    trace: "on-first-retry",

    // Capture screenshot only when a test fails
    screenshot: "only-on-failure",

    // Record video only for failing tests to save disk space
    video: "retain-on-failure",

    // Run tests in headless mode (no visual UI)
    headless: true,

    // Browser viewport dimensions
    viewport: { width: 1280, height: 720 },

    // Ignore HTTPS certificate errors in staging / test environments
    ignoreHTTPSErrors: true,
  },

  // Matrix of target browser projects
  projects: [
    {
      name: "chromium",
      use: { ...devices["Desktop Chrome"] },
    },
    {
      name: "firefox",
      use: { ...devices["Desktop Firefox"] },
    },
    {
      name: "webkit",
      use: { ...devices["Desktop Safari"] },
    },
    // Optional Mobile Viewport Emulation
    {
      name: "Mobile Chrome",
      use: { ...devices["Pixel 7"] },
    },
  ],
});

5. Dedicated Browser Binaries vs System Browsers

Unlike Selenium, which searches for and launches your locally installed Google Chrome or Mozilla Firefox, Playwright downloads and manages custom, reproducible open-source browser builds (Chromium, Firefox, and WebKit). This guarantees deterministic behavior across development workstations and CI servers.

# Manually install all 3 browser binaries (Chromium, Firefox, WebKit)
npx playwright install

# Install only Chromium to save disk space and network bandwidth
npx playwright install chromium

# Install browsers AND missing OS system dependencies (mandatory on Linux / Docker / CI)
npx playwright install --with-deps

Where Playwright caches browser binaries on your machine:

  • Windows: %USERPROFILE%\AppData\Local\ms-playwright
  • macOS: ~/Library/Caches/ms-playwright
  • Linux: ~/.cache/ms-playwright

Because browser binaries are cached in the user's home directory rather than node_modules, multiple Playwright projects on the same machine share the same browser binaries without redundant downloads.

6. Writing Your First Playwright Test Spec

Create a test spec file at tests/auth-login.spec.ts. Playwright tests import test and expect directly from @playwright/test:

import { test, expect } from "@playwright/test";

test.describe("Authentication - Customer Portal", () => {

  test.beforeEach(async ({ page }) => {
    // Navigates using baseURL configured in playwright.config.ts
    await page.goto("/practice-test-login/");
  });

  test("should successfully log in with valid credentials", async ({ page }) => {
    // 1. Verify page title with web-first auto-retrying assertion
    await expect(page).toHaveTitle(/Test Login/);

    // 2. Locate elements using resilient user-facing locators
    const usernameInput = page.getByLabel("Username");
    const passwordInput = page.getByLabel("Password");
    const submitButton  = page.getByRole("button", { name: "Submit" });

    // 3. Fill in credentials (Playwright automatically waits for visibility and readiness)
    await usernameInput.fill("student");
    await passwordInput.fill("Password123");

    // 4. Click Submit
    await submitButton.click();

    // 5. Validate successful URL redirection
    await expect(page).toHaveURL(/.*logged-in-successfully/);

    // 6. Validate success message is visible and contains expected text
    const successBanner = page.locator(".post-title");
    await expect(successBanner).toBeVisible();
    await expect(successBanner).toContainText("Logged In Successfully");

    // 7. Verify Log Out button is now accessible
    const logoutBtn = page.getByRole("link", { name: "Log out" });
    await expect(logoutBtn).toBeVisible();
  });

  test("should display error message on invalid password", async ({ page }) => {
    await page.getByLabel("Username").fill("student");
    await page.getByLabel("Password").fill("IncorrectPassword");
    await page.getByRole("button", { name: "Submit" }).click();

    const errorMessage = page.locator("#error");
    await expect(errorMessage).toBeVisible();
    await expect(errorMessage).toHaveText("Your password is invalid!");
  });

});

7. Test Execution Modes & CLI Commands

Playwright provides several execution modes tailored for developer feedback loops, debugging, and headless CI runs:

# 1. Run all tests across all configured projects in headless mode
npx playwright test

# 2. Run tests on a single browser project (e.g., Chromium only)
npx playwright test --project=chromium

# 3. Run a specific test spec file
npx playwright test tests/auth-login.spec.ts

# 4. Run tests with visible browser window (Headed Mode)
npx playwright test --headed

# 5. Launch interactive UI Mode (Time-travel, locator playground, live watch)
npx playwright test --ui

# 6. Launch Playwright Inspector for step-by-step interactive debugging
npx playwright test --debug

# 7. Open the generated HTML test report in browser
npx playwright show-report

Interactive UI Mode (--ui): The killer feature of Playwright. It gives developers a graphical runner with instant watch mode, time-travel DOM snapshots before and after every click, network request inspection, and live locator testing without rerunning tests from scratch.

9. Critical Traps & Anti-Patterns in Playwright Setup

  1. Forgetting the await keyword:
    All Playwright actions (page.click(), page.fill()) and web-first assertions (expect(locator).toBeVisible()) return asynchronous Promises. Omitting await causes the test to finish before actions execute, leading to silent race conditions or unhandled promise rejections.
  2. Using page.waitForTimeout(5000):
    Hardcoded sleeps are an anti-pattern. Playwright features built-in auto-waiting for actionability (visible, stable, enabled) and auto-retrying assertions (expect(locator).toBeVisible()). Hardcoded timeouts slow down suites and cause arbitrary CI flakiness.
  3. Mixing Jest or Mocha Assertions with Playwright:
    Never use expect(await locator.isVisible()).toBe(true). That evaluates a one-time snapshot without retrying. Always use Playwright's web-first assertion: await expect(locator).toBeVisible(), which automatically polls until the timeout expires.
  4. Missing --with-deps on Linux CI / Docker:
    Running npx playwright install on Ubuntu/Debian installs browser binaries but leaves out OS shared libraries (like font rendering or audio libs), causing headless Chromium to crash on startup. Always run npx playwright install --with-deps in CI environments.

10. Interview Q&A: Playwright Setup & Architecture

  1. How does Playwright's connection architecture differ from Selenium WebDriver?
    Selenium WebDriver communicates via HTTP requests over the W3C WebDriver specification, sending individual stateless POST/GET requests for each browser action and polling for state changes. Playwright establishes a single, persistent, bi-directional WebSocket connection via Chrome DevTools Protocol (CDP) or native browser pipes, allowing real-time event streaming and sub-millisecond execution speeds.
  2. What is the difference between a Browser, BrowserContext, and Page in Playwright?
    A Browser is the single operating system process (e.g., chromium.exe). A BrowserContext is an isolated incognito session created inside the browser with its own cookies, localStorage, and cache. Creating a context takes ~5-10ms with virtually zero memory overhead. A Page is a single browser tab inside a context. In Playwright, tests share browser processes but run in completely isolated contexts for 100% test independence and blazing-fast parallelism.
  3. Why does Playwright download its own browser binaries instead of using Google Chrome?
    To ensure 100% deterministic, reproducible test results across developer workstations and CI servers. Locally installed browsers receive automatic updates that can introduce unexpected regressions or driver mismatches. Playwright pins each library release to exact patched browser revisions built and tested against that version.
  4. What is the role of fullyParallel: true in playwright.config.ts?
    By default, Playwright runs tests inside a single spec file sequentially. Setting fullyParallel: true instructs the runner to execute all tests across all files concurrently across available worker processes, dramatically reducing total suite execution time.
