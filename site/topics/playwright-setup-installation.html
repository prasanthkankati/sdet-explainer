Playwright

1.1 Playwright Introduction, Key Features, TS vs JS & Setup

1. What is Playwright?

Playwright is an open-source test automation framework developed by Microsoft (released in 2020) for end-to-end web testing and browser automation across modern single-page applications and micro-frontends.

Interview Answer: "Playwright Test is an end-to-end test framework for modern web apps created by Microsoft. It bundles a test runner, auto-waiting assertions, isolated browser contexts, parallelization, and rich tooling. It natively supports Chromium, WebKit, and Firefox across Windows, Linux, and macOS in both headless and headed modes, with built-in mobile emulation for Chrome (Android) and Mobile Safari."

Core Architectural Pillars:

  • Runtime Foundation: Built on Node.js (Google V8 JavaScript runtime), executing automation code outside the browser while communicating over high-speed native debugging pipes.
  • Connection Protocol: Communicates over a persistent, bi-directional WebSocket connection (using Chrome DevTools Protocol / CDP for Chromium and native internal socket protocols for Firefox and WebKit) rather than stateless HTTP roundtrips.
  • Unified Scope: Supports complete end-to-end browser automation alongside a dedicated APIRequestContext client to test backend REST APIs and seed test data without third-party HTTP libraries.

2. Key Features of Playwright (Deep Explanation)

Playwright addresses the historical pain points of UI automation through 9 foundational capabilities:

FeatureHow It Works TechnicallyWhy It Matters to QA / SDET
1. Cross-Browser Support Directly automates Chromium (Google Chrome, Microsoft Edge), Firefox (Gecko), and WebKit (Apple Safari) using exact rendering engine builds. Ensures true cross-browser compatibility across all major browser engines without installing separate vendor drivers (e.g., no ChromeDriver or GeckoDriver management).
2. Cross-Platform Runs identically on Windows, macOS, and Linux operating systems, as well as containerized Docker environments and Windows Subsystem for Linux (WSL). Enables seamless test portability between local developer machines (macOS/Windows) and continuous integration runners (Ubuntu Linux).
3. Multi-Language Support The Playwright core protocol exposes official SDK language bindings for TypeScript, JavaScript, Python, Java, and C# (.NET). Teams can adopt Playwright using their existing enterprise language stack without forcing an organization-wide migration.
4. Mobile Web Testing Emulates mobile screen viewports, device scale factors, user-agent headers, geolocation, and touch gestures for Chrome for Android and Mobile Safari (iOS). Validates responsive mobile web applications directly on desktop hardware without requiring expensive third-party device clouds or local Appium servers.
5. API Testing Provides a built-in APIRequestContext accessible directly inside tests via the { request } fixture. Enables fast test setup (generating auth tokens via API, seeding database records) and teardown, drastically reducing end-to-end execution time.
6. Auto-Waiting Before executing any action (e.g., click(), fill()), Playwright performs automatic actionability checks: attached to DOM, visible, stable (not animating), enabled, and non-obscured. Eliminates arbitrary Thread.sleep() and manual wait polling, removing 95%+ of typical test flakiness.
7. Handles Complex Elements Playwright locators naturally penetrate and pierce open Shadow DOM subtrees without requiring custom JavaScript executors, and seamlessly traverses nested <iframe> elements via frameLocator(). Simplifies automation of modern web components and embedded third-party widgets (e.g., payment gateways) that traditionally break Selenium locators.
8. Parallel Execution Leverages isolated OS worker processes and lightweight BrowserContext instances (creating a clean incognito session in ~5–10ms with zero memory bloat). Executes hundreds of test specs simultaneously across multi-core processors, turning hour-long regression suites into 3-minute runs.
9. Built-in & Third-Party Reporting Natively outputs HTML, JSON, and JUnit XML formats, and easily integrates with enterprise visual reporters like Allure. Provides actionable test results with embedded screenshots, videos, and time-travel execution traces ready for CI/CD dashboards.

4. JavaScript vs. TypeScript in Test Automation

Playwright supports both JavaScript and TypeScript out of the box with zero build configuration. Understanding the architectural differences is critical when architecting an enterprise test suite:

1. JavaScript (Dynamically Typed)

In JavaScript, variable types are resolved dynamically at runtime. Variables can change types at any point, and the interpreter enforces no strict type checking during authoring:

let age = 30;       // Number
let name = "John";  // String
age = "thirty";     // Valid in JS — variable mutated from Number to String without error

Automation Risk: A typo in a method call or an invalid locator payload will only be caught when the test actually runs and fails in the browser, wasting significant developer and CI debugging time.

2. TypeScript (Statically Typed)

TypeScript is an open-source language developed by Microsoft as a strict syntactical superset of JavaScript. It adds optional static typing, compile-time contract validation, and rich IDE tooling:

let age: number = 30; // Strictly typed as number
let name: string = "John";
age = "thirty";       // COMPILE ERROR: Type 'string' is not assignable to type 'number'

3. Why Use TypeScript for Playwright?

  • ECMAScript Standard: TypeScript compiles cleanly down to standard ECMAScript (JavaScript) that executes in any standard Node.js runtime.
  • Catches Errors Early: Syntax errors, missing parameters, and wrong assertion signatures are caught immediately inside VS Code before launching expensive browser sessions.
  • Superior IDE Autocompletion (IntelliSense): Typing page. or expect(locator). instantly displays every available method, parameter signature, and documentation snippet.
  • Refactoring Confidence: When renaming a Page Object property or updating a test data interface, TypeScript automatically identifies all broken references across the entire repository.

5. Installing Playwright & Project Scaffolding

Scaffold a brand-new Playwright automation repository using your preferred package manager:

# Recommended: Initialize via npm
npm init playwright@latest

# Alternative package managers
yarn create playwright
pnpm create playwright

Interactive CLI Setup Choices:

  • TypeScript or JavaScript: Choose TypeScript (default and industry best practice).
  • Where to put end-to-end tests: tests (standard convention).
  • Add a GitHub Actions workflow: Choose Yes to auto-generate CI/CD configuration.
  • Install Playwright browsers: Choose Yes (downloads Chromium, Firefox, WebKit binaries).

7. Writing Your First Playwright Test Spec

Examine the generated tests/example.spec.ts. It demonstrates Playwright's core mental model:

import { test, expect } from "@playwright/test";

test("has title", async ({ page }) => {
  await page.goto("https://playwright.dev/");

  // Expect a title "to contain" a substring.
  await expect(page).toHaveTitle(/Playwright/);
});

test("get started link", async ({ page }) => {
  await page.goto("https://playwright.dev/");

  // Click the get started link.
  await page.getByRole("link", { name: "Get started" }).click();

  // Expects page to have a heading with the name of Installation.
  await expect(page.getByRole("heading", { name: "Installation" })).toBeVisible();
});

Key architectural primitives:

  • { page } Fixture: Playwright automatically creates an isolated browser page in a brand-new BrowserContext for each test. No manual browser opening or closing needed.
  • Auto-Waiting: click() automatically waits for the element to be visible, stable, enabled, and clickable before firing the event.
  • Web-First Assertions: await expect(locator).toBeVisible() continuously retries until the element appears or the timeout expires.

8. Running Your Tests & CLI Commands

Execute tests from your terminal using Playwright's versatile runner flags:

# Run all tests across all configured projects (Chromium, Firefox, WebKit) in headless mode
npx playwright test

# Run tests with visible browser windows (Headed Mode)
npx playwright test --headed

# Run tests on a specific browser project only
npx playwright test --project=chromium

# Run a single specific test file
npx playwright test tests/example.spec.ts

# Run tests that match a specific title or regex
npx playwright test -g "has title"

# Launch interactive UI Mode (time-travel debugging, watch mode, locator playground)
npx playwright test --ui

# Open the auto-generated HTML test report
npx playwright show-report

9. Installing & Managing Dedicated Browser Binaries

Playwright uses custom patched browser builds matching exact library versions. Manage browser binaries via the CLI:

# Install all default browser binaries (Chromium, Firefox, WebKit)
npx playwright install

# Install a single browser engine
npx playwright install chromium

# Install browsers AND missing OS system dependencies (essential for Linux CI / Docker)
npx playwright install --with-deps

Local Browser Cache Locations:

  • Windows: %USERPROFILE%\AppData\Local\ms-playwright
  • macOS: ~/Library/Caches/ms-playwright
  • Linux: ~/.cache/ms-playwright

10. Updating Playwright

To upgrade Playwright to the latest release and download matching browser binaries:

# Update @playwright/test to latest version
npm install -D @playwright/test@latest

# Download matching new browser binaries and dependencies
npx playwright install --with-deps
