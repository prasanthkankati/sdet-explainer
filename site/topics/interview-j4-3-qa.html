J4.3 Question Bank: Access Modifiers & Encapsulation (21 Questions)

Tier 1: Core Definitions, Classification & Theory (Q1–Q3)

  1. List Java's four access modifiers in order from most restrictive to least restrictive.
    From tightest to widest visibility: private (same class only), package-private / default (same class and same package), protected (same package plus subclasses in external packages), and public (accessible everywhere). Choosing the narrowest visibility that compiles keeps coupling minimal.
  2. What is Encapsulation in Java and why does it matter in test automation?
    Encapsulation wraps state (fields) and behavior (methods) inside a single class while restricting direct external access to internal representation via private fields. In Selenium Page Objects, hiding private final By locators ensures test classes call public business methods like addProductToCart() rather than directly referencing fragile CSS/XPath selectors. When UI markup changes, only the Page Object changes.
  3. Can a top-level Java class be marked private or protected?
    No. Top-level classes and interfaces can only be public or package-private (no modifier). Only nested member classes, fields, constructors, and methods support private and protected.

Tier 2: How It Works & Internal Mechanics (Q4–Q6)

  1. How does protected behave across packages when a subclass holds a reference to a parent object?
    Inside a subclass in package B extending parent class BasePage in package A, the subclass can access protected members inherited on this or on another instance of the subclass itself. However, the subclass in package B cannot create a raw new BasePage() parent reference and access its protected members directly—cross-package protected access works strictly through inheritance.
  2. Are sub-packages like com.qkart.tests.login considered part of com.qkart.tests for default/package-private access?
    No. In Java, packages have a flat visibility boundary regardless of folder nesting. com.qkart.tests and com.qkart.tests.login are treated as completely separate packages with zero package-private sharing between them.
  3. Does encapsulation still allow mutating an object's internal state if a getter returns a mutable List?
    Returning a raw reference to a mutable private List or array breaks encapsulation because external callers can invoke page.getItems().clear() and mutate internal state silently. Return an unmodifiable copy using List.copyOf(items) or Collections.unmodifiableList(items) to protect internal state.

Tier 3: Real-World SDET & Selenium Scenarios (Q7–Q9)

  1. In an enterprise Selenium framework, which modifier should be used for BasePage.driver, By locators, and PageObject action methods?
    Declare By locators as private final inside each specific Page Object so neither tests nor other pages depend on them. Declare shared wait/click helpers and driver on BasePage as protected so child Page Objects across packages reuse them while @Test classes cannot call raw Selenium primitives. Mark business workflow methods like checkout() as public.
  2. How does Encapsulation protect test data POJOs used in API testing?
    Marking fields private inside an API request POJO lets setter or builder methods validate constraints—including rejecting negative quantities or malformed emails—before serializing JSON to the API endpoint.
  3. Why does TestNG require @Test methods and constructors to be public (or package-visible in matching packages) in typical CI suites?
    TestNG scans classes from outside your test package using reflection, and @Test methods represent entry points invoked by the external runner. Keeping @Test methods public guarantees TestNG discovers and runs them reliably.

Tier 4: Troubleshooting, Exceptions & Failure Modes (Q10–Q12)

  1. Why did moving WaitHelper from package pages into utils break compilation on package-private helper methods?
    Methods written without an access modifier default to package-private visibility, so relocating callers into a separate package immediately cuts off visibility with 'method is not public in WaitHelper; cannot be accessed from outside package'. Explicitly add public for cross-package utilities.
  2. Why does overriding a parent method with narrower visibility like changing public void click() to protected void click() fail compilation?
    Java enforces Liskov Substitution rules on overridden methods: any caller holding a parent reference expects public access, so narrowing visibility on a child override breaks polymorphic calls and triggers 'attempting to assign weaker access privileges'. You may widen visibility (for example, protected to public), never narrow it.
  3. Why can two instances of the exact same class read each other's private fields?
    In Java, private restricts visibility at the class boundary, not the individual object boundary. Inside equals(Object o) on User, casting to User other allows reading other.id directly even though id is private.

Tier 5: Design Choices & Rapid-Fire Recall (Q13–Q21)

  1. Why should automated framework engineers start every new field or helper as private and widen only when needed?
    Minimizing surface area prevents external classes from accidentally coupling to internal fields or helper details. Once a member is made public, refactoring or removing it requires auditing the entire codebase; keeping helpers private or package-private preserves refactoring freedom.
  2. When building a fluent Page Object API, why should low-level methods like waitForElement(By) be protected rather than public?
    Exposing low-level wait or click primitives publicly invites test authors to pass raw By locators inside @Test classes, eroding Page Object Model boundaries. Making those primitives protected in BasePage keeps them strictly inside the Page Object hierarchy.
  3. Why do modern Java 16+ record classes make fields private final automatically?
    Records model immutable data carriers (like API response DTOs or test configuration pairs) where encapsulation forbids post-construction field tampering. Generating private final fields alongside read-only accessors enforces immutability with zero boilerplate.
  4. What are Java's 4 access levels?
    private, default (package-private), protected, and public.
  5. Which keyword applies package-private visibility?
    No keyword at all (omitting any access modifier).
  6. Can an overridden method have narrower visibility than the parent method?
    No; it can only keep the same visibility or widen it.
  7. What visibility modifier should Page Object By locators use?
    private final.
  8. What access modifiers are legal on a top-level class?
    public or package-private only.
  9. What is the difference between package-private and protected?
    protected additionally grants access to subclasses residing in different packages.
