6.2 Explicit Waits & ExpectedConditions

Targeted client-side synchronization using WebDriverWait, until(), and ExpectedConditions for visibility, clickability, and state transitions.

An Explicit Wait is a targeted, code-defined synchronization mechanism that polls the browser from the Java client until a specific condition evaluates to a non-null/true value or the timeout expires. In Selenium 4, WebDriverWait(driver, Duration.ofSeconds(10)) pairs with the ExpectedConditions utility class or custom Java lambda expressions.

Before you start

Prerequisite: 6.1 Waiting Strategies Overview & Implicit Waits

Where it fits

WebDriverWait is encapsulated inside BasePage helper methods (waitForVisible, waitForClickable, waitForUrl) and invoked before every Page Object interaction.

Key points

  1. WebDriverWait extends FluentWait<WebDriver> with a default polling interval of 500 milliseconds and automatically ignores NoSuchElementException.
  2. wait.until(ExpectedConditions.visibilityOfElementLocated(By)) waits until the element exists in the DOM AND is visibly rendered with width and height > 0.
  3. wait.until(ExpectedConditions.elementToBeClickable(By)) waits until the element is both visible AND enabled.
  4. wait.until(ExpectedConditions.invisibilityOfElementLocated(By)) waits for loading spinners or modal backdrops to disappear or be removed from the DOM.
  5. If the condition is not satisfied within the configured Duration, wait.until() throws org.openqa.selenium.TimeoutException.

How it works

  1. Instantiate WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(10)).
  2. Call wait.until(...) passing an ExpectedCondition or a lambda function (d -> ...).
  3. Every 500ms (default), WebDriverWait evaluates the condition against the browser while ignoring NoSuchElementException.
  4. As soon as the condition returns a non-null object or Boolean.TRUE, wait.until() returns that value immediately; if 10 seconds elapse, it throws TimeoutException.

Synchronizing dynamic elements with WebDriverWait and ExpectedConditions:

package dev.selenium.waits; // Declares package

import org.openqa.selenium.By; // Imports By locator class
import org.openqa.selenium.WebDriver; // Imports WebDriver interface
import org.openqa.selenium.WebElement; // Imports WebElement interface
import org.openqa.selenium.chrome.ChromeDriver; // Imports ChromeDriver
import org.openqa.selenium.support.ui.ExpectedConditions; // Imports ExpectedConditions utility
import org.openqa.selenium.support.ui.WebDriverWait; // Imports WebDriverWait class
import java.time.Duration; // Imports Duration class

public class ExplicitWaitExample { // Declares class
    public static void main(String[] args) { // Main method
        WebDriver driver = new ChromeDriver(); // Starts Chrome session
        try { // Guarded block
            driver.get("https://www.selenium.dev/selenium/web/dynamic.html"); // Opens dynamic test page
            WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(10)); // Creates 10s explicit wait

            driver.findElement(By.id("reveal")).click(); // Clicks button that reveals a hidden input
            WebElement revealed = wait.until( // Polls every 500ms until input becomes visible
                ExpectedConditions.visibilityOfElementLocated(By.id("revealed")) // Checks DOM presence + visibility
            ); // Returns visible WebElement
            revealed.sendKeys("Synchronized!"); // Types into input once visible
            System.out.println("Typed: " + revealed.getDomProperty("value")); // Prints typed value
        } finally { // Teardown block
            driver.quit(); // Closes browser
        } // Ends finally
    } // Ends main
} // Ends class

Common mistakes

  1. Using presenceOfElementLocated(By) before calling click() or sendKeys(), which fails with ElementNotInteractableException if the element is still hidden in the DOM; fix by using visibilityOfElementLocated(By) or elementToBeClickable(By).
  2. Passing driver.findElement(By.id("foo")) inside ExpectedConditions.visibilityOf(driver.findElement(...)) when the element is not in the DOM yet, causing findElement() to throw NoSuchElementException before WebDriverWait even starts; fix by passing the By locator to visibilityOfElementLocated(By).
  3. Using a 60-second WebDriverWait everywhere, which hides real application performance regressions and makes failed tests hang for a full minute.

Interview questions

Basics

What is an Explicit Wait and how is it created in Selenium 4?
An Explicit Wait pauses execution until a specific condition is met for a targeted element or browser state. It is created via new WebDriverWait(driver, Duration.ofSeconds(10)) and executed with wait.until(condition).

What is the default polling interval of WebDriverWait?
WebDriverWait polls the condition every 500 milliseconds (0.5 seconds) by default.

What is the difference between presenceOfElementLocated() and visibilityOfElementLocated()?
presenceOfElementLocated() succeeds as soon as the element exists in the HTML DOM, even if it is hidden (display:none). visibilityOfElementLocated() waits until the element exists in the DOM AND is visibly rendered with height and width greater than zero.

How it works

Why does WebDriverWait not fail on the first 500ms poll when findElement() throws NoSuchElementException?
WebDriverWait's constructor automatically calls ignoring(NotFoundException.class), which is the superclass of NoSuchElementException. Whenever a poll throws NoSuchElementException, WebDriverWait catches it, sleeps 500ms, and polls again until the timeout expires.

What happens if wait.until() times out after 10 seconds because the element never appeared?
wait.until() throws an org.openqa.selenium.TimeoutException, and its getCause() contains the last NoSuchElementException thrown during the final poll.

How do you write a custom Explicit Wait in Selenium 4 using a Java lambda expression instead of ExpectedConditions?
wait.until() accepts any Function<WebDriver, T>. For example, wait.until(d -> d.findElement(By.id("status")).getText().equals("READY")) polls until the lambda returns true.

Real situations

How do you wait for a loading spinner to appear and then disappear before clicking a button?
Wait for invisibility: wait.until(ExpectedConditions.invisibilityOfElementLocated(By.cssSelector(".loading-spinner"))), and then call wait.until(ExpectedConditions.elementToBeClickable(buttonLocator)).click().

How do you wait for a table or section to finish refreshing after selecting a filter dropdown?
Grab a reference to an old element in the table before selecting the filter, select the filter, and then call wait.until(ExpectedConditions.stalenessOf(oldTableElement)) to confirm the old DOM was replaced.

How do you combine two conditions (for example, waiting for either a Dashboard header OR an Error banner)?
Use ExpectedConditions.or(ExpectedConditions.visibilityOfElementLocated(dashboardLoc), ExpectedConditions.visibilityOfElementLocated(errorLoc)).

Troubleshooting

Why did wait.until(ExpectedConditions.visibilityOf(driver.findElement(By.id("msg")))) throw NoSuchElementException immediately at 0 seconds?
In Java, method arguments are evaluated before the outer method runs. Calling driver.findElement() inside the argument executes immediately before wait.until() starts polling. Pass the By locator to ExpectedConditions.visibilityOfElementLocated(By.id("msg")) instead.

Why did elementToBeClickable() succeed, but element.click() still threw ElementClickInterceptedException?
elementToBeClickable() checks that the button itself is visible and enabled, but it does not check if a transparent backdrop overlay is sitting on top of its z-index. Wait for invisibilityOfElementLocated(overlayLocator) first.

Why does wait.until() throw StaleElementReferenceException when an element is re-rendered mid-poll?
If the DOM node is replaced between locating it and checking its visibility, StaleElementReferenceException is thrown. ChainExpectedConditions.refreshed(ExpectedConditions.visibilityOfElementLocated(By)) or add StaleElementReferenceException to .ignoring().

Design choices

Why is wrapping ExpectedConditions inside ExpectedConditions.refreshed(...) useful in React/Angular apps?
React and Angular frequently re-mount components during state hydration, causing StaleElementReferenceException. ExpectedConditions.refreshed() automatically catches StaleElementReferenceException and re-evaluates the inner condition.

Why should explicit wait helper methods live in a BasePage class rather than inside @Test classes?
Synchronization is an implementation detail of interacting with the UI. Centralizing waitForClickable(By) and waitForVisible(By) in BasePage keeps @Test classes clean and readable.

When should you use a custom lambda in wait.until() instead of ExpectedConditions?
Use a lambda when waiting for custom application conditions not covered by ExpectedConditions, such as waiting for a list of elements to reach a specific count or waiting for a JavaScript variable to settle.

Quick answers

  1. What is the default polling interval of WebDriverWait? 500 milliseconds.
  2. Which exception does WebDriverWait ignore by default? NotFoundException (including NoSuchElementException).
  3. Which exception is thrown when WebDriverWait expires? org.openqa.selenium.TimeoutException.
  4. What is the difference between presenceOf and visibilityOf? presenceOf only checks DOM existence; visibilityOf also requires the element to be visibly rendered.
  5. Which ExpectedCondition waits for an old element to be detached from the DOM? ExpectedConditions.stalenessOf(element).
