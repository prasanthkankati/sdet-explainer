4.2 Constructors: Default, Parameterized, Chaining & Singleton

Default vs parameterized constructors, compiler injection rules, constructor overloading, this() vs super() chaining, and private Singleton constructors.

A constructor is a specialized initialization block executed automatically by the JVM immediately after new allocates Heap memory for an object. Mastering constructor chaining via this() and super(), compiler default rules, and private constructors prevents initialization bugs in Page Objects, BasePage hierarchies, and Singleton utilities.

Before you start

Prerequisite: 4.1 Class & Object (Selenium + Interview Edition)

Where it fits

Every Selenium Page Object uses a parameterized constructor (public LoginPage(WebDriver driver)) to receive the active browser driver and initialize explicit waits or super(driver) on BasePage.

Key points

  1. A constructor must share the exact class name (case-sensitive), declare no return type (not even void), and cannot use abstract, static, final, or synchronized modifiers.
  2. The compiler injects an implicit no-argument default constructor only if the class defines zero explicit constructors; defining public LoginPage(WebDriver d) removes the default no-arg constructor.
  3. Constructor Overloading allows a class to declare multiple constructors with distinct parameter lists so objects initialize cleanly across optional defaults.
  4. this(...) invokes another overloaded constructor in the same class, while super(...) invokes a parent class constructor; either call must be the exact first statement inside a constructor, so this() and super() can never both appear in the same constructor.
  5. If neither this() nor super() is written explicitly, the compiler silently inserts super(); as the first line.
  6. Making a constructor private prevents external new calls—used for stateless utility classes (like Math) and thread-safe Singleton classes (like ConfigReader.getInstance()).

How it works

  1. Calling new LoginPage(driver) allocates Heap memory and enters the LoginPage(WebDriver) constructor.
  2. The constructor delegates to super(driver); on line 1, initializing BasePage.driver and BasePage.wait before child fields run.
  3. Execution returns to LoginPage to initialize page-specific fields and complete object construction.
  4. For a Singleton ConfigReader, the private constructor restricts instantiation to a single controlled getInstance() accessor.

Chaining Page Object constructors with super(), overloaded this(), and a Singleton ConfigReader:

package dev.java.oop; // Declares package

import org.openqa.selenium.WebDriver; // Imports WebDriver interface
import java.time.Duration; // Imports Duration class

class BasePage { // Parent base page class
    protected final WebDriver driver; // Shared driver field inherited by Page Objects
    protected final Duration timeout; // Shared wait timeout

    BasePage(WebDriver driver, Duration timeout) { // Parameterized parent constructor
        this.driver = driver; // Assigns driver reference
        this.timeout = timeout; // Assigns wait duration
    } // Ends BasePage constructor
} // Ends BasePage class

public class LoginPageConstructor extends BasePage { // Child Page Object extending BasePage
    public LoginPageConstructor(WebDriver driver) { // Overloaded 1-arg constructor
        this(driver, Duration.ofSeconds(10)); // Chains to 2-arg constructor on line 1
    } // Ends 1-arg constructor

    public LoginPageConstructor(WebDriver driver, Duration timeout) { // Overloaded 2-arg constructor
        super(driver, timeout); // Chains directly to BasePage constructor on line 1
    } // Ends 2-arg constructor
} // Ends LoginPageConstructor class

Common mistakes

  1. Accidentally adding void to a constructor declaration (public void LoginPage(WebDriver d)); Java treats it as a plain method returning void rather than a constructor, leaving driver uninitialized as null.
  2. Extending a parent class that defines only a parameterized constructor (BasePage(WebDriver)) without calling super(driver) in the child constructor; compilation fails because the compiler's implicit super() no-arg constructor does not exist.
  3. Using a Singleton pattern for WebDriver across parallel TestNG tests; a global Singleton shares one browser instance across all concurrent threads and breaks parallel isolation (use ThreadLocal instead, keeping Singletons for read-only ConfigReader).
  4. Putting both this(...) and super(...) inside the same constructor body; both require line 1, causing an immediate compile error.

Interview questions

Basics

What are the strict rules that distinguish a constructor from a normal method?
A constructor must match its enclosing class name character-for-character and must declare zero return type (not even void). Constructors cannot be marked static, final, or abstract, and they are never inherited by subclasses. They execute automatically once during object creation via new.

When does the Java compiler generate a default no-argument constructor, and when does it omit it?
If a class contains zero written constructors, javac generates a hidden no-arg constructor whose access modifier matches the class and whose body simply calls super();. The moment you write any explicit constructor—for example, public LoginPage(WebDriver driver)—the compiler stops generating the implicit no-arg constructor. Any caller attempting new LoginPage() afterward fails compilation unless you declare a no-arg constructor explicitly.

Why can a constructor be declared private, and where is it useful?
Marking a constructor private prevents external classes from instantiating the class directly with new. It is used in stateless utility classes (like java.lang.Math or a WaitUtils helper with only static methods) and in the Singleton pattern (like a read-only ConfigReader) where a single shared instance is returned via getInstance().

How it works

Explain the execution order of constructors when ChildPage extends BasePage.
When new ChildPage(driver) runs, the child constructor invokes super(driver) on its very first line before executing its own body. BasePage's constructor runs first (after implicitly calling Object()), initializes inherited fields, and returns control to ChildPage's remaining constructor statements. Parent fields are always ready before child constructor code runs.

Why must this(...) and super(...) always be the very first statement inside a constructor?
Guaranteeing the superclass or delegated constructor executes first ensures all parent invariants and inherited fields are initialized before the current constructor attempts to read them. Because both require position 1, a constructor can invoke at most one of them, and any constructor using this() delegates the responsibility of calling super() to the target constructor.

What happens if a recursive constructor call occurs, for instance Constructor A calling this(x) which calls this()?
Java detects direct or cyclic constructor recursion at compile time and immediately rejects the file with 'recursive constructor invocation'.

Real situations

Why do TestNG @Test classes and Jackson POJOs normally require a public no-argument constructor?
TestNG instantiates test classes via reflection using the zero-argument constructor unless a custom object factory is configured. Similarly, Jackson deserializes JSON strings into Java objects by invoking the class's no-arg constructor first and then populating fields or setters. Adding only a parameterized constructor to a POJO without adding an explicit no-arg constructor breaks JSON deserialization.

When is the Singleton pattern safe vs dangerous in a Selenium automation framework?
Singleton is safe and beneficial for immutable, read-only resources like loading config.properties once via ConfigReader.getInstance() so tests do not re-read disk files 100 times. Singleton is dangerous for WebDriver because parallel threads would share one browser instance, leading to session collisions and NoSuchSessionException.

How can a BasePage constructor enforce that every Page Object receives a non-null WebDriver?
Inside BasePage(WebDriver driver), validate this.driver = Objects.requireNonNull(driver, "WebDriver cannot be null");. Failing immediately inside the constructor catches setup errors at the exact line of page creation rather than three steps later inside a click method.

Troubleshooting

Why did adding public void LoginPage(WebDriver driver) compile without error, yet leave this.driver as null?
Putting void before the name turns LoginPage into a standard method rather than a constructor, so new LoginPage() actually calls the compiler's implicit no-arg constructor instead. Remove void so the constructor signature reads public LoginPage(WebDriver driver).

Why does class CheckoutPage extends BasePage fail to compile with 'constructor BasePage in class BasePage cannot be applied to given types'?
BasePage defines an explicit parameterized constructor BasePage(WebDriver driver), so it no longer has a zero-arg constructor. Because CheckoutPage omitted an explicit super(driver) call, Java inserted super() implicitly and failed to find a no-arg constructor on BasePage. Declare public CheckoutPage(WebDriver driver) { super(driver); } to fix it.

Why does a private-constructor Singleton break under multi-threaded parallel TestNG startup if written naively?
A lazy Singleton checking if (instance == null) instance = new ConfigReader(); without synchronization allows two TestNG threads starting concurrently to both see null and construct two separate instances. Fix this using double-checked locking with volatile, eager static initialization, or the Bill Pugh static inner holder class.

Design choices

Why should constructors avoid launching browsers, navigating URLs, or calling overridable methods?
Heavy side effects or throwing exceptions inside constructors creates partially constructed objects and couples instantiation to network timing. Moreover, calling an overridable method inside a parent constructor runs the subclass override before the subclass's own fields are initialized. Keep constructors lightweight: validate and assign fields only.

Between eager initialization, synchronized getInstance(), and Bill Pugh static holder, which Singleton implementation is cleanest in Java?
The Bill Pugh static inner holder (private static class Holder { static final ConfigReader INSTANCE = new ConfigReader(); }) or a Java enum Singleton provides guaranteed lazy loading and JVM-enforced thread safety during class initialization without synchronization lock overhead on every getInstance() call.

Why is constructor injection preferred over setter injection for passing WebDriver into Page Objects?
Constructor injection makes the driver dependency mandatory at compile time and allows marking the field private final WebDriver driver;. Setter injection allows callers to forget calling setDriver() and permits reassigning the driver midway through a test.

Quick answers

  1. Does a constructor have a return type? No; not even void.
  2. When does the compiler generate a default no-arg constructor? Only when the class declares zero constructors explicitly.
  3. Which statement must be first inside a constructor: this() or super()? Whichever is used must be line 1; both cannot appear in the same constructor.
  4. Are constructors inherited by subclasses? No, subclasses invoke parent constructors via super(...).
  5. How do you block external instantiation with new? Declare the constructor private.
  6. Why should WebDriver NOT be a global Singleton? Parallel test threads would overwrite and share one browser session.
