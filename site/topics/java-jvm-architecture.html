JVM Architecture and Memory Areas

1. Definition

The JVM is a program with 4 parts: a Class Loader that brings code in, Memory Areas that store it, an Execution Engine that runs it, and a Native Interface that talks to the OS.

2. Memory hook

Load, Store, Run, Reach out: L-S-R-R. Class Loader loads, Memory Areas store, Execution Engine runs, Native Interface reaches out to the OS.

3. Architecture (read top to bottom, follow the arrows)

JVM one JVM process per running Java program
Input: Hello.class (bytecode on disk). Output: your program running.
① Class Loader Subsystem the delivery person
Brings .class files from disk into memory, only when first needed (lazy loading).
LoadingFinds the .class file, reads its bytes, creates the class description.
LinkingVerify (is it safe?), Prepare (static variables get default 0/null), Resolve (names become real addresses).
InitializationStatic variables get real values; static { } blocks run.
stores the loaded class information in
② Runtime Data Areas the JVM's memory: where things live
Allocated from your computer's RAM when the JVM starts.
SHARED by all threads (one copy):
HeapAll objects (new Dog()) and arrays. Cleaned by the Garbage Collector.
MetaspaceClass info: method bytecode, field names, constant pool. Lives in native memory.
ONE PER THREAD (each thread gets its own):
StackOne frame per method call: local variables and parameters. Frame is removed when the method returns.
PC RegisterRemembers which bytecode instruction this thread runs next.
Native Method StackSame as Stack, but for native (C/C++) methods.
the engine reads bytecode from these areas, and creates objects and frames in them
③ Execution Engine the cooks
Does the actual running of the program.
InterpreterRuns bytecode one instruction at a time. Starts fast, slow when repeated.
JIT CompilerFinds hot code (run many times) and compiles it to native machine code, then caches it. Why Java speeds up after warm-up.
Garbage CollectorFinds objects nothing points to and frees their Heap memory automatically.
calls out when it needs the operating system
④ Native Interface (JNI) + Native Libraries the outside suppliers
Bridge to C/C++ code: file access, network, the OS's own functions. The JVM itself uses it constantly. You rarely write it.
runs on
Operating System + Hardware Windows / Mac / Linux, CPU, RAM, disk

6. Code example: where does each thing live?

public class Demo {
    static int count = 5;             // class info in Metaspace; value kept with the class (Heap in modern Java)
    public static void main(String[] a) {
        int x = 10;                   // Stack: local primitive
        Dog d = new Dog();            // d (reference) in Stack; the Dog object in Heap
    }
}

7. Execution flow, step by step

  1. java Demo starts a JVM process.
  2. Class Loader loads, verifies and prepares Demo (and String, System from the libraries).
  3. Metaspace stores the class info. main gets a frame on the Stack.
  4. Execution Engine runs the bytecode (Interpreter first, JIT for hot parts).
  5. Objects created with new go to the Heap. The GC cleans them up later.
  6. Program ends, the JVM exits, memory returns to the OS.

10. Why it matters

Heap vs Stack explains NullPointerException, StackOverflowError, OutOfMemoryError and why d1 == d2 is false for two objects.

SDET link: Selenium jars load through the Application Class Loader via the classpath. A leaky test suite fills the Heap, which is what OutOfMemoryError means. Parallel tests mean multiple threads, each with its own Stack.

11. Quick test

Where does new Dog() live? Heap. Where does the variable d holding its reference live? Stack.
