1.2 JVM Architecture & Class Loader Subsystem

How the JVM loads, verifies, links, and initializes classes using the three ClassLoaders and routes them into Runtime Data Areas.

A JVM process does not read every class file on the classpath at startup; instead, the Class Loader Subsystem loads classes lazily on demand when code first references them. Once loaded, classes are stored in shared Runtime Data Areas where the Execution Engine and Java Native Interface (JNI) run the program against the host operating system.

Before you start

Prerequisite: 1.1 JDK vs JRE vs JVM & Bytecode Portability

Where it fits

Every Selenium library class (WebDriver, ChromeDriver), TestNG runner class, and Page Object class is dynamically discovered and initialized by the Application ClassLoader before a single browser action runs.

Key points

  1. The JVM contains four major subsystems: Class Loader Subsystem, Runtime Data Areas, Execution Engine, and Java Native Interface (JNI).
  2. Classes load lazily in three sequential stages: Loading (reading binary bytes), Linking (Verify, Prepare, Resolve), and Initialization (assigning real static values and running static {} blocks).
  3. The three built-in ClassLoaders are Bootstrap (core JDK modules like java.lang.String), Platform (platform extension modules), and Application (project classes and Selenium/TestNG JARs from the classpath).
  4. ClassLoaders enforce the Parent Delegation Model: a child loader delegates upward to its parent before attempting to load a class itself, preventing spoofed core classes.
  5. Shared memory areas (Heap and Metaspace) are shared across all threads, whereas Stack, PC Register, and Native Method Stack are isolated one per thread.
  6. ClassNotFoundException is a checked exception thrown during explicit dynamic loading (Class.forName()), whereas NoClassDefFoundError is an unchecked Error thrown when a class existed at compile time but is missing or failed static initialization at runtime.

How it works

  1. Loading: The Application ClassLoader locates the .class bytes on disk or inside a JAR, creates a Class<?> metadata object in memory, and registers it using Parent Delegation.
  2. Linking — Verify: The Bytecode Verifier inspects stack frames, operand types, and jump offsets to reject corrupted or malicious class files (VerifyError).
  3. Linking — Prepare: The JVM allocates memory for all static fields and sets them to type defaults (0, false, or null) before executing any user code.
  4. Linking — Resolve: Symbolic references in the constant pool (for example, org/openqa/selenium/WebDriver) are replaced with direct memory references.
  5. Initialization: All explicit static variable initializers and static { } blocks execute sequentially from top to bottom once per class.

Observing ClassLoaders and static initialization order in Java:

package dev.java.jvm; // Declares package

public class ClassLoaderTrace { // Loaded by Application ClassLoader
    static int retryLimit = 3; // Prepare sets 0; Initialization sets 3
    static { // Static block runs once during Initialization phase
        System.out.println("Static init ran; retryLimit=" + retryLimit); // Prints during class initialization
    } // Ends static initializer block
    public static void main(String[] args) { // Entry point invokes initialization before running
        ClassLoader appLoader = ClassLoaderTrace.class.getClassLoader(); // Fetches Application ClassLoader
        System.out.println("App class loader: " + appLoader); // Prints AppClassLoader instance
        System.out.println("String loader: " + String.class.getClassLoader()); // Prints null (native Bootstrap)
    } // Ends main method
} // Ends ClassLoaderTrace class

Common mistakes

  1. Assuming String.class.getClassLoader() returning null means an error; Bootstrap ClassLoader is written in native C/C++ rather than Java, so getClassLoader() intentionally returns null.
  2. Confusing ClassNotFoundException with NoClassDefFoundError; the former occurs on dynamic string-based loading (Class.forName("com.mysql.Driver")), while the latter occurs when a class compiled cleanly or threw an exception inside its static {} block.
  3. Placing slow or brittle external calls inside a static {} block; any uncaught exception inside static {} raises ExceptionInInitializerError on the first reference and NoClassDefFoundError on every subsequent reference.
  4. Thinking all .class files inside every dependency JAR load into memory when the JVM starts; the JVM loads classes lazily only when an instruction first references them.

Interview questions

Basics

What are the four main subsystems of the JVM architecture?
The four subsystems are the Class Loader Subsystem, the Runtime Data Areas, the Execution Engine, and the Java Native Interface (JNI). The Class Loader reads and validates bytecode, Runtime Data Areas store objects and execution state, the Execution Engine runs instructions and collects garbage, and JNI communicates with native OS libraries. Every TestNG test runs across all four subsystems simultaneously.

Which three ClassLoaders ship with a standard JVM?
The JVM uses the Bootstrap ClassLoader, Platform ClassLoader, and Application ClassLoader in top-to-bottom hierarchy. Bootstrap loads core JDK classes including java.lang.String, Platform loads extended platform modules, and Application loads your test code and third-party JARs like selenium-java. Calling String.class.getClassLoader() returns null because Bootstrap is native C/C++ code.

Which JVM Runtime Data Areas are shared across threads versus created per thread?
The Heap and Metaspace are shared across every thread inside a single JVM process. By contrast, each thread gets its own isolated JVM Stack, Program Counter (PC) Register, and Native Method Stack. This separation explains why local variables inside a test method are automatically thread-safe while shared static Heap objects cause race conditions in parallel Selenium runs.

How it works

What happens during the three sub-phases of Linking: Verify, Prepare, and Resolve?
Verify checks bytecode structural integrity, stack bounds, and type safety to prevent memory corruption. Prepare allocates memory for static fields and assigns their default zeroed values (0, false, or null) without running initializers. Resolve replaces symbolic class and method names in the runtime constant pool with direct memory pointers.

How does the Parent Delegation Model protect Java security?
When the Application ClassLoader receives a request to load java.lang.String, it delegates upward to Platform, which delegates upward to Bootstrap before trying the local classpath. Bootstrap immediately resolves the authentic JDK String class, ignoring any spoofed java.lang.String placed on the application classpath. This guarantees core Java APIs cannot be replaced.

What is the difference between the Prepare phase and the Initialization phase for static fields?
During Prepare, the JVM allocates space for static int timeout = 10; and sets timeout to its default 0. During Initialization, the JVM executes the actual assignment to set timeout = 10 and runs any static { } blocks in source order. Note that static final compile-time constants are inlined directly into the constant pool and do not wait for Initialization.

Real situations

A Selenium test uses JDBC to validate database rows and throws ClassNotFoundException: com.mysql.cj.jdbc.Driver. Why did compilation succeed?
Class.forName("com.mysql.cj.jdbc.Driver") passes the class name as a String literal, so javac cannot verify at compile time whether that class exists on the classpath. At runtime, the Application ClassLoader searches the classpath JARs, fails to find the driver JAR, and throws the checked ClassNotFoundException. Adding the MySQL driver dependency to pom.xml resolves it.

How does parallel TestNG execution map to the JVM's Runtime Data Areas?
When TestNG runs 4 test methods concurrently with parallel="methods" thread-count="4", the JVM maintains 4 separate JVM Stacks and 4 PC Registers—one per worker thread. All 4 threads share the single Heap and Metaspace. Local variables like By locators inside each method stay isolated on their own Stack, whereas a single shared static WebDriver on the Heap causes threads to collide on the same browser.

Where does Selenium's ChromeDriver class get loaded compared to java.lang.Object?
java.lang.Object resides in the JDK's java.base module and is loaded by the native Bootstrap ClassLoader. org.openqa.selenium.chrome.ChromeDriver resides inside the selenium-chrome-driver.jar on the Maven test classpath, so the Application ClassLoader loads it after Bootstrap and Platform delegate back down.

Troubleshooting

Why does a class throw ExceptionInInitializerError on the first test and NoClassDefFoundError on every test after?
When a static { } initializer throws an uncaught runtime exception (for example, failing to load config.properties), the JVM aborts initialization with ExceptionInInitializerError and marks that class as erroneous in Metaspace. Any subsequent test referencing that same class cannot initialize it again and immediately fails with NoClassDefFoundError. Fixing the underlying static block exception cures both errors.

What causes NoClassDefFoundError: org/openqa/selenium/WebDriver in a packaged Selenium project?
The project compiled cleanly because the Selenium JAR was present on the compile classpath, but the JAR is absent on the runtime classpath (for example, declaring <scope>provided</scope> in pom.xml or omitting dependency JARs from a fat JAR). At runtime, the Application ClassLoader attempts to resolve WebDriver and throws NoClassDefFoundError. Ensuring runtime scope or bundling dependencies via Maven Shade fixes the issue.

What causes java.lang.VerifyError when launching tests?
VerifyError occurs during the Linking Verify phase when loaded bytecode violates JVM type rules, most commonly caused by two incompatible versions of a library JAR (Guava or ASM, for instance) on the classpath. Inspecting the build with mvn dependency:tree reveals the duplicate transitive dependency so the older version can be excluded.

Design choices

Why does the JVM load classes lazily instead of loading the entire classpath at startup?
Enterprise test suites often carry dozens of third-party JARs containing tens of thousands of classes, only a fraction of which run during a given test execution. Lazy loading loads only the classes actively touched by the execution path, keeping startup latency low and Metaspace usage minimal.

Why do test frameworks like TestNG and Maven Surefire sometimes create custom ClassLoaders?
Isolated ClassLoaders allow build plugins and test runners to load specific plugin dependencies without colliding with versions used by the application under test. By maintaining separate classloader namespaces, two versions of the same library can coexist cleanly inside one JVM process.

Why did Java design the Parent Delegation Model to search upward first instead of loading from the local application classpath first?
Searching upward first guarantees that core runtime classes including java.lang.Object, String, and SecurityManager always resolve to the single canonical JDK definition. If application JARs loaded first, a misconfigured or malicious dependency JAR could redefine core language types and break type compatibility across the entire JVM.

Quick answers

  1. What are the 3 built-in JVM ClassLoaders? Bootstrap, Platform, and Application ClassLoader.
  2. What are the 3 phases of Class Loading? Loading, Linking (Verify, Prepare, Resolve), and Initialization.
  3. Which Runtime Data Areas are shared by all threads? Heap and Metaspace.
  4. Which Runtime Data Areas are created per thread? JVM Stack, PC Register, and Native Method Stack.
  5. What is the difference between ClassNotFoundException and NoClassDefFoundError? ClassNotFoundException is a checked exception on dynamic string loading; NoClassDefFoundError is an unchecked Error when a compiled dependency is missing or failed static init at runtime.
  6. Which ClassLoader loads Selenium WebDriver classes? The Application ClassLoader.
