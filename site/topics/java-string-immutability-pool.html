3.1 String Immutability & String Constant Pool

Why java.lang.String is final and immutable, how literals share memory in the String Constant Pool versus new String() on the Heap, and intern() mechanics.

In Java, a String object cannot be modified after creation; any operation returning altered text allocates a new String instance instead of mutating existing characters. String literals are interned inside the String Constant Pool on the Heap so identical text constants reuse a single shared instance across the entire JVM.

Before you start

Prerequisite: 2.6 Methods, Parameters, Return Types & Varargs

Where it fits

Every Selenium locator string, URL (https://qkart-qa-web.labs.crio.do/login), assertion message, and HashMap<String, String> test-data lookup relies on String immutability and pool sharing.

Key points

  1. java.lang.String is declared public final class String, and its internal character array (private final byte[] value since Java 9 Compact Strings) cannot be reassigned or exposed.
  2. The 4 primary reasons String is immutable are: String Constant Pool memory sharing, automatic thread-safety without locks, cached hashCode for fast HashMap keys, and security for class names, URLs, and credentials.
  3. A string literal (String a = "QKart";) checks the String Constant Pool (SCP) inside the Heap first and reuses the pooled object if present.
  4. Calling new String("QKart") forces a brand-new String object outside the pool on the regular Heap (creating up to 2 objects if "QKart" was not already pooled).
  5. Calling s.intern() returns the canonical pooled reference from the String Constant Pool if present, or adds the string to the pool and returns that reference.
  6. == compares Stack memory addresses (reference identity), whereas .equals() compares exact character content and .equalsIgnoreCase() compares ignoring case.

How it works

  1. During class loading, literal "QKart" is placed in the String Constant Pool on the Heap.
  2. Executing String a = "QKart"; points Stack variable a directly to that pooled object.
  3. Executing String b = new String("QKart"); allocates a second wrapper object in regular Heap space pointing to the internal byte buffer.
  4. Evaluating a == b compares the Stack addresses and returns false, while a.equals(b) compares underlying characters and returns true.
  5. Calling b.intern() looks up "QKart" in the String Constant Pool and returns the matching pooled reference equal to a.

Tracing String Constant Pool sharing, new String() Heap allocation, and == vs .equals():

package dev.java.strings; // Declares package

public class StringPoolDemo { // Demonstrates String immutability and pooling
    public static void main(String[] args) { // Main method entry
        String literal1 = "QKart"; // Stored in String Constant Pool (SCP)
        String literal2 = "QKart"; // Reuses identical SCP object reference
        String heapObj = new String("QKart"); // Allocates distinct Heap object outside SCP
        String interned = heapObj.intern(); // Fetches canonical SCP reference

        System.out.println("literal1 == literal2 : " + (literal1 == literal2)); // Prints: true
        System.out.println("literal1 == heapObj  : " + (literal1 == heapObj)); // Prints: false
        System.out.println("literal1.equals(heap): " + literal1.equals(heapObj)); // Prints: true
        System.out.println("literal1 == interned : " + (literal1 == interned)); // Prints: true

        literal1.toUpperCase(); // Creates and discards new String; literal1 stays unchanged
        System.out.println("After ignored toUpperCase: " + literal1); // Prints: QKart
    } // Ends main method
} // Ends StringPoolDemo class

Common mistakes

  1. Using == to compare text retrieved from Selenium element.getText() against a string literal; getText() constructs a new Heap String at runtime, so == always returns false even when the text matches identically.
  2. Ignoring the return value of title.trim(); or title.replace("$", "");; because String is immutable, ignoring the return value discards the modified result and leaves the original variable unchanged.
  3. Calling actualText.equals("QKart") without a null check; calling "QKart".equals(actualText) (or Objects.equals) safely returns false instead of throwing NullPointerException when actualText is null.
  4. Thinking String immutability stores passwords securely in memory; immutable pooled or Heap String objects remain readable in memory dumps until Garbage Collected, so sensitive secrets belong in char[] arrays that can be zeroed immediately.

Interview questions

Basics

What does it mean that String is immutable in Java?
Once a String instance is created on the Heap or inside the String Constant Pool, its character content can never change. Any transformation method like toLowerCase(), substring(), or replace() leaves the original String untouched and constructs a brand-new String object. The class itself is also marked final so subclasses cannot override methods to expose mutable state.

List the 4 main reasons Java made String immutable.
First, String Constant Pool sharing: multiple references safely point to one shared literal without one variable corrupting another. Second, Thread Safety: immutable strings require zero synchronization across parallel threads. Third, HashMap caching: String computes and caches its hashCode once, making Map<String, V> lookups fast and preventing key bucket corruption. Fourth, Security: database URLs, file paths, and class names cannot mutate after security validation.

Where does the String Constant Pool live in modern Java (Java 8 through Java 21)?
Prior to Java 7, the String Constant Pool lived inside PermGen, which frequently caused OutOfMemoryError: PermGen space. Starting in Java 7 and continuing through Java 21, the String Constant Pool resides inside the main Heap memory so unused dynamically interned strings can be reclaimed by the Garbage Collector.

How it works

How many objects are created by String s = new String("QKart");?
Assuming "QKart" has not yet been loaded into the String Constant Pool, this single line creates two objects: one pooled literal object inside the String Constant Pool when the class loads, plus one distinct non-pooled String object on the Heap referenced by s. If "QKart" already existed in the pool from an earlier literal, only one new Heap object is created.

How does Java 9+ Compact Strings reduce String memory usage?
In Java 8, every String stored characters in a char[] using 2 bytes per character even for plain ASCII text. Starting in Java 9, String stores a byte[] value alongside a 1-byte coder flag (LATIN1 or UTF16), cutting memory consumption roughly in half for standard ASCII HTML text, locators, and JSON payloads.

Why does "a" + "b" == "ab" evaluate to true while String x = "a"; x + "b" == "ab" evaluates to false?
In the first case, both operands are compile-time string constants, so javac folds them during compilation directly into the single literal "ab" in the String Constant Pool. In the second case, x is a variable resolved at runtime, so the JVM builds a new String on the Heap using invokedynamic (StringConcatFactory), returning a different address than the pooled "ab".

Real situations

In a Selenium test on https://qkart-qa-web.labs.crio.do/, why does driver.getTitle() == "QKart" fail even when the printed title is QKart?
driver.getTitle() returns a dynamically deserialized String from the HTTP W3C JSON response allocated on the Heap, whereas "QKart" resides in the String Constant Pool. Using == compares their different memory addresses and evaluates to false. Always use driver.getTitle().equals("QKart") or TestNG Assert.assertEquals(driver.getTitle(), "QKart").

Why is String ideal as the key type in Map<String, String> test-data loaders?
Because String is immutable, its characters never change after insertion into a HashMap, guaranteeing its bucket hash stays valid forever. Additionally, String caches its computed hashCode inside an internal field after the first calculation, making repeated config lookups like config.get("base.url") extremely fast.

What happens if a Page Object writes text.trim(); without reassigning the result?
trim() returns a newly allocated trimmed String while leaving the original text variable pointing to the untrimmed characters. In test assertions, write text = text.trim(); or chain directly inside the assertion.

Troubleshooting

Why does if (actualError.equals("Invalid Password")) throw NullPointerException when no error appears?
When an optional UI element text variable is null, calling .equals() on it attempts to dereference null. Inverting the comparison to "Invalid Password".equals(actualError) (or using Objects.equals(actualError, "Invalid Password")) avoids NPE completely and cleanly returns false.

Why should automated security or login helpers avoid calling .intern() blindly on millions of dynamic API response strings?
Each interned string is registered inside the fixed-bucket internal String Pool table. Interning huge volumes of unique UUIDs, timestamps, or random payload strings inflates the String Table hash buckets and degrades lookup speed across the JVM. Reserve intern() strictly for small sets of repeated domain identifiers.

Why does storing database passwords in a String field raise security scanner flags?
Because String is immutable, you cannot overwrite its characters with zeroes after authentication finishes; the plaintext password lingers on the Heap until GC runs and reclaims it, exposing credentials in heap dumps. Use char[] or clearable secret buffers when handling sensitive tokens.

Design choices

Why did Java mark the String class itself as final rather than only making its internal fields private final?
If subclasses could extend String, a caller accepting a String could receive a mutable subclass overriding equals() or hashCode() to return changing values over time. Marking the class final locks down inheritance and guarantees immutability for every String reference anywhere in the JVM.

Why did Java move from char[] to byte[] in Java 9 String internals?
Heap profiling of enterprise JVM workloads showed String objects routinely consumed 25%–40% of total Heap memory, with the vast majority holding single-byte ASCII/Latin-1 text. Switching to compact byte[] storage reduced GC frequency and Heap footprint transparently without breaking any public String API.

Why did Java choose a String Constant Pool on the Heap rather than interning every runtime string automatically?
Automatically interning every short-lived runtime string (like loop fragments or HTTP response bodies) would add expensive hash-table synchronization overhead on every string creation. Limiting automatic pooling to compile-time literals and explicit intern() calls keeps normal runtime string allocation fast while sharing repeated literals efficiently.

Quick answers

  1. Where are String literals stored? In the String Constant Pool on the Heap.
  2. What does == check on two String variables? Whether both variables hold the exact same Heap memory address.
  3. What does .equals() check on two String variables? Whether both strings contain the exact same sequence of characters.
  4. How many objects can new String("abc") create if "abc" is not yet pooled? 2 objects (1 in the String Constant Pool and 1 on the regular Heap).
  5. What does str.intern() do? Returns the canonical reference from the String Constant Pool.
  6. Why is String marked final? To prevent subclassing from breaking immutability, security, and HashMap key consistency.
