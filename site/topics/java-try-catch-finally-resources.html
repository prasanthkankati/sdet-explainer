6.2 try-catch-finally, try-with-resources, throw/throws &amp; Custom Exceptions

Deterministic cleanup, ordered multi-catch blocks, automatic AutoCloseable resource closing, and domain-specific test exceptions prevent leaked files and silent Selenium failures.

Knowing the hierarchy is only half of safe error handling; an SDET must also write exception handlers that release Excel workbooks, close input streams automatically, avoid hiding real failures inside finally, and raise clear custom exceptions when a QKart checkout invariant breaks.

Before you start

Prerequisite: 6.1 Exception Hierarchy (Checked vs Unchecked vs Error)

Where it fits

Every Selenium framework relies on try-catch inside custom wait helpers, try-with-resources in data readers and screenshot savers, and custom unchecked exceptions to translate cryptic low-level errors into actionable failure messages in CI reports.

Key points

  1. Ordered catch blocks: Specific subclass catch blocks must come before broader superclass catches (e.g., FileNotFoundException before IOException), or compilation fails with an unreachable catch error.
  2. Multi-catch (Java 7+): A single handler can list unrelated siblings with a pipe, for example catch (IOException | TimeoutException e), where e is effectively final.
  3. The finally contract: The finally block executes whether the try block succeeds or throws (unless the JVM exits via System.exit() or crashes natively), and overriding its return value suppresses pending exceptions.
  4. try-with-resources: Any resource implementing java.lang.AutoCloseable (or Closeable) opened in try (...) is closed automatically in reverse declaration order, preserving the original failure as the primary exception and attaching any close error via getSuppressed().
  5. throw vs throws and custom exceptions: throw raises an instance inside code, while throws declares checked propagation on a method signature; custom framework exceptions should pass the original cause (`super(message, cause)`) so stack traces are never lost.

How it works

  1. When execution enters try (R1 a = ...; R2 b = ...), resources a then b are initialized left to right.
  2. If the body or an exception leaves the try block, Java closes b first and then a before entering any explicit catch or finally block attached to that try-with-resources.
  3. If both the try body and a resource's close() method throw exceptions, Java keeps the body's exception as the main thrown exception and records the close() exception in its suppressed array.
  4. When translating a checked error into a custom exception, calling super(message, cause) attaches the underlying stack trace under a Caused by: section for fast root-cause debugging.

Using try-with-resources and a custom unchecked exception with cause chaining

package com.qkart.exceptions; // Package for resource handling and custom exceptions

import java.io.BufferedReader; // Reader with AutoCloseable support
import java.io.IOException; // Checked I/O exception
import java.nio.file.Files; // NIO file helper
import java.nio.file.Path; // Path value object

class QKartTestDataException extends RuntimeException { // Custom unchecked framework exception
    public QKartTestDataException(String message, Throwable cause) { // Constructor preserving root cause
        super(message, cause); // Chains original exception for full stack trace visibility
    } // End constructor
} // End QKartTestDataException

public class SafeResourceReader { // Helper showing deterministic closing and custom wrapping

    public static String readFirstLine(Path filePath) { // Clean signature without checked throws
        try (BufferedReader reader = Files.newBufferedReader(filePath)) { // AutoCloseable opened in try header
            String line = reader.readLine(); // Read first configuration line from file
            if (line == null || line.isBlank()) { // Validate file is not empty
                throw new IllegalStateException("Empty QKart test data file: " + filePath); // Fail loudly
            } // End blank check
            return line; // Reader closes automatically before returning to caller
        } catch (IOException ex) { // Catch checked I/O failure after automatic close
            throw new QKartTestDataException("Failed loading QKart config from " + filePath, ex); // Wrap with cause
        } // End try-with-resources
    } // End readFirstLine

    public static void main(String[] args) { // Quick execution demo
        try { // Attempt reading missing file
            readFirstLine(Path.of("qkart-users.csv")); // Invokes safe reader
        } catch (QKartTestDataException ex) { // Catches custom unchecked exception
            System.out.println("Error: " + ex.getMessage()); // Prints friendly context message
            System.out.println("Root cause: " + ex.getCause().getClass().getSimpleName()); // Prints NoSuchFileException
        } // End demo catch
    } // End main
} // End SafeResourceReader

Common mistakes

  1. Putting return inside a finally block: Returning inside finally silently discards any exception thrown in try or catch and masks failures.
  2. Placing catch (Exception e) before catch (IOException e): Superclass-first ordering fails to compile because the specific handler becomes unreachable.
  3. Dropping the cause when rethrowing a custom exception: Calling throw new FrameworkException(ex.getMessage()) instead of new FrameworkException(msg, ex) deletes the original stack trace and line number.
  4. Forgetting that resources in try-with-resources are implicitly final or effectively final: Trying to reassign a resource variable declared inside the try (...) header fails compilation.

Interview questions

Basics

What is the exact difference between throw and throws?
throw is an executable statement inside a block that throws a single exception object (e.g., throw new IllegalArgumentException();). throws appears in a method declaration header to list checked exceptions the method may propagate to callers.

Does a finally block run even when try contains a return statement?
Yes. Before transferring control back to the caller with the computed return value, the JVM executes the finally block.

What interface must an object implement to be managed by try-with-resources?
java.lang.AutoCloseable (or its subinterface java.io.Closeable).

How it works

Why is try-with-resources safer than closing a stream inside a manual finally block?
In a manual finally block, an exception inside stream.close() overwrites and hides any exception that occurred inside the try block. try-with-resources preserves the original exception as primary and attaches any close() failure via addSuppressed().

In what order are multiple resources closed in a try (R1 a = ...; R2 b = ...) statement?
Reverse order of declaration: b.close() runs first, then a.close(), because later resources commonly wrap earlier ones (for example, a BufferedReader wrapping a FileReader).

Why is the exception variable in a multi-catch block (catch (IOException | TimeoutException e)) implicitly final?
Because e has no single concrete static type better than their common supertype (for example, Exception), so Java disallows reassigning e inside the block to avoid type-safety violations.

Real situations

Should a custom framework exception (for example ExcelReadException) extend Exception or RuntimeException?
Extend RuntimeException. Checked custom exceptions force every test and Page Object in the call chain to declare throws ExcelReadException, whereas an unchecked exception keeps tests clean and still triggers TestNG failure reporting.

Can Selenium's WebDriver be wrapped in an AutoCloseable helper or closed in finally?
In TestNG, lifecycle hooks (@AfterMethod) normally call driver.quit() rather than local try-with-resources so listeners can take screenshots before quitting. However, small standalone scripts or utility checks can safely wrap a driver wrapper in AutoCloseable calling driver.quit().

In a QKart checkout helper, clickBuyNow() fails and an automatic cleanup also fails. Which exception appears first in the report?
If the cleanup ran through try-with-resources, the clickBuyNow() failure remains the top exception and cleanup failure appears under Suppressed: in the stack trace.

Troubleshooting

A method returns true inside try and returns false inside finally. Which value does the caller receive?
false, because the finally block's return overrides the pending return value from try — and would even cancel any thrown exception.

Why does catch (FileNotFoundException | IOException e) refuse to compile?
Multi-catch syntax forbids listing a subclass alongside its own superclass (FileNotFoundException extends IOException). Catch only the broader IOException or write two separate ordered catch blocks.

Stack traces in Jenkins show only your custom TestConfigException line without showing where the underlying JSON syntax broke. Why?
The custom exception constructor omitted the cause parameter (e.g., called super(msg) instead of super(msg, ex)), breaking the exception chain.

Design choices

Should you override equals or leave default Constructors on a custom exception?
Provide at least two standard constructors: (String message) and (String message, Throwable cause) so every call site can supply context and preserve chained failures.

When is an exception better logged and rethrown versus only wrapped and rethrown?
Avoid logging and rethrowing at every intermediate layer, because that prints the same huge stack trace three or four times per failure. Wrap with context and rethrow cleanly, letting the top-level TestNG listener log it once.

Under what rare condition does a finally block fail to execute?
If the JVM is killed via System.exit(0), receives a fatal OS termination signal (`SIGKILL`), runs on an unresponsive daemon thread when all non-daemon threads end, or suffers power loss.

Quick answers

  1. How do you ensure automatic closing of streams and workbooks? Declare them inside try (...) so Java closes every AutoCloseable in reverse order.
  2. What happens if finally executes a return? It overwrites the try return value and silently swallows any pending exception.
  3. How do you keep original stack traces in custom exceptions? Pass the caught exception as the second parameter: super(message, cause).
  4. Can one catch block handle unrelated exception classes? Yes, via multi-catch: catch (IOException | SQLException ex).
