TestNG

1.1 TestNG Overview, Test Runner & Lifecycle

Core architecture of TestNG 7.x, the complete 10-annotation execution hierarchy, XML runner anatomy, and thread-safe test isolation.

TestNG ("Test Next Generation") is an enterprise Java test automation framework inspired by JUnit and NUnit, specifically engineered to support complex integration, end-to-end browser automation, and data-driven testing. While unit testing frameworks traditionally lack fine-grained lifecycle scoping, TestNG provides a 5-tier hierarchical runner architecture configured via testng.xml, built-in parameterization, parallel test execution down to the method level, and lifecycle interception hooks via listener interfaces.

1. TestNG Framework Architecture

In automated testing architectures, Selenium WebDriver acts purely as a browser automation API—it provides no test runner, assertion library, or lifecycle orchestration. TestNG acts as the execution backbone and control plane that wraps WebDriver, managing test suites, instantiation order, parallel worker threads, and failure reporting.

2. The XML Runner Hierarchy

A TestNG execution is strictly structured by an XML document conforming to the TestNG DTD. The hierarchical nesting directly determines thread scoping, parameter inheritance, and execution boundaries:

<!DOCTYPE suite SYSTEM "https://testng.org/testng-1.0.dtd">
<suite name="RegressionSuite" parallel="classes" thread-count="4" verbose="2">
  <parameter name="environment" value="staging" />

  <listeners>
    <listener class-name="com.sdet.listeners.ExecutionListener" />
  </listeners>

  <test name="ChromeSmokeTests">
    <parameter name="browser" value="chrome" />
    <classes>
      <class name="com.sdet.tests.LoginTest">
        <methods>
          <include name="validLoginTest" />
          <exclude name="legacyOAuthTest" />
        </methods>
      </class>
      <class name="com.sdet.tests.DashboardTest" />
    </classes>
  </test>
</suite>
  • <suite>: The root container. One XML file represents one suite. Configures parallel thread counts, global listeners, and suite-level parameters.
  • <test>: Logical test tag representing a functional module or browser run. (Note: A TestNG <test> tag is not a single @Test method).
  • <classes>: Container holding all test classes targeted for execution.
  • <class>: Individual compiled Java class containing @Test and configuration methods.
  • <methods>: Optional filter to selectively <include> or <exclude> specific test methods.

3. The Complete 10-Annotation Lifecycle

TestNG executes annotations in a rigorous deterministic hierarchy from the broadest global scope down to the individual test method invocation:

[1]  @BeforeSuite       — Runs ONCE before all tests in the XML suite
      [2]  @BeforeTest        — Runs ONCE before any test class inside a <test> tag
            [3]  @BeforeGroups      — Runs before specific group tests execute
                  [4]  @BeforeClass       — Runs ONCE before the first method in current class
                        [5]  @BeforeMethod      — Runs BEFORE EACH @Test method
                              [*]  @Test              — The actual test payload
                        [6]  @AfterMethod       — Runs AFTER EACH @Test method
                  [7]  @AfterClass        — Runs ONCE after all methods in current class
            [8]  @AfterGroups       — Runs after specific group tests complete
      [9]  @AfterTest         — Runs ONCE after all classes in a <test> tag complete
[10] @AfterSuite       — Runs ONCE after all tests in the XML suite complete

Detailed Scoping Guide

  1. @BeforeSuite / @AfterSuite: Global initialization. Used to spin up Docker containers, initialize Extent/Allure reporting instances, and delete old screenshot directories.
  2. @BeforeTest / @AfterTest: Scoped to the <test> tag in testng.xml. Often used to parse environment-level configurations or initialize module-level test databases.
  3. @BeforeGroups / @AfterGroups: Executes before/after the first and last test method belonging to specified groups (e.g., groups = {"database", "smoke"}).
  4. @BeforeClass / @AfterClass: Executes once per Java class instantiation. Used to launch heavy browser sessions when reusing a single driver across multiple class tests.
  5. @BeforeMethod / @AfterMethod: Executes immediately prior to and after every single @Test method. Standard location for WebDriver initialization (for isolated browser instances) and cleanup (driver.quit()).

4. Production Thread-Safe TestNG Base Pattern

In modern CI/CD pipelines where tests run concurrently across multiple CPU threads, using raw static WebDriver instances causes catastrophic race conditions. TestNG lifecycle methods must combine with ThreadLocal to guarantee thread safety:

package com.sdet.core;

import org.openqa.selenium.WebDriver;
import org.openqa.selenium.chrome.ChromeDriver;
import org.openqa.selenium.firefox.FirefoxDriver;
import org.testng.annotations.*;
import java.time.Duration;

public abstract class BaseTest {
    // ThreadLocal container guarantees each worker thread has an isolated WebDriver instance
    private static final ThreadLocal<WebDriver> driverThreadLocal = new ThreadLocal<>();

    public static WebDriver getDriver() {
        return driverThreadLocal.get();
    }

    @BeforeSuite(alwaysRun = true)
    public void setupSuite() {
        System.out.println("[SUITE INIT] Initializing Test Run & Global Services");
    }

    @Parameters({"browser"})
    @BeforeMethod(alwaysRun = true)
    public void setUp(@Optional("chrome") String browser) {
        WebDriver driver;
        if (browser.equalsIgnoreCase("firefox")) {
            driver = new FirefoxDriver();
        } else {
            driver = new ChromeDriver();
        }

        driver.manage().window().maximize();
        driver.manage().timeouts().implicitlyWait(Duration.ofSeconds(5));
        driverThreadLocal.set(driver);
    }

    @AfterMethod(alwaysRun = true)
    public void tearDown() {
        WebDriver driver = driverThreadLocal.get();
        if (driver != null) {
            driver.quit();
            driverThreadLocal.remove(); // Prevent memory leaks in Jenkins thread pools
        }
    }

    @AfterSuite(alwaysRun = true)
    public void tearDownSuite() {
        System.out.println("[SUITE TEARDOWN] Flushing Reports & Cleaning Resources");
    }
}

5. Senior SDET Interview Q&A

  1. What is the exact execution hierarchy between @BeforeTest and @BeforeClass?
    @BeforeTest runs before @BeforeClass. @BeforeTest executes once per <test> tag defined in testng.xml before any class inside that tag is loaded. @BeforeClass executes once before the first method of a specific Java class.
  2. What does alwaysRun = true do on configuration methods?
    By default, if an earlier configuration method (like @BeforeClass) fails, TestNG skips all subsequent configuration methods and test methods. Specifying @AfterMethod(alwaysRun = true) guarantees cleanup logic (such as driver.quit()) runs even if the test method or setup failed, preventing orphaned browser processes.
  3. Why should you avoid priority in enterprise test automation suites?
    Using priority couples test execution order, turning tests into dependent integration flows rather than atomic, independent units. Prioritized tests are difficult to run reliably in parallel because failures in earlier priorities can cascade. Prefer atomic tests seeded via APIs, and use dependsOnMethods only when an absolute hard prerequisite exists.
  4. How does TestNG handle multi-threaded parallel execution?
    Via the parallel attribute in testng.xml, which accepts methods, classes, or tests, paired with thread-count="N". When set to classes, TestNG executes up to N test classes simultaneously using a thread pool.
