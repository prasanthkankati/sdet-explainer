1.3 Stack vs Heap Memory & Pass-by-Value

How Stack frames store local variables and method calls, how the Heap allocates objects, and why Java is strictly Pass-by-Value.

Java separates short-lived method execution state from long-lived object data by storing method calls and local variables on the JVM Stack while allocating objects on the shared Heap. Every parameter passed to a Java method—whether a primitive value or an object reference—is copied by value onto the called method's Stack frame.

Before you start

Prerequisite: 1.2 JVM Architecture & Class Loader Subsystem

Where it fits

Understanding Stack frames and Heap references explains why passing a WebDriver into a Page Object shares the same browser session, while reassigning a parameter inside a helper method leaves the caller's variable unchanged.

Key points

  1. Each thread owns a private Last-In-First-Out (LIFO) JVM Stack that pushes a new Stack Frame on every method call and pops it immediately when the method returns.
  2. Every Stack Frame contains a Local Variable Array (method parameters and local variables), an Operand Stack (intermediate computation values), and Frame Data (return address and constant pool reference).
  3. Local primitives store their actual value directly inside the Stack Frame, whereas local object variables store only the 32-bit or 64-bit Heap memory address (reference).
  4. The Heap is a single shared memory area across all threads where every object created with new and every array lives until reclaimed by the Garbage Collector.
  5. Java is strictly Pass-by-Value: passing a primitive copies its numeric/boolean value; passing an object passes a copy of its Heap address reference, never the caller's variable slot itself.
  6. Unbounded recursion exhausts per-thread stack memory and throws java.lang.StackOverflowError, whereas retaining excessive live objects on the Heap throws java.lang.OutOfMemoryError: Java heap space.

How it works

  1. When main() starts, the JVM pushes a main frame onto the thread's Stack holding local variable driver.
  2. Executing new ChromeDriver() allocates the object block on the Heap (address @A1) and writes @A1 into the driver slot on the Stack.
  3. Calling openLogin(driver) pushes a new openLogin frame onto the Stack and copies the value @A1 into parameter d.
  4. Invoking d.get(...) dereferences @A1 on the Heap, modifying the shared browser session visible to the caller.
  5. Reassigning d = null; inside openLogin overwrites only the copied local slot in the openLogin frame; once the frame pops, main's driver still holds @A1.

Demonstrating Pass-by-Value behavior on primitives and object references:

package dev.java.jvm; // Declares package

public class StackHeapTrace { // Class loaded into Metaspace
    static class PageConfig { // Static nested class for Heap object state
        int timeoutSeconds = 10; // Instance field lives inside the Heap object
    } // Ends PageConfig
    static void mutateAndReassign(int retries, PageConfig cfg) { // Pushes new Stack frame with copies
        retries = 99; // Modifies local primitive copy on this frame only
        cfg.timeoutSeconds = 30; // Dereferences Heap address and mutates caller's object
        cfg = new PageConfig(); // Reassigns local reference copy to a brand-new Heap object
        cfg.timeoutSeconds = 50; // Modifies only the new local Heap object
    } // Pops Stack frame; local new object becomes unreachable for GC
    public static void main(String[] args) { // Pushes main Stack frame
        int retries = 3; // Local primitive stored directly on main Stack frame
        PageConfig config = new PageConfig(); // Reference on Stack points to Heap object
        mutateAndReassign(retries, config); // Passes copies of 3 and Heap reference
        System.out.println(retries + " | " + config.timeoutSeconds); // Prints: 3 | 30
    } // Pops main Stack frame
} // Ends StackHeapTrace

Common mistakes

  1. Claiming Java passes primitives by value and objects by reference; Java passes ALL arguments strictly by value, meaning object parameters receive a copied value of the Heap address rather than the caller's Stack variable slot.
  2. Writing a recursive Page Object wait retry helper without a termination counter; infinite self-invocation fills the Stack with frames and crashes with StackOverflowError.
  3. Storing large screenshots or base64 logs in a static List<byte[]> without clearing it; objects remain reachable from Metaspace forever and eventually trigger OutOfMemoryError: Java heap space.
  4. Assuming local variables inside a method need manual null cleanup before return; Stack Frames are popped automatically on method exit, dropping those references immediately.

Interview questions

Basics

What is the difference between Stack memory and Heap memory in Java?
Stack memory is allocated per thread in LIFO order to hold active method frames, local primitive values, and object references. Heap memory is shared across all threads and holds the actual objects created with new along with their instance fields and arrays. Stack memory is reclaimed instantly when a method returns, while Heap memory is reclaimed asynchronously by the Garbage Collector.

Why is Java considered strictly Pass-by-Value?
When a method is invoked, the JVM copies the contents of each caller variable into the new Stack frame's parameter slots. For primitives, that value is the number or boolean; for objects, that value is the Heap memory address. Because the called method only holds a copy of the address, reassigning the parameter variable (cfg = new PageConfig()) never changes which object the caller's variable points to.

Where do instance variables live versus local variables?
Local variables declared inside a method or constructor always live inside that method's Stack Frame (holding either the primitive value or the object reference). Instance variables belong to an object, so they always live inside that object's memory block on the Heap for the entire life of the object.

How it works

How can a helper method modify a caller's object if Java is Pass-by-Value?
Although the reference parameter is a copy of the caller's Stack slot, both variables now hold the identical Heap address. Calling a setter or mutating a field through the dot operator (cfg.timeoutSeconds = 30) follows that shared Heap address and modifies the single Heap object that the caller also points to. Reassigning the parameter itself breaks the link only for the callee's frame.

What are the three components inside a single JVM Stack Frame?
Each Stack Frame contains a Local Variable Array for parameters and local variables, an Operand Stack where bytecode instructions push and pop operands during arithmetic or method invocation, and Frame Data holding the return address and reference to the class's constant pool. When an exception occurs, the JVM reads active Stack Frames to build the printed stack trace.

What happens to objects created inside a method once that method returns?
When a method returns, its Stack Frame is popped and all local reference variables inside that frame vanish. Any Heap object created inside the method that was not returned or saved to a longer-lived field becomes unreachable. During the next Garbage Collection cycle, the JVM reclaims that unreachable Heap memory.

Real situations

In a Selenium framework, BaseTest passes driver into new LoginPage(driver), and LoginPage later calls driver = null; in a teardown bug. Why is BaseTest.driver not null?
Passing driver into the LoginPage constructor copied the Heap address of the ChromeDriver object into the constructor parameter and then into LoginPage.driver. Setting LoginPage's field to null only zeroes out LoginPage's reference copy. The driver reference inside BaseTest still holds the original Heap address.

Why can two parallel threads run the exact same Page Object method simultaneously without corrupting local variables?
Each TestNG thread owns an independent JVM Stack. Even when two threads invoke loginPage.enterCredentials(user, pass) on the same bytecode at the same millisecond, Thread 1 creates its frame with its own user and pass slots on Stack 1 while Thread 2 creates a separate frame on Stack 2. Only shared instance or static fields on the Heap risk thread interference.

Why does a swap(WebElement a, WebElement b) method fail to swap the two caller variables?
Inside swap, swapping parameters a and b only exchanges the two copied Heap addresses inside swap's Stack Frame. The moment swap returns, its Stack Frame is popped and the caller's original a and b variables retain their original Heap addresses.

Troubleshooting

How do you diagnose and fix a StackOverflowError in an automation test?
A StackOverflowError stack trace shows the same two or three method names repeating hundreds of times until the thread stack fills up. Common automation triggers include a method calling itself without a base exit condition, mutual recursion between Page Object constructors (Page A creates Page B which creates Page A), or a circular toString() implementation on an API POJO. Adding a termination guard or breaking the constructor cycle eliminates the error.

What causes OutOfMemoryError: Java heap space during a long Selenium regression run?
This error happens when live references hold onto large Heap objects across hundreds of tests so the Garbage Collector cannot free enough memory. Frequent culprits in test frameworks include storing full-page screenshot byte arrays in a static report list, leaking unclosed XSSFWorkbook Excel objects, or retaining finished WebDriver objects inside a non-cleaned collection. Releasing references after each test and increasing -Xmx prevents Heap exhaustion.

How do you adjust Stack size or Heap size for a Maven TestNG run?
Stack size per thread is configured via the JVM flag -Xss (for example, -Xss512k), and initial/maximum Heap sizes are configured via -Xms and -Xmx (for example, -Xms512m -Xmx2g). In Maven Surefire, pass these flags inside the <argLine> configuration element so forked test JVMs inherit the expanded memory.

Design choices

Why does Java keep Stack memory separate per thread instead of using a single global Stack?
Isolating one Stack per thread eliminates the need for thread locking when pushing frames, reading local variables, or evaluating method expressions. Every thread executes method calls at full speed without waiting for other threads, which directly enables scalable multi-threaded execution.

Why should Selenium Page Objects avoid storing mutable test state inside Heap fields when running parallel tests?
If a single Page Object instance or static utility class holds mutable instance fields on the shared Heap, concurrent threads overwrite each other's values. Keeping temporary data as local method variables on each thread's Stack guarantees isolation without locking.

Why did Java keep Pass-by-Value semantics for all parameters rather than adding C#-style ref or C++ pass-by-pointer-reference parameters?
Strict Pass-by-Value keeps method call behavior predictable because callers know a called method can never silently swap out which object a local Stack variable points to. When multiple values must be returned from a Page Object helper, returning a clean immutable DTO or record makes data flow explicit.

Quick answers

  1. Where are objects created with new stored? On the Heap.
  2. Where are local primitive variables and method parameters stored? On the thread's JVM Stack inside the active Stack Frame.
  3. Is Java Pass-by-Value or Pass-by-Reference? Strictly Pass-by-Value (references are copied as address values).
  4. Which memory error occurs on infinite recursion? StackOverflowError.
  5. Which JVM flags control minimum and maximum Heap size? -Xms (initial) and -Xmx (maximum).
  6. Which JVM flag controls per-thread Stack size? -Xss.
