Interview

P1.1 Question Bank: Playwright Architecture, Features, Tools & Setup (30 Questions)

Tier 1: Core Definitions, Architecture & Theory (Q1–Q7)

  1. What is Playwright at its core, and who develops it? (common)
    Playwright is an open-source test automation library and end-to-end testing framework created by Microsoft in 2020. It bundles a built-in test runner, auto-waiting web assertions, isolated browser contexts, and rich developer tooling. It automates Chromium, Firefox, and WebKit on Windows, macOS, and Linux without third-party drivers.
  2. How does Playwright communicate with browsers differently from Selenium WebDriver? (common)
    Selenium sends individual stateless HTTP commands over the W3C WebDriver wire protocol to an external driver binary (like ChromeDriver), which polls for state changes. Playwright establishes a single, persistent, bi-directional WebSocket connection directly to the browser process using native debugging protocols (such as Chrome DevTools Protocol / CDP). This enables real-time event streaming, network interception, and execution speeds measured in milliseconds.
  3. What is the difference between a Browser, a BrowserContext, and a Page in Playwright? (common)
    A Browser represents the single operating system binary process (e.g., chromium.exe). A BrowserContext is an isolated incognito-equivalent session inside that browser process, possessing its own independent cookies, localStorage, and cache. A Page is a single browser tab or window residing within a context.
  4. Why are Playwright assertions described as "web-first"? (common)
    Traditional assertion libraries (like Chai or JUnit) evaluate a condition as a one-time snapshot, immediately failing if an element is still rendering. Web-first assertions (e.g., await expect(locator).toBeVisible()) are asynchronous and automatically poll the DOM until the expected condition passes or the configured timeout expires. This eliminates explicit synchronization loops and timing race conditions.
  5. What is the difference between JavaScript and TypeScript in test automation? (common)
    JavaScript is dynamically typed, meaning types are evaluated at runtime and variables can mutate types without compiler errors. TypeScript is a statically typed superset of JavaScript that enforces strict type contracts at compile time. In test automation, TypeScript catches invalid locator payloads and incorrect method calls inside the IDE before running expensive browser tests.
  6. Why does TypeScript compile to JavaScript before running in Node.js? (common)
    Node.js and modern browser engines (like V8) natively execute ECMAScript (standard JavaScript) bytecode and do not understand TypeScript type annotations. The TypeScript compiler (tsc or Babel) strips away all type interfaces and compiles the source code into clean JavaScript. Playwright handles this compilation step on the fly with zero extra configuration.
  7. Which major browser rendering engines does Playwright support? (common)
    Playwright natively supports Chromium (the foundation for Google Chrome and Microsoft Edge), Firefox (Mozilla Gecko engine), and WebKit (Apple Safari engine). It executes tests against exact revisions of these rendering engines on Windows, macOS, and Linux.

Tier 2: Mechanics & How It Works (Q8–Q14)

  1. What exact actionability checks does Playwright perform during auto-waiting? (common)
    Before executing pointer or keyboard actions (like click() or fill()), Playwright verifies five sequential conditions: the element is attached to the DOM, visible, stable (not animating or moving), enabled (not disabled), and receiving events (not covered by an overlay). If any condition fails, Playwright retries continuously until the action timeout expires.
  2. How does Playwright handle Shadow DOM elements? (advanced)
    Playwright locators penetrate open Shadow DOM subtrees by default without requiring special XPath functions, pierce selectors, or JavaScript execution scripts. Locators like page.locator('custom-button') seamlessly locate elements nested within shadow roots as if they were standard DOM nodes.
  3. What occurs under the hood when executing npm init playwright@latest? (common)
    The initialization CLI creates a package.json (or updates the existing one) with the @playwright/test dependency, generates a production-ready playwright.config.ts, creates starter spec files in the tests/ folder, optionally configures a GitHub Actions CI workflow, and downloads the matching browser engine binaries.
  4. Why does Playwright download dedicated browser binaries instead of launching system Google Chrome? (advanced)
    System browsers receive automated background updates that can introduce unexpected regressions, driver mismatches, or OS-level profile locks. Playwright downloads pinned, reproducible open-source browser builds specifically tested against that exact Playwright library release. This guarantees 100% deterministic test execution across local workstations and headless CI pipelines.
  5. Where does Playwright cache downloaded browser binaries on the local filesystem? (common)
    On Windows, binaries are saved in %USERPROFILE%\AppData\Local\ms-playwright. On macOS, they reside in ~/Library/Caches/ms-playwright. On Linux, they are cached in ~/.cache/ms-playwright. Because binaries are stored globally in user home directories, multiple projects share identical browser versions without redundant downloads.
  6. How does Playwright's parallel execution model achieve high speed without heavy memory consumption? (advanced)
    Playwright launches a limited number of OS worker processes matching available CPU cores, and each worker runs a single browser instance. Within that browser instance, every test runs in a fresh, lightweight BrowserContext created in ~5–10ms. This avoids the heavy operating system overhead of launching and killing hundreds of browser processes.
  7. What is the purpose of the { page } fixture in Playwright test functions? (common)
    The { page } fixture is an automatically injected, isolated browser tab created within a pristine BrowserContext specifically for that individual test. Playwright manages its lifecycle, automatically opening the context before the test begins and closing it when the test completes.

Tier 3: Real Situations & Scenarios (Q15–Q20)

  1. You have a regression suite of 300 tests that takes 45 minutes in Selenium. How does Playwright reduce this time? (common)
    Playwright runs tests in parallel across worker processes using zero-overhead BrowserContext instances rather than cold browser boots. Furthermore, Playwright's persistent WebSocket connection eliminates HTTP request-response latency, and auto-waiting removes unnecessary hardcoded sleeps. Together, these features typically reduce a 45-minute suite to under 4 minutes.
  2. How do you emulate an iPhone 14 Pro Max in Playwright without connecting a real physical device? (common)
    Configure the project in playwright.config.ts using Playwright's built-in device descriptor: { name: 'Mobile Safari', use: { ...devices['iPhone 14 Pro Max'] } }. Playwright automatically configures the WebKit engine with the exact screen resolution, device pixel ratio, touch event support, and mobile user-agent string.
  3. How do you generate authentication state once and reuse it across 50 tests without logging in via the UI every time? (advanced)
    Execute a single setup test that logs in through the UI or API and saves the authenticated cookies and local storage to a file using await page.context().storageState({ path: 'auth.json' }). Then, configure storageState: 'auth.json' in playwright.config.ts so all worker contexts boot pre-authenticated, skipping login screens entirely.
  4. Your company tests both backend REST APIs and frontend web applications. How does Playwright consolidate this? (common)
    Playwright includes a built-in APIRequestContext accessible via the { request } fixture inside any test. You can send GET, POST, and PUT requests to seed database records, authenticate users, or validate JSON schemas directly inside the same framework that runs UI tests, eliminating the need for Postman, RestAssured, or Axios.
  5. An element on your web page renders inside a nested <iframe>. How do you interact with it in Playwright? (common)
    Use Playwright's page.frameLocator() API: await page.frameLocator('#payment-iframe').getByRole('button', { name: 'Submit Payment' }).click(). Playwright automatically waits for the iframe to load, switches context internally, and executes the click without needing driver.switchTo().frame() or manual parent frame resets.
  6. How do you record user interactions on an existing website and convert them into clean Playwright test code? (common)
    Run npx playwright codegen https://example.com in your terminal. Playwright launches a browser window alongside the Playwright Inspector, recording all clicks, form fills, and navigation events, while generating resilient, user-facing role locators (getByRole) in real time.

Tier 4: Troubleshooting & Debugging (Q21–Q25)

  1. Your test runs and completes with a PASS status, but none of the clicks or assertions actually happened. What went wrong? (common)
    You forgot the await keyword before an asynchronous Playwright action (e.g., page.click() instead of await page.click()). In JavaScript/TypeScript, calling an async function without await returns an unhandled Promise; the test execution finishes before the browser event loop processes the action.
  2. A test fails on your Ubuntu Linux CI pipeline with error while loading shared libraries: libasound.so.2, but passes locally on Windows. Why? (advanced)
    The browser binaries were downloaded without their required Linux graphic, audio, and font rendering system libraries. To resolve this on Ubuntu or Docker containers, execute npx playwright install --with-deps, which invokes the system package manager (apt-get) to install all missing operating system dependencies.
  3. A flaky test intermittently fails with a TimeoutError: locator.click: Timeout 30000ms exceeded. How do you troubleshoot this using Playwright tools? (common)
    Enable tracing by configuring trace: 'on-first-retry' in playwright.config.ts and view the generated trace via npx playwright show-trace trace.zip. The Trace Viewer allows you to scrub through time-travel DOM snapshots before and after the action, review console errors, and examine network waterfall requests to identify whether an API hung or an invisible overlay blocked the element.
  4. Why is using page.waitForTimeout(5000) considered a severe anti-pattern in Playwright? (common)
    Hardcoded sleeps force tests to wait for the entire fixed duration even if the application responded in 50 milliseconds, unnecessarily inflating suite run times. If network latency exceeds the hardcoded duration, the test still fails unpredictably. Playwright's auto-waiting and web-first assertions dynamically wait only for the exact milliseconds required for the element to become actionable.
  5. What is the difference between npx playwright test --debug and npx playwright test --ui? (common)
    --debug opens the Playwright Inspector, allowing line-by-line breakpoint stepping, live click-target highlighting, and manual console locator evaluations. --ui opens the Playwright UI Mode, a full visual test runner featuring watch mode, interactive time-travel DOM snapshots, network log inspection, and side-by-side spec editing.

Tier 5: Design Choices & Architecture (Q26–Q30)

  1. Why does Playwright default to fullyParallel: true in playwright.config.ts? (advanced)
    In legacy testing frameworks, tests inside a single file execute sequentially by default. Playwright's architecture isolates tests using ephemeral BrowserContext instances with zero shared state. Setting fullyParallel: true runs all test cases across all spec files concurrently across available worker threads, achieving maximum hardware resource saturation.
  2. Why should you use user-facing locators like getByRole over CSS selectors or XPath in Playwright? (common)
    User-facing locators (e.g., getByRole('button', { name: 'Submit' })) mirror how real users and assistive accessibility technologies perceive the application. They are decoupled from fragile DOM implementation details (like class names, div nesting, and auto-generated test IDs), making tests resilient to frontend refactoring and CSS redesigns.
  3. What is the purpose of the forbidOnly: !!process.env.CI setting in playwright.config.ts? (common)
    During local development, engineers frequently use test.only() to isolate and debug a single failing test. If committed to version control, forbidOnly ensures the continuous integration pipeline immediately fails the build, preventing developers from accidentally deploying suites where 99% of regression tests were skipped.
  4. How does Playwright's Trace Viewer differ from standard video recording? (advanced)
    Video recording captures a flat, non-interactive pixel stream that cannot be inspected. Trace Viewer records full DOM snapshots, action metadata, console logs, and network request/response headers. While reviewing a trace, engineers can open DevTools, inspect DOM elements, copy locators, and view exact HTTP payloads long after the test completed.
  5. When should an organization choose Playwright over Selenium for greenfield automation projects? (advanced)
    Choose Playwright when testing modern web applications that require auto-waiting, built-in network mocking, fast parallel cross-browser execution without driver maintenance, and first-class TypeScript tooling. Choose Selenium only when legacy browser support (like Internet Explorer), non-standard custom browser forks, or strict adherence to W3C-only vendor certifications are required.
