S1.1 Question Bank: Selenium WebDriver Architecture, The W3C Protocol & Driver Setup (35 Questions)

Tier 1: Core Definitions, Classification & Theory (Q1–Q7)

  1. What is Selenium WebDriver?
    Selenium WebDriver is an open-source, multi-language browser automation framework that controls web browsers natively by sending W3C-standard HTTP requests directly to browser-specific driver executables.
  2. Why did Selenium Core fail in 2004?
    Selenium Core operated via JavaScript injection directly into the webpage, which caused tests to crash whenever a test navigated across different domains due to the browser's Same-Origin Policy (RFC 6454).
  3. What was Selenium RC (Selenium 1.0) and how did it attempt to solve the Same-Origin Policy?
    Selenium RC introduced a local HTTP proxy server (running on port 4444) that intercepted browser requests, rewritten domain headers, and tricked the browser into believing the test script and the application under test originated from the same host.
  4. Why did Simon Stewart create WebDriver?
    WebDriver was created to bypass JavaScript execution sandboxes completely by controlling browsers from the outside through native operating system calls and browser debugging interfaces.
  5. What was the JSON Wire Protocol used in Selenium 2 and 3?
    It was a custom REST-like protocol where client libraries encoded commands into proprietary JSON envelopes with desiredCapabilities, requiring driver binaries to decode and translate them into native browser commands.
  6. What major architectural change occurred in Selenium 4 regarding protocols?
    Selenium 4 completely removed the JSON Wire Protocol and standardized all client-driver communication strictly on the W3C WebDriver specification, eliminating the translation layer.
  7. What is WebDriver BiDi?
    WebDriver BiDi is a next-generation W3C bidirectional protocol that operates over persistent WebSockets, allowing the browser to stream asynchronous events (console logs, network requests, DOM mutations) back to the client test script in real time.

Tier 2: Why / Why Not & Deep Comparisons (Q8–Q14)

  1. Why does Selenium WebDriver use native OS events instead of synthetic JavaScript events?
    Synthetic JavaScript events do not generate hardware scan codes and cannot interact with OS file dialogs, system-level alerts, or cross-domain iframes. Native OS events accurately replicate human user behavior.
  2. What is the difference between driver.close() and driver.quit()?
    driver.close() sends an HTTP POST command that closes only the active browser tab or window. driver.quit() sends an HTTP DELETE command that destroys all open windows and terminates the underlying driver binary operating system process.
  3. Why does failing to call driver.quit() lead to CI/CD agent failure?
    Orphaned driver executables (e.g. chromedriver.exe) remain active in background memory. In CI/CD pipelines executing hundreds of builds, these orphaned processes exhaust system RAM and CPU, eventually causing OutOfMemory crashes.
  4. How does Selenium WebDriver compare against Playwright?
    Selenium is built on the W3C WebDriver specification and communicates over HTTP/REST with BiDi WebSockets across 5 languages. Playwright runs over direct WebSockets via the Chrome DevTools Protocol across 4 languages and features built-in auto-waiting and browser context isolation.
  5. How does Selenium compare against Cypress?
    Selenium executes out-of-process and controls real browser windows natively across multiple tabs and origins. Cypress executes in-process inside an iframe within the browser DOM, restricting native multi-tab and cross-origin testing.
  6. Why is SearchContext the root interface rather than WebDriver?
    Because both WebDriver (the browser window) and WebElement (a specific DOM element) must possess the ability to search for elements using findElement() and findElements().
  7. Why is RemoteWebDriver significant in the class hierarchy?
    RemoteWebDriver is the core concrete class implementing WebDriver and JavascriptExecutor. All browser-specific classes (ChromeDriver, FirefoxDriver) extend RemoteWebDriver.

Tier 3: Setup, Driver Management & Build Tools (Q15–Q21)

  1. What was the problem with the manual System.setProperty() driver management approach?
    Desktop browsers auto-update every 4 weeks. Hardcoded paths to local driver binaries inevitably led to binary-browser version mismatches, throwing SessionNotCreatedException.
  2. How does Selenium Manager (Selenium 4.6.0+) resolve driver binaries?
    Selenium Manager automatically queries the operating system registry to determine the installed browser version, checks ~/.cache/selenium, and downloads the exact matching driver binary from vendor repositories if missing.
  3. What is the failure mode of Selenium Manager in corporate enterprise environments?
    In air-gapped networks or corporate environments protected by firewalls, Selenium Manager cannot access external vendor endpoints, throwing a NoSuchDriverException unless configured with proxy environment variables (SE_PROXY).
  4. What are the default communication ports for ChromeDriver and GeckoDriver?
    ChromeDriver defaults to port 9515; GeckoDriver (Firefox) defaults to port 4444.
  5. What exact dependencies are required in Maven for a Selenium TestNG project?
    org.seleniumhq.selenium:selenium-java (version 4.28.1) and org.testng:testng (version 7.10.2).
  6. What is the role of useTestNG() in a Gradle build.gradle file?
    It overrides Gradle's default test execution engine (which defaults to JUnit) to configure and run the suite using TestNG.
  7. Where does Selenium Manager store cached driver executables on Windows and Linux?
    On Windows: %USERPROFILE%\.cache\selenium\; on Linux/macOS: ~/.cache/selenium/.

Tier 4: Enterprise Production, Headless & Parallelism (Q22–Q28)

  1. Why is ThreadLocal<WebDriver> required in parallel TestNG execution?
    In multi-threaded execution, multiple tests run concurrently. A static WebDriver variable would be overwritten by concurrent threads, causing race conditions and test failures. ThreadLocal gives each thread its own isolated driver copy.
  2. Why must ThreadLocal.remove() be called in teardown?
    Test runners and application servers use thread pools that reuse threads. If remove() is not invoked, stale driver references linger in heap memory, causing severe memory leaks.
  3. Why is the --headless=new flag used in modern Chrome instead of legacy --headless?
    Chrome v109 introduced --headless=new, which runs the full, real Chrome browser engine without a UI shell, ensuring identical DOM rendering and extension support compared to headed Chrome.
  4. Why are --no-sandbox and --disable-dev-shm-usage required in Docker CI/CD containers?
    Docker containers default to a 64MB /dev/shm shared memory partition, which Chrome quickly exhausts, causing browser crashes. --no-sandbox disables OS security sandboxing when running as the root user.
  5. What does options.addArguments("--start-maximized") prevent?
    It prevents Chrome from launching in a small default 800x600 viewport, which causes responsive web designs to collapse desktop navigation elements into hidden mobile hamburger menus.
  6. What is the TestNG lifecycle order for WebDriver initialization and teardown?
    @BeforeSuite → @BeforeTest → @BeforeClass → @BeforeMethod (initialize driver) → @Test → @AfterMethod (quit and remove driver) → @AfterClass → @AfterTest → @AfterSuite.
  7. How do you execute tests in parallel across methods using testng.xml?
    Set <suite name="Suite" parallel="methods" thread-count="4"> in the testng.xml suite descriptor.

Tier 5: Common Exceptions, Root Causes & Rapid-Fire Traps (Q29–Q35)

  1. What causes SessionNotCreatedException: This version of ChromeDriver only supports Chrome version X?
    A version mismatch between the installed Google Chrome browser and the cached or hardcoded ChromeDriver executable.
  2. What causes IllegalStateException: The path to the driver executable must be set?
    Using Selenium 3 without configuring System.setProperty("webdriver.chrome.driver", path) and without having the executable on the OS PATH.
  3. What causes WebDriverException: address already in use: bind?
    An orphaned driver executable process from an earlier crashed test session is still running in the background and holding its default port (9515).
  4. How do you terminate orphaned driver executables on Windows and Linux via command line?
    Windows: taskkill /F /IM chromedriver.exe /T; Linux/macOS: pkill -f chromedriver.
  5. What causes NoSuchSessionException: Session ID is null?
    Calling a WebDriver method (e.g. driver.findElement()) after driver.quit() has already been executed on that session.
  6. What is the default implicit wait timeout in Selenium 4 if unconfigured?
    Exactly 0 seconds (0 milliseconds).
  7. Can WebDriver control mobile browsers on physical devices?
    Yes, via Appium, which extends the W3C WebDriver protocol to native, hybrid, and mobile web applications on iOS and Android.
