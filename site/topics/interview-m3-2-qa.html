M3.2 Question Bank: Decision Table, State Transition, Use Case & White-Box (35 Questions)

Tier 1: Core Definitions & Formulas (Q1–Q10)

  1. Q1: What is Decision Table Testing and when do we use it?
    A: Decision Table Testing (Cause-Effect Table) is a Black-Box technique used when system behavior depends on logical combinations of multiple input conditions. Each column represents one unique rule combination and maps to one test case.
  2. Q2: What is the formula to calculate the number of rules (columns) in a Decision Table?
    A: For $n$ boolean (True/False) conditions, the total number of combinations is $2^n$. If Condition 1 has 3 values, Condition 2 has 2 values, and Condition 3 has 2 values, the formula is the product of choices: $3 \times 2 \times 2 = 12$ rules.
  3. Q3: What does a hyphen (`-`) or `N/A` mean in a Collapsed Decision Table?
    A: `-` means "Don't Care" (the value of that condition does not affect the outcome—e.g., if `AccountLocked == True`, whether `PasswordValid` is True or False does not matter). `N/A` means the combination is logically impossible/mutually exclusive.
  4. Q4: What is State Transition Testing and when do we use it?
    A: State Transition Testing is a Black-Box technique used when a system has finite states and its output depends on both the current event/input AND its previous state history (e.g., order status lifecycles, ATM PIN lockout, multi-step wizard flows).
  5. Q5: What are the 4 components of a State Transition Diagram?
    A: (1) States (nodes the system can be in), (2) Events/Triggers (inputs causing a transition), (3) Guard Conditions (boolean rules allowing/blocking the transition), and (4) Actions/Outputs (results produced during the transition).
  6. Q6: What is the difference between a State Diagram and a State Transition Table?
    A: A State Diagram visually shows valid transitions between states (used for positive testing). A State Transition Table lists every state against every possible event in a grid, exposing invalid/null transitions (used for negative state testing).
  7. Q7: What is Use Case Testing and what are its 3 flow types?
    A: Use Case Testing derives end-to-end test scenarios from Actor ↔ System interactions: (1) Basic / Main Success Flow (happy path), (2) Alternative Flows (valid optional branches), and (3) Exception / Error Flows (system failures or invalid user actions).
  8. Q8: What is Error Guessing and Fault Attack Testing?
    A: An Experience-Based technique where the tester uses domain knowledge of historical defects to intentionally feed error-prone inputs (`null`, `0`, empty spaces, SQL injection quotes, rapid double-clicks, back-button navigation).
  9. Q9: What are the 2 primary White-Box (Structure-Based) coverage metrics?
    A: (1) Statement Coverage (percentage of executable lines of code run at least once), and (2) Branch / Decision Coverage (percentage of `true` and `false` outcomes of every `if/else/switch/loop` executed).
  10. Q10: What is Cyclomatic Complexity in White-Box testing?
    A: A metric ($V(G) = E - N + 2P$, or simply `1 + number of decision points [if, while, for, case, &&, ||]`) that equals the minimum number of independent test paths required to achieve 100% Basis Path / Branch Coverage of a method.

Tier 2: Why / Why Not & Deep Comparisons (Q11–Q18)

  1. Q11: Why does 100% Branch Coverage always guarantee 100% Statement Coverage, while 100% Statement Coverage does NOT guarantee 100% Branch Coverage?
    A: Consider `if (x > 0) { count++; } return count;`. A single test with `x = 5` executes every line of code (100% Statement Coverage), but it never tests what happens when `x <= 0` (the invisible `false` branch, so Branch Coverage is only 50%). Conversely, executing every branch (`true` and `false`) forces every reachable statement inside those branches to execute.
  2. Q12: Why do we need a State Transition Table in addition to a State Transition Diagram?
    A: Diagrams only draw arrows for *allowed* transitions (e.g., `PAID -> SHIPPED`). They omit disallowed transitions (e.g., what happens if someone sends a `SHIP` API request while the order is still in `CART` or `CANCELLED` state?). A State Table crosses every State × every Event, forcing QA to test every invalid cell.
  3. Q13: What is 0-Switch (1-Step) vs 1-Switch (2-Step) Coverage in State Transition Testing?
    A: 0-Switch Coverage tests every single individual valid transition arrow (`State A -> State B`) in isolation. 1-Switch Coverage tests every valid pair of two consecutive transitions (`State A -> State B -> State C`) to catch bugs that only occur when passing through sequences of states.
  4. Q14: When a Decision Table has 10 conditions ($2^{10} = 1,024$ rules), how do you reduce the test cases without missing critical defects?
    A: Use Decision Table Collapsing (merging "Don't Care `-`" columns and removing impossible `N/A` combinations) or Pairwise (All-Pairs) Testing, which guarantees every pair of condition values is tested together in ~15–20 test cases.
  5. Q15: What is the difference between Condition Coverage and Decision (Branch) Coverage in White-Box testing?
    A: In `if (A || B)`: Decision Coverage only requires the whole `if` to evaluate to `true` once (e.g., `A=T, B=F`) and `false` once (`A=F, B=F`). Condition Coverage requires each individual boolean sub-expression (`A` and `B`) to evaluate to both `true` and `false` at least once. MC/DC (Modified Condition/Decision Coverage) requires each condition to independently affect the decision outcome.
  6. Q16: Why is Error Guessing always used as a supplement to formal techniques (EP, BVA, Decision Tables) and never as a replacement?
    A: Because Error Guessing is unsystematic and depends entirely on the individual tester's memory and experience; without EP/BVA/Decision Tables first, you have zero mathematical proof of requirement coverage.
  7. Q17: How does Decision Table Testing help during STLC Phase 1 (Requirement Analysis)?
    A: Building a $2^n$ table immediately exposes missing requirements and contradictions in the SRS! For example, the Product Owner specifies what happens when `(VIP=True, Domestic=True)` and `(VIP=False, Domestic=False)`, completely forgetting to define the rule for `(VIP=True, Domestic=False)`.
  8. Q18: What is Checklist-Based Testing vs Exploratory Testing?
    A: Checklist-Based Testing uses a pre-built list of high-level verification items derived from past failures/standards (e.g., UI & API security checklist), whereas Exploratory Testing dynamically invents new hypotheses and tests in real time during a time-boxed session.

Tier 3: Real-World Tricky & Calculation Scenarios (Q19–Q25)

  1. Q19: Scenario: Calculate the Cyclomatic Complexity and minimum test cases for this Java method: `if (a > 0) { if (b > 0) { x = 1; } else { x = 2; } } else { x = 3; }`
    A: There are 2 decision points (`if (a > 0)` and `if (b > 0)`). Formula: V(G) = Decisions + 1 = 2 + 1 = 3. Therefore, a minimum of 3 test cases (`[a=1, b=1]`, `[a=1, b=-1]`, `[a=-1, b=0]`) achieves 100% Branch Coverage.
  2. Q20: Scenario: An airline booking flow has states: `SEARCH -> SEAT_SELECTED -> PAYMENT_PENDING -> TICKETED -> CANCELLED`. A user opens two browser tabs at `PAYMENT_PENDING`, cancels the booking in Tab 1 (`CANCELLED`), and clicks "Pay" in Tab 2. The system charges their card and moves the cancelled booking to `TICKETED`. What kind of bug is this?
    A: An Invalid State Transition / Race Condition Defect—the backend API failed to enforce the State Guard Condition (`if (order.getState() != PAYMENT_PENDING) throw InvalidStateException`) before processing payment.
  3. Q21: Scenario: A credit card application has 3 conditions: `Salary >= $50k (T/F)`, `CreditScore >= 700 (T/F)`, `ExistingCustomer (T/F)`. However, if `CreditScore < 700`, the bank ALWAYS rejects the application regardless of Salary or ExistingCustomer status. How many rules are in the Full Table vs the Collapsed Table?
    A: Full Table: 23 = 8 rules. Collapsed Table: The 4 rules where `CreditScore >= 700` is `False` collapse into 1 single rule (`Salary: -, CreditScore: F, Existing: - => REJECT`), reducing the table from 8 rules to `4 + 1 = 5` rules!
  4. Q22: Scenario: In a Java microservice, JaCoCo reports 92% Statement Coverage and 85% Branch Coverage, yet a `NullPointerException` crashes production on `user.getAddress().getCity()`. Why didn't high code coverage prevent this?
    A: Code coverage only measures what percentage of *existing written code* was executed by tests—it cannot detect missing null-check branches that the developer forgot to write (`if (user.getAddress() != null)`), nor does it test data permutations unless negative `null` inputs are passed.
  5. Q23: Scenario: You are testing a Wizard form (`Step 1: Personal Info -> Step 2: Employment -> Step 3: Upload Docs -> Step 4: Review & Submit`). What State Transition tests must you execute beyond clicking `Next -> Next -> Next -> Submit`?
    A: (1) Clicking `Back` from Step 3 to Step 2 and verifying entered data is preserved, (2) Directly typing `/wizard/step-4` in the URL while still on Step 1 (forced URL state-jumping), (3) Refreshing (`F5`) on Step 3, and (4) Session timeout on Step 3 followed by re-login.
  6. Q24: Scenario: A requirement states: "Users can apply a Promo Code OR Loyalty Points, but never both in the same order." Which technique best models this rule?
    A: Decision Table Testing with 2 conditions (`PromoCodeApplied [T/F]`, `LoyaltyPointsApplied [T/F]`) = 22 = 4 rules, explicitly verifying that `Rule 1 (T, T)` triggers a mutual-exclusion error message.
  7. Q25: Scenario: How do you combine EP, BVA, Decision Tables, and State Transition on a single "ATM Cash Withdrawal" feature?
    A: (1) State Transition: Card Inserted → PIN Entered (1st, 2nd, 3rd wrong attempt lockout) → Authenticated. (2) Decision Table: `[Account Active? T/F] x [Balance >= Amount? T/F] x [ATM Has Cash? T/F]`. (3) EP & BVA: Withdrawal amount field (`min = $10, max = $1,000`, step `$10` → test `$0, $9, $10, $11, $990, $1000, $1010`).

Tier 4: SDET, Automation (Selenium / TestNG / JaCoCo) Application (Q26–Q30)

  1. Q26: How do you translate a Decision Table directly into a TestNG automated test?
    A: Each column (Rule) of the Decision Table becomes 1 row in a TestNG `@DataProvider` array (`new Object[][] { {true, true, true, true, true}, {true, true, false, true, false}, ... }`), passed into a single `@Test(dataProvider = "shippingRules")` method.
  2. Q27: How do you enforce White-Box Statement and Branch coverage automatically in a Maven CI/CD pipeline?
    A: Add the `jacoco-maven-plugin` to `pom.xml` with a `check` goal rule (`<counter>BRANCH</counter><value>COVEREDRATIO</value><minimum>0.80</minimum>`). If a developer's PR drops branch coverage below 80%, `mvn verify` fails the build automatically.
  3. Q28: How do you test Invalid State Transitions faster than clicking through a browser in Selenium?
    A: Use RestAssured API tests to create an order in state `CREATED`, cancel it (`POST /orders/{id}/cancel`), and immediately send `POST /orders/{id}/ship` or `POST /orders/{id}/pay`, asserting that the backend returns `409 Conflict` or `400 Bad Request`.
  4. Q29: In Selenium UI automation, how do Use Case tests map to your framework structure?
    A: Each end-to-end Use Case maps to an end-to-end `@Test` method that chains multiple Page Objects (`LoginPage -> ProductSearchPage -> CartPage -> CheckoutPage -> OrderConfirmationPage`).
  5. Q30: What is Mutation Testing (e.g., PITest in Java) and how does it go beyond JaCoCo Branch Coverage?
    A: A developer can get 100% JaCoCo coverage by running code *without writing a single `Assert` statement*! PITest (Mutation Testing) automatically modifies bytecode in memory (changing `+` to `-` or `>=` to `>`) and re-runs tests—if your tests still pass when the code is mutated, your assertions are weak ("escaped mutant").

Tier 5: Rapid-Fire Yes/No & 1-Liner Traps (Q31–Q35)

  1. Q31: How many rules are in a full Decision Table with 5 boolean conditions?
    A: 25 = 32 rules.
  2. Q32: Is Cause-Effect Graphing related to Decision Table Testing?
    A: Yes—a Cause-Effect Graph is visually converted into a Decision Table.
  3. Q33: Does 100% Statement Coverage guarantee 100% Branch Coverage?
    A: No (100% Branch Coverage guarantees 100% Statement Coverage, not vice versa).
  4. Q34: Which technique is best for testing a 3-attempt PIN lockout rule?
    A: State Transition Testing.
  5. Q35: Is Error Guessing a Black-Box, White-Box, or Experience-Based technique?
    A: Experience-Based technique.
