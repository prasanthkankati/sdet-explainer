2.2 Functional Testing: Smoke vs Sanity & Regression vs Retesting

1. The Base: What is Functional Testing and What Problem Does It Solve?

Functional Testing is the branch of Dynamic Testing that verifies WHAT the system does by feeding valid, invalid, and boundary inputs into every feature and asserting that the actual output matches the business specification (SRS / User Stories).

The Problem It Solves: In an active project, developers deploy new builds every day—sometimes adding a new feature, sometimes fixing a single bug, and sometimes refactoring shared code. If QA runs all 2,000 test cases on every tiny build, testing takes 3 days per build. If QA only tests the 1 changed line, a broken checkout flow escapes to production. Functional Testing divides execution into targeted execution types (`Smoke`, `Sanity`, `Retesting`, `Regression`, `Exploratory`, `Ad-Hoc`) so QA knows which exact subset of tests to run on each build drop.

2. Core Terms & Their Properties Defined First

Before comparing the functional testing types, understand the 4 foundational properties that distinguish them:

  • 1. Breadth vs Depth (Wide & Shallow vs Narrow & Deep):
    • Wide & Shallow: Touching every major module of the application (Login, Search, Cart, Checkout, Profile) with 1–2 basic happy-path tests each, without digging into negative edge cases.
    • Narrow & Deep: Focusing on only 1–2 recently modified modules (e.g., only the Coupon Engine) and testing every positive, negative, and boundary rule inside that module.
  • 2. Positive Testing vs Negative Testing:
    • Positive Testing (Happy Path): Providing valid inputs (`amount = 500`) to prove the application works as expected.
    • Negative Testing (Sad/Error Path): Providing invalid, malformed, or out-of-range inputs (`amount = -50`, expired card, SQL string) to prove the application gracefully rejects bad data with the right error message instead of crashing.
  • 3. Scripted Testing vs Unscripted (Experience-Based) Testing:
    • Scripted Testing: Following pre-written Test Cases or automated Selenium/TestNG scripts step by step (`Smoke, Sanity, Retesting, Regression`).
    • Unscripted Testing: Simultaneous learning, test design, and execution by a human tester using domain knowledge (`Exploratory, Ad-Hoc, Monkey Testing`).

3. Classification Tree: All 6 Functional Execution Types

Based on why the build was deployed and what risk we are checking, Functional Testing splits into 6 core execution types:

  1. Smoke Testing (Build Verification Testing — BVT) — Wide & Shallow health check on a new build.
  2. Sanity Testing — Narrow & Deep check on a specific newly changed/fixed module.
  3. Retesting (Confirmation Testing) — Re-running a previously failed test case to confirm a specific bug is fixed.
  4. Regression Testing — Re-running existing passing test cases to ensure code changes did not break old features.
    • Sub-Types: Unit Regression, Regional (Partial) Regression, and Full Regression.
  5. Exploratory Testing — Structured, time-boxed (Session-Based) unscripted investigation of edge cases.
  6. Ad-Hoc Testing (Monkey / Gorilla Testing) — Informal, random unscripted bug hunting without test charters.

4. Each Functional Testing Type Defined & Explained in Order

① Smoke Testing (Build Verification Testing — BVT)

  • Definition: A fast, surface-level (Wide & Shallow) health check executed on a newly deployed build to verify that critical end-to-end functionalities (App launch, Login, Home, Cart, DB connection) work without crashing.
  • Key Properties: (a) Runs at STLC Phase 4 Gate, (b) Checks only positive happy paths across all major modules, (c) Fully scripted/automated (`@Test(groups="smoke")`), (d) Performed by Dev (pre-drop) and QA/CI-CD (post-drop).
  • In what exact cases we perform it: Immediately on every new build deployment or Git Pull Request before spending any manual QA effort.

② Sanity Testing

  • Definition: A focused, Narrow & Deep evaluation of a specific module or functionality after receiving a relatively stable build containing minor code changes or bug fixes, to verify that the new logic works rationally before running full regression.
  • Key Properties: (a) Narrow scope (only the impacted module, e.g., Checkout Tax calculation), (b) Deep checks (positive + negative + boundary rules of that module), (c) Unscripted or a targeted subset of Regression, (d) Performed strictly by QA.
  • In what exact cases we perform it: On Build #10, #11, #12 when a developer changes the GST discount formula in the Cart module and you want to deeply verify the Cart module in 15 minutes before triggering a 2-hour regression run.

③ Retesting (Confirmation Testing)

  • Definition: Executing a previously failed test case again on a new build using the exact same test steps and test data to confirm that the reported defect has actually been fixed by the developer.
  • Key Properties: (a) Targets only `FAILED` test cases linked to fixed Jira bugs, (b) Uses identical input data that triggered the bug, (c) Cannot be pre-automated ahead of time as a permanent suite (though once fixed, the test joins Regression).
  • In what exact cases we perform it: Whenever a developer moves a Jira bug from `IN PROGRESS` to `READY FOR QA`.

④ Regression Testing (And Its 3 Sub-Types)

  • Definition: Re-executing previously passing test cases across existing modules after a code change, bug fix, or configuration update to ensure that old working features have not regressed (broken as an unintended side effect).
  • The 3 Sub-Types of Regression Testing:
    1. Unit Regression: Testing only the single changed code unit/component in isolation after a tiny local fix.
    2. Regional (Partial / Impact-Based) Regression: Testing the modified module plus its directly connected neighbor modules identified via Impact Analysis (e.g., if `Cart` changed, run Regression on `Product Catalog`, `Cart`, and `Payment`).
    3. Full Regression: Executing 100% of the regression suite across the entire application—mandatory before a major production release, framework upgrade, or database migration.
  • Why Regression is #1 for Selenium Automation: Manual regression of 1,500 test cases every 2-week sprint is impossible; SDETs automate Regression in Selenium/Playwright + TestNG to run in parallel on CI/CD every night.

⑤ Exploratory Testing vs ⑥ Ad-Hoc Testing

  • Exploratory Testing (Structured Unscripted): Time-boxed (typically 60–90 minute Session-Based Test Management [SBTM] charters) where an experienced QA engineer simultaneously explores the app, designs edge-case attacks on the fly, and logs notes/defects.
  • Ad-Hoc Testing (Unstructured Unscripted): Informal, random bug-hunting without any test cases, charters, or timers. Includes Monkey Testing (random chaotic clicks/inputs to crash the app) and Buddy/Pair Testing (1 Dev + 1 QA testing together at one desk).

Interview Answer: "Smoke vs Sanity: Smoke testing is wide and shallow across the whole application on initial builds to verify stability, whereas Sanity testing is narrow and deep on a specific module after minor changes or bug fixes. Retesting vs Regression: Retesting re-runs previously failed test cases to confirm a specific bug fix works, whereas Regression re-runs previously passing test cases to ensure that the code change didn't accidentally break existing functionality."

6. Real Selenium + TestNG Code Trace: Running Smoke, Sanity & Regression via Groups

In a real Maven + TestNG + Selenium framework, SDETs tag `@Test` methods with `groups` so Jenkins can trigger Smoke (3 mins), Sanity on Checkout (5 mins), or Full Regression (30 mins) via a single CLI flag:

import org.testng.Assert;
import org.testng.annotations.Test;

public class OrderFlowTest extends BaseTest {

    // 1. SMOKE TEST: Wide & Shallow health check (Runs on EVERY PR & Build drop)
    @Test(groups = {"smoke", "regression"})
    public void verifyLoginAndHomeDashboardLoad() {
        LoginPage login = new LoginPage(getDriver());
        DashboardPage dash = login.loginAs("qa_user@shop.com", "Pass#123");
        Assert.assertTrue(dash.isLoaded(), "Smoke Failed: Dashboard did not load!");
    }

    // 2. SANITY + REGRESSION TEST: Narrow & Deep check on Coupon Module after a fix
    @Test(groups = {"sanity-coupon", "regression"})
    public void verifyExpiredCouponShowsExactErrorBanner() {
        CartPage cart = new CartPage(getDriver());
        cart.applyCoupon("EXPIRED2020");
        Assert.assertEquals(cart.getErrorText(), "ERR_COUPON_EXPIRED");
    }

    // 3. RETESTING -> REGRESSION: Added for Jira BUG-409 (Tax rounding on $99.99)
    @Test(groups = {"regression"}, description = "BUG-409: Confirm tax rounding fix")
    public void verifyTaxRoundingOnNinetyNineNinetyNine() {
        CartPage cart = new CartPage(getDriver());
        Assert.assertEquals(cart.calculateTax(99.99, 18.0), 18.00);
    }
}
# Trigger only Smoke Gate on PR (Fast 3-minute build check):
mvn clean test -Dgroups="smoke"

# Trigger only Coupon Sanity suite after Dev fixes Coupon service:
mvn clean test -Dgroups="sanity-coupon"

# Trigger Full Nightly Regression Suite in parallel:
mvn clean test -Dgroups="regression" -Dparallel="methods" -DthreadCount=4
