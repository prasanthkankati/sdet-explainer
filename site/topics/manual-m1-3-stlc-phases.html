1.3 STLC: All 6 Phases, Entry & Exit Criteria

1. The Base: What is STLC and How Does It Fit Inside SDLC?

The Software Testing Life Cycle (STLC) is the structured 6-phase testing workflow executed by the QA and SDET team—spanning Requirement Analysis, Test Planning, Test Case Development, Environment Setup, Test Execution, and Test Cycle Closure—to systematically verify and validate software.

Where It Falls (SDLC vs STLC): While SDLC governs the entire engineering organization (Product, Architects, Developers, QA, DevOps) from idea to production maintenance, STLC is the dedicated Testing sub-lifecycle that runs in parallel with SDLC phases so QA is never an unstructured afterthought.

The Problem It Solves (In Plain Words): Without a structured testing lifecycle, three chaotic failures happen in every project:

  1. Testing Unstable Code (Wasted QA Time): Developers hand over an uncompiled or crashing version of the app, and QA wastes hours trying to run tests on a server where even the Login page crashes.
  2. Missed Business Rules (Zero Requirement Tracking): A specification has 50 business rules, but QA only writes tests for 40 of them because nobody tracked which requirement maps to which test case.
  3. Subjective Releases (Guesswork Sign-Off): The product is pushed to customers based on "it looks fine" rather than proving that 100% of planned tests ran and zero critical bugs remain open.

2. Core Terms & Their Properties Defined First (Before Reading the 6 Phases)

Before walking through the 6 STLC phases, you must know the exact meaning and properties of the 5 foundational STLC building blocks:

① What is a Software Build vs a Broken Build?

  • Software Build: When developers finish writing source code (.java / .ts), a CI server (like Jenkins) compiles, packages, and deploys that code into a testable version (e.g., Build #142 or app-v2.4.jar) on the QA server.
  • Broken Build: A deployed build that fails basic compilation, fails server startup, or crashes on core primary flows (like Login or Database connection), making full QA testing impossible.
  • Exact Properties of a Broken Build:
    • Property 1 — Build Identifier: Version tag / Git commit SHA (e.g., v2.4.1-b142) that uniquely identifies the faulty drop.
    • Property 2 — Failure Stage: Fails during compilation, database migration, container startup, or the Phase 4 Smoke Test Gate.
    • Property 3 — Blocking Impact: Blocks 50%–100% of downstream manual and Selenium test execution (e.g., HTTP 500 on login).
    • Property 4 — QA Protocol: QA immediately rejects a broken build at Phase 4, logs a Blocker defect, and halts Phase 5 until Dev deploys a healthy build.

② What is an RTM (Requirement Traceability Matrix) & Its Properties?

  • Definition: An RTM is a structured mapping document (Excel sheet, Jira Xray, or TestRail table) that connects every single Requirement ID to its Test Case IDs, Execution Status, and Defect IDs so zero requirements are ever missed.
  • The 3 Types of Traceability in an RTM:
    1. Forward Traceability (Requirement → Test Case): Maps each Requirement ID to its Test Cases to verify "Does every requirement have at least one positive and negative test case?"
    2. Backward / Reverse Traceability (Test Case → Requirement): Maps each Test Case ID back to a Requirement ID to verify "Are we writing gold-plated tests for features nobody asked for?"
    3. Bi-Directional Traceability (Forward + Backward): Combines both directions—the industry standard used in STLC.
  • Exact Properties (Columns) of a Real RTM:

③ What are Entry Criteria, Exit Criteria, Deliverables & Sign-Off Criteria?

  1. Entry Criteria (Prerequisites to Start): The mandatory inputs and conditions that must exist before a phase is allowed to begin (e.g., "QA will not start Phase 5 Test Execution until the Smoke Test passes 100%").
  2. Deliverables (Work Products): The tangible documents, scripts, or reports produced as output of a phase (e.g., Test Plan, RTM, Automated Scripts, Test Summary Report).
  3. Exit Criteria (Gate to Finish): The measurable quality conditions that must be completed before a phase can be closed (the Exit Criteria of Phase N unlock the Entry Criteria of Phase N+1).
  4. Release Sign-Off Criteria (Final Phase 6 Gate): The objective checklist required to approve a production release: (a) 100% Requirement Coverage in RTM, (b) 100% Planned Tests Executed, (c) ≥ 95% Pass Rate, and (d) 0 Open Blocker/Critical Defects.

Interview Answer: "SDLC is the overarching development lifecycle for the whole product, whereas STLC is the 6-phase testing lifecycle owned by QA. Every STLC phase is governed by strict Entry Criteria (prerequisites to start), Activities, Deliverables (like the RTM), and Exit Criteria (like passing the Smoke Test to reject Broken Builds and meeting Release Sign-Off criteria)."

4. Deep Breakdown of Each STLC Phase in Order

① Phase 1: Requirement Analysis

  • Goal: Understand what to test, spot missing/contradictory rules early (Static Verification), and decide what can be automated.
  • Entry Criteria: BRS / SRS / Jira User Stories and Architecture/Wireframe docs are shared with QA.
  • Activities:
    1. Identify Functional vs Non-Functional testable requirements.
    2. Log requirement gaps, missing edge cases, and ambiguities with the BA/Product Owner.
    3. Initialize the RTM (Requirement Traceability Matrix) listing every Requirement ID.
    4. Perform Automation Feasibility Analysis (evaluate DOM stability, ROI, API availability, and tool support for Selenium/Playwright).
  • Exit Criteria & Deliverables: All requirement ambiguities resolved; **Ambiguity Review Report**, **Initial RTM**, and **Automation Feasibility Report** signed off.

② Phase 2: Test Planning

  • Goal: Define the blueprint of how, who, when, and with what tools testing will be done.
  • Entry Criteria: Clarified requirements, initial RTM, and Automation Feasibility Report.
  • Activities:
    1. Draft the **Test Plan** document: define **In-Scope** (features/browsers to test) and **Out-of-Scope** items.
    2. Select test types (Smoke, Sanity, Regression, API, Performance) and automation stack (`Java`, `Selenium`, `TestNG`, `Maven`, `Jenkins`).
    3. Perform **Test Effort Estimation** (using Work Breakdown Structure, Story Points, or 3-Point Estimation) and assign QA roles.
    4. Define **Risk & Mitigation Plan** (e.g., what if staging DB is delayed?) and set formal Entry/Exit criteria for execution.
  • Exit Criteria & Deliverables: **Approved Test Plan Document** and **Effort/Schedule Baseline**.

③ Phase 3: Test Case Design & Development

  • Goal: Write detailed positive/negative manual test cases, prepare test data, and build automated test scripts.
  • Entry Criteria: Approved Test Plan, frozen UI designs/locators, and API contracts.
  • Activities:
    1. Write step-by-step **Test Cases** (Preconditions, Test Steps, Test Data, Expected Result) using **Equivalence Partitioning** and **Boundary Value Analysis**.
    2. Conduct **Peer Review** (Static Verification) of written test cases and map every Test Case ID to its Requirement ID in the **RTM**.
    3. Create **Test Data** sets (`.xlsx` sheets, `.json` payloads, SQL seed scripts).
    4. Write & review **Selenium Page Objects and TestNG `@Test` scripts** in Git.
  • Exit Criteria & Deliverables: **Reviewed & Approved Test Cases**, **Updated RTM**, **Test Data files**, and **Merged Automation Scripts**.

④ Phase 4: Test Environment Setup

  • Goal: Prepare the hardware, software, network, and database where dynamic testing will run, and verify build health.
  • Entry Criteria: Test Plan specifying environment needs; Dev build deployed to QA server.
  • Activities:
    1. Configure QA server URLs, database connections, mock services, and Selenium Grid / Docker / BrowserStack nodes.
    2. Load baseline test data into the QA database.
    3. Execute the **Smoke Test (Build Verification Test)** to verify core application stability before opening full QA execution.
  • Exit Criteria & Deliverables: QA Environment operational; **Smoke Test Report = PASSED**. *(If Smoke Test fails, the build is rejected immediately!)*

⑤ Phase 5: Test Execution

  • Goal: Run manual and automated test cases against the live QA build, report defects, and verify fixes.
  • Entry Criteria: Smoke Test passed, Approved Test Cases & Test Data ready, RTM mapped.
  • Activities:
    1. Execute manual test cases and trigger automated **Selenium / API suites** (`mvn clean test`).
    2. Compare Actual Result vs Expected Result; mark each test `PASS`, `FAIL`, or `BLOCKED` in the RTM / Jira Xray / TestRail.
    3. Log failed test cases as **Defects in Jira** with clear steps to reproduce, severity/priority, screenshots, and logs.
    4. Perform **Retesting (Confirmation Testing)** on fixed bugs and **Regression Testing** to verify fixes didn't break existing flows.
  • Exit Criteria & Deliverables: 100% planned test cases executed; all Blocker/Critical/High defects fixed and verified; **Completed RTM**, **Defect Reports**, and **Automation Execution Reports (ExtentReports)**.

⑥ Phase 6: Test Cycle Closure

  • Goal: Formally evaluate release readiness, archive test assets, calculate quality metrics, and sign off.
  • Entry Criteria: Test Execution phase completed; all Exit Criteria met (or open low-priority bugs formally waived by Product).
  • Activities:
    1. Verify 100% requirement coverage in the final RTM.
    2. Calculate quality metrics: **Test Coverage %**, **Defect Density**, **Defect Removal Efficiency (DRE)**, and **Automation Pass Rate**.
    3. Document **Lessons Learned** (what caused delays or flaky tests) and clean up test environments.
    4. Publish the **Test Closure / Test Summary Report** and issue formal **QA Release Sign-Off**.
  • Exit Criteria & Deliverables: **Signed-Off Test Summary Report** and **Release Go/No-Go Sign-Off**.

6. Real SDET Code Trace: Enforcing STLC Phase 4 Smoke Gate & Phase 5 RTM

// In TestNG + Selenium, we tag tests by STLC phase & RTM Requirement ID:
public class CheckoutTest extends BaseTest {

    // Phase 4 Gate: Runs in 'mvn test -Dgroups=smoke' — blocks Phase 5 if it fails!
    @Test(groups = {"smoke"}, description = "RTM_REQ_101: Verify Checkout page loads")
    public void verifyCheckoutPageLoads() {
        CheckoutPage page = new CheckoutPage(getDriver());
        Assert.assertTrue(page.isLoaded(), "Smoke Gate Failed: Checkout page down!");
    }

    // Phase 5 Execution: Runs only after Smoke Gate passes
    @Test(groups = {"regression"}, dependsOnGroups = {"smoke"},
          description = "RTM_REQ_102: Verify discount coupon deduction")
    public void verifyDiscountCoupon() {
        CheckoutPage page = new CheckoutPage(getDriver());
        Assert.assertEquals(page.applyCoupon("SAVE20", 100.0), 80.0);
    }
}
