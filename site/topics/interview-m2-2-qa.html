M2.2 Question Bank: Smoke vs Sanity & Regression vs Retesting (35 Questions)

Tier 1: Core Definitions & Classification (Q1–Q10)

  1. Q1: What is Functional Testing?
    A: Functional Testing is black-box dynamic testing that validates what the software does—verifying every feature, user workflow, API response, and business rule against the SRS/User Stories using valid, invalid, and boundary inputs.
  2. Q2: What is Smoke Testing and why is it also called Build Verification Testing (BVT)?
    A: Smoke Testing is a wide and shallow health check executed immediately when a new build is deployed to verify that core end-to-end happy paths work. It is called BVT because it decides whether the build is stable enough to be accepted into QA or rejected as a Broken Build.
  3. Q3: What is Sanity Testing?
    A: Sanity Testing is a narrow and deep check executed on a specific module or feature after receiving a relatively stable build with minor code changes or bug fixes, verifying that the new logic works rationally before running full regression.
  4. Q4: What is Retesting (Confirmation Testing)?
    A: Retesting is re-executing a previously failed test case with the exact same steps and input data on a new build to confirm that a specific defect reported earlier has been successfully fixed.
  5. Q5: What is Regression Testing?
    A: Regression Testing is re-executing previously passing test cases after code changes, bug fixes, enhancements, or configuration updates to ensure that existing, unchanged features were not accidentally broken.
  6. Q6: What are the 3 types of Regression Testing?
    A: (1) Unit Regression (testing only the changed code unit), (2) Regional / Partial Regression (testing the changed module plus directly impacted adjacent modules), and (3) Full Regression (testing the entire application end-to-end before a release).
  7. Q7: What is Positive Testing vs Negative Testing?
    A: Positive Testing feeds valid inputs to verify the system completes the happy path as expected. Negative Testing feeds invalid, unexpected, or boundary-violating inputs to verify the system handles errors gracefully without crashing or exposing stack traces.
  8. Q8: What is Exploratory Testing and how is it structured?
    A: Exploratory Testing is an experience-based approach where test design and execution happen simultaneously. In professional QA, it is structured using Session-Based Test Management (SBTM): 60–90 minute time-boxed charters targeting a specific module and risk area.
  9. Q9: What is Ad-Hoc Testing vs Monkey Testing vs Gorilla Testing?
    A: Ad-Hoc Testing is informal, unstructured testing without test cases or documentation. Monkey Testing feeds random, rapid, chaotic clicks/inputs with zero domain rules to check if the app crashes. Gorilla Testing repeatedly hammers one single module deeply with every possible input to test its robustness.
  10. Q10: Which testing type is a subset of Acceptance Testing, and which is a subset of Regression Testing?
    A: Smoke Testing is a subset of Acceptance/System Testing (verifying build acceptance); Sanity Testing is a subset of Regression Testing (verifying a narrow slice of regression deeply).

Tier 2: Why / Why Not & Deep Comparisons (Q11–Q18)

  1. Q11: What are the 5 key differences between Smoke Testing and Sanity Testing?
    A: (1) Scope: Smoke is Wide & Shallow across the whole app; Sanity is Narrow & Deep on 1–2 changed modules. (2) Timing: Smoke runs on initial/every build drop; Sanity runs on stable builds after minor fixes/changes. (3) Scripted: Smoke is formally scripted & automated; Sanity is often unscripted or a targeted subset. (4) Who runs it: Smoke is run by Dev or QA/CI; Sanity is run strictly by QA. (5) Goal: Smoke checks overall build stability; Sanity checks rationality of a specific change.
  2. Q12: What are the 4 key differences between Retesting and Regression Testing?
    A: (1) Target cases: Retesting runs previously *failed* test cases; Regression runs previously *passed* test cases. (2) Goal: Retesting verifies a bug fix worked; Regression checks for unexpected side effects in old features. (3) Order: Retesting always runs *before* Regression on a fix build. (4) Automation: Regression is automated; initial Retesting is targeted to the specific defect.
  3. Q13: Why does Retesting always come BEFORE Regression Testing when a bug-fix build is deployed?
    A: Because if the developer's bug fix didn't even work (Retesting fails), running a 2-hour Regression suite to see if that broken fix caused side effects is a complete waste of compute and QA time.
  4. Q14: Why do we automate Smoke and Regression suites first, rather than automating Ad-Hoc or Exploratory tests?
    A: Smoke and Regression tests are repetitive, predictable, and executed hundreds of times across sprints (giving massive ROI when automated in Selenium/Playwright), whereas Exploratory and Ad-Hoc tests rely on human intuition, creativity, and changing hypotheses.
  5. Q15: Why do existing features break when a developer only fixes a 2-line bug in another module (Why does Regression happen)?
    A: Due to shared dependencies: shared utility classes, global CSS styles, database foreign-key constraints, shared Redux/session state, or common REST API DTOs. Changing a shared helper for Module A can silently alter behavior in Module B.
  6. Q16: How do you perform Impact Analysis to select a Regional Regression suite when time is limited?
    A: (1) Inspect the Git PR diff / changed classes and API endpoints, (2) Query the RTM and architecture dependency graph to see which downstream modules call those classes/tables, (3) Select high-priority/business-critical test cases (`P0/P1`) covering those modules, and (4) Include historically bug-prone hotspot modules (Principle #4).
  7. Q17: Why is Negative Testing often where the highest-severity production bugs are found?
    A: Developers naturally test the Positive "happy path" on their local machine before committing code, so happy paths rarely fail completely. However, developers frequently forget null checks, double-click race conditions, expired tokens, or special-character payloads—which only Negative Testing uncovers.
  8. Q18: What is Defect Cascading vs Side-Effect Regression?
    A: Defect Cascading is when one unspotted bug inside Module A triggers a chain of secondary bugs in Modules B and C at runtime. Side-Effect Regression is when the *code change written to fix* a bug in Module A breaks previously working code in Module B.

Tier 3: Real-World Tricky & Edge-Case Scenarios (Q19–Q25)

  1. Q19: Scenario: Build #25 is deployed at 10:00 AM with 3 bug fixes in the "Forgot Password" flow. Walk through the exact sequence of functional tests you execute from 10:00 AM onward.
    A: (1) 10:00 AM — Smoke Test: Run the automated Smoke suite (`mvn test -Dgroups=smoke`) to ensure Build #25 boots and core flows work. (2) 10:05 AM — Retesting: Re-run the exact 3 failed test cases for the 3 fixed "Forgot Password" bugs to confirm they now pass. (3) 10:15 AM — Sanity Testing: Deeply test adjacent rules in the "Forgot Password / OTP" module (expired link, wrong OTP, resend cooldown). (4) 10:30 AM — Regional Regression: Run the Authentication & User Profile automated regression suite to ensure Login/Signup/Session didn't break.
  2. Q20: Scenario: During Retesting of `BUG-512` ("Apply Coupon fails for $100 cart"), the test passes with `$100`, so you close `BUG-512`. Immediately after, during Sanity testing, you try `$150` and it fails with a different error. Do you reopen `BUG-512` or log a new bug?
    A: Log a new defect (linking it to `BUG-512` for context), because the original steps and expected condition of `BUG-512` passed (Retesting succeeded), while Sanity/Regression uncovered a distinct defect on a different condition.
  3. Q21: Scenario: You have 1,200 Regression test cases (manual + automated), and an urgent production hotfix must go live in 45 minutes. Which tests do you run?
    A: Never run all 1,200 tests and delay an urgent hotfix, and never skip testing. Execute: (1) Retesting of the exact hotfix bug (5 mins), (2) Automated Smoke Suite across critical P0 business flows (5 mins), and (3) Sanity + Targeted Regional Regression on the exact module modified by the hotfix (25 mins).
  4. Q22: Scenario: Your automated Selenium Smoke Test suite takes 45 minutes to run. What is wrong with this Smoke suite, and how do you fix it?
    A: A Smoke suite taking 45 minutes violates the core definition of Smoke Testing (it has bloated into a mini-Regression suite). Fix it by: (1) trimming it down to 15–20 critical happy-path checks (`< 5 mins`), (2) moving deep negative/edge checks back to the `regression` group, (3) using API login/data setup instead of UI navigation where possible, and (4) running in parallel (`thread-count=4`).
  5. Q23: Scenario: Every feature in the Sprint passed scripted test cases, yet customers report a bug when pressing the browser `Back` button right after clicking "Pay Now". Which testing type was missing in QA?
    A: Exploratory Testing & Negative State-Transition Testing—scripted test cases checked standard linear steps, whereas an exploratory charter testing double-clicks, browser Back/Refresh buttons, and network throttling during payment would have caught it.
  6. Q24: Scenario: When should a test case be removed or retired from a Regression Test Suite?
    A: When: (1) the feature it tests is deprecated/removed from the product, (2) two test cases test the exact same code path (redundant duplication), or (3) a slow UI test is replaced by a faster API-level regression test covering the exact same business rule.
  7. Q25: Scenario: Can Sanity Testing ever be executed BEFORE Smoke Testing?
    A: No. Smoke Testing always comes first on any build drop to verify basic build health (server up, DB connected, login working). You cannot run deep Sanity tests on the Checkout module if the app can't even log in!

Tier 4: SDET, Automation (Selenium / TestNG / CI-CD) Application (Q26–Q30)

  1. Q26: How do you configure `testng.xml` or Maven to maintain Smoke, Sanity, and Regression suites in the same Selenium repository without duplicating test code?
    A: Tag `@Test` methods with multiple group names (e.g., `@Test(groups = {"smoke", "regression"})` or `@Test(groups = {"sanity-cart", "regression"})`) and pass `-Dgroups=${SUITE_TYPE}` dynamically from a parameterized Jenkins build job.
  2. Q27: When a developer fixes a bug that slipped into QA or Production, what is the SDET rule for the Regression suite?
    A: Every escaped defect must result in a new automated regression test (`@Test(groups="regression", description="BUG-409")`) merged into the suite so that exact bug can never regress silently in future sprints.
  3. Q28: How do you stop flaky Selenium tests from blocking the CI/CD Smoke Gate?
    A: (1) Replace all `Thread.sleep()` with explicit `WebDriverWait` / `ExpectedConditions`, (2) use stable `id` or `data-testid` locators, (3) isolate test data per thread so parallel tests don't collide, and (4) quarantine any genuinely flaky environment test into a `@Test(groups="quarantine")` bucket until fixed within 24 hours.
  4. Q29: How can Git diff analysis (`Test Impact Analysis`) speed up Regression testing in CI/CD?
    A: By mapping packages/microservices to TestNG groups (e.g., changes under `src/main/java/com/app/payment/**` automatically trigger `-Dgroups="smoke,sanity-payment"` on PRs, while the full `regression` suite runs nightly).
  5. Q30: In Playwright, how do you tag tests for Smoke vs Sanity vs Regression?
    A: Use Playwright's `@tag` syntax (`test('verify login', { tag: ['@smoke', '@regression'] }, async ({ page }) => { ... })`) and execute via `npx playwright test --grep @smoke`.

Tier 5: Rapid-Fire Yes/No & 1-Liner Traps (Q31–Q35)

  1. Q31: Which testing is called "Wide and Shallow"?
    A: Smoke Testing.
  2. Q32: Which testing is called "Narrow and Deep"?
    A: Sanity Testing.
  3. Q33: Does Retesting check passed test cases or failed test cases?
    A: Only previously failed test cases.
  4. Q34: Is Sanity Testing a subset of Regression Testing or Acceptance Testing?
    A: A subset of Regression Testing.
  5. Q35: Can developers perform Smoke Testing before handing a build to QA?
    A: Yes (Developer Smoke Test / Pre-drop BVT prevents handing over broken builds).
