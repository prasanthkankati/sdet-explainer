M4.1 Question Bank: Complete Bug Life Cycle & Defect States (35 Questions)

Tier 1: Core Definitions & States (Q1–Q10)

  1. Q1: What is the Bug Life Cycle?
    A: The structured sequence of states a defect moves through from discovery (`New`) to assignment (`Assigned`), debugging (`Open`), resolution (`Fixed`), confirmation (`Pending Retest` / `Verified`), and completion (`Closed` or `Reopened`).
  2. Q2: What is the difference between Error, Defect (Bug), and Failure?
    A: Error = human mistake; Defect/Bug = flaw inside code or specification; Failure = observable incorrect behavior at runtime when executing the program.
  3. Q3: What are the mandatory fields in a Jira Defect Report?
    A: Defect ID, Summary, Environment & Build #, Steps to Reproduce, Test Data, Expected vs Actual Result, Severity, Priority, and Evidence (Screenshot/Video/HAR/Logs).
  4. Q4: What is the `Deferred` state?
    A: A valid defect intentionally postponed to a future sprint or release due to low business impact or tight release timelines.
  5. Q5: What is the `Rejected` state?
    A: When a logged ticket is not actually a defect (e.g., misunderstood requirement, wrong test data, or working as designed in SRS).
  6. Q6: What is the `Duplicate` state?
    A: When the exact same root-cause defect has already been logged by another team member; the new ticket is linked to the master ticket and closed as Duplicate.
  7. Q7: What does `Reopened` mean and when is it triggered?
    A: Triggered by QA during Retesting when a developer's `Fixed` build still reproduces the original defect.
  8. Q8: What is the difference between `Verified` and `Closed`?
    A: `Verified` means QA confirmed the fix passes on QA env; `Closed` is final sign-off once regression passes or the fix is deployed/merged cleanly.
  9. Q9: What is a "Latent Defect" vs a "Masked Defect"?
    A: A Latent Defect sits hidden in the system for months/years until a specific rare condition triggers it. A Masked Defect is a bug hidden behind another blocking bug (once Bug A is fixed, Bug B becomes visible).
  10. Q10: Who can change a bug's status from `Fixed` to `Closed`?
    A: Only QA (never the developer who fixed it), after verifying on a deployed QA build.

Tier 2: Why / Why Not & Comparisons (Q11–Q18)

  1. Q11: Why should a developer NEVER directly mark their own bug `Closed`?
    A: Independent verification prevents bias, missing merge commits, environment config mismatches, and unverified regressions.
  2. Q12: Why is "Build Version / Git Commit SHA" critical inside a defect report?
    A: Developers may push 5 builds a day; without knowing which exact build failed, a developer may test on a newer build and wrongly mark the bug `Cannot Reproduce`.
  3. Q13: How do you handle a developer who repeatedly marks valid bugs as `Rejected` or `Cannot Reproduce`?
    A: Never argue over chat—attach indisputable evidence (screen recording, exact HAR network payload, server timestamp, curl command) and schedule a 5-minute pairing call or escalate to Bug Triage with the Product Owner.
  4. Q14: What is Defect Age and Defect Reopen Rate?
    A: Defect Age = Time elapsed from `New` to `Closed` (measures turnaround speed). Reopen Rate = `(Reopened Bugs / Total Fixed Bugs) * 100` (high reopen rate signals poor developer unit testing before handoff).
  5. Q15: What is a `Won't Fix` / `By Design` status?
    A: When Product Management confirms the behavior is intentional or the cost/risk of changing legacy code outweighs the minor inconvenience.
  6. Q16: Why should you log two separate bugs instead of bundling 3 unrelated UI issues into 1 Jira ticket?
    A: Bundled bugs cannot be tracked or closed independently—if 2 issues are fixed and 1 fails, the whole ticket gets `Reopened` and metrics/routing to different Frontend vs Backend devs break.
  7. Q17: What is Bug Triage?
    A: A recurring meeting (QA Lead, Dev Lead, Product Owner) to review `New` defects, validate root causes, assign Severity/Priority, and decide `Fix Now` vs `Defer`.
  8. Q18: What is "Defect Clustering" in Defect Management?
    A: Roughly 80% of logged defects come from 20% of complex modules; tracking defect counts per component helps prioritize refactoring and Selenium regression coverage.

Tier 3: Real-World Tricky Scenarios (Q19–Q25)

  1. Q19: Scenario: A bug happens intermittently (1 out of 5 tries). Should you log it, and how?
    A: Yes! Log it with the exact reproduction ratio (`~20%`), attach timestamps, console/network logs, and suspected triggers (e.g., race condition, double-click, slow 3G).
  2. Q20: Scenario: During Retesting, the original bug is fixed, but the fix broke another button on the same page. Do you `Reopen` the original ticket or log a new bug?
    A: Close the original ticket (its exact issue is fixed) and log a new Regression Defect linked to the original ticket (`relates to / caused by`).
  3. Q21: Scenario: A bug is found in Production that only occurs on Safari iOS 17. Developer uses Windows Chrome and marks it `Cannot Reproduce`. What do you do?
    A: Provide a BrowserStack/device video recording, exact iOS Safari Web Inspector console error, and the exact API request/response payload.
  4. Q22: Scenario: How do you verify a bug is not caused by stale browser cache or old QA test data before logging it?
    A: Re-test in a fresh Incognito/Private browser window, hard-reload (`Ctrl+Shift+R`), check Network tab (`200` vs `500`), and verify with a newly created test user.
  5. Q23: Scenario: A `Deferred` bug from Sprint 4 suddenly starts blocking an enterprise client in Sprint 8. What happens?
    A: Product/Triage moves the ticket from `Deferred` back to `Open` / current Sprint backlog with elevated Priority (`P1`).
  6. Q24: Scenario: What if a bug is confirmed in QA, but nobody knows whether it's Frontend or Backend?
    A: Open Chrome DevTools Network Tab: inspect the API request payload and HTTP response body. If the API returns wrong data or `500`, assign to Backend; if the API returns valid `200 JSON` and UI renders wrongly, assign to Frontend.
  7. Q25: Scenario: Can an Automated Selenium test automatically log defects in Jira?
    A: Technically possible via Jira REST API, but strongly discouraged for flaky UI failures because it floods Jira with duplicate noise; instead, SDETs attach Allure/ExtentReports logs and triage failures before logging valid bugs.

Tier 4 & 5: SDET & Rapid-Fire Traps (Q26–Q35)

  1. Q26: How do you capture full evidence automatically when a Selenium test fails?
    A: Implement TestNG `ITestListener#onTestFailure`: capture `TakesScreenshot`, browser console logs (`driver.manage().logs().get(LogType.BROWSER)`), current URL, and attach them to ExtentReports/Allure.
  2. Q27: How do you attach a failed API request/response automatically in RestAssured?
    A: Use `RestAssured.enableLoggingOfRequestAndResponseIfValidationFails()` or an Allure `AllureRestAssured` filter so every failed API assertion prints exact headers, URL, and JSON body.
  3. Q28: What is `git bisect` and how do devs/SDETs use it for regression bugs?
    A: A binary-search Git command (`git bisect start`, `good`, `bad`) that automatically finds the exact commit that introduced a regression bug.
  4. Q29: How do you link automated tests to fixed Jira bugs?
    A: Add `@Test(description = "BUG-409: ...")` or `@Issue("BUG-409")` in Allure so the regression suite documents why the test exists.
  5. Q30: What is a "Blocker" defect in CI/CD?
    A: A defect that prevents the Smoke suite or downstream testing from running at all (e.g., Login API down).
  6. Q31: Can a bug go directly from `New` to `Closed` without `Fixed`?
    A: Yes, if it is marked `Rejected` or `Duplicate`.
  7. Q32: Is "Works on my machine" a valid final closure reason?
    A: No—it requires environment/data investigation.
  8. Q33: Does a `Deferred` bug mean the bug is invalid?
    A: No—it is a valid bug postponed to a future release.
  9. Q34: Who owns the `New` and `Closed` states?
    A: QA owns logging (`New`) and final verification (`Closed`).
  10. Q35: What is the #1 rule for writing Steps to Reproduce?
    A: Write exact, minimal, deterministic steps with exact test data so anyone can reproduce it in under 1 minute.
