6.1 Exception Hierarchy: Checked vs Unchecked & Error

1. Definition

All Java crashes extend Throwable, splitting into Error (fatal JVM/assertion failures), Checked Exceptions (javac enforces try-catch or throws), and Unchecked RuntimeException (runtime bugs and Selenium exceptions).

2. Memory hook

Throwable splits into Error (do not catch!) & Exception; RuntimeException = Unchecked; IO/SQL = Checked!

  • Checked exceptions: direct children of Exception outside RuntimeException (IOException, InterruptedException) — code won't compile unless handled or declared.
  • Unchecked exceptions: RuntimeException and subclasses (NullPointerException, Selenium's WebDriverException / NoSuchElementException / TimeoutException).
  • AssertionError lives under Error: so catching Exception never hides failing TestNG assertions!

3. The java.lang.Throwable Hierarchy Tree

java.lang.Throwable root class of all throw/catch objects
Never catch bare Throwable in test helpers — let Error and assertions fail tests cleanly.
Error (Unchecked)OutOfMemoryError, StackOverflowError, TestNG AssertionError
Checked ExceptionIOException, SQLException, InterruptedException (compile check!)
RuntimeException (Unchecked)NullPointerException, NoSuchElementException, StaleElementReferenceException

4. Error vs Checked Exception vs Unchecked RuntimeException

BranchCompile-Time Check?Should Test Code Catch?Examples
ErrorNoNo — let assertions/JVM crashes fail fastAssertionError, OutOfMemoryError
Checked ExceptionYes (try-catch or throws required)Yes — handle missing files or wrap clearlyIOException, FileNotFoundException, InterruptedException
RuntimeExceptionNoFix nulls/locators; catch only transient states inside waitsNoSuchElementException, TimeoutException, NPE

5. Code example: checked IOException vs unchecked Selenium exception vs AssertionError

import java.io.IOException;
import java.nio.file.*;
import org.openqa.selenium.NoSuchElementException;

public class ExceptionTreeDemo {
    static String readCfg(Path p) throws IOException { // compiler requires 'throws'
        return Files.readString(p);
    }

    static void clickSafe(boolean found) {               // NO 'throws' needed for RuntimeException
        if (!found) throw new NoSuchElementException("QKart login btn missing");
    }

    public static void main(String[] args) {
        try {
            assert false : "Title mismatch!";            // throws AssertionError (subclass of Error)
        } catch (Exception e) {
            System.out.println("Skipped! Error does NOT extend Exception");
        } catch (Error err) {
            System.out.println("Caught AssertionError separately: " + err.getMessage());
        }
    }
}

6. Execution flow, step by step

  1. Files.readString(p) declares checked IOException, forcing readCfg to catch it or declare throws IOException.
  2. Throwing NoSuchElementException compiles with zero throws declaration because WebDriverException extends RuntimeException.
  3. When assert false runs, Java allocates an AssertionError, pauses the method, and scans upward for matching catch blocks.
  4. catch (Exception e) does NOT match because Error and Exception sit on separate sibling branches under Throwable.
  5. catch (Error err) catches it cleanly (in real tests, you let TestNG catch AssertionError to fail the test report).

8. Why it matters

Distinguishing checked external I/O faults from unchecked runtime bugs keeps business/page methods clean without throws Exception clutter.

SDET link: Every Selenium failure (NoSuchElementException, StaleElementReferenceException, TimeoutException) extends WebDriverException -> RuntimeException so @Test methods stay clean, while TestNG Assert throws AssertionError.

9. Quick test

Will catch (Exception e) catch an OutOfMemoryError or TestNG AssertionError? No — both extend Error, not Exception.
