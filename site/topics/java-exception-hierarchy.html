6.1 Exception Hierarchy (Checked vs Unchecked vs Error)

The Throwable inheritance tree decides whether the Java compiler forces explicit handling before running or lets failures propagate during Selenium execution.

Every crash during a test run — from a missing locator in Selenium to running out of JVM heap — enters Java as a subclass of java.lang.Throwable. Interviewers frequently test whether an SDET can read the hierarchy under Throwable, tell compile-time checked exceptions apart from runtime unchecked exceptions, and choose the right parent class without swallowing Error objects.

Before you start

Prerequisite: 5.6 Lambdas, Streams, Method References &amp; Optional

Where it fits

Exception architecture governs every Selenium Page Object method, Apache POI reader, wait helper, and TestNG listener. Knowing the split between Error, checked Exception, and RuntimeException keeps test methods free of noisy throws Exception clauses while letting real assertion or webdriver failures bubble cleanly to TestNG reports.

Key points

  1. Single root class: java.lang.Throwable is the direct superclass of both Error and Exception; only Throwable subclasses can appear in a throw expression or catch parameter.
  2. Error branch: Error subclasses including OutOfMemoryError, StackOverflowError, and AssertionError signal serious JVM or test-assertion problems outside normal application recovery.
  3. Checked exceptions: Direct subclasses of Exception that do not extend RuntimeException — including IOException, SQLException, InterruptedException, and ClassNotFoundException — are checked by javac at compile time.
  4. Unchecked exceptions: RuntimeException and all of its subclasses bypass compile-time checks; examples include NullPointerException, IndexOutOfBoundsException, and Selenium's WebDriverException family (NoSuchElementException, TimeoutException, StaleElementReferenceException).
  5. Special note on AssertionError: TestNG and JUnit assertions throw java.lang.AssertionError, which extends Error rather than Exception, so catching Exception does not accidentally hide failed assertions.

How it works

  1. At compile time, javac inspects every method body for checked exception types thrown by called methods or explicit throw statements; if neither a matching catch block nor a method throws declaration handles them, compilation fails.
  2. When a failure occurs at runtime, the JVM creates an instance of the specific Throwable subclass, captures the current thread stack trace inside that object, and stops normal statement execution in the current method.
  3. The JVM unwinds stack frames upward until it finds an enclosing try block whose catch parameter matches the thrown object via an is-a relationship (polymorphism).
  4. If no matching catch exists on the call stack, the thread passes the unhandled exception to TestNG (or the thread's uncaught handler), which marks the test method as failed and prints the stack trace.

Inspecting Checked, Unchecked, and Error branches inside a QKart test helper

package com.qkart.exceptions; // Declare package for exception hierarchy demo

import java.io.IOException; // Checked exception for file/network I/O
import java.nio.file.Files; // NIO utility to read config files
import java.nio.file.Path; // File path representation
import org.openqa.selenium.NoSuchElementException; // Unchecked Selenium RuntimeException

public class ExceptionHierarchyDemo { // Class demonstrating Throwable branches

    public static String loadConfigOrFail(Path path) throws IOException { // Caller must handle checked IOException
        return Files.readString(path); // readString declares checked IOException in its signature
    } // End loadConfigOrFail

    public static void checkElementOrFail(boolean elementPresent) { // No throws needed for unchecked exception
        if (!elementPresent) { // Guard condition checking whether locator matched in DOM
            throw new NoSuchElementException("QKart login button not found on https://qkart-qa-web.labs.crio.do/login"); // Unchecked RuntimeException
        } // End presence guard
    } // End checkElementOrFail

    public static void main(String[] args) { // Entry point showing catch behavior across branches
        try { // Guard block invoking checked I/O operation
            loadConfigOrFail(Path.of("missing-qkart.properties")); // Triggers checked IOException
        } catch (IOException ex) { // Compile-time requirement satisfied here
            System.out.println("Checked caught: " + ex.getClass().getSimpleName()); // Prints NoSuchFileException
        } // End checked try-catch

        try { // Guard block throwing AssertionError (Error branch)
            assert false : "Expected Selenium home title mismatch"; // Throws java.lang.AssertionError
        } catch (Exception ex) { // Does NOT catch AssertionError because Error does not extend Exception
            System.out.println("This block will not run for Error"); // Skipped for Error subclasses
        } catch (Throwable t) { // Matches any Error or Exception subclass
            System.out.println("Caught via Throwable: " + t.getClass().getSimpleName()); // Prints AssertionError
        } // End Error try-catch
    } // End main
} // End ExceptionHierarchyDemo

Common mistakes

  1. Catching Exception or Throwable silently everywhere: Swallowing Throwable catches AssertionError and OutOfMemoryError too, turning broken assertions and dead JVMs into false-green tests.
  2. Adding throws Exception on every Page Object and @Test method: Propagating raw checked Exception forces every caller to declare throws and blurs real I/O issues from locator bugs.
  3. Misclassifying NoSuchElementException or TimeoutException as checked: Selenium intentionally extends RuntimeException across WebDriverException so UI methods remain clean without forced try-catch blocks.
  4. Using try-catch for ordinary flow control instead of waits: Looping with raw try { click(); } catch (Exception e) hides real crashes like malformed locators.

Interview questions

Basics

What is the root class of Java's exception hierarchy?
java.lang.Throwable is the sole root class. Its two immediate children are java.lang.Error and java.lang.Exception.

How do checked exceptions differ from unchecked exceptions?
Checked exceptions descend directly from Exception (excluding RuntimeException) and must be caught or declared in a method's throws clause for the code to compile. Unchecked exceptions descend from RuntimeException or Error and do not require compile-time declaration.

Does catch (Exception e) catch a failing TestNG assertion?
No. TestNG Assert methods throw java.lang.AssertionError, which extends Error, a sibling of Exception under Throwable.

How it works

What steps does the JVM perform when a throw statement executes?
The JVM instantiates the exception object (populating its stack trace array by walking the active thread's call stack frames), halts the rest of the current block, and scans outward along the call stack for the first compatible catch parameter.

Why is InterruptedException checked while NullPointerException is unchecked?
InterruptedException represents a legitimate coordination signal between threads that callers are expected to recover from or restore the interrupt flag for. NullPointerException indicates a programming defect that can arise at almost any dereference, so checking it at compile time would make code unusable.

How are Selenium WebDriver exceptions modeled in this hierarchy?
org.openqa.selenium.WebDriverException extends java.lang.RuntimeException. Specific classes including NoSuchElementException, TimeoutException, StaleElementReferenceException, and ElementClickInterceptedException all inherit from WebDriverException and are therefore unchecked.

Real situations

Your config helper uses Properties.load(InputStream) which throws checked IOException. How should a Page Object call it?
Handle IOException inside the config loader itself, log the missing file path, and rethrow a descriptive unchecked framework exception (for example, a custom FrameworkConfigException extends RuntimeException) so Page Objects stay uncluttered.

During parallel runs on https://qkart-qa-web.labs.crio.do/, a test crashes with OutOfMemoryError. Should you catch it inside @AfterMethod?
No. Once heap space is exhausted, cleanup code inside the same JVM cannot run reliably. Instead, fail fast, inspect heap dumps or unclosed browser streams/POI workbooks, and lower thread concurrency or raise -Xmx.

Why does FluentWait.ignoring(NoSuchElementException.class) work cleanly without catching assertions?
Because ignoring(...) filters by exact runtime class membership against the list of transient exceptions (NoSuchElementException, StaleElementReferenceException), while letting unrelated errors or assertions abort waiting immediately.

Troubleshooting

Why does a Selenium click wrapper throw NullPointerException on line 1 instead of NoSuchElementException?
Either the WebDriver field itself is null (never initialized in @BeforeMethod or broken in ThreadLocal) or PageFactory.initElements was skipped for that Page Object before calling an @FindBy element.

A compiler error says 'unreported exception InterruptedException; must be caught or declared to be thrown'. How do you fix it properly?
Do not slap an empty catch (InterruptedException e) {} on it. Catch InterruptedException, call Thread.currentThread().interrupt() to preserve the thread's interrupt status, and throw an unchecked exception or exit cleanly — better yet, replace sleeps with explicit WebDriverWait.

Why does calling driver.findElement(...) after navigating away from https://www.selenium.dev/ raise StaleElementReferenceException instead of NoSuchElementException?
A previously found WebElement handle points to an old DOM node ID in the browser; when the DOM refreshes or detaches that node, acting on the stale reference raises StaleElementReferenceException rather than saying the locator failed.

Design choices

Why did Java framework authors shift away from checked exceptions toward unchecked exceptions for APIs like Selenium and Spring?
Forced checked exceptions either clutter intermediate layers with brittle throws clauses or tempt developers into empty catch blocks that swallow errors. Unchecked domain exceptions preserve clean signatures while letting centralized handlers report failures.

When should an SDET still declare a checked exception rather than an unchecked one?
When writing a low-level utility where callers can genuinely take an immediate fallback action — for example parsing an optional override file before falling back to defaults.

Where in a test framework should general Exception catching actually live?
At the framework boundary — inside TestNG ITestListener.onTestFailure or an Allure/Extent reporting wrapper — never inside low-level Page Object helpers where swallowing errors corrupts subsequent test steps.

Quick answers

  1. What sits at the top of Java's exception tree? java.lang.Throwable, splitting into Error and Exception.
  2. What makes an exception checked? It extends Exception without extending RuntimeException, so javac forces handling or throws.
  3. Are Selenium exceptions checked or unchecked? Unchecked: WebDriverException extends RuntimeException.
  4. Does catch (Exception e) catch AssertionError? No; AssertionError extends Error, not Exception.
