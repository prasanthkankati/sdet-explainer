1.1 JDK vs JRE vs JVM & Bytecode Portability

How javac compiles Java source files into platform-neutral bytecode and how the JDK, JRE, and JVM work together to execute tests.

Java separates compilation from execution so the same compiled test suite runs across Windows, macOS, and Linux without rewriting code. The Java Development Kit (JDK) compiles source files into bytecode, while the Java Virtual Machine (JVM) inside the Java Runtime Environment (JRE) verifies and executes that bytecode on the host operating system.

Where it fits

Every Selenium and TestNG automation run starts with the JDK compiling your test classes into bytecode and the JVM executing them when Maven or your IDE launches the suite.

Key points

  1. The javac compiler inside the JDK translates human-readable .java source files into platform-independent .class bytecode files.
  2. Every compiled .class file begins with the 4-byte magic number 0xCAFEBABE followed by a major class file version (52.0 for Java 8, 55.0 for Java 11, 61.0 for Java 17, 65.0 for Java 21).
  3. The JVM is the execution engine that reads bytecode, manages runtime memory, and translates instructions into native CPU machine code for the current operating system.
  4. The JRE bundles the JVM together with the core Java class libraries (java.base containing String, System, and ArrayList) and runtime configuration files.
  5. The JDK is a superset of the JRE that adds developer tools including javac (compiler), jar (archiver), javadoc, jdb, and jlink.
  6. Starting with Java 11, Oracle and OpenJDK stopped distributing a standalone JRE download; the JDK contains the full runtime and jlink builds custom minimal runtimes.
  7. Compiling with a newer JDK and running on an older JVM throws java.lang.UnsupportedClassVersionError because older JVMs reject higher class file major versions.

How it works

  1. An engineer writes Java source code inside a .java file using classes from the JDK and Selenium libraries.
  2. The javac compiler checks syntax and type rules, then generates a binary .class file containing JVM bytecode instructions.
  3. When java ClassName starts, the operating system spawns a JVM process tailored to that exact CPU and OS (Windows, macOS, or Linux).
  4. The JVM loads the .class bytecode along with required standard library classes from the runtime modules.
  5. The bytecode verifier checks stack bounds and type safety before the Execution Engine interprets or JIT-compiles the instructions into native CPU machine code.

    public static void main(String[] args) { // JVM entry point invoked after class loading

        WebDriver driver = new ChromeDriver(); // Instantiates driver object on the Heap
        driver.get("https://qkart-qa-web.labs.crio.do/"); // Dispatches W3C HTTP navigate command
        driver.quit(); // Terminates browser session before JVM exits
    } // Ends main method frame
} // Ends BytecodeDemo class

Common mistakes

  1. Confusing platform independence of bytecode with platform independence of the JVM; bytecode is identical across operating systems, whereas the JVM executable itself is OS-specific and CPU-specific.
  2. Setting JAVA_HOME to a JRE directory instead of a JDK root; Maven fails compilation because javac is absent from a JRE-only path.
  3. Targeting Java 8 in pom.xml while depending on Selenium 4; Selenium 4 is compiled for Java 11 bytecode (version 55.0) and throws UnsupportedClassVersionError on a Java 8 JVM.
  4. Assuming the JVM contains the source code of String or ArrayList; those classes reside inside JRE module libraries (java.base), not inside the JVM binary.

Interview questions

Basics

What is the exact relationship between JDK, JRE, and JVM?
The JVM is the core engine that executes bytecode, the JRE wraps the JVM together with standard class libraries, and the JDK wraps the JRE together with development tools including javac and jar. The JDK is strictly a superset of the JRE, which is a superset of the JVM. For example, writing and compiling a Selenium test requires the JDK, while running a pre-compiled JAR only requires the runtime inside the JRE.

Why is Java called 'Write Once, Run Anywhere' (WORA)?
The javac compiler produces standardized .class bytecode that has no dependency on Windows, macOS, or Linux CPU instructions. Each operating system runs its own native JVM implementation that understands that identical bytecode format. A Selenium framework JAR compiled on a macOS laptop executes without recompilation on a Linux Jenkins agent.

Is the JVM itself platform-independent?
No, the JVM is platform-dependent because it must interface directly with the host operating system's memory manager, threads, and CPU architecture. A Windows machine uses a Windows JVM binary, while a Linux container uses a Linux JVM binary. Bytecode is platform-independent precisely because each OS provides a platform-specific JVM to translate it.

What is bytecode and where is it stored?
Bytecode is the compact binary instruction format generated by javac for the JVM stack-based execution model rather than for physical hardware registers. It is stored in .class files on disk or packaged inside .jar archives. Every valid .class file starts with the 4-byte hexadecimal signature 0xCAFEBABE.

How it works

Why can the JVM not execute a Java program without the JRE libraries?
The JVM binary provides class loading, memory areas, and instruction execution, but it does not bundle standard classes like java.lang.String, java.lang.System, or java.util.ArrayList. Those classes live in the runtime libraries supplied by the JRE (packaged in lib/modules since Java 9). Without those libraries, even a minimal System.out.println() fails to link.

What happens step by step between running javac Test.java and java Test?
First, javac Test.java parses the source text, enforces compile-time type safety, and writes Test.class bytecode to disk. Next, java Test launches a native JVM process, loads Test.class into memory, verifies bytecode safety rules, and invokes public static void main(String[] args). Finally, the Execution Engine interprets or JIT-compiles the instructions onto the CPU.

What does the class file major version inside a .class file represent?
Bytes 6 and 7 of every .class file store the major version number indicating the minimum JVM specification required to run it. Java 8 uses version 52.0, Java 11 uses 55.0, Java 17 uses 61.0, and Java 21 uses 65.0. When a Maven build runs under Java 8 against a Selenium 4 JAR built for version 55.0, the JVM rejects the class during loading.

Real situations

A Jenkins pipeline compiles tests on JDK 21 locally but fails on a CI runner with UnsupportedClassVersionError: class file version 65.0. What happened?
The CI runner is executing the compiled bytecode using an older JVM, typically Java 11 or Java 17, which cannot read Java 21 class files (version 65.0). Fix this either by upgrading the CI agent's JAVA_HOME to JDK 21 or by configuring <maven.compiler.release>17</maven.compiler.release> in pom.xml so javac emits Java 17 bytecode.

Why did standalone JRE installers disappear after Java 8?
Starting with Java 9 modules and Java 11, Oracle and OpenJDK discontinued shipping a separate JRE distribution because desktop browser applets were obsolete and server deployments preferred self-contained runtimes. Instead, teams ship the JDK or use the JDK's jlink tool to assemble a stripped-down custom runtime containing only the modules an application uses. For CI test runners, using a standard JDK image provides both build tools and runtime.

Why does a Selenium Maven project still fail when java -version works in the shell?
java -version only proves a runtime binary exists on the system PATH, which could be a JRE or an outdated Java version. Maven requires javac and reads the JAVA_HOME environment variable to locate the JDK compiler and tools. If JAVA_HOME is unset or points to a JRE folder, Maven aborts the compile phase.

Troubleshooting

How do you tell if a machine only has a JRE or a full JDK?
Check whether the compiler executable javac is present alongside the java executable inside the Java bin directory. If java -version responds with a version number but javac is missing or unrecognized, only a runtime environment is available and compilation will fail. In CI containers, switching from a jre base image to a jdk base image resolves this immediately.

What is the difference between ClassNotFoundException and UnsupportedClassVersionError at startup?
UnsupportedClassVersionError means the JVM successfully located the .class file on the classpath, read its header bytes, and rejected it because its major version exceeds the running JVM's version. ClassNotFoundException means the ClassLoader could not locate the requested .class file anywhere on the classpath. Checking the version number in the error message immediately pinpoints a JDK mismatch.

Why do Maven builds fail with 'invalid target release: 21' even when JDK 21 is on the system?
This happens when the system PATH lists JDK 21, but the JAVA_HOME variable still points to an older JDK directory including JDK 11 or JDK 17. Maven invokes the compiler found under JAVA_HOME rather than searching PATH first. Aligning JAVA_HOME with the JDK 21 directory resolves the target release error.

Design choices

Why did Java adopt a bytecode virtual machine instead of compiling directly to native binaries like C++?
Native compilation ties every build artifact to a single operating system and CPU architecture, forcing teams to maintain separate builds and toolchains. Compiling to bytecode creates a single portable artifact (a .jar) that ships unchanged across developer laptops and heterogeneous CI nodes. In addition, the JVM can optimize hot code at runtime using actual execution profiles via the JIT compiler.

Why does Selenium 4 enforce Java 11 as its minimum supported version?
Java 11 introduced the standard java.net.http.HttpClient with built-in HTTP/2 and WebSocket support inside the standard library. Relying on the built-in client allowed Selenium 4 to drop heavy third-party HTTP dependencies and support WebDriver BiDi cleanly. Consequently, all Selenium 4 artifacts are compiled to class file major version 55.0.

When packaging an automation project, why do teams configure maven.compiler.release instead of only source and target?
Setting source and target only alters syntax checking and class file version headers, without preventing accidental calls to APIs added in newer JDKs. Setting <maven.compiler.release>17</maven.compiler.release> links compilation against the exact Java 17 standard library signatures as well. This guarantees bytecode compatibility when executing on Java 17 CI agents.

Quick answers

  1. What does the JDK contain that the JRE lacks? Development tools including the javac compiler, jar packager, jdb debugger, and jlink.
  2. What does the JRE contain that the JVM lacks? Core Java class libraries (java.base modules) and runtime configuration files.
  3. Which file extension holds Java bytecode? .class (or packaged inside a .jar archive).
  4. What is the minimum Java version for Selenium 4? Java 11 (class file major version 55.0).
  5. What error indicates a class was compiled on a newer JDK than the running JVM? java.lang.UnsupportedClassVersionError.
  6. What environment variable do Maven and Gradle read to find the JDK? JAVA_HOME.
