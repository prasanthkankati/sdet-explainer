2.3 Wrapper Classes, Autoboxing & Integer Cache (-128 to 127)

How Java boxes primitives into immutable Heap objects for Collections, how Integer.valueOf() vs parseInt() differ, and the Integer Cache == trap.

Java Generics and the Collections Framework operate strictly on object references rather than raw primitive types, so every primitive has a corresponding immutable wrapper class inside java.lang. Java automatically converts between primitives and wrappers via autoboxing and unboxing, while caching small Integer instances between -128 and 127 to reduce Heap churn.

Before you start

Prerequisite: 2.2 Variables, Primitive vs Reference Types & Type Casting

Where it fits

Whenever an automation test stores product quantities in a List<Integer>, parses text counts from DOM badges with Integer.parseInt(el.getText()), or maps JSON flags to POJO Boolean fields, wrapper classes and boxing rules execute behind the scenes.

Key points

  1. All 8 wrapper classes live in java.lang and are final and immutable: Byte, Short, Integer, Long, Float, Double, Character, and Boolean.
  2. Autoboxing automatically converts a primitive to its wrapper using Wrapper.valueOf(primitive) (for example, Integer x = 42; compiles to Integer.valueOf(42)).
  3. Unboxing automatically extracts the primitive using .xxxValue() (for example, int y = x; compiles to x.intValue()).
  4. The Integer Cache (`-128` to `127`): Integer.valueOf(int) returns a pre-allocated cached instance for values from -128 through 127 inclusive, so a == b evaluates to true inside that range and false outside it (for example, 128 == 128 is false).
  5. Integer.parseInt("42") returns a raw primitive int without creating a Heap object, whereas Integer.valueOf("42") returns a cached or new Integer wrapper object.
  6. Unboxing a null wrapper reference throws NullPointerException at runtime, and parsing non-numeric DOM text throws NumberFormatException.

How it works

  1. When Java initializes Integer, the static nested IntegerCache populates an array of 256 Integer objects covering values -128 to 127.
  2. Executing Integer a = 127; Integer b = 127; compiles to two calls to Integer.valueOf(127), returning identical references to the cached slot.
  3. Executing Integer c = 128; Integer d = 128; falls outside the cache range, allocating two separate Heap instances where c == d is false while c.equals(d) is true.
  4. Comparing a wrapper with a primitive (c == 128) triggers automatic unboxing (c.intValue() == 128), yielding true.

Tracing autoboxing, IntegerCache equality, parseInt vs valueOf, and null unboxing NPE:

package dev.java.core; // Declares package

public class WrapperCacheDemo { // Demonstrates wrapper boxing and cache bounds
    public static void main(String[] args) { // Main method starts
        Integer cached1 = 127; // Autoboxes via Integer.valueOf(127) -> cached instance
        Integer cached2 = 127; // Returns same cached instance from IntegerCache
        System.out.println("127 == 127 : " + (cached1 == cached2)); // Prints: true (same reference)

        Integer uncached1 = 128; // Out of -128..127 range -> new Heap Integer(128)
        Integer uncached2 = 128; // Second distinct Heap Integer(128)
        System.out.println("128 == 128 : " + (uncached1 == uncached2)); // Prints: false (different addresses)
        System.out.println("128 equals : " + uncached1.equals(uncached2)); // Prints: true (value comparison)

        int parsedCount = Integer.parseInt("25"); // Extracts primitive int without Heap allocation
        Integer wrappedCount = Integer.valueOf("25"); // Returns cached Integer object
        System.out.println("Unboxed match: " + (wrappedCount == parsedCount)); // Unboxes wrappedCount -> true
    } // Ends main method
} // Ends WrapperCacheDemo class

Common mistakes

  1. Comparing two Integer objects with == instead of .equals(); tests pass for small sample counts under 127 and unexpectedly fail in production when counts exceed 127.
  2. Writing for (Integer i = 0; i < 10000; i++) sum += i;; mixing a wrapper loop counter with arithmetic unboxes and re-boxes on every iteration, generating thousands of short-lived Heap objects.
  3. Calling int count = response.getCount(); when the POJO field is a nullable Integer; if the JSON field is missing or null, unboxing throws an unexpected NullPointerException.
  4. Passing text with currency symbols or spaces directly into Integer.parseInt("$49"); clean whitespace with .trim() and strip non-digits before parsing to avoid NumberFormatException.

Interview questions

Basics

Why do wrapper classes exist in Java when primitives already exist?
Java Collections (List, Set, Map) and Generics store only object references descending from Object and reject raw primitives like int or boolean. Wrapper classes bridge that gap by encapsulating a primitive inside an immutable object, adding utility parsing methods like Integer.parseInt(), and allowing null to represent missing JSON or database values.

List all 8 primitive types and their exact wrapper class names.
byte -> Byte, short -> Short, int -> Integer, long -> Long, float -> Float, double -> Double, char -> Character, and boolean -> Boolean. Notice that Integer and Character spell out full words, while the other 6 simply capitalize the primitive name.

Are wrapper classes mutable or immutable?
All 8 wrapper classes in java.lang are final classes with private final value fields, making every wrapper instance strictly immutable. Assigning x = x + 1; on an Integer unboxes x, adds 1, and assigns a brand-new Integer reference rather than mutating the original object.

How it works

Explain why Integer a = 100, b = 100; a == b is true while Integer c = 200, d = 200; c == d is false.
Autoboxing translates assignments into Integer.valueOf(), which checks an internal IntegerCache array initialized for integers between -128 and 127 inclusive. Because 100 falls inside the cached range, both a and b receive the exact same Heap address, making == true. Because 200 exceeds 127, each call allocates a separate Heap object, making == compare distinct addresses and return false.

Which other wrapper classes besides Integer cache values?
Byte caches all 256 possible byte values (-128 to 127). Short and Long cache -128 to 127, Character caches 0 to 127 (ASCII range), and Boolean exposes just two constant instances (Boolean.TRUE and Boolean.FALSE). Floating-point wrappers Float and Double never cache values.

What happens at bytecode level during Integer x = 5; int y = x + 2;?
The compiler rewrites Integer x = 5; into Integer x = Integer.valueOf(5); (autoboxing). On the next line, javac rewrites x + 2 into x.intValue() + 2 (unboxing) because arithmetic operators only execute on primitive values.

Real situations

Why can comparing two TestNG Integer assertion parameters with == pass locally and fail on real data?
During local smoke testing with small item counts (like 1, 5, or 25), both expected and actual Integer objects point to the identical IntegerCache instance, so == returns true accidentally. Once staging data returns order counts of 150 or 500, valueOf() allocates distinct Heap objects and == breaks. Always use Assert.assertEquals(actual, expected) or .equals().

In a Selenium test verifying cart badge count on https://qkart-qa-web.labs.crio.do/, should you call Integer.parseInt() or Integer.valueOf()?
Call Integer.parseInt(badge.getText().trim()) when comparing against a primitive int because parseInt() returns a raw primitive int without allocating a wrapper object. Reserve Integer.valueOf() for cases where an Integer object is explicitly required, including inserting into a List<Integer>.

How do API deserialization POJOs benefit from using Integer and Boolean instead of int and boolean?
In REST API response payloads mapped with Jackson, an omitted or explicit null field becomes 0 or false on primitive fields, hiding whether the API sent 0 intentionally or omitted the field entirely. Wrapper fields preserve null distinctly so assertions can catch missing JSON properties.

Troubleshooting

Why does Boolean flag = null; if (flag) { ... } compile cleanly and crash at runtime?
if (flag) compiles because Java inserts automatic unboxing to flag.booleanValue(). At runtime, calling .booleanValue() on a null reference immediately throws java.lang.NullPointerException. Always guard nullable wrapper fields with Boolean.TRUE.equals(flag).

What causes NumberFormatException: For input string: "" when reading text from a Selenium WebElement?
The element was rendered in the DOM without visible text (for instance, while loading asynchronously or hidden via CSS), causing element.getText() to return an empty string "". Wait for non-empty text via WebDriverWait before invoking Integer.parseInt().

Why did new Integer(5) trigger a deprecation warning starting in Java 9?
new Integer(5) forces a fresh Heap allocation on every call, bypassing IntegerCache completely, and was marked deprecated for removal in Java 9 (and for-removal in Java 16). Replace it with Integer.valueOf(5) or direct autoboxing.

Design choices

Why did the Java team introduce IntegerCache for -128 to 127 rather than caching all integers?
Integers like loop counters, HTTP status buckets, array offsets, and small IDs cluster heavily between -128 and 127, so pre-allocating 256 immutable instances eliminates massive object churn at negligible RAM cost. Caching billions of arbitrary integers would waste gigabytes of Heap before any application code even ran. The upper bound can be tuned via -XX:AutoBoxCacheMax=<size> when needed.

When writing a high-frequency math helper or TestNG loop, why should you prefer primitive types over wrapper classes?
Primitives avoid object header overhead (12–16 bytes per object), stay in CPU registers or Stack slots, and avoid GC pressure from repeated unboxing and re-boxing. Use primitives for calculations and reserve wrappers strictly for generic collections and nullable fields.

Why did Java design all 8 wrapper classes to be final and immutable?
Because wrapper instances are cached inside pools like IntegerCache and commonly used as HashMap keys, mutating an existing wrapper's value would corrupt hash buckets and cached references across unrelated threads. Immutability guarantees safe sharing without defensive copying.

Quick answers

  1. What is the range of Java's default IntegerCache? -128 to 127 inclusive.
  2. What is the return type of Integer.parseInt("50") vs Integer.valueOf("50")? parseInt returns primitive int; valueOf returns an Integer wrapper object.
  3. What happens if you unbox a null wrapper object? Throws NullPointerException at runtime.
  4. Why do Collections require List<Integer> instead of List<int>? Java Generics support only reference types descending from Object, never primitive types.
  5. How should two Integer wrapper variables always be compared for numerical equality? With .equals() (or Objects.equals(a, b)), never ==.
  6. Why was new Integer(n) deprecated? It forces Heap allocation on every call instead of reusing IntegerCache via Integer.valueOf(n).
