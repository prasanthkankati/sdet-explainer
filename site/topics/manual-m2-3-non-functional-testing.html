2.3 Non-Functional Testing: Performance, Security, Usability & Compatibility

1. The Base: What is Non-Functional Testing and Why Does It Exist?

Non-Functional Testing is the branch of Dynamic Testing that evaluates HOW WELL the software performs its functions—measuring speed, scalability under concurrent user load, security against attacks, usability, cross-browser compatibility, and crash recovery against measurable SLAs.

The Problem It Solves: Suppose an e-commerce checkout feature passes 100% of Functional Testing when 1 QA engineer clicks "Pay Now" in Chrome. On Black Friday, 50,000 customers click "Pay Now" simultaneously: the server takes 45 seconds to respond, leaks database connections after 4 hours, breaks on Safari iOS, or allows an attacker to view another user's invoice by changing `?orderId=101` to `?orderId=102` in the URL. Functional Testing checks WHAT the button does for 1 user; Non-Functional Testing guarantees HOW WELL, HOW FAST, and HOW SAFELY it works in the real world.

2. Core Terms & Their Properties Defined First (Throughput, Latency, SLA, I18n vs L10n)

Before exploring each Non-Functional testing type, understand the 5 core engineering metrics and properties used to measure them:

  • 1. Response Time (Latency) & Percentiles (`p95`, `p99`): The total time taken from sending an HTTP request to receiving the response (e.g., `p95 < 500ms` means 95% of all user requests complete in under 500 milliseconds).
  • 2. Throughput (RPS / TPS): The number of Requests Per Second (RPS) or Transactions Per Second (TPS) the server successfully processes under load.
  • 3. Concurrent Users (Virtual Users / VUs): The number of simulated users simultaneously active on the system at the same instant.
  • 4. SLA (Service Level Agreement): The formal contract defining exact pass/fail thresholds for non-functional metrics (e.g., "99.9% uptime, p95 response time ≤ 800ms at 5,000 concurrent users, 0% HTTP 5xx error rate").
  • 5. I18n (Internationalization) vs L10n (Localization):
    • Internationalization (`I18n` — 18 letters between `I` and `n`): Designing the application's architecture so it can support multiple languages, UTF-8 characters, time zones, and currencies without hardcoding English strings in code.
    • Localization (`L10n` — 10 letters between `L` and `n`): Adapting and testing the product for a specific target locale/region (e.g., Japanese `ja-JP` translation, `Â¥` Yen currency, `YYYY/MM/DD` date format, or Arabic Right-to-Left UI layout).

3. Classification Tree: The 5 Pillars of Non-Functional Testing

Based on which quality attribute of the system is being measured, Non-Functional Testing splits into 5 major families:

  1. Family 1: Performance Testing — Speed, scalability, and stability under traffic.
    • 5 Sub-Types: 1. Load Testing, 2. Stress Testing, 3. Spike Testing, 4. Endurance (Soak) Testing, 5. Volume (Flood) Testing.
  2. Family 2: Security Testing (Penetration & Vulnerability Testing) — Protecting data, authentication, and APIs against attacks.
  3. Family 3: Compatibility Testing — Verifying behavior across Browsers, OS, Devices, Networks, and API versions (Forward vs Backward Compatibility).
  4. Family 4: Usability & Accessibility (a11y) Testing — Ease of use, user experience, and WCAG screen-reader compliance.
  5. Family 5: Reliability, Recovery & Globalization Testing — Failover recovery (`RTO/RPO`) and `I18n / L10n`.

4. Each Non-Functional Family Explained in Order

① Performance Testing (Load, Stress, Spike, Endurance, Volume)

  • Load Testing: Tests system behavior under expected normal and peak concurrent user load (e.g., 5,000 VUs) to verify SLA compliance.
  • Stress Testing: Tests system behavior beyond normal peak capacity (e.g., 15,000 VUs) to find the exact breaking point and verify whether the system fails gracefully (returning `HTTP 429/503`) and recovers automatically once load subsides.
  • Spike Testing: Tests an instantaneous extreme surge and drop in user traffic (e.g., Flash Sale at midnight).
  • Endurance (Soak) Testing: Runs continuous load for 12–72 hours to catch slow memory leaks, connection pool exhaustion, and log-disk saturation.
  • Volume (Flood) Testing: Populates the database with massive data volumes (hundreds of millions of rows) to test query indexing and storage performance.

② Security Testing (Authentication vs Authorization & OWASP Top Risks)

  • Definition: Evaluating the application to uncover vulnerabilities that could allow unauthorized access, data theft, or service disruption.
  • Core Security Checks Every SDET Must Know:
    1. Authentication (`401 Unauthorized` — "Who are you?"): Verifying password hashing, MFA/OTP expiration, brute-force account lockout, and JWT token signature validation.
    2. Authorization (`403 Forbidden` — "What are you allowed to do?"): Verifying a standard user cannot access `/admin` endpoints or view another customer's order (`IDOR` — Insecure Direct Object Reference).
    3. SQL Injection (SQLi) & Cross-Site Scripting (XSS): Ensuring malicious inputs like ' OR 1=1 -- or <script>alert(1)</script> are sanitized and parameterized.
  • Tools: OWASP ZAP, Burp Suite, SonarQube SAST.

③ Compatibility Testing (Cross-Browser, Device & Backward/Forward)

  • Browser & OS Compatibility: Running Selenium Grid / BrowserStack / Playwright projects across Chromium (Chrome/Edge), WebKit (Safari), and Gecko (Firefox) on Windows, macOS, iOS, and Android.
  • Backward Compatibility: Verifying that a new backend API v2 or new app version still works seamlessly with older mobile app clients or legacy database data.
  • Forward Compatibility: Verifying that the current system works smoothly on upcoming OS/Browser beta versions (e.g., Chrome Beta / iOS Beta).

④ Usability & Accessibility (`a11y`) Testing

  • Usability Testing: Evaluating how intuitive and frictionless the UI is for humans (clear error messages, logical tab order, minimal clicks to checkout).
  • Accessibility (`a11y`) Testing: Verifying the app is usable by people with disabilities per WCAG (Web Content Accessibility Guidelines)—checking `aria-label` attributes, keyboard-only navigation (`Tab`/`Enter`), color contrast ratios, and screen-reader compatibility (automated in Selenium/Playwright via `@axe-core`).

⑤ Reliability, Recovery (Failover) & Globalization (`I18n` / `L10n`)

  • Recovery / Failover Testing: Intentionally killing a microservice pod or primary DB node to verify how fast the standby replica takes over (`RTO` — Recovery Time Objective) without losing committed transactions (`RPO` — Recovery Point Objective).
  • Globalization (`I18n` + `L10n`): Testing multi-language UTF-8 rendering, currency conversions, and date/number formatting across global regions.

Interview Answer: "Functional testing checks WHAT the software does against business rules, whereas Non-Functional testing checks HOW WELL it performs—covering Load testing (expected peak users), Stress testing (pushing beyond capacity to find the breaking point), Spike testing (sudden traffic surge), Endurance testing (long duration for memory leaks), Volume testing (substantial DB records), Security, Accessibility, and Cross-Browser Compatibility."

6. Real SDET Code Trace: Cross-Browser Compatibility, Response SLA & Accessibility in Selenium

While dedicated load tests run in JMeter / k6, SDETs enforce Cross-Browser Compatibility, API/UI Response Time SLAs, and Accessibility (`aria-label`) directly inside automated TestNG suites:

import org.openqa.selenium.*;
import org.openqa.selenium.chrome.ChromeDriver;
import org.openqa.selenium.edge.EdgeDriver;
import org.openqa.selenium.firefox.FirefoxDriver;
import org.testng.Assert;
import org.testng.annotations.Parameters;
import org.testng.annotations.Test;

public class NonFunctionalChecksTest {

    // 1. CROSS-BROWSER COMPATIBILITY + RESPONSE TIME SLA CHECK
    @Test
    @Parameters({"browser"})
    public void verifyDashboardLoadTimeAndAccessibility(String browser) {
        WebDriver driver = switch (browser.toLowerCase()) {
            case "firefox" -> new FirefoxDriver();
            case "edge"    -> new EdgeDriver();
            default        -> new ChromeDriver();
        };
        try {
            long startMs = System.currentTimeMillis();
            driver.get("https://qa-shop.internal/login");
            long loadTimeMs = System.currentTimeMillis() - startMs;

            // Non-Functional SLA Assertion: Page load must be <= 2000ms
            Assert.assertTrue(loadTimeMs <= 2000,
                "SLA Breach on " + browser + ": Load took " + loadTimeMs + "ms");

            // Accessibility (a11y) Assertion: Submit button must have aria-label for screen readers
            WebElement loginBtn = driver.findElement(By.id("login-btn"));
            Assert.assertNotNull(loginBtn.getAttribute("aria-label"),
                "a11y Violation: login-btn is missing aria-label attribute!");
        } finally {
            driver.quit();
        }
    }
}

7. Self-Check

  1. Which performance testing type runs a steady load for 24–48 hours specifically to detect memory leaks and unclosed database connections? (Endurance / Soak Testing)
  2. What is the difference between Load Testing and Volume Testing? (Load Testing tests concurrent user traffic up to expected peak; Volume Testing tests massive amounts of data stored in the database.)
  3. What is the difference between `I18n` (Internationalization) and `L10n` (Localization)? (`I18n` is engineering the codebase to support multiple languages/locales without code changes; `L10n` is translating and adapting UI/currency/dates for one specific locale like `ja-JP`.)
