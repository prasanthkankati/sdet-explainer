4.2 Severity vs Priority (4×4 Matrix with Real Examples)

1. The Base: What Are Severity and Priority?

Severity measures the technical impact of a defect on the system's functionality (assigned by QA). Priority measures the business urgency of how soon the defect must be fixed (assigned by Product / Triage Lead).

The Problem It Solves: A typo in a company logo on the home page causes zero technical crashes, yet the CEO demands it fixed before tonight's launch. Meanwhile, a crash inside an obsolete "Export to Fax" page used by 0.01% of users is technically severe, yet business won't delay a release for it. Separating Severity (Technical Impact) from Priority (Fix Order) prevents engineering teams from fixing the wrong bugs first.

2. Severity Levels & Priority Levels Listed in Order

  • 4 Standard Severity Levels (Technical Impact — QA Owns):
    1. S1 — Blocker / Showstopper: Entire app or core module crashes/unusable; blocks all further testing (e.g., Login fails with HTTP 500).
    2. S2 — Critical: Major business feature fails with no workaround (e.g., Checkout fails to process payments).
    3. S3 — Major / Medium: Feature fails partially or is inconvenient, but a valid workaround exists.
    4. S4 — Minor / Trivial: Cosmetic UI alignment, typo, color mismatch; zero impact on core functionality.
  • 4 Standard Priority Levels (Business Urgency — Product / Lead Owns):
    1. P1 — Urgent / High: Must be fixed immediately (within hours / current hotfix) before release.
    2. P2 — High / Medium: Must be fixed within the current Sprint before sign-off.
    3. P3 — Normal / Low: Fix when time permits or schedule for next sprint.
    4. P4 — Low: Cosmetic/nice-to-have; can be deferred to backlog.

5. In Selenium & SDET Automation

  • Mapping Severity to CI Test Suites: Blocker/Critical Selenium flows (Login, Checkout, Payment) run in the smoke suite on every Pull Request, whereas Minor UI/layout checks run in the nightly regression suite.
  • Failure Triage: When a Selenium assertion fails in Jenkins, SDETs distinguish an application Blocker (HTTP 500 on checkout) from a test-script NoSuchElementException caused by a locator rename before assigning Severity.
