5.5 Sorting (Comparable vs Comparator) & Fail-Fast Iterators

Natural ordering with Comparable vs multi-strategy Comparator, verifying UI table column sorting, and Fail-Fast vs Fail-Safe Iterators (ConcurrentModificationException).

Sorting custom domain objects and verifying sorted product grids in Selenium requires knowing when a class defines its own natural order via Comparable<T> versus supplying external sorting strategies via Comparator<T>. Simultaneously, modifying collections safely during traversal prevents ConcurrentModificationException caused by Fail-Fast iterators.

Before you start

Prerequisite: 5.4 Map: HashMap Internal Working & equals/hashCode Contract

Where it fits

Asserting ascending/descending price sorting on QKart product listings uses Comparator and Collections.sort(), while filtering active alerts or items mid-loop uses Iterator.remove() or removeIf().

Key points

  1. java.lang.Comparable<T> defines a class's single natural ordering by implementing int compareTo(T other) inside the domain class itself.
  2. java.util.Comparator<T> defines external, flexible sorting strategies via int compare(T o1, T o2), enabling multiple sort orders (price ascending, rating descending, name A-Z) without editing the target class.
  3. Java 8+ Comparator.comparing(), .reversed(), and .thenComparing() compose multi-column sorts cleanly with zero verbose anonymous classes.
  4. Fail-Fast Iterators (ArrayList, HashSet, HashMap) maintain an internal modification counter modCount; modifying structure outside iterator.remove() (for example, calling list.remove(x) inside a for-each loop) throws ConcurrentModificationException immediately.
  5. Fail-Safe (Weakly Consistent) Iterators (CopyOnWriteArrayList, ConcurrentHashMap) iterate over a snapshot or volatile state and never throw ConcurrentModificationException during concurrent modifications.
  6. Safe in-place removal patterns include iterator.remove(), Java 8+ collection.removeIf(predicate), or building a filtered result via Streams.

How it works

  1. Scrape visible product prices from the QKart UI into List<Double> actualPrices in DOM order.
  2. Create a copy List<Double> expectedSorted = new ArrayList<>(actualPrices); and sort using expectedSorted.sort(Comparator.reverseOrder());.
  3. Assert Assert.assertEquals(actualPrices, expectedSorted) to prove the UI rendered prices in descending order.
  4. When removing invalid rows from a mutable list during traversal, call list.removeIf(String::isBlank) or it.remove() via an explicit Iterator rather than mutating inside for-each.

Using Comparable, multi-field Comparator chaining, UI sort verification, and safe Iterator removal:

package dev.java.collections; // Declares package

import java.util.ArrayList; // Imports ArrayList
import java.util.Collections; // Imports Collections.sort
import java.util.Comparator; // Imports Comparator
import java.util.Iterator; // Imports Iterator
import java.util.List; // Imports List

class CatalogItem implements Comparable<CatalogItem> { // Natural ordering by name
    final String name; // Product display name
    final double price; // Product price

    CatalogItem(String name, double price) { // Constructor initializes item
        this.name = name; // Assigns name
        this.price = price; // Assigns price
    } // Ends constructor

    @Override // Defines natural alphabetical sort order
    public int compareTo(CatalogItem other) { // Single natural comparison method
        return this.name.compareToIgnoreCase(other.name); // Delegates to String comparison
    } // Ends compareTo
} // Ends CatalogItem

public class SortingAndIteratorsDemo { // Demonstrates sorting and safe removal
    public static void main(String[] args) { // Main method entry
        List<CatalogItem> items = new ArrayList<>(List.of( // Mutable list of products
            new CatalogItem("Watch", 49.0), // Item 1
            new CatalogItem("Shoes", 79.0), // Item 2
            new CatalogItem("Bag", 49.0) // Item 3
        )); // Ends list setup

        Collections.sort(items); // Sorts via CatalogItem.compareTo (Bag, Shoes, Watch)
        items.sort(Comparator.comparingDouble((CatalogItem c) -> c.price).thenComparing(c -> c.name)); // Multi-key custom sort
        System.out.println("Cheapest first: " + items.get(0).name); // Prints: Bag (49.0 before Watch)

        Iterator<CatalogItem> it = items.iterator(); // Obtains Fail-Fast iterator
        while (it.hasNext()) { // Traverses safely
            if (it.next().price > 60.0) it.remove(); // Updates expectedModCount properly; no CME
        } // Ends safe iterator loop
        System.out.println("Remaining affordable count: " + items.size()); // Prints: 2
    } // Ends main method
} // Ends class

Common mistakes

  1. Calling list.remove(item) directly inside a for (String item : list) enhanced loop; the loop wraps a hidden Iterator whose expectedModCount mismatches the modified modCount, throwing ConcurrentModificationException on the next pass.
  2. Writing subtraction shortcuts like return a.price - b.price; or return a.id - b.id; inside a Comparator; integer overflow on large negative/positive values flips the sign and breaks sorting—always use Integer.compare(a, b) or Double.compare(a, b).
  3. Mutating and sorting the original scraped UI list in place before comparing it to itself (Collections.sort(actual); assertEquals(actual, actual);); always copy into a separate expected list before sorting.
  4. Returning non-zero values inconsistent with equals() inside a TreeSet comparator, causing distinct items to drop silently as duplicates.

Interview questions

Basics

Compare Comparable and Comparator in Java.
Comparable<T> lives in java.lang, is implemented inside the target class itself via compareTo(T o), and defines the single natural order of that class (used by Collections.sort(list)). Comparator<T> lives in java.util, is defined externally via compare(T o1, T o2) or lambdas, and lets you define unlimited independent sort strategies (sort by price, sort by rating, sort by date) without modifying the domain class.

What is the difference between a Fail-Fast iterator and a Fail-Safe iterator?
A Fail-Fast iterator (used by ArrayList, HashSet, and HashMap) detects structural changes made outside the iterator during traversal and immediately throws ConcurrentModificationException. A Fail-Safe iterator (used by CopyOnWriteArrayList and ConcurrentHashMap) iterates safely without throwing that exception because it operates over a cloned snapshot or weakly consistent concurrent buckets.

What return values must compareTo(o) and compare(o1, o2) follow?
Both methods return a negative integer if the first object is ordered before the second, 0 if both are equal in sort rank, and a positive integer if the first object comes after the second. Always delegate to wrapper helpers like Integer.compare(x, y) and Double.compare(x, y) instead of manual subtraction to prevent overflow bugs.

How it works

How does an ArrayList iterator detect modification and throw ConcurrentModificationException?
ArrayList maintains a counter field modCount incremented on every structural edit (add, remove, clear). When list.iterator() creates an iterator (including implicitly in every for-each loop), the iterator snapshots expectedModCount = modCount. Calling list.remove() directly updates modCount without updating expectedModCount, so the next call to iterator.next() detects the mismatch and immediately throws ConcurrentModificationException—even on a single thread!

Why does calling iterator.remove() succeed without throwing ConcurrentModificationException?
When you call it.remove() on the iterator itself, the iterator deletes the last returned element from the underlying list AND synchronizes expectedModCount = modCount internally. Note that you must call it.next() before calling it.remove(), otherwise it throws IllegalStateException.

How does CopyOnWriteArrayList avoid ConcurrentModificationException internally?
Every write operation (add, set, remove) acquires a lock, copies the entire internal array into a fresh modified array, and atomically swaps the backing array reference. Any active iterator holds the immutable snapshot reference from when the loop started, so reads never lock and never throw ConcurrentModificationException—at the expense of copying the array on writes.

Real situations

How do you write a Selenium UI test verifying that a product table sorted properly by Price Low-to-High?
Scrape all price cells from the UI into List<Double> actual = elements.stream().map(e -> Double.parseDouble(e.getText().replaceAll("[^0-9.]", ""))).toList();. Build a mutable copy List<Double> expected = new ArrayList<>(actual); Collections.sort(expected);, and assert Assert.assertEquals(actual, expected). Copying first guarantees you never compare a sorted list against itself.

In a multi-column sort requirement (sort products by category ascending, then price descending, with nulls last), how does Java 8 Comparator write this cleanly?
Chain Comparator.comparing(Item::category, Comparator.nullsLast(String::compareToIgnoreCase)).thenComparing(Comparator.comparingDouble(Item::price).reversed()). This reads cleanly and guards against missing price or category fields without throwing NullPointerException.

How do you safely strip blank entries from a scraped List<String> in one line in Java 8+?
Call list.removeIf(s -> s == null || s.isBlank());. Internally ArrayList.removeIf() shifts matching items in a single linear O(n) pass using a bitset and increments modCount once, running faster and cleaner than manual iterator loops.

Troubleshooting

Why did a single-threaded for (WebElement el : rows) { if (el.getText().isEmpty()) rows.remove(el); } throw ConcurrentModificationException?
The exception name misleads newcomers into thinking multiple threads are required. Removing an element directly from rows inside an enhanced for-each loop violates the hidden Iterator's modCount invariant on the very same thread. Replace the loop with rows.removeIf(el -> el.getText().isEmpty()) or an explicit Iterator.

Why did Collections.sort(actualPrices) pass an assertion comparing actualPrices to itself even when the UI table was completely unsorted?
Collections.sort(list) mutates the list in place and returns void. Writing List<Double> sorted = actualPrices; Collections.sort(sorted); creates an alias pointing to the identical Heap list, so both variables point to the sorted list afterward! Always allocate new ArrayList<>(actualPrices) before sorting.

Why did return o1.price - o2.price cast to int inside a Comparator put $10.90 equal to $10.20?
Truncating 10.90 - 10.20 = 0.70 to int evaluates to 0, falsely reporting two unequal prices as equal! Always use Double.compare(o1.price, o2.price) instead of subtracting.

Design choices

Why did Java design standard collections like ArrayList and HashMap with Fail-Fast iterators rather than making all iterators Fail-Safe?
Cloning an entire array or map on every loop would create massive memory overhead and hide subtle concurrency bugs where iterations operate on stale data. Fail-Fast checks cost a single integer comparison per step and catch structural modification defects immediately during testing.

When building a custom framework entity (like TestCaseResult), when should it implement Comparable vs relying on Comparator?
Implement Comparable only when the type has one unmistakable, universal natural order (like alphabetical String or chronological LocalDate). When items can legitimately sort by timestamp, duration, status, or module name depending on the report view, expose named Comparator constants instead.

When should you choose CopyOnWriteArrayList over ArrayList?
Choose CopyOnWriteArrayList strictly for small collections that are read constantly across parallel threads and mutated rarely—for instance, registering custom test execution listeners at startup and notifying them concurrently during tests.

Quick answers

  1. Which method does Comparable define vs Comparator? Comparable defines compareTo(T o); Comparator defines compare(T o1, T o2).
  2. What exception does a Fail-Fast iterator throw when a list is modified mid-loop? ConcurrentModificationException.
  3. Name two safe ways to remove items from an ArrayList while iterating. iterator.remove() or list.removeIf(predicate).
  4. Which collections have Fail-Safe iterators? CopyOnWriteArrayList and ConcurrentHashMap.
  5. Does Collections.sort(list) return a new list? No; it sorts the target list in place and returns void.
  6. Why should numeric comparators use Integer.compare() instead of a - b? To avoid integer overflow bugs and decimal truncation.
