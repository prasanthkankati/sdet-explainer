1.2 testng.xml Suite Configuration & Package Scanning

Mastering the XML runner: suite/test nesting, package-level auto discovery, class/method filtering, and parameter scopes.

The testng.xml file is the declarative manifest that directs the TestNG engine. Rather than hardcoding test execution lists in source code, enterprise automation suites use XML configurations to declare test suites, assign parallel thread counts, inject cross-browser parameters, and target specific packages or test classes for regression and smoke runs.

1. Real-Time Project Structure: Where XML Suites Live

In standard enterprise repositories, XML suite runners reside at the project root or in src/test/resources/suites/, directly referenced by Maven Surefire Plugin in pom.xml:

sdet-test-framework/
├── pom.xml                               # Defines testng.xml
├── testng.xml                            # 📍 Root Suite Runner: Global orchestrator
├── src/test/resources/suites/
│   ├── smoke-suite.xml                   # 📍 Smoke XML: Packages com.sdet.tests.smoke.*
│   └── crossbrowser-suite.xml            # 📍 Parallel XML: Chrome vs Firefox  blocks
└── src/test/java/com/sdet/
    ├── cart/                             # Package targeted by 
    ├── payment/                          # Package targeted with sub-exclusions
    └── tests/AuthenticationTest.java     # Class filtered via

2. XML Schema & Root Attributes

The root tag of any TestNG configuration is <suite>. Key suite-level attributes determine the global runner behavior:

  • name: Mandatory identifier for the test suite, reflected in generated reports.
  • parallel: Concurrency mode: methods, tests, classes, or instances.
  • thread-count: Maximum concurrent worker threads allocated by the suite thread pool.
  • verbose: Console logging verbosity (0 = quiet, 1-10 = detailed execution output).
  • preserve-order: When set to "true" (default), preserves the declaration order of <test> and <class> tags.

2. Package Scanning vs Explicit Classes

For scalable enterprise projects with hundreds of test classes, manually declaring every class in XML is high-maintenance. TestNG supports automated package scanning using the <packages> tag:

<!DOCTYPE suite SYSTEM "https://testng.org/testng-1.0.dtd">
<suite name="CheckoutSuite" verbose="1">
  <test name="CartAndPaymentTests">
    <packages>
      <!-- Automatically scans and runs all @Test classes inside com.sdet.cart and sub-packages -->
      <package name="com.sdet.cart.*" />
      <package name="com.sdet.payment">
        <exclude name="com.sdet.payment.crypto.*" />
      </package>
    </packages>
  </test>
</suite>

3. Method-Level Include & Exclude Filters

When running a subset of tests within a class, <methods> allows fine-grained filtering using exact names or regular expressions:

<test name="SelectiveAuthTests">
  <classes>
    <class name="com.sdet.tests.AuthenticationTest">
      <methods>
        <include name="validLoginTest" />
        <include name=".*OAuth.*" />
        <exclude name="twoFactorSmsTest" />
      </methods>
    </class>
  </classes>
</test>

4. Senior SDET Interview Q&A

  1. What happens if a method is matched by both an <include> and an <exclude> tag?
    In TestNG, <exclude> always takes precedence over <include>. If a method matches an exclude pattern, it is omitted regardless of any include declaration.
  2. How does parameter scoping work between <suite> and <test>?
    A parameter defined at the <suite> level is globally accessible by all tests in that suite. However, a parameter defined inside a specific <test> tag overrides the suite-level parameter with the same name for classes within that test scope.
  3. How do you execute testng.xml from the command line in CI/CD?
    Via Maven Surefire Plugin in pom.xml: configure <suiteXmlFiles><suiteXmlFile>testng.xml</suiteXmlFile></suiteXmlFiles> and invoke mvn clean test -DsuiteXmlFile=testng.xml.
