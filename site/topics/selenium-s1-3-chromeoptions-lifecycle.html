S1.3 Browser Configuration (ChromeOptions) & close() vs quit()

Learning Goal: Configure Chrome sessions using ChromeOptions, master command-line switches and user preferences, select page load strategies, and manage browser lifecycle correctly with close() vs quit() to prevent memory leaks.

1. Definition (3 Distinct Styles)

Concept 1: ChromeOptions

Style A — The 1-Sentence High-Impact Definition:
ChromeOptions is a specialized capability-configuration class in Selenium Java that aggregates browser startup switches, user profile preferences, binary overrides, and W3C session capabilities into a single JSON payload delivered to ChromeDriver before browser initialization.

Style B — The Architectural / Mechanical Definition:
ChromeOptions extends ChromiumOptions<ChromeOptions> and encapsulates the goog:chromeOptions dictionary within the W3C alwaysMatch capability block; upon invoking new ChromeDriver(options), ChromeDriverService serializes these flags into command-line arguments (passed to the Chrome executable during OS process creation) and JSON DevTools/preference configurations before opening the TCP automation port.

Style C — The Professional Plain-English Mental Model:
ChromeOptions is the pre-flight instruction checklist for the browser: before the browser launches, it dictates the window dimensions, turns off popup notifications, activates headless mode, and specifies where downloaded files must go, ensuring the browser runs in a consistent, predictable state every time.

Concept 2: close() vs quit()

Style A — The 1-Sentence High-Impact Definition:
close() destroys only the currently focused browser window or tab without terminating the driver daemon, whereas quit() destroys every open window, dispatches a W3C Delete Session command, and terminates the underlying driver binary operating system process.

Style B — The Architectural / Mechanical Definition:
driver.close() issues an HTTP DELETE request to /session/{id}/window, leaving the HTTP server listening on localhost and the session ID valid; driver.quit() issues an HTTP DELETE request to /session/{id}, which causes the browser driver process (chromedriver.exe) to close all socket connections, unbind its TCP port, terminate its child browser processes, and exit cleanly.

Style C — The Professional Plain-English Mental Model:
close() is clicking the red 'X' on a single browser tab while leaving the computer program running; quit() is completely shutting down the entire application, closing all open windows, and killing the background engine so it uses zero computer memory.

2. Class Hierarchy & Architectural Placement

Understanding where ChromeOptions sits in the Java type hierarchy explains why it can be passed to local constructors, remote grids, and generic capability consumers:

java.lang.Object
   |
   +-- org.openqa.selenium.MutableCapabilities           (Base map of string-to-object capabilities)
         |
         +-- org.openqa.selenium.remote.AbstractDriverOptions<DO>  (Type-safe driver options base)
               |
               +-- org.openqa.selenium.chromium.ChromiumOptions<T> (Shared by Chrome & Edge)
                     |
                     +-- org.openqa.selenium.chrome.ChromeOptions   (Chrome-specific flags & prefs)

Because ChromeOptions extends MutableCapabilities, it complies with the W3C WebDriver standard and is accepted by both ChromeDriver(ChromeOptions) and RemoteWebDriver(URL, Capabilities).

3. The Three Ways to Configure Chrome

Configuration MechanismJava Code SyntaxOperating System & Protocol EffectTypical Use Case
1. Command-Line Arguments (Switches)options.addArguments("--start-maximized")Appended as CLI flags when launching the Chrome operating system process (e.g. chrome.exe --headless=new).Window geometry, headless execution, sandboxing, and security policy overrides.
2. User Preferences (Experimental Options)options.setExperimentalOption("prefs", map)Written to Chrome's runtime JSON user profile file before session startup.Download directory, blocking notification prompts, disabling save-password bubbles.
3. W3C Session Capabilitiesoptions.setAcceptInsecureCerts(true)Sent inside the root W3C capabilities JSON object during the initial POST /session handshake.Accepting untrusted SSL certificates, defining page load strategies, and proxy binding.

Crucial Timing Rule: All configuration options must be defined prior to driver instantiation. Once new ChromeDriver(options) executes, Chrome has already launched and the options container is decoupled from the active session. Calling methods on options after driver startup has zero effect on the running browser.

4.1 Page Load Strategies: NORMAL vs EAGER vs NONE

By default, when you execute driver.get("https://example.com"), Selenium blocks thread execution until the page finishes loading. PageLoadStrategy controls the exact document readiness event that unblocks your test code:

StrategyDocument Ready StateWhen driver.get() ReturnsSDET Trade-Off & Usage
NORMAL (Default)document.readyState === "complete"Waits until the initial HTML, all stylesheets, images, iframes, and subresources finish downloading.Safest and most stable for standard web pages; slower on pages with heavy analytics or streaming assets.
EAGERdocument.readyState === "interactive"Returns as soon as the DOM tree is parsed, before images, stylesheets, or async scripts complete loading.Significantly accelerates test execution on asset-heavy web applications; requires explicit waits on interactive elements.
NONERaw navigation initiatedReturns immediately after the HTTP request is dispatched, without waiting for the DOM to parse.Fastest return; high risk of immediate NoSuchElementException unless comprehensive explicit waits are implemented.

6. Hands-On Implementation: Configured Session with User Preferences

User preferences control internal Chrome behaviors that cannot be set via command-line arguments, such as custom download folders and permission toggles:

package com.sdet.config;

import org.openqa.selenium.PageLoadStrategy;
import org.openqa.selenium.WebDriver;
import org.openqa.selenium.chrome.ChromeDriver;
import org.openqa.selenium.chrome.ChromeOptions;

import java.util.HashMap;
import java.util.Map;

public class ConfiguredChromeSession {
    public static void main(String[] args) {
        // Step 1: Instantiate the options container
        ChromeOptions options = new ChromeOptions();

        // Step 2: Configure command-line switches
        options.addArguments("--start-maximized");
        options.addArguments("--disable-notifications");
        options.addArguments("--lang=en-US");
        options.addArguments("--remote-allow-origins=*");

        // Step 3: Configure Chrome user preferences via the 'prefs' dictionary
        Map<String, Object> prefs = new HashMap<>();
        // Sets custom file download location
        prefs.put("download.default_directory", "C:\\automation_downloads");
        // Prevents browser prompt asking where to save files
        prefs.put("download.prompt_for_download", false);
        // Blocks notification permission prompts at the profile preference level (2 = Block)
        prefs.put("profile.default_content_setting_values.notifications", 2);
        // Disables built-in PDF viewer so files download immediately
        prefs.put("plugins.always_open_pdf_externally", true);
        
        options.setExperimentalOption("prefs", prefs);

        // Step 4: Configure W3C session-level capabilities
        options.setPageLoadStrategy(PageLoadStrategy.EAGER);
        options.setAcceptInsecureCerts(true);

        // Step 5: Start the browser session with verified options
        WebDriver driver = new ChromeDriver(options);

        try {
            driver.get("https://prasanthkankati.github.io/sdet-explainer/");
            System.out.println("Page Title: " + driver.getTitle());
        } finally {
            // Step 6: Guarantee full session and process termination
            driver.quit();
        }
    }
}

7. Professional ChromeOptions Factory Pattern

In enterprise test automation frameworks, options should never be configured directly inside test classes or declared as static fields. Implement a dedicated ChromeOptionsFactory:

package com.sdet.config;

import org.openqa.selenium.PageLoadStrategy;
import org.openqa.selenium.chrome.ChromeOptions;

import java.util.HashMap;
import java.util.Map;

public final class ChromeOptionsFactory {

    private ChromeOptionsFactory() {}

    /**
     * Local workstation options: headed execution with maximized viewport.
     */
    public static ChromeOptions getLocalOptions() {
        ChromeOptions options = new ChromeOptions();
        options.addArguments("--start-maximized", "--disable-notifications", "--lang=en-US");
        options.setPageLoadStrategy(PageLoadStrategy.NORMAL);
        options.setAcceptInsecureCerts(true);
        return options;
    }

    /**
     * CI/CD Docker execution options: headless execution with container stability flags.
     */
    public static ChromeOptions getHeadlessOptions() {
        ChromeOptions options = new ChromeOptions();
        options.addArguments(
            "--headless=new",
            "--no-sandbox",
            "--disable-dev-shm-usage",
            "--disable-gpu",
            "--window-size=1920,1080",
            "--remote-allow-origins=*"
        );
        options.setPageLoadStrategy(PageLoadStrategy.EAGER);
        options.setAcceptInsecureCerts(true);

        Map<String, Object> prefs = new HashMap<>();
        prefs.put("download.default_directory", "/tmp/automation_downloads");
        prefs.put("profile.default_content_setting_values.notifications", 2);
        options.setExperimentalOption("prefs", prefs);

        return options;
    }
}

8. Deep Breakdown: close() versus quit()

8.1 Architectural & Mechanical Comparison

8.2 Step-by-Step Window Lifecycle Code Example

package com.sdet.lifecycle;

import com.sdet.config.ChromeOptionsFactory;
import org.openqa.selenium.JavascriptExecutor;
import org.openqa.selenium.WebDriver;
import org.openqa.selenium.chrome.ChromeDriver;
import org.testng.Assert;
import org.testng.annotations.AfterMethod;
import org.testng.annotations.BeforeMethod;
import org.testng.annotations.Test;

public class WindowLifecycleTest {

    private WebDriver driver;

    @BeforeMethod
    public void setUp() {
        driver = new ChromeDriver(ChromeOptionsFactory.getLocalOptions());
    }

    @Test
    public void managePopupsWithClose() {
        driver.get("https://prasanthkankati.github.io/sdet-explainer/");
        String parentWindowHandle = driver.getWindowHandle();

        // Open auxiliary child tab via JavaScript
        ((JavascriptExecutor) driver).executeScript("window.open('https://www.selenium.dev/', '_blank');");

        // Iterate through window handles to identify the child tab
        for (String handle : driver.getWindowHandles()) {
            if (!handle.equals(parentWindowHandle)) {
                driver.switchTo().window(handle);
                // close() closes ONLY the child tab; driver process and session stay alive
                driver.close();
            }
        }

        // Switch focus back to the parent window
        driver.switchTo().window(parentWindowHandle);
        Assert.assertTrue(driver.getTitle().contains("SDET"), "Parent window must remain active");
    }

    @AfterMethod
    public void tearDown() {
        if (driver != null) {
            // quit() destroys all remaining windows, terminates chromedriver process, and purges RAM
            driver.quit();
            driver = null;
        }
    }
}

10. Always-Do and Never-Do Rules

Always-Do Rules:

  1. Always configure ChromeOptions prior to calling new ChromeDriver(options); options modified after initialization are ignored.
  2. Always call driver.quit() inside your TestNG @AfterMethod or finally block to prevent zombie processes from locking system RAM.
  3. Always supply --headless=new, --no-sandbox, --disable-dev-shm-usage, and --window-size=1920,1080 for Linux CI/CD Docker execution.
  4. Always switch focus back to a valid window handle via driver.switchTo().window(handle) immediately after invoking driver.close().

Never-Do Rules:

  1. Never call driver.close() as your primary framework teardown method; it leaves chromedriver.exe running in background memory.
  2. Never use --disable-web-security to bypass CORS issues in automation; doing so hides critical cross-origin security bugs.
  3. Never use legacy --headless (without =new); legacy headless mode uses an outdated rendering fork that does not accurately reflect real browser behavior.
  4. Never declare a single static ChromeOptions variable shared across tests; concurrent threads can mutate settings and cause race conditions.

11. Interview Section

30-Second Spoken Readout

"We configure browser sessions using ChromeOptions, which allows us to set command-line arguments like --headless=new and --window-size=1920,1080 for CI/CD, user preferences like download directories and notification blocking via experimental options, and W3C capabilities like acceptInsecureCerts and PageLoadStrategy. For session lifecycle, we use driver.close() strictly to shut individual child tabs inside a test, and always call driver.quit() in teardown because quit destroys all windows, sends the W3C Delete Session command, and terminates the underlying chromedriver operating system process."

Top 8 Technical Interview Questions & Answers

  1. [Common] What is the difference between driver.close() and driver.quit()?
    driver.close() sends the W3C Close Window command (HTTP DELETE /session/{id}/window) to shut only the active window/tab, leaving the driver process and session active. driver.quit() sends the W3C Delete Session command (HTTP DELETE /session/{id}), which closes all windows, invalidates the session, and terminates the chromedriver.exe operating system process.
  2. [Common] What happens if an automation framework only calls driver.close() in teardown?
    The underlying chromedriver executables and background browser processes remain active in operating system memory. Over hundreds of test runs in a CI/CD pipeline, these orphaned zombie processes exhaust server RAM and CPU, eventually causing the execution agent to crash with out-of-memory errors.
  3. [Common] Why is --headless=new preferred over the legacy --headless flag?
    Introduced in Chrome 109, --headless=new utilizes the identical, authentic Blink rendering engine and features as standard desktop Chrome (supporting extensions, printing, and accurate DOM layouts). The legacy --headless flag invoked an isolated, separate headless browser fork with known rendering bugs.
  4. [Common] What are the three PageLoadStrategy values and when would you use EAGER?
    The three values are NORMAL (waits for full page load including all images and subresources), EAGER (returns when DOM parsing completes at DOMContentLoaded), and NONE (returns immediately after navigation starts). EAGER is used on heavy enterprise portals with third-party tracking scripts to speed up test execution while relying on explicit waits for element readiness.
  5. [Advanced] How do you configure a custom file download directory in Selenium 4?
    Create a Map<String, Object> containing the key download.default_directory mapped to the target folder path, and pass this map to ChromeOptions using options.setExperimentalOption("prefs", map) before instantiating ChromeDriver.
  6. [Advanced] What flags are mandatory for running Chrome headlessly inside Docker containers?
    The essential flags are --headless=new, --no-sandbox (to prevent Chrome from crashing when running as the container's root user), --disable-dev-shm-usage (to write shared memory to /tmp instead of the constrained 64MB /dev/shm partition), and --window-size=1920,1080.
  7. [Advanced] What exception occurs if you interact with the driver after calling driver.close() on the only open tab?
    Selenium throws NoSuchWindowException: no such window: target window already closed because the session is still active, but there is no valid window handle currently focused.
  8. [Advanced] What exception occurs if you interact with the driver after calling driver.quit()?
    Selenium throws NoSuchSessionException: Session ID is null. Using WebDriver after calling quit()? because the session was destroyed and the driver reference is invalid.
