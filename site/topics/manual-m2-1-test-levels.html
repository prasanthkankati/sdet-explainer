2.1 Levels of Testing: Unit, Integration, System & UAT

1. The Base: What is a "Test Level" and Why Do We Need Levels?

A Test Level is a specific stage of dynamic software testing defined by the size and scope of the software under test—progressing from a single isolated method/class (Unit), to connected modules/APIs (Integration), to the complete end-to-end application (System), and finally to real business user sign-off (UAT).

The Problem It Solves: Imagine an e-commerce app with 500 Java classes, 40 REST APIs, a database, and a web UI. If you wait until the entire app is assembled and only test through the browser UI, when a checkout button fails you have no idea whether the bug is inside a 3-line tax formula, a broken JSON field between two services, a database timeout, or a browser JavaScript error. Testing in 4 progressive levels catches each bug at the smallest, fastest, and cheapest layer where it originates.

2. Core Terms & Their Properties Defined First (Stubs, Drivers, Contracts & Environments)

Before walking through the 4 Test Levels, you must know the exact meaning and properties of the 4 building blocks used during level-by-level testing:

  • 1. Module / Component (Unit): The smallest independently testable piece of source code—such as a single Java method (calculateTax()), a Java class (CartService), or a UI component.
  • 2. Stub (Top-Down Dummy Called Module): When a high-level parent module (e.g., CheckoutController) is ready to be tested, but the lower-level child module it calls (e.g., PaymentGatewayService) is not built yet, developers replace the missing child with a Stub—a lightweight dummy object hardcoded to return a canned response (e.g., return "PAYMENT_SUCCESS").
    • Properties of a Stub: (a) Used in Top-Down Integration, (b) Replaces a called (lower-level) child module, (c) Passive—it waits to be called and returns static dummy data.
  • 3. Driver (Bottom-Up Dummy Caller Module): When a low-level child module (e.g., TaxCalculationDao) is ready, but the top-level UI/Controller that calls it is not built yet, a Driver is a small test harness/main program written to invoke the child module, pass test parameters, and print/assert its return value.
    • Properties of a Driver: (a) Used in Bottom-Up Integration, (b) Replaces a calling (higher-level) parent module, (c) Active—it initiates the call into the module under test (e.g., a TestNG/JUnit test runner or RestAssured script).
  • 4. Test Automation Pyramid (Mike Cohn's Cost vs Speed Law): The architectural rule governing how many automated tests belong at each level:
    • Base (70% — Unit Tests): Milliseconds to run, zero network/browser overhead, pinpoints exact line of failure.
    • Middle (20% — Integration / API Tests): Milliseconds to seconds, verifies service-to-service and database contracts without slow UI rendering.
    • Top (10% — System / UI E2E Tests): Seconds to minutes per test (Selenium / Playwright), validates critical end-to-end user journeys in a real browser.

3. Classification Tree: The 4 Levels of Testing & Their Sub-Types

Based on granularity of scope and who performs the validation, Dynamic Testing is structured into 4 sequential levels:

  1. Level 1: Unit Testing (Component Testing) — Testing a single method/class in complete isolation.
  2. Level 2: Integration Testing — Testing data flow and contracts between connected modules/services.
    • Sub-Types: 1. Incremental Integration (Top-Down, Bottom-Up, Sandwich/Hybrid) and 2. Non-Incremental Integration (Big Bang).
  3. Level 3: System Testing (End-to-End QA Testing) — Testing the fully integrated application against the SRS.
  4. Level 4: User Acceptance Testing (UAT) — Business/End-Users validating fitness for release.
    • Sub-Types: 1. Alpha Testing (In-house simulated environment) and 2. Beta Testing (Real users in real world).

4. Each Test Level & Sub-Type Explained in Order

① Level 1: Unit Testing (Component Testing)

  • Definition: Testing the smallest testable unit of code (a single method or class) in isolation from databases, networks, or external APIs by using mocks/stubs (`Mockito`).
  • Technique: White-Box Testing—the developer inspects internal `if/else` branches, loops, and exception paths.
  • In what exact cases we perform it: Every time a developer writes or modifies a class (`CartCalculator.java`) before opening a Git Pull Request.

② Level 2: Integration Testing (And All 4 Sub-Types)

  • Definition: Testing the interfaces, data contracts, JSON serialization, and error propagation when two or more tested units/services are combined (e.g., `OrderService` calling `PaymentService` and writing to `PostgreSQL`).
  • The 4 Sub-Types of Integration Testing Explained in Order:
    1. Top-Down Integration: Testing starts from the top-level parent module (UI / Controller) downward. Lower-level modules that aren't ready yet are simulated using Stubs.
      When used: When critical control logic sits at the top layer and needs early verification.
    2. Bottom-Up Integration: Testing starts from the lowest-level database/utility modules upward. Because the parent caller isn't ready yet, a Driver invokes the lower modules.
      When used: When core database/calculation engines must be rock-solid before building controllers.
    3. Sandwich (Hybrid / Bi-Directional) Integration: Combines Top-Down (using Stubs for bottom layers) and Bottom-Up (using Drivers for middle layers) simultaneously, meeting at the middle target layer.
      When used: Large enterprise microservice systems where UI and DB teams work in parallel.
    4. Big Bang Integration (Non-Incremental): Waiting until 100% of modules are coded, coupling all of them together at once, and testing the whole bundle.
      Why risky: When a failure occurs, isolating which interface among 20 coupled modules caused the bug is extremely difficult.

③ Level 3: System Testing (End-to-End Testing)

  • Definition: Testing the fully integrated software product as a whole in a production-like QA environment to verify both Functional requirements (UI workflows, validations, edge cases) and Non-Functional requirements (performance, security, compatibility) against the SRS.
  • Technique: Primarily Black-Box Testing—QA and SDETs test through the real Browser UI (`Selenium WebDriver` / `Playwright`) and public APIs as an end user would.
  • In what exact cases we perform it: Inside every Sprint once features are deployed to the QA environment and pass the Phase 4 Smoke Gate.

④ Level 4: User Acceptance Testing (UAT — Alpha vs Beta)

  • Definition: The final validation level performed by the Client, Product Owner, Business Stakeholders, or real End-Users to confirm the software satisfies business goals (BRS) and is ready for commercial go-live.
  • The 2 Sub-Types of UAT Explained in Order:
    1. Alpha Testing: Performed in-house at the developer's organization (in a dedicated UAT staging environment) by internal business staff, product teams, or client representatives before external release. Both white-box and black-box insights can be used, and critical bugs are fixed immediately before public exposure.
    2. Beta Testing: Performed by real external customers in their own real-world hardware/network environments using a pre-release ("Beta") version of the product. It is strictly Black-Box; feedback and crash telemetry are collected to polish the final General Availability (GA) release.

Interview Answer: "The 4 levels of testing are Unit, Integration, System, and UAT. Unit testing is white-box testing of individual methods by developers. Integration testing checks interfaces and APIs between modules using Top-Down (Stubs) or Bottom-Up (Drivers) approaches. System testing is black-box end-to-end validation of the full app in QA by SDETs using Manual, Selenium, and API suites. UAT is business validation via Alpha (in-house staging) and Beta (real customer environment) testing before go-live."

6. Real Runnable Java & Selenium Code Trace Across All Levels

Here is a complete, runnable Java program demonstrating Level 1 (Unit Test) and Level 2 (Top-Down Integration using a Stub + Bottom-Up Driver), followed by how Level 3 (System Test in Selenium) validates the exact same checkout flow:

// 1. Interface for the lower-level child module (Payment Gateway)
interface PaymentGateway {
    boolean chargeCard(String cardNo, double amount);
}

// 2. High-level parent module (OrderService) that depends on PaymentGateway
class OrderService {
    private final PaymentGateway gateway;
    public OrderService(PaymentGateway gateway) { this.gateway = gateway; }

    // Pure calculation unit
    public double calculateTotalWithTax(double price, double taxPct) {
        return price + (price * taxPct / 100.0);
    }

    // Integration flow calling child module
    public String placeOrder(String cardNo, double price, double taxPct) {
        double total = calculateTotalWithTax(price, taxPct);
        boolean paid = gateway.chargeCard(cardNo, total);
        return paid ? "ORDER_CONFIRMED:$" + total : "PAYMENT_DECLINED";
    }
}

// 3. STUB (Replaces the unbuilt child PaymentGateway for Top-Down Integration)
class PaymentGatewayStub implements PaymentGateway {
    @Override
    public boolean chargeCard(String cardNo, double amount) {
        return amount <= 5000.0; // Dummy rule: approve up to $5000
    }
}

// 4. DRIVER (Main test harness that drives Unit + Integration tests)
public class TestLevelsDemo {
    public static void main(String[] args) {
        OrderService service = new OrderService(new PaymentGatewayStub());

        // LEVEL 1 — UNIT TEST: Test calculateTotalWithTax() in isolation
        double unitResult = service.calculateTotalWithTax(100.0, 18.0);
        System.out.println("L1 Unit Test (100 + 18% tax) : " + unitResult);

        // LEVEL 2 — TOP-DOWN INTEGRATION TEST: OrderService -> PaymentGatewayStub
        String intResult = service.placeOrder("4111-XXXX", 100.0, 18.0);
        System.out.println("L2 Integration (with Stub)   : " + intResult);
    }
}
L1 Unit Test (100 + 18% tax) : 118.0
L2 Integration (with Stub)   : ORDER_CONFIRMED:$118.0

Level 3 (System Testing in Selenium WebDriver): Once the real frontend, backend, and payment sandbox are deployed to the QA environment, SDET runs the end-to-end browser System Test:

@Test(groups = {"system"})
public void verifyEndToEndOrderPlacement() {
    WebDriver driver = getDriver();
    driver.get("https://qa-shop.internal/checkout");
    driver.findElement(By.id("card-input")).sendKeys("4111222233334444");
    driver.findElement(By.id("place-order-btn")).click();

    String banner = driver.findElement(By.id("order-status")).getText();
    Assert.assertEquals(banner, "ORDER_CONFIRMED:$118.0");
}

7. Self-Check

  1. In Top-Down Integration, when a lower-level child module is missing, do we write a Stub or a Driver? (A Stub — because it replaces the called child module.)
  2. Which level of testing maps directly to HLD (High-Level Design), and which maps to SRS? (HLD → Integration Testing; SRS → System Testing.)
  3. Why should a project have 70% Unit tests, 20% Integration/API tests, and 10% Selenium UI System tests instead of 100% Selenium UI tests? (The Test Automation Pyramid: UI tests are slowest and most brittle; Unit and API tests run in milliseconds and isolate exact root causes.)
