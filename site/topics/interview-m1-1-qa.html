Interview

M1.1 Question Bank: Verification vs Validation & Static vs Dynamic Testing (35 Questions)

Tier 1: Core Definitions, Classification & Theory (Q1–Q10)

  1. What is Software Testing at its base, and why can't we just rely on developers writing careful code?
    Software Testing is the systematic evaluation of work products (requirements, design, code) and the running software to prevent and detect defects. Even careful developers misunderstand ambiguous business requirements, make boundary logic errors, or miss environment/integration interactions.
  2. How is Software Testing classified based on code execution?
    It splits into two branches: Static Testing (evaluating documents and source code without executing the program) and Dynamic Testing (evaluating the software by executing compiled code with test inputs).
  3. What is the exact relationship between Static/Dynamic Testing and Verification/Validation?
    Static Testing is how we perform Verification (checking work products against specifications without running code). Dynamic Testing is how we perform Validation (executing the running product to confirm it satisfies user business needs).
  4. What is the one-line difference between Verification and Validation?
    Verification asks: "Are we building the product right?" (matches specification). Validation asks: "Did we build the right product?" (solves the user's real problem).
  5. List all 4 manual Static Review types from least formal to most formal.
    1. Informal Review (buddy/peer check) → 2. Walkthrough (author-led meeting) → 3. Technical Review (SME/architect peer review) → 4. Inspection (moderator-led formal audit with checklists and metrics).
  6. What are the exact roles in a formal Inspection, and why is the Author not allowed to be the Moderator?
    Roles: Moderator (leads and enforces entry/exit criteria), Author (created the work product), Reader (paraphrases sections aloud), Recorder/Scribe (logs defects), and Inspector/Reviewer. The Author cannot be the Moderator because of cognitive bias—people naturally overlook mistakes in their own work.
  7. What is Automated Static Code Analysis, and what tools perform it?
    Parsing source code without executing it to find bugs, security vulnerabilities (SAST), code bloat, and style violations. Tools: SonarQube, Checkstyle, PMD, SpotBugs (Java), and ESLint (JS/TS).
  8. What are the main sub-types of Dynamic Testing?
    1. Functional Dynamic Testing: Unit, Integration, System, and User Acceptance Testing (UAT).
    2. Non-Functional Dynamic Testing: Performance (Load, Stress, Spike, Endurance), Security (DAST/Pen-testing), Usability, and Compatibility testing.
  9. How do QA (Quality Assurance) and QC (Quality Control) map to Verification and Validation?
    QA is process-oriented and preventative, aligning with Verification / Static Testing (preventing defects from entering the build). QC is product-oriented and detective, aligning with Validation / Dynamic Testing (identifying defects inside the built software).
  10. What is the IBM / NIST Cost of Defect Rule (1:10:100), and why does it justify Static Testing?
    A defect caught during Requirement/Design Review (Static Verification) costs 1x to fix; caught during QA Dynamic Execution costs 10x; caught in Production costs 100x. Static testing catches defects at the 1x stage.

Tier 2: Why / Why Not & Deep Comparisons (Q11–Q18)

  1. Why do we still need Dynamic Testing if our team did 100% thorough Static Reviews and SonarQube showed 0 issues?
    Because Static Testing cannot see runtime state: database deadlocks, third-party API downtime, memory leaks under load, browser rendering bugs, network timeouts, or whether the workflow actually makes sense to a real customer.
  2. Why not skip Static Testing in Agile since sprints are only 2 weeks long and we want to move fast?
    Skipping a 15-minute static requirement review in a 2-week sprint causes developers to spend 4 days coding a misunderstood feature, leaving QA with a broken build on Day 8 and causing sprint spillover. Static review is what makes fast sprints possible.
  3. What is the difference between a Walkthrough and a Technical Review?
    A Walkthrough is led by the author to educate the team and gather general feedback, often including non-technical stakeholders. A Technical Review focuses strictly on technical correctness, architecture, and standards, evaluated by domain/technical peers and senior engineers.
  4. Can Static Testing find a NullPointerException in Java? Why or why not?
    Partially yes: Static analyzers like SonarQube and SpotBugs use data-flow analysis to flag potential null dereferences when a method can return null without a null check. However, if the null comes from an unexpected runtime JSON payload or uninitialized TestNG lifecycle state, only Dynamic Testing will trigger the actual runtime NullPointerException.
  5. Can Dynamic Testing find dead (unreachable) code or unused variables? Why or why not?
    No (unless combined with a code-coverage profiler). Dynamic testing only observes external outputs for given inputs; unused private fields or dead helper methods silently sit in the bytecode without failing any dynamic test, whereas Static Analysis flags them immediately.
  6. What is the difference between SAST and DAST in security testing?
    SAST (Static Application Security Testing) scans source code/dependencies without running the app (Static Verification—e.g., finding hardcoded passwords or SQL concatenation in Java). DAST (Dynamic Application Security Testing) attacks the running web server/API from the outside (Dynamic Validation—e.g., OWASP ZAP injecting payloads into live endpoints).
  7. Does executing a dry-run / syntax check of a test script count as Static or Dynamic testing?
    Static Testing—compiling (`javac`) or running Cucumber `dryRun = true` only checks syntax and step-definition bindings without launching a browser or executing application logic.
  8. Between Verification and Validation, which one requires domain/business knowledge more, and which requires specification/technical accuracy more?
    Verification relies heavily on specification conformance and technical standards (matching SRS/HLD/coding rules). Validation relies heavily on domain and user empathy (knowing how a real banker, shopper, or patient uses the system).

Tier 3: Real-World Tricky & Edge-Case Scenarios (Q19–Q26)

  1. [Scenario — The "Code-Less" Sprint Day 1] Developers have finished the Technical Design Document and Swagger API spec for a payment microservice, but zero Java code is written yet. An interviewer asks: "Can you test right now?" How do you answer?
    "Yes—I will perform Static Testing (Verification)." I will review the Swagger contract for missing HTTP error codes (`400`, `401`, `403`, `422`), boundary rules (negative or zero payment amounts, currency decimals), idempotency keys for duplicate clicks, and lint the OpenAPI schema.
  2. [Scenario — Verification Passes, Validation Fails] Give a real production example where Verification passed 100% but Validation failed.
    A healthcare requirement spec mistakenly stated: "Allow birth year between 1950 and current year." Developers coded `year >= 1950`, unit tests and QA checks against the spec passed (**Verification passed**). When released, patients born in 1945 (age 80+) could not book appointments (**Validation failed** because the spec itself violated real-world user needs).
  3. [Scenario — Validation Passes, Verification Fails] Can Validation pass while Verification fails? Give an example.
    Yes. Suppose a developer builds a working search filter that customers love in UAT (**Validation passes**), but the developer hardcoded database credentials in the Java class, skipped logging standards, and ignored the agreed API contract in the SRS (**Verification fails** during code/architecture inspection).
  4. [Scenario — The Green Selenium Build That Lost Money] Your Selenium checkout script ran in Jenkins, clicked "Pay Now", and passed green. In production, customers were charged $0.00 because the button rendered "Pay $0.00". Was this a Static or Dynamic failure, and verification or validation?
    The test was **Dynamic Testing**, and it suffered a **Validation failure** disguised as a technical pass. The script only checked DOM element clickability (`elementToBeClickable`), failing to validate the business rule that the displayed charge amount and backend order total must match the non-zero cart price.
  5. [Scenario — The Vague Requirement Trap] A Jira story says: "The search results must load fast." You run a dynamic JMeter test and measure 2.2 seconds, which the Product Owner rejects saying it must be under 500ms. Where did the failure actually happen?
    It happened during **Static Testing (Requirement Verification)** in Sprint Refinement. Words like *"fast"*, *"user-friendly"*, or *"secure"* are untestable. QA must reject vague requirements statically before coding starts and enforce measurable Acceptance Criteria (e.g., `p95 response time < 500ms at 200 RPS`).
  6. [Scenario — Missing Requirement in Spec] During Dynamic System Testing, you notice clicking the browser Back button after logout re-displays the user's bank balance from cache. The SRS document says nothing about browser Back button behavior. Is this a bug?
    Yes—it is a Validation / Security defect. Even if the SRS omitted it (so strict Verification against the written text wouldn't flag it), Dynamic Validation evaluates fitness and security for real-world usage. You log the defect and also update the SRS/security checklist.
  7. [Scenario — Reviewing Your Own Test Cases] Why shouldn't an SDET be the sole reviewer of their own Test Cases or Automation Scripts?
    If you misunderstood a requirement while writing the test case, you will repeat that exact same misunderstanding when reviewing your own work. Peer review (Informal/Technical Review) brings an independent mental model to catch blind spots.
  8. [Scenario — Third-Party API Upgrade] A payment gateway announces they are deprecating a JSON field next month. No build has changed yet. What testing do you do today?
    Static Impact Analysis (Verification): Inspect your codebase, POJO classes, API contract tests, and mock payloads to identify every place referencing the deprecated field before the external change breaks runtime execution.

Tier 4: SDET, Automation (Selenium/Playwright) & CI/CD Context (Q27–Q31)

  1. Is Test Automation only Dynamic Testing, or does Automation exist in Static Testing too?
    Automation exists in **both**:
    • **Static Automation:** SonarQube, Checkstyle, SpotBugs, ESLint, OpenAPI linters, and Git pre-commit hooks scanning code/specs without running the app.
    • **Dynamic Automation:** JUnit, TestNG, RestAssured, Selenium WebDriver, and Playwright executing the live application.
  2. When reviewing a teammate's Selenium Java Pull Request (Static Testing), what top 6 flaws do you check for?
    1. Hardcoded `Thread.sleep()` instead of `WebDriverWait`.
    2. `static WebDriver` fields that break parallel `ThreadLocal` execution.
    3. Fragile absolute XPaths (`/html/body/div[3]...`) instead of `By.id` / CSS / relative XPath.
    4. Public `By` or `WebElement` fields violating Page Object encapsulation.
    5. TestNG `Assert` statements placed inside Page Object classes instead of `@Test` classes.
    6. Unclosed file streams (`FileInputStream` / `XSSFWorkbook`) causing resource leaks.
  3. In a CI/CD pipeline (Jenkins / GitHub Actions), in what exact order should Static and Dynamic automated stages run, and why?
    Stage 1: Compile & Static Analysis (SonarQube / Linters) (~30 seconds) → Stage 2: Dynamic Unit Tests (~1 min) → Stage 3: Deploy & Dynamic API Tests (~3 mins) → Stage 4: Dynamic Selenium/Playwright UI Tests (~10 mins). We run Static checks first ("Fail Fast") so we never waste 15 minutes spinning up browsers for code that has a static syntax or null-pointer defect.
  4. How do you verify a Requirement Traceability Matrix (RTM) statically before Dynamic Execution starts?
    Cross-check every Requirement ID in the SRS/Jira Epic against your Test Case IDs and automated `@Test` methods to ensure **zero orphan requirements** (requirements with 0 test cases) and **full negative/boundary coverage**.
  5. In Playwright (TypeScript), how does the TypeScript compiler (`tsc --noEmit`) act as Static Verification for your test suite?
    Before a browser ever launches, `tsc` statically verifies that all Page Object method calls, test data interfaces, and `Promise` return types match—catching typos and missing parameters at compile time rather than failing mid-test after 40 seconds of browser navigation.

Tier 5: Rapid-Fire Curveballs & True/False Traps (Q32–Q35)

  1. True or False: "Unit Testing is Static Testing because developers do it in the IDE before QA gets the build."
    False. Unit testing executes compiled code (`@Test` methods) with inputs and asserts runtime outputs—so it is **Dynamic Testing**, regardless of who runs it.
  2. True or False: "Executing a SQL query against a live QA database to check if an order row was inserted is Static Testing."
    False. Querying a live database after an application action is **Dynamic Database Validation**. Reviewing the `.sql` migration script file before running it is **Static Verification**.
  3. Can Static Testing be performed on already-deployed Production software?
    Yes—reviewing production architecture diagrams, auditing production IAM security policies/configs, or running static log/code audits can happen at any time without executing user transactions.
  4. If you have to summarize this entire topic in 20 seconds to a Hiring Manager, what do you say?
    "Software testing splits by code execution into Static Testing (Verification—inspecting requirements, design, and code before execution to prevent bugs at 1x cost) and Dynamic Testing (Validation—executing Unit, API, and Selenium/Playwright tests against the running build to ensure the product works for the user). In my workflow, I combine static PR/story reviews with dynamic CI/CD automation."
