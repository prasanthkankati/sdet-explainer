1.4 Metaspace, static Memory & Execution Engine (JIT + GC)

Where class metadata and static variables reside, how the Interpreter and JIT compiler execute bytecode, and how Garbage Collection reclaims Heap memory.

Java replaced the fixed-size Permanent Generation (PermGen) with Metaspace in Java 8 so class metadata grows dynamically in native operating system memory rather than inside a bounded Heap region. Meanwhile, the Execution Engine pairs a fast-starting Bytecode Interpreter with a Just-In-Time (JIT) compiler and an automatic Garbage Collector to optimize throughput and reclaim unused Heap objects.

Before you start

Prerequisite: 1.3 Stack vs Heap Memory & Pass-by-Value

Where it fits

Long-running Jenkins CI test suites rely on Metaspace to hold loaded framework classes, the JIT compiler to speed up repeated Selenium helper calls, and Garbage Collection to recycle short-lived WebElement and String objects between tests.

Key points

  1. Metaspace (introduced in Java 8, replacing PermGen) lives in native OS memory outside the Heap and stores class metadata, method bytecode, field descriptors, and runtime constant pools.
  2. In modern JVMs (Java 8+), static variables and the interned String Constant Pool live on the Heap alongside normal objects, while class structure metadata lives in Metaspace.
  3. The Interpreter executes bytecode sequentially without startup delay, while the JIT Compiler compiles frequently executed ('hot') methods into cached native CPU machine code.
  4. The Garbage Collector (GC) identifies live objects by tracing reachability from GC Roots (active Stack references, static fields, active threads, and JNI references); any unreachable object is eligible for collection.
  5. Generational GC partitions the Heap into the Young Generation (Eden plus two Survivor spaces, S0 and S1, cleaned by fast Minor GC) and the Old/Tenured Generation (cleaned by slower Major/Full GC).
  6. G1GC (Garbage-First Collector) is the default collector in Java 11, Java 17, and Java 21; calling System.gc() is only an advisory request that the JVM may ignore.

How it works

  1. When a class loads, its structure and constant pool enter Metaspace while new instances enter the Heap's Eden space.
  2. During execution, the Interpreter runs bytecode immediately while profiling invocation and loop back-edge counters.
  3. Once a method crosses the compilation threshold (commonly 10,000 invocations in C2), the JIT compiler translates that bytecode into optimized native machine code stored in the Code Cache.
  4. When Eden fills up, a Minor GC pauses application threads briefly (Stop-The-World), marks objects reachable from GC Roots, copies live objects to a Survivor space (S0 or S1), and clears Eden.
  5. Objects surviving multiple Minor GC cycles (aging threshold, default 15) are promoted to the Old Generation, which is collected less frequently by Major/Mixed GC.

Inspecting JVM memory regions, GC activity, and reachability in Java:

package dev.java.jvm; // Declares package

public class MemoryAndGcDemo { // Class metadata stored in Metaspace
    static String suiteEnv = "STAGING"; // Static reference lives on Heap with Class object
    public static void main(String[] args) { // Main thread root on JVM Stack
        Runtime rt = Runtime.getRuntime(); // Accesses JVM memory runtime metrics
        String tempBanner = new String("Temporary QKart Banner"); // Allocated in Young Gen Eden
        tempBanner = null; // Removes reference; object is now unreachable from GC Roots
        long freeMb = rt.freeMemory() / (1024 * 1024); // Computes free Heap in megabytes
        long maxMb = rt.maxMemory() / (1024 * 1024); // Computes configured -Xmx limit in MB
        System.out.println(suiteEnv + " Free/Max MB: " + freeMb + "/" + maxMb); // Prints runtime stats
    } // Ends main method; Stack root drops
} // Ends MemoryAndGcDemo class

Common mistakes

  1. Calling System.gc() after every Selenium test to 'force' memory cleanup; this is only a hint, and when honored it triggers an expensive Stop-The-World Full GC that slows down the test suite.
  2. Believing an object with a cyclic reference (Object A points to Object B, Object B points to Object A) cannot be garbage collected; the JVM uses reachability tracing from GC Roots rather than reference counting, so disconnected islands are collected cleanly.
  3. Leaving static collections populated across a long test suite; static fields are GC Roots tied to the loaded class in Metaspace, keeping referenced objects alive until JVM exit.
  4. Assuming Java has zero memory leaks because of Garbage Collection; memory leaks occur whenever unneeded objects remain reachable from active roots including unclosed ThreadLocal variables or static maps.

Interview questions

Basics

What is Metaspace and how does it differ from PermGen?
PermGen (Permanent Generation) was a fixed-size contiguous portion of the Heap in Java 7 and earlier used for class metadata and interned strings, frequently failing with OutOfMemoryError: PermGen space. Java 8 replaced PermGen with Metaspace, which allocates class metadata dynamically in native OS memory rather than inside the Java Heap. Metaspace grows automatically up to available RAM unless bounded explicitly by -XX:MaxMetaspaceSize.

Where do static variables and class definitions live in Java 21?
Class structural definitions, method bytecode, and field metadata live in Metaspace (native memory). The static field slots themselves and any objects they point to reside on the Heap alongside the class's runtime java.lang.Class instance. This allows static data to participate cleanly in normal Heap Garbage Collection if a custom ClassLoader is unloaded.

What is the difference between the Interpreter and the JIT compiler?
The Interpreter reads and executes bytecode one instruction at a time, giving Java instant startup without waiting to compile an entire application beforehand. The JIT (Just-In-Time) compiler monitors execution counters, detects frequently run methods and loops ('hot code'), and compiles them into native CPU machine code cached for direct execution. Using both gives Java fast startup and near-native steady-state speed.

How it works

How does the Garbage Collector decide whether an object on the Heap can be deleted?
The JVM builds an object reachability graph starting from active GC Roots, which include local variables in active Stack frames, static fields on loaded classes, running Thread objects, and JNI references. Any object reachable through a chain of references from a GC Root is marked alive and preserved. Any object unreachable from all GC Roots is treated as dead garbage and reclaimed—even if dead objects point to each other.

How does Generational Garbage Collection organize the Heap?
Because empirical studies show most Java objects (loop strings, iterators, and WebElement wrappers) die almost immediately, the Heap is divided into Young Generation and Old Generation. New objects allocate in Eden; survivors copy between S0 and S1 during Minor GC, incrementing an age counter each time. Once an object reaches the tenuring threshold (default 15), it moves to the Old Generation so Minor GC never wastes time scanning long-lived framework objects.

What does 'Weak Generational Hypothesis' mean for test automation code?
The Weak Generational Hypothesis states that most objects become unreachable very quickly after creation. In a Selenium test, thousands of transient objects—By locators, HTTP JSON strings, and short-lived WebElement instances—are allocated per test method and die when the method ends. Young Generation Minor GC sweeps those short-lived objects in milliseconds without triggering expensive Old Generation collections.

Real situations

If an automation framework clears all references inside a test, does System.gc() guarantee immediate memory cleanup?
No. Calling System.gc() only submits a polite suggestion to the JVM, and production CI environments commonly disable it altogether with the -XX:+DisableExplicitGC flag. Even when accepted, System.gc() forces a Stop-The-World Full GC that freezes all parallel TestNG worker threads unnecessarily. Designing short-lived objects and cleaning up ThreadLocal entries is the reliable approach.

Why can a TestNG suite with 500 tests produce a Java memory leak even though GC runs automatically?
Garbage Collection only reclaims unreachable objects; it never deletes an object that a live reference still points to. In parallel Selenium suites, forgetting to call tlDriver.remove() on a ThreadLocal<WebDriver> leaves the closed driver object anchored inside the pooled worker thread's map, or storing every test's screenshot byte array in a static List anchors them permanently to a GC Root. Eventually the Old Generation fills up and crashes with OutOfMemoryError.

Why do long-running Selenium suites execute faster after the first 20 tests warm up?
During the initial tests, the JVM executes shared Page Object wrappers and wait polling loops through the Bytecode Interpreter while collecting runtime type profiles. Once those helper methods cross JIT compilation thresholds, the C2 compiler produces optimized native machine code and inlines tiny getters directly. Subsequent tests bypass bytecode interpretation entirely.

Troubleshooting

How do you investigate java.lang.OutOfMemoryError: GC overhead limit exceeded?
This error fires when the JVM spends over 98% of its CPU time running Garbage Collection while recovering less than 2% of Heap space—meaning the Heap is nearly full of live objects that cannot be collected. Capture a heap dump automatically on failure by adding -XX:+HeapDumpOnOutOfMemoryError and inspect retained sizes in Eclipse MAT or VisualVM to find which static collection or unclosed resource is holding references.

What causes java.lang.OutOfMemoryError: Metaspace in dynamic test runners?
Metaspace runs out of room when dynamic proxy generation (from Mockito, Spring, or bytecode instrumentation across test runs) creates thousands of unique classes that are never unloaded, or when -XX:MaxMetaspaceSize is set too low for the project's library count. Raising -XX:MaxMetaspaceSize or reusing proxy configurations eliminates the failure.

How can you inspect which Garbage Collector and Heap limits a Maven build uses?
Add -Xlog:gc* (Java 9+) to the Maven Surefire <argLine> configuration to print exact GC pauses, collector name (G1GC by default), and Young/Old generation sizes before and after collection. Comparing Eden vs Old generation usage across tests exposes memory retention immediately.

Design choices

Why did Java 9+ make G1GC the default Garbage Collector instead of Parallel GC?
Parallel GC maximizes raw throughput but can trigger multi-second Stop-The-World pauses when collecting huge Old Generations, causing HTTP timeouts in distributed tests and web services. G1GC splits the Heap into uniform regions and targets predictable pause-time goals (-XX:MaxGCPauseMillis=200 by default) by prioritizing regions containing the most garbage first. That balance suits both CI build agents and enterprise microservices.

Why did Java deprecate and remove Object.finalize() in modern releases?
finalize() runs unpredictably on a single low-priority GC thread, can accidentally resurrect dead objects, and severely delays memory reclamation. Modern Java replaces finalizers with explicit AutoCloseable implementations used inside try-with-resources blocks and java.lang.ref.Cleaner for native resources. Deterministic cleanup in @AfterMethod is always faster and safer.

Why did Java replace PermGen with Metaspace instead of simply increasing the default PermGen limit?
PermGen required picking a rigid maximum size upfront before JVM startup and shared contiguous address space management with the Garbage Collector, leading to fragmentation and tuning failures as frameworks grew. Allocating class metadata in native OS memory lets Metaspace expand elastically with loaded classes and simplifies GC pauses.

Quick answers

  1. What did Metaspace replace in Java 8? PermGen (Permanent Generation).
  2. Where does Metaspace allocate memory? In native operating system memory outside the Java Heap.
  3. What makes an object eligible for Garbage Collection? When it is no longer reachable from any GC Root.
  4. What does the JIT compiler do? Compiles hot frequently executed bytecode into native CPU machine code at runtime.
  5. What is the default Garbage Collector in Java 11, 17, and 21? G1GC (Garbage-First Collector).
  6. Does calling System.gc() guarantee immediate Garbage Collection? No, it is only a hint that the JVM can ignore.
