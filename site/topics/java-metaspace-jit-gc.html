1.4 Metaspace, static Memory & Execution Engine (JIT + GC)

1. Definition

Metaspace holds loaded class blueprints in native OS memory, static fields stay bound to the class object rather than individual objects, and the Execution Engine combines an Interpreter, JIT compiler, and Garbage Collector.

2. Memory hook

Metaspace = Rulebook shelf, Interpreter = Reads line by line, JIT = Caches hot code, GC = Sweeps dead Heap objects.

  • Metaspace replaced fixed PermGen in Java 8 and grows in native OS memory as classes load.
  • Interpreter + JIT give both fast startup and fast long-running test speed once hot loops compile to native machine code.
  • Garbage Collector walks from GC Roots (Stack pointers, static fields) and frees unreachable Heap objects.

5. Code example: how reachability decides what GC frees

public class GcLifecycleDemo {
    static String suiteEnv = "QA";    // GC Root: alive for the life of the class

    public static void main(String[] args) {
        Object temp = new Object();   // allocated in Young Gen (Eden); temp holds ref
        temp = null;                  // zero Stack refs left -> eligible for Minor GC
        for (int i = 0; i < 20000; i++) {
            score(i);                 // hot loop -> JIT compiles score() to CPU code
        }
    }
    static int score(int x) { return x * 2; }
}

6. Execution flow, step by step

  1. The JVM loads GcLifecycleDemo metadata into Metaspace and creates the static field anchor.
  2. Inside main, new Object() sits in the Eden region of the Young Generation.
  3. Setting temp = null leaves that Heap object unreachable from any Stack or static root, so the next Minor GC can reclaim it.
  4. Meanwhile, the Interpreter runs the loop early on, detects score(i) getting hot, and asks the JIT Compiler to cache native machine code.
  5. Any object still referenced after multiple Minor GCs promotes to the Old Generation, while static anchors stay alive until the class unloads.

8. Why it matters

Java frees you from manual malloc/free memory bugs, yet keeping stray references inside global static lists still leaks Heap forever because GC cannot delete reachable objects.

SDET link: A static List<byte[]> storing screenshots from 500 Selenium tests stays a GC Root for the entire CI suite and causes OutOfMemoryError. Write screenshots to disk and drop the reference after each test.

9. Quick test

Does setting an object reference to null delete it immediately? No — it only marks it unreachable so GC can free it on the next cycle.
