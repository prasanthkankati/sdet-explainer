J2.6 Question Bank: Methods, Parameters, Return Types & Varargs (21 Questions)

Tier 1: Core Definitions, Classification & Theory (Q1–Q3)

  1. Which parts of a method declaration belong to its official Java method signature?
    Strictly two parts belong to the method signature: the method name and the ordered list of parameter types. Access modifiers (public/private), static, return type (void vs int), parameter variable names, and throws clauses are NOT part of the signature. Therefore two methods in the same class cannot share the same name and parameter types even if they return different types.
  2. What is the difference between a parameter and an argument?
    A parameter (formal parameter) is the typed placeholder variable declared in the method definition, for example String username in enterUsername(String username). An argument (actual parameter) is the concrete expression supplied at the call site, for example "qkart_user1". Arguments are evaluated first, then copied into parameters on the new Stack Frame.
  3. What are the two strict syntax rules for varargs in Java?
    First, a method may declare at most one varargs parameter—having two like log(String... a, int... b) is a compile error. Second, the varargs parameter must always be the final parameter in the parameter list. Internally, the compiler transforms Type... name into a standard Type[] name array.

Tier 2: How It Works & Internal Mechanics (Q4–Q6)

  1. How does Selenium's WebElement.sendKeys(CharSequence... keysToSend) accept both a String and Keys.ENTER in one call?
    Both java.lang.String and Selenium's org.openqa.selenium.Keys enum implement the standard Java interface java.lang.CharSequence. Because sendKeys declares a CharSequence... varargs parameter, calling box.sendKeys("watch", Keys.ENTER) causes the compiler to pack both arguments into a CharSequence[] array automatically. Inside sendKeys, Selenium reads the array elements sequentially.
  2. How does overload resolution behave when both an exact fixed-parameter method and a varargs method match?
    Java resolves method overloads using three priority levels: exact match without boxing or varargs wins first, boxing/unboxing matches win second, and varargs matches win last as a fallback. If a class defines both click(By) and click(By...), calling click(loginBtn) always binds to the fixed 1-argument method to avoid unnecessary array allocation.
  3. What happens if a varargs method is invoked with zero trailing arguments, for instance logStep("AUTH")?
    The compiler silently constructs and passes a zero-length array (new String[0]), never null. That guarantees iterating over for (String s : messages) inside the method runs zero times safely without throwing a NullPointerException.

Tier 3: Real-World SDET & Selenium Scenarios (Q7–Q9)

  1. When designing a Selenium framework, should Page Object methods be static or instance methods?
    Page Object action methods must be instance methods because each Page Object encapsulates an instance WebDriver field for the active browser thread. Making Page Object methods static forces shared static driver state, which causes parallel TestNG threads to hijack each other's browser windows. Reserve static purely for stateless helpers like WaitUtils.waitVisible(driver, locator) or StringUtils.
  2. How does fluent method chaining improve Selenium Page Object tests?
    When an action keeps the user on the same page, returning this lets tests chain loginPage.enterUser("u").enterPassword("p"). When an action navigates elsewhere, returning new InventoryPage(driver) enforces valid page transitions directly in the test's compile-time type chain.
  3. How does JavascriptExecutor.executeScript(String script, Object... args) use varargs?
    The first mandatory parameter holds the JavaScript snippet string, and the trailing Object... args parameter passes zero or more Selenium WebElement or primitive arguments into JavaScript's arguments[0], arguments[1] array. Without varargs, callers would have to construct a boilerplate new Object[]{el} array on every JS call.

Tier 4: Troubleshooting, Exceptions & Failure Modes (Q10–Q12)

  1. Why does calling log(null) on a varargs method like void log(String... items) produce a compiler warning and a runtime NullPointerException?
    When a single literal null is passed to String... items, the compiler assumes you passed a null reference for the entire String[] array itself rather than a 1-element array containing null. Inside the method, accessing items.length or looping over items immediately throws NullPointerException. Pass new String[]{null} if a single null element is actually intended.
  2. Why does a method fail compilation with 'missing return statement' even though an if block returns a value?
    The compiler verifies statically that every conceivable execution branch returns a compatible value or throws an exception. If a return only appears inside an if block without an unconditional fallback return or else return, compilation fails immediately.
  3. Why does Assert.assertEquals(actual, expected) behave unexpectedly if you swap argument order?
    Java binds arguments strictly by position, not parameter name. In TestNG Assert.assertEquals(actual, expected), passing expected first causes failure reports to swap 'expected [actual] but found [expected]', misleading engineers debugging CI failures.

Tier 5: Design Choices & Rapid-Fire Recall (Q13–Q21)

  1. Why did Java exclude the return type from the method signature?
    Callers in Java are allowed to ignore a method's return value (for instance, calling list.remove(item); without assigning the returned boolean). If two methods differed only by return type, the compiler could never tell which overload a standalone statement call intended to invoke.
  2. When should a utility method accept Collection<T> instead of T... varargs?
    Use varargs when callers normally type 1 to 4 inline arguments directly at the call site, because callers avoid creating a list manually. Accept List<T> or Collection<T> when callers already hold dynamic results like driver.findElements(By), avoiding heap array copies and ambiguous overloads.
  3. Why should methods stay small with 3 or fewer parameters in automation frameworks?
    Methods accepting 6 or 7 positional String parameters make call sites unreadable and prone to swapping arguments of the same type (like first name and email). Encapsulating multi-field inputs inside a clean POJO or Builder object makes test intent self-documenting.
  4. What makes up a Java method signature?
    Method name plus parameter types and their order.
  5. Is the return type part of the method signature?
    No.
  6. Where must a varargs parameter be placed?
    Strictly as the last parameter in the parameter list.
  7. How does the Java compiler treat String... args internally?
    As a standard String[] args array.
  8. What does a varargs parameter receive when zero optional arguments are passed?
    An empty array of length 0 (never null).
  9. Can a static method access this or instance fields directly?
    No, because static methods execute on the class without an object instance.
