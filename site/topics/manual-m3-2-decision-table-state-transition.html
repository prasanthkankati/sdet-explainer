3.2 Decision Table, State Transition, Use Case & White-Box Techniques

1. The Base: Why Are EP and BVA Alone Not Enough?

While Equivalence Partitioning and BVA test a single input field's range in isolation, real business systems depend on combinations of multiple conditions (Decision Tables), sequences of state changes over time (State Transitions), end-to-end actor interactions (Use Cases), and internal code branch execution (White-Box Coverage).

The Problem They Solve:

  • Problem 1 (Multiple Interdependent Conditions): A shipping discount depends on 3 conditions together: Is user a Prime Member? + Is cart ≥ $50? + Is payment via Credit Card? EP/BVA cannot model how 3 boolean conditions interact; Decision Table Testing solves this.
  • Problem 2 (History / Sequence of Events Matters): Entering a wrong ATM PIN once shows a warning, twice shows a warning, and the 3rd consecutive time locks the card. The input is identical all 3 times, so only State Transition Testing can model how past attempts change the system's state.

2. Core Terms & Formulas Defined First

  • 1. Decision Table Formula ($2^n$ Rule): If a business feature has $n$ boolean (True/False) conditions, the total number of possible rule combinations (columns) in a full Decision Table is $2^n$ (e.g., 3 conditions = $2^3 = 8$ test rules; 4 conditions = $2^4 = 16$ test rules).
  • 2. The 4 Elements of a State Transition Machine:
    1. State (Circle): The current condition/mode of the object (e.g., `NEW_ORDER`, `PAID`, `SHIPPED`, `CANCELLED`).
    2. Event / Trigger (Arrow Input): The action that initiates a change (e.g., `Click Pay`, `Click Cancel`).
    3. Guard Condition: A prerequisite boolean rule required for the event to succeed (e.g., `[Balance >= OrderTotal]`).
    4. Action / Output: The side effect produced during transition (e.g., `Send Invoice Email` and move to `PAID`).
  • 3. White-Box Coverage Formulas:
    • Statement Coverage %: `(Executed Statements / Total Statements) * 100`
    • Branch / Decision Coverage %: `(Executed True & False Outcomes / Total Decision Outcomes) 100` (Note: 100% Branch Coverage guarantees 100% Statement Coverage, but NOT vice versa!)*

3. Technique 1: Decision Table Testing (Cause-Effect Table)

Definition: A structured tabular Black-Box technique that lists all Conditions (Inputs/Causes) in the top rows and all Actions (Outputs/Effects) in the bottom rows, where every vertical column (`Rule 1 .. Rule 2^n`) becomes 1 Test Case.

Real Example: E-Commerce Shipping Fee Rules (`n = 3` Boolean Conditions → $2^3 = 8$ Rules; collapsed where "Don't Care `-`" applies):

Conditions / ActionsRule 1Rule 2Rule 3Rule 4Rule 5Rule 6Rule 7Rule 8
C1: Prime Member?TTTTFFFF
C2: Cart ≥ $500?TTFFTTFF
C3: Express Coupon?TFTFTFTF
A1: Free Shipping?YESYESYESYESYESYESNONO
A2: Extra 10% Off?YESNONONOYESNONONO
  • Collapsed Decision Table: Notice in Rules 3 & 4 that if `C1 (Prime) = T` and `C2 (Cart >= $500) = F`, the user gets Free Shipping with NO extra 10% off regardless of `C3`. When a condition does not affect the outcome, we mark it `-` (Don't Care) to collapse redundant test cases.
  • In what exact cases we use Decision Tables: Insurance premium calculators, credit card approval matrices, tax/discount engines, and role-based access control (RBAC) permissions.

4. Technique 2: State Transition Testing

Definition: A Black-Box technique used when an application's output depends not only on the current input, but also on previous inputs and the current internal state of the system. We test both Valid Transitions (via a State Diagram) and Invalid/Blocked Transitions (via a State Table).

STATE TRANSITION PIPELINE Example: Account Login Lockout After 3 Failed Attempts

5. Technique 3 (Use Case & Error Guessing) & Technique 4 (White-Box Coverage)

  • Use Case Testing (Black-Box): Designing end-to-end test scenarios based on Actor ↔ System interactions, covering the Main Success Scenario (Basic Flow), Alternative Flows (e.g., user pays by UPI instead of Card), and Exception Flows (e.g., bank server times out).
  • Error Guessing (Experience-Based): Using a tester's past experience of common developer mistakes to attack weak spots (`null`, empty string, `0`, negative numbers, emojis, double-clicking submit, SQL quotes `'`).
  • White-Box Statement vs Branch Coverage (With Proof):
// Look at why 100% Statement Coverage DOES NOT mean 100% Branch Coverage:
public class BonusCalculator {
    public static int calculateBonus(int salary, boolean isTopPerformer) {
        int bonus = 0;                       // Statement 1
        if (isTopPerformer) {                // Decision Branch (True / False)
            bonus = salary / 10;             // Statement 2
        }
        return bonus;                        // Statement 3
    }
}
// If we run ONLY 1 test: calculateBonus(50000, true):
// -> Statements 1, 2, and 3 ALL execute = 100% Statement Coverage!
// -> But the 'false' branch of the if-statement was NEVER tested = only 50% Branch Coverage!

Interview Answer: "Decision Table testing handles complex combinations of multiple conditions using the $2^n$ rule. State Transition testing validates systems where past history and state changes matter (testing both valid transitions and invalid transitions like paying for a cancelled order). In White-Box testing, 100% Branch Coverage guarantees 100% Statement Coverage, whereas 100% Statement Coverage does not guarantee 100% Branch Coverage."

7. In Selenium & SDET Automation

  • Decision Table via TestNG @DataProvider: Every column/rule in a Decision Table maps directly to one row in a TestNG Object[][] @DataProvider, driving Selenium checkout/discount assertions across all rule combinations without duplicating test methods.
  • State Transition in WebDriver Tests: Automate negative state transitions (e.g., navigating directly via driver.get(checkoutUrl) or replaying a cancelled order ID) and assert that the UI blocks progression or redirects to ACCOUNT_LOCKED / 403.
