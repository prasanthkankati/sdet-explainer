4.1 Complete Bug Life Cycle & Defect States

1. The Base: What is a Bug Life Cycle and Why Does It Exist?

The Bug Life Cycle (Defect Life Cycle) is the end-to-end state-machine workflow a software defect travels through from the moment QA discovers and logs it in a bug tracker (like Jira), through developer triage and fixing, to QA retesting and final closure.

The Problem It Solves: If a QA engineer simply messages a developer on Slack saying "Checkout is broken", that bug gets forgotten when the sprint gets busy, nobody knows who is fixing it, whether the fix has been deployed to QA yet, or whether QA verified it before release. A strict state workflow (`New → Assigned → Open → Fixed → Pending Retest → Verified → Closed`) enforces accountability at every handoff.

2. Core Terms & Defect Report Properties Defined First

  • 1. Error vs Defect (Bug) vs Failure: A human mistake (Error) introduces a flaw in code/spec (Defect / Bug), which manifests as wrong runtime output (Failure).
  • 2. The 10 Mandatory Fields of a Professional Jira Defect Report:
    1. Defect ID & Summary Title: Concise 1-line headline (`[Checkout] Applying expired coupon throws HTTP 500 instead of error banner`).
    2. Environment & Build Version: `QA-Staging`, `Build #148`, `Chrome 130 / Windows 11`.
    3. Steps to Reproduce: Exact numbered steps so a developer can reproduce it in 30 seconds.
    4. Expected Result vs Actual Result: Clear contrast against the SRS/Acceptance Criteria.
    5. Severity & Priority: Technical impact (`Critical`) vs Business fix urgency (`P1`).
    6. Attachments / Evidence: Screenshot, screen recording, HAR network log, browser console error, and backend stack trace.

4. The 4 Special / Non-Happy-Path Defect States Explained

  1. REJECTED (Invalid / Not a Bug): Developer or BA rejects the ticket because the software actually matches the SRS, or QA misunderstood the requirement / used wrong test data.
  2. DUPLICATE: Another QA engineer already logged the exact same defect earlier (`BUG-102` is linked as a duplicate of `BUG-088`).
  3. DEFERRED (Postponed): A valid bug, but Product/Triage decides to fix it in a future sprint/release because its Severity/Priority is Low or the release deadline is hours away.
  4. CANNOT REPRODUCE (Works on My Machine): Developer cannot trigger the bug locally—usually caused by environment differences, missing browser cache clear, or specific seed data. QA must attach exact HAR logs/video/user ID or re-verify on Staging.

Interview Answer: "A defect moves from New → Assigned → Open → Fixed → Pending Retest → Retest → Verified → Closed. If retesting fails, QA moves it to Reopened. Non-standard terminal/hold states include Rejected (not a bug), Duplicate (already logged), Deferred (valid bug postponed to a future release), and Cannot Reproduce."

5. In Selenium & SDET Automation

  • Automated Defect Evidence: In Selenium/TestNG ITestListener.onTestFailure(), capture TakesScreenshot, browser console errors, and the failing URL/build tag so Jira defects never hit CANNOT REPRODUCE.
  • Retesting via Targeted Groups: Tag bug-fix verification tests with @Test(groups = {"retest", "BUG-104"}) so CI can re-verify a fix in seconds before QA moves the ticket to CLOSED.

6. Self-Check

  1. Who has the final authority to move a defect to CLOSED—the Developer or QA? (QA, after confirming the fix via Retesting on the deployed QA environment.)
  2. What is the difference between Rejected and Deferred? (Rejected = invalid/not a real bug; Deferred = valid real bug intentionally postponed to a later release.)
