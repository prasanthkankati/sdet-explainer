3.2 String vs StringBuilder vs StringBuffer

Eliminating O(n^2) concatenation garbage using mutable StringBuilder and thread-safe StringBuffer with dynamic capacity expansion.

Because String is immutable, concatenating strings inside a loop with + allocates and copies progressively larger intermediate strings on every pass. Java provides StringBuilder for fast single-threaded string construction and StringBuffer for synchronized multi-threaded mutation using an expandable internal character array.

Before you start

Prerequisite: 3.1 String Immutability & String Constant Pool

Where it fits

Dynamic XPath generation, HTML report formatting, CSV/JSON payload assembly, and multi-row table log capture in Selenium utilities rely on StringBuilder to avoid unnecessary Heap garbage.

Key points

  1. Concatenating a String inside a loop (s += item;) creates $O(n^2)$ total character copies because each pass constructs a brand-new String object and copies all previous characters.
  2. StringBuilder (Java 5+) is mutable, non-synchronized, and the fastest choice for building strings inside local method scopes and single-threaded automation utilities.
  3. StringBuffer (Java 1.0) exposes the exact same API as StringBuilder, except all public mutation methods carry the synchronized keyword, making it thread-safe at the cost of monitor locking overhead.
  4. Both StringBuilder and StringBuffer default to an internal capacity of 16 characters (or str.length() + 16) and expand automatically using (oldCapacity * 2) + 2 when exceeded.
  5. Neither StringBuilder nor StringBuffer overrides Object.equals(); comparing two StringBuilder objects directly checks reference identity, so convert with .toString().equals(...) first.
  6. Single-statement concatenations like "User: " + user + " passed" outside loops are already optimized by the Java compiler, whereas loops always require an explicit StringBuilder.

How it works

  1. Instantiate StringBuilder sb = new StringBuilder(64); inside a method to pre-allocate an internal buffer on the Heap.
  2. On each loop iteration, sb.append(rowText) writes characters directly into the existing array without allocating intermediate String objects.
  3. If appended text exceeds the current capacity, StringBuilder allocates a new array of size (oldCapacity * 2) + 2 and copies once.
  4. Call sb.toString() after the loop finishes to freeze the accumulated characters into a final immutable String.

Building a formatted table report and reversing text using StringBuilder:

package dev.java.strings; // Declares package

import java.util.List; // Imports List interface

public class BuilderVsBufferDemo { // Compares StringBuilder operations
    static String buildAuditLog(List<String> items) { // Builds log cleanly in O(n) time
        StringBuilder sb = new StringBuilder(128); // Pre-sizes internal buffer on Heap
        for (int i = 0; i < items.size(); i++) { // Iterates over collected element texts
            sb.append("Row ").append(i + 1).append(": ").append(items.get(i)).append("\n"); // Fluent chaining mutates buffer in place
        } // Zero intermediate String objects created inside loop
        return sb.toString(); // Converts final mutable buffer into immutable String
    } // Ends buildAuditLog

    public static void main(String[] args) { // Main execution entry
        List<String> rows = List.of("Login Pass", "Cart Updated", "Checkout OK"); // Sample step names
        System.out.println(buildAuditLog(rows)); // Prints assembled multi-line log
        StringBuilder rev = new StringBuilder("QKart"); // Initializes mutable buffer with QKart
        rev.reverse(); // Reverses characters in place without extra method loop
        System.out.println("Reversed: " + rev.toString()); // Prints: traKQ
    } // Ends main method
} // Ends class

Common mistakes

  1. Concatenating strings with += inside a for loop over hundreds of Excel or table rows; this allocates hundreds of discarded String objects and causes quadratic $O(n^2)$ memory copies.
  2. Using StringBuffer inside a single method's local variable; because a local variable on the Stack is never shared across threads, synchronization locks add pointless overhead where StringBuilder is strictly faster.
  3. Asserting sb1.equals(sb2) directly on two StringBuilder instances; because StringBuilder does not override equals(), the assertion returns false even for identical text unless you call sb1.toString().equals(sb2.toString()).
  4. Storing a single shared static StringBuilder field across parallel TestNG threads without synchronization, corrupting output when concurrent threads interleave append() calls.

Interview questions

Basics

Compare String, StringBuilder, and StringBuffer in one concise overview.
String is immutable and stored in the String Constant Pool or Heap, making every edit allocate a new object. StringBuilder is mutable and unsynchronized, giving the fastest performance for single-threaded loops. StringBuffer is also mutable, with synchronized methods that guarantee thread-safety at a slight locking cost.

When should you choose StringBuilder instead of String?
Choose StringBuilder whenever text is assembled iteratively across a loop, conditional branch sequence, or dynamic query/XPath generator. For fixed constants or a single "Hello " + name expression outside loops, plain String stays cleaner and equally fast because the compiler optimizes single-expression concatenation automatically.

Why did Java 5 introduce StringBuilder when StringBuffer already existed?
In real Java programs, over 99% of string-building buffers live strictly as local variables inside one method and are never shared between threads. Paying synchronization lock acquisition and release cost on every single append() call in StringBuffer wasted CPU cycles, so Java 5 added StringBuilder as a drop-in unsynchronized replacement.

How it works

Why does String res = ""; for (int i=0; i<1000; i++) res += i; harm Heap performance?
Because String is immutable, each res += i iteration allocates a new internal concatenation buffer, copies all existing characters from res plus the new digits, produces a brand-new Heap String, and abandons the previous String as garbage. Over 1,000 iterations, this generates roughly 1,000 dead Heap strings and copies characters quadratically. Using a single StringBuilder performs all appends in one array.

How does StringBuilder grow its capacity when appended text exceeds initial capacity?
An empty new StringBuilder() allocates an initial backing array of 16 characters (new StringBuilder("abc") allocates 3 + 16 = 19). When an append() exceeds capacity, StringBuilder computes a new capacity of (oldCapacity * 2) + 2 (or exact required length if larger) and copies contents via Arrays.copyOf(). Passing an estimated capacity like new StringBuilder(512) avoids intermediate array copies altogether.

Does sb.toString() share the backing array with StringBuilder?
No; calling sb.toString() allocates a fresh immutable String with a copy of the active characters (from index 0 to sb.length()). Subsequent sb.append() mutations on the StringBuilder never affect the previously returned String.

Real situations

In a Selenium WebTable test, how should you collect and compare text from 500 table rows?
Create a local StringBuilder inside the extraction method, loop through row elements calling sb.append(row.getText()).append('|'), and return sb.toString(). Keeping the StringBuilder local ensures every TestNG parallel thread gets its own isolated buffer on its own Stack frame without needing StringBuffer.

When building a shared multi-threaded custom logger buffer accessed concurrently by 4 TestNG threads, which mutable class avoids garbled text?
If multiple threads genuinely append to one shared mutable buffer instance, choose StringBuffer (or a thread-safe queue/logger like SLF4J/Log4j2) so concurrent append() calls serialize cleanly without corrupting character indices. However, using ThreadLocal<StringBuilder> or Log4j2 appenders scales better under heavy concurrency.

How do you check whether a UI string is a palindrome during an SDET coding interview?
Normalize case and characters first, then pass the string into new StringBuilder(cleaned).reverse().toString().equals(cleaned), or scan inward with two index pointers (left and right) for zero extra Heap allocation.

Troubleshooting

Why did new StringBuilder("OK").equals(new StringBuilder("OK")) return false in a unit test?
Neither StringBuilder nor StringBuffer overrides Object.equals() or hashCode(), so equals() falls back to reference identity (==). Always convert both buffers via .toString() or compare via Java 11 sb1.compareTo(sb2) == 0.

Why did a shared static StringBuilder reportBuffer throw ArrayIndexOutOfBoundsException during parallel TestNG runs?
StringBuilder provides zero thread synchronization; when two worker threads append concurrently, one thread reads an outdated internal count field while another expands the buffer, causing index corruption or out-of-bounds failures. Make the buffer local to each method or replace it with a thread-safe structure.

What happens if you pass null directly into new StringBuilder((String) null) vs sb.append((String) null)?
Passing null into the new StringBuilder(String) constructor throws NullPointerException immediately because it calls str.length(). By contrast, calling sb.append((String) null) safely appends the literal four characters "null" without throwing.

Design choices

Why does modern Java (Java 11+) use StringJoiner or String.join(", ", list) instead of manual StringBuilder loops for comma-separated text?
Manual loops building delimited lists require clumsy trailing-comma checks (if (i > 0) sb.append(", ")). String.join(", ", list) and Collectors.joining(", ") handle delimiters cleanly in one readable call using StringJoiner internally.

Why should public method signatures return String rather than StringBuilder?
Returning a mutable StringBuilder exposes an internal buffer that callers could accidentally mutate downstream, violating encapsulation. Convert to an immutable String via toString() at the method boundary.

When is StringBuffer legitimately preferred over StringBuilder today?
Only when maintaining legacy APIs expecting a StringBuffer parameter (including older java.util.regex.Matcher methods prior to Java 9) or sharing a single mutable text accumulator directly across threads without external locking.

Quick answers

  1. Which class is fastest for single-threaded string concatenation in loops? StringBuilder.
  2. What makes StringBuffer thread-safe? Its mutation methods are declared synchronized.
  3. What is the default initial capacity of new StringBuilder()? 16 characters.
  4. How does StringBuilder.equals() compare two instances? By reference identity (==), because it does not override Object.equals().
  5. What happens when calling new StringBuilder((String) null)? Throws NullPointerException.
  6. What does sb.append((String) null) append? The four characters "null".
