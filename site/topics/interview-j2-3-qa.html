J2.3 Question Bank: Wrapper Classes, Autoboxing & Integer Cache (-128 to 127) (35 Questions)

Tier 1: Core Definitions, Classification & Theory (Q1–Q7)

  1. Why do wrapper classes exist in Java when primitives already exist?
    Java Collections (List, Set, Map), Generics (<T>), and Reflection operate exclusively on object references that inherit from java.lang.Object. Wrapper classes bridge this gap by encapsulating each of the 8 primitives inside an immutable Heap object. They also allow null to indicate uninitialized or omitted data (such as optional JSON payload fields) and provide rich utility parsing methods like Integer.parseInt().
  2. List all 8 primitive types, their exact wrapper class names, and their parent superclasses.
    Six numeric wrappers extend abstract class java.lang.Number: byte -> Byte, short -> Short, int -> Integer, long -> Long, float -> Float, and double -> Double. Two non-numeric wrappers extend java.lang.Object directly: char -> Character and boolean -> Boolean. Note that Integer and Character spell full words, while the remaining 6 match capitalized primitive names.
  3. Are wrapper classes mutable or immutable? Explain what happens during Integer i = 5; i++;.
    All 8 wrapper classes in java.lang are public final with private final internal value fields, making every wrapper instance strictly immutable. Executing i++ does not mutate the existing object; instead, Java unboxes i via i.intValue(), adds 1 to get primitive 6, and boxes it into a brand-new Integer reference via Integer.valueOf(6), assigning that new address back to i.
  4. What is the difference between Boxing, Unboxing, Autoboxing, and Auto-unboxing?
    Boxing is explicitly converting a primitive into an object (e.g. Integer.valueOf(10)). Unboxing is explicitly extracting the primitive value (e.g. obj.intValue()). Autoboxing is the compiler automatically inserting valueOf() when a primitive is assigned where an object is expected. Auto-unboxing is the compiler automatically inserting xxxValue() when a wrapper is used where a primitive is required (e.g. in arithmetic or boolean expressions).
  5. Why does List<int> fail to compile in Java?
    Java Generics use Type Erasure, replacing generic type arguments with java.lang.Object (or bounded supertypes) at compile time. Because primitive types like int do not inherit from Object, they cannot substitute for generic type parameters. Java requires the reference type List<Integer>.
  6. What are the default values of primitive fields versus wrapper object fields in a class?
    Primitive class fields receive default values: 0 (for integer types), 0.0 (for floats/doubles), false (for boolean), and '\u0000' (for char). Wrapper class fields, being object references, always default to null unless explicitly initialized.
  7. What is the memory footprint difference between primitive int and wrapper Integer on a 64-bit JVM?
    A primitive int occupies exactly 4 bytes of memory, stored directly on the Stack or packed in an array. An Integer object on a standard 64-bit JVM with compressed oops requires 16 bytes on the Heap (12-byte object header + 4-byte int payload), plus an 8-byte reference pointer on the Stack, consuming 24 bytes total—a 6x memory overhead per element.

Tier 2: How It Works & Internal Mechanics (Q8–Q14)

  1. Explain why Integer a = 100, b = 100; a == b is true, while Integer c = 200, d = 200; c == d is false.
    Autoboxing compiles to Integer.valueOf(). Java maintains an internal static pool called IntegerCache initialized with pre-allocated Integer instances for values from -128 through 127. Because 100 is within this range, a and b receive the exact same cached object reference on the Heap, making a == b return true. Because 200 is outside this range, Java executes new Integer(200) for each assignment, creating two distinct Heap objects with different memory addresses, making c == d return false.
  2. Which wrapper classes support value caching, and what are their exact caching ranges?
    Byte caches all 256 values (-128 to 127). Short and Long cache -128 to 127. Character caches 0 to 127 (\u0000 to \u007f, the standard ASCII range). Boolean caches its only two instances (Boolean.TRUE and Boolean.FALSE). Float and Double never cache any values due to infinite decimal fractions.
  3. What happens at the bytecode level during Integer x = 5; int y = x + 2;?
    The compiler transforms Integer x = 5; into an invokestatic java/lang/Integer.valueOf(I) instruction. In the next line, the compiler emits invokevirtual java/lang/Integer.intValue()I to extract the raw primitive before applying the iadd instruction with 2.
  4. Can the upper bound of IntegerCache be modified, and if so, how?
    Yes. While the lower bound is permanently fixed at -128, the upper bound (default 127) can be increased via the JVM command-line argument -XX:AutoBoxCacheMax=<size> or system property -Djava.lang.Integer.IntegerCache.high=<size>. This is frequently used in high-throughput enterprise systems to cache numbers up to 10000 or higher.
  5. Why don't Float and Double have a value cache like Integer?
    Integer types have discrete, predictable values that cluster heavily around small whole numbers (0, 1, 10, 100). In contrast, floating-point numbers represent continuous real numbers with infinite values even within a small interval (such as between 0.0 and 1.0). Caching would provide virtually zero cache-hit rate while wasting vast amounts of Heap memory.
  6. What happens when you compare a primitive int and an Integer wrapper using ==?
    When one operand is a primitive and the other is a wrapper (e.g. int x = 200; Integer y = 200; x == y), Java automatically unboxes the wrapper to its primitive value via .intValue() before executing the comparison. Therefore, x == y compares values directly (200 == 200) and evaluates to true.
  7. Why was new Integer(int) deprecated in Java 9 and marked for removal?
    Calling new Integer(n) guarantees the allocation of a brand-new object on the Heap for every invocation, completely bypassing the memory savings and speed of IntegerCache. Deprecation steers developers toward static factory methods like Integer.valueOf(n) or direct autoboxing, which leverage cached instances and allow the JVM compiler optimization flexibility.

Tier 3: Real-World SDET & Selenium Scenarios (Q15–Q21)

  1. When parsing UI cart badge text or item counts in Selenium, should you use Integer.parseInt() or Integer.valueOf()?
    Use Integer.parseInt(badgeText.trim()). It returns a raw primitive int without creating any Heap object, avoiding unnecessary garbage collection in large regression test suites. Reserve Integer.valueOf() for situations where an Integer object reference is strictly required, such as inserting into a List<Integer> or a generic test data map.
  2. Why can comparing two TestNG Integer assertion parameters with == pass in local dev but fail on production staging data?
    In local smoke tests with small numbers (e.g., verifying 5 cart items or 10 search results), both actual and expected Integer objects fall inside the -128..127 cache range, so == happens to return true by object identity. In staging environments with real data (e.g., 250 orders or 500 search results), values exceed 127, allocating distinct Heap objects and causing == to fail. Always use Assert.assertEquals(actual, expected) or actual.equals(expected).
  3. Why are wrapper classes preferred over primitives in REST API response DTOs / POJOs (e.g., Jackson / Gson)?
    In JSON API responses, optional fields might be omitted entirely or explicitly returned as null. If a DTO model uses a primitive int age; or boolean isVerified;, the JSON deserializer assigns default values 0 or false, masking the difference between an intentional zero and an omitted/missing field. Using Integer age; and Boolean isVerified; preserves the distinct null state.
  4. How does TestNG's @DataProvider handle primitive return types when returning Object[][]?
    An Object[][] matrix can only hold object references. When test methods pass primitive literals like { "admin", "pass123", 3 } in the array, the Java compiler automatically autoboxes the primitive int 3 into an Integer object reference at compile time.
  5. How should you safely read optional numeric query parameters or headers in REST Assured tests without risking NPE?
    Headers and query parameters are returned as String objects or null. When parsing them, always verify non-null and non-empty status before calling Integer.parseInt(): 
    String retryHeader = response.getHeader("X-Retry-Count");
int retries = (retryHeader != null && !retryHeader.isBlank()) 
    ? Integer.parseInt(retryHeader.trim()) : 0;
  6. How do you extract and parse digits from a Selenium price text string like "$1,499.99 USD"?
    Clean the string by removing currency symbols, commas, and whitespace using regex before parsing into a primitive double: 
    String priceText = driver.findElement(By.id("price")).getText(); // "$1,499.99 USD"
String cleanText = priceText.replaceAll("[^0-9.]", "");           // "1499.99"
double price = Double.parseDouble(cleanText);                    // 1499.99
  7. In Selenium explicit waits (WebDriverWait), why does Duration.ofSeconds() take long primitives rather than Long wrappers?
    High-frequency framework timing utilities require primitive parameters (long seconds) to eliminate nullability bugs and guarantee zero object allocation overhead during frequent polling loops in the wait cycle.

Tier 4: Troubleshooting, Exceptions & Failure Modes (Q22–Q28)

  1. Why does Boolean flag = null; if (flag) { ... } compile without error but crash at runtime?
    The if condition requires a primitive boolean. The compiler automatically inserts an auto-unboxing call: if (flag.booleanValue()). Because flag holds null, attempting to invoke the instance method .booleanValue() immediately throws a runtime java.lang.NullPointerException.
  2. How do you write a completely NPE-safe boolean check for a nullable Boolean wrapper?
    Use the static singleton comparison pattern: 
    if (Boolean.TRUE.equals(flag)) {
    // Executes ONLY if flag is non-null AND true
}
    Because Boolean.TRUE is guaranteed non-null, calling .equals(flag) safely returns false if flag is null or Boolean.FALSE, without throwing any exception.
  3. Explain the ternary operator trap: why does Integer val = condition ? 1 : null; compile but throw NullPointerException when condition is false?
    Java's ternary operator specification dictates that if one branch is a primitive (1 is an int) and the other is a wrapper or null, the entire conditional expression is promoted to the primitive type (int). When condition is false, Java evaluates the null branch and immediately attempts to auto-unbox it to primitive int, triggering an instant NullPointerException before assignment. Fix: use Integer.valueOf(1) instead of primitive 1.
  4. What exception does Integer.parseInt(" 42 ") throw, and how do you prevent it?
    It throws java.lang.NumberFormatException: For input string: " 42 " because parseInt() does not tolerate leading or trailing whitespace. Prevent it by calling .trim() or .strip() on the string: Integer.parseInt(str.trim()).
  5. Why does Long l = 100; fail to compile even though long l = 100; compiles cleanly?
    In long l = 100;, Java performs primitive widening conversion from int literal 100 to primitive long. However, autoboxing does not perform simultaneous primitive widening and object boxing. Java would have to widen int -> long and then box long -> Long, which the language specification forbids. Fix: supply the L suffix: Long l = 100L;.
  6. Can you cast an Integer object to a Long object using (Long) intObj? What happens?
    It fails at compile time with incompatible types: Integer cannot be converted to Long. Integer and Long are sibling classes inheriting from Number with no parent-child relationship. To convert, unbox to primitive first or call intObj.longValue().
  7. What is the performance risk of using Integer wrappers as loop counters in high-iteration test loops?
    Integer sum = 0;
for (int i = 0; i < 1_000_000; i++) {
    sum += i; // Disaster: unboxes sum, adds i, boxes into NEW Integer Heap object!
}
    Every iteration creates a brand-new Integer object on the Heap because wrappers are immutable. In 1,000,000 iterations, this allocates approximately 24 MB of garbage objects, creating severe GC pauses and slowing execution dramatically. Always use primitive long sum = 0; for accumulators.

Tier 5: Senior/Staff Design & Architecture Rubrics (Q29–Q35)

  1. Why did Java designers introduce IntegerCache for -128..127 rather than caching all integers or none?
    Empirical software studies demonstrate that over 80% of integer operations involve numbers within the 1-byte range (-128 to 127)—such as zero checks, 1-offsets, loop indices, HTTP codes, and small IDs. Pre-allocating 256 immutable instances occupies less than 4 KB of RAM, yielding enormous performance gains and eliminating billions of temporary Heap allocations. Caching all integers is physically impossible, and caching larger arbitrary ranges would consume gigabytes of Heap before user code executes.
  2. Why are wrapper classes designed as public final with private final fields? What vulnerability would mutability introduce?
    Because wrapper instances are actively shared via static pools like IntegerCache and commonly used as keys in hash-based collections (HashMap, HashSet). If an Integer were mutable, modifying its value would corrupt its hash code and bucket placement inside HashMap, while mutating a cached instance like Integer.valueOf(1) would unpredictably alter the value of 1 across every unrelated thread in the JVM. Immutability guarantees thread safety and hash stability.
  3. Contrast Integer.parseInt(s), Integer.valueOf(s), and new Integer(s) in terms of return type, memory, and performance.
    • Integer.parseInt(s): Returns primitive int. Allocates zero Heap memory. Fastest performance.
    • Integer.valueOf(s): Returns Integer wrapper object. Reuses cached instances from IntegerCache if between -128 and 127; allocates new Heap object otherwise.
    • new Integer(s): Returns Integer wrapper object. Always allocates a fresh Heap object, bypassing cache. Deprecated since Java 9 and marked for removal.
  4. How does Project Valhalla (Value Objects / Primitive Types in Generics) plan to resolve Java's primitive vs wrapper dichotomy?
    Project Valhalla introduces Value Objects ("codes like a class, works like an int"). Value objects have no object identity (no memory address, no identity ==, no synchronization lock), allowing them to be flattened into contiguous memory and CPU registers without object headers. This will allow Generics like List<int> without wrapper class overhead or boxing penalties.
  5. How does the Flyweight design pattern manifest in Java's wrapper implementations?
    The Flyweight pattern minimizes memory usage by sharing as much data as possible with similar objects. Java's IntegerCache, ByteCache, ShortCache, LongCache, and CharacterCache are canonical implementations of the Flyweight pattern: an immutable intrinsic state (the primitive value) is stored once in a static lookup array, and shared globally among all client callers via static factory methods (valueOf()).
  6. In framework architecture, when would you intentionally choose a primitive type over a wrapper type, and vice versa?
    Choose Primitives: In performance-critical paths, mathematical counters, loops, array buffers, framework timing intervals, and when a value is mandatory and can never semantically be null.
    Choose Wrappers: In generic Collections (List<T>, Map<K,V>), REST API request/response DTOs where fields are optional or nullable, database entity fields matching nullable columns, and TestNG/JUnit reflection parameter matrices.
  7. Senior SDET Evaluation Rubric: How would you evaluate a candidate who asserts API status codes using Assert.assertTrue(response.statusCode() == 200) vs Assert.assertEquals(response.getStatusCode(), 200)?
    • Junior Answer: "Both assert that the status code is 200. There's no difference." (Fails to understand TestNG assertion reporting or type equality).
    • Mid-Level Answer: "assertEquals is better because when it fails, TestNG prints 'expected [200] but found [404]', whereas assertTrue only prints 'expected [true] but found [false]'." (Understands reporting, misses boxing mechanics).
    • Senior/Staff Answer: "assertEquals(actual, expected) provides meaningful diff reporting. Crucially, if actual and expected are both Integer wrapper objects (e.g. deserialized from POJOs or config), using == compares Heap references; because 200 is outside the -128..127 Integer Cache, == evaluates to false even when values match! Assert.assertEquals invokes .equals(), ensuring true value equality regardless of caching or boxing."
